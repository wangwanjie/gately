# STUN 통과

통신사가 고정 공인 포트를 제공하지 않을 때, STUN 통과는 NAT 홀 펀칭으로 공인 매핑 주소와 포트를 얻어 외부에서 내부 서비스에 접속할 수 있게 합니다.

## 기능

- TCP / UDP 통과와 연결 유지
- UPnP / NAT-PMP로 라우터에 포트 매핑을 자동 생성
- 내장 포워딩: 통과로 얻은 공인 포트를 내부 대상으로 바로 전달
- 공인 주소나 포트가 바뀌면 Webhook과 스크립트를 실행하며 DNS 갱신이나 클라이언트 알림 등에 활용할 수 있으며, Webhook은 프록시(전역 업데이트 프록시 또는 사용자 지정 프록시)를 거쳐 보낼 수 있습니다
- 내장 전달의 출발지 IP 접근 제어(허용 목록 / 차단 목록).

## 함께 쓰기

STUN으로 얻은 공인 포트는 보통 바뀌므로 다음과 함께 쓰기를 권장합니다.

- [동적 DNS](/ko/docs/modules/ddns) 또는 Webhook / 스크립트로 새 주소를 DNS에 동기화(동적 DNS 레코드 값에 `{STUN_규칙이름_PORT}` 등의 변수를 직접 쓸 수 있으며 규칙 주소가 바뀌면 바로 동기화됩니다. [레코드 값 변수](/ko/docs/modules/ddns#record-vars) 참고)
- [웹 서비스](/ko/docs/modules/web)로 HTTPS 진입점 제공
- 웹 서비스의 리다이렉트 사이트에서 `{STUN_규칙이름_PORT}` 등의 변수로 규칙의 현재 공인 주소를 참조할 수 있으며, 포트가 바뀌면 자동으로 새 포트로 이동합니다. [리다이렉트 변수](/ko/docs/modules/web#redirect-vars) 참고.

## 제한 사항과 다중 NAT

- **통신사급 NAT(CGNAT)**: 라우터 WAN이 `100.64.0.0/10` 같은 내부 주소를 받는 경우, 관통 가능 여부는 통신사 쪽 NAT 유형에 달려 있습니다. 풀 콘(외부의 어떤 주소든 매핑된 포트에 접근 가능)이면 관통할 수 있고, 포트 제한형이나 대칭형이면 불가능합니다. 이때는 [Tailscale, frp 또는 Cloudflare 터널](/ko/docs/modules/tunnels)을 사용하세요.
- **다중 NAT에서의 UPnP**: UPnP / NAT-PMP를 켜면 Gately는 라우터에서 터널 포트를 이 호스트로 매핑합니다. 라우터의 외부 주소가 STUN으로 얻은 공인 주소와 다르면 바깥에 NAT가 한 단계 더 있고 공인 포트는 그 바깥 NAT의 것이므로, Gately는 터널 포트 매핑만 유지하고 공인 포트에 대한 추가 매핑은 하지 않습니다.
- **로컬 포트 고정과 방화벽 허용**: 로컬 포트를 비워 두면 시작할 때마다 무작위로 정해집니다. 호스트에 방화벽(예: fnOS 시스템 방화벽)이 켜져 있다면 규칙의 로컬 포트를 고정하고 방화벽에서 그 포트를 허용하세요(STUN 규칙용 포트 범위를 미리 열어 둘 수도 있습니다). 그렇지 않으면 수신 연결이 방화벽에서 버려져 관통 주소에 접속할 수 없습니다.
- **TCP와 라우터의 콘형 NAT**: 일부 라우터의 「NAT1 / 풀 콘」은 UDP에만 적용되고 TCP는 나갈 때 출발지 포트가 바뀝니다. TCP 규칙은 UPnP를 켜거나 라우터에서 터널 포트를 이 호스트로 매핑해야 합니다.

## 방화벽 자동 허용 {#auto-firewall}

규칙에서 "방화벽 자동 허용"을 켜면 Gately가 이 호스트의 방화벽에서 채널 포트를 허용하고(UPnP / NAT-PMP 내부 포트를 지정했다면 그 포트도 허용), 규칙이 멈추거나 삭제되면 제거합니다. OpenWrt 같은 라우터나 방화벽을 켠 Linux 호스트에서 Gately를 실행할 때 사용합니다. Linux 전용입니다.

- nftables: input 훅에 걸린 모든 필터 체인(예: OpenWrt fw4, firewalld) 맨 앞에 허용 규칙을 넣습니다.
- iptables: filter 테이블 INPUT 체인 맨 앞에 허용 규칙을 넣습니다(예: OpenWrt fw3, ufw).
- 허용 규칙에는 `gately-open:` 주석이 붙습니다. 방화벽을 다시 불러오면 규칙이 지워지며, Gately가 30초마다 확인해 다시 추가합니다.
- nf_tables가 없는 커널(Synology DSM 등)에서는 iptables(legacy)를 사용합니다. 허용 규칙은 Gately 전용 filter 체인(`GTLY_OPEN_`으로 시작)에 쓰이고, INPUT의 첫 규칙이 이 체인으로 점프합니다. 시스템 방화벽이 자신의 규칙을 앞에 넣으면 30초 안에 점프 규칙을 맨 앞으로 되돌립니다. Docker 이미지에는 iptables(legacy)가 포함되어 있습니다.
- Docker 배포에는 host 네트워크와 `cap_add: NET_ADMIN`이 필요하며, 규칙 카드에 결과나 실패 이유가 표시됩니다.
- fnOS 시스템 방화벽처럼 nftables / iptables를 거치지 않는 방화벽은 해당 설정에서 직접 포트를 허용해야 합니다.

## 출발지 IP 접근 제어

내장 전달을 사용할 때 각 규칙에 허용 목록 또는 차단 목록을 설정해 출발지 IP로 대상 전달 여부를 결정할 수 있습니다. 목록과 구독 IP 목록 사용법은 [포트 포워딩](/ko/docs/modules/portforward#출발지-ip-접근-제어)과 같고, 침입 방지의 차단이 우선하는 점도 같습니다. 목록은 전달에만 적용되며 STUN 조회와 채널 검사에는 영향이 없습니다. 목록을 수정해도 다시 터널링하지 않아 공인 포트가 그대로 유지됩니다. UDP는 패킷마다 판단합니다. 내장 전달을 쓰지 않으면 외부 연결이 Gately를 거치지 않으므로 목록이 적용되지 않습니다. 「노크 필요」도 선택할 수 있으며, fwknop으로 노크에 성공한 출처만 전달됩니다. 자세한 내용은 [포트 노킹](/ko/docs/modules/knock#gately-entries)을 참고하세요.

## 배포 팁

STUN은 호스트 포트를 직접 수신해야 하므로 Docker 배포에서는 `--network host`를 권장합니다.
