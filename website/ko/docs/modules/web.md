# 웹 서비스

도메인별 리버스 프록시, 리다이렉트, 정적 파일, 고정 텍스트를 제공하는 Gately의 통합 웹 진입점입니다. 메뉴 위치: 사이드바 「웹 → 웹 서비스」.

## 구조: 리스너, 사이트, 기본 사이트

설정은 세 계층입니다.

1. 리스너: 수신 포트 하나. 네트워크(`tcp` 듀얼 스택, `tcp4`, `tcp6`), 수신 주소(비우면 모든 주소), 포트, HTTPS 스위치, 최소 TLS 버전(1.0 / 1.1 / 1.2 / 1.3), PROXY 프로토콜 수신 여부 필드가 있습니다.
2. 사이트: 리스너 아래에서 도메인으로 매칭되는 사이트. 도메인은 정확한 도메인, `*.example.com`(모든 단계의 서브도메인과 일치), `api-*.example.com`(첫 레이블 안의 `*` 하나가 그 레이블 안의 0개 이상 문자와 일치하며 `.`을 넘지 않음), `*`(모두 일치)를 지원하며 매칭 우선순위는 정확한 도메인, 와일드카드, `*` 순입니다. 여러 와일드카드가 동시에 일치하면 더 긴 규칙이 우선하고, 길이가 같으면 목록에서 앞에 있는 사이트가 우선합니다. 첫 레이블 와일드카드는 가져오기, 일괄 편집, 리디렉션 변수 `{1}`에서도 사용할 수 있습니다. HTTPS 사이트에는 실제 접속 도메인을 포함하는 인증서(예: `*.example.com`)가 필요하며, 인증 기관은 `*.example.com` 형식의 와일드카드 인증서만 발급합니다.
3. 기본 사이트: 일치하는 사이트가 없을 때 사용되며 사용하지 않으면 404를 반환합니다. 기본 사이트를 「연결 끊기」로 설정하면 알 수 없는 도메인 요청에 아무 응답도 하지 않습니다. 기본 사이트를 설정하면 사이트 목록 맨 끝에 표시됩니다. 아직 설정하지 않았다면 리스너 카드의 「기본 사이트 설정」을 클릭해 설정합니다.

사이트나 기본 사이트의 변경을 저장하면 사이트 목록이 그 자리에서 교체됩니다. 리스너는 계속 실행되고, 열려 있는 연결(WebSocket 포함)은 유지되며, 각 사이트의 통계도 그대로 이어집니다. 새 설정이 올바르지 않으면 이전 사이트가 계속 서비스됩니다. 리스너 자체의 설정(네트워크, 주소, 포트, HTTPS, 최소 TLS, HTTP/3, PROXY 프로토콜)을 바꾸면 해당 리스너가 재시작됩니다.

사이트 목록의 구체적인 도메인은 클릭할 수 있는 전체 URL로, 새 탭에서 열리며 옆의 버튼으로 URL을 복사할 수 있습니다. 와일드카드 도메인(`*.example.com`, `*`)은 그대로 텍스트로 표시합니다. URL은 리스너에서 추정합니다. HTTPS를 켜면 `https`, 아니면 `http`이고 포트는 리스너 포트이며 443, 80 같은 기본 포트는 생략합니다(예: `https://example.com:8443`). 리스너의 접속 포트가 비어 있고 활성화된 프로토콜 라우팅 또는 포트 포워딩 규칙이 이 리스너로 전달하면, 사이트 링크는 규칙의 입구(수신) 포트를 자동으로 사용합니다(예: 프로토콜 라우팅이 443에서 8443 리스너로 넘기면 443). 규칙의 대상 주소는 이 리스너에 닿아야 합니다. 모든 주소에서 수신하는 리스너는 루프백 또는 미지정 주소, 특정 주소에서 수신하는 리스너는 같은 주소입니다. 프로토콜 라우팅은 도메인별로 라우팅과 같은 순서(정확한 도메인, 가장 구체적인 와일드카드, `*`, 기본 대상)로 맞춰 보며, 비활성화된 경로와 `acme-tls/1` 같은 브라우저 외 ALPN만 받는 경로는 건너뜁니다. UDP만 전달하는 포트 포워딩 규칙은 제외하고, 포트 범위는 일대일로 대응시키며, 여러 규칙이 맞으면 첫 번째 활성 규칙을 씁니다. 리스너 제목에 감지한 포트와 출처 규칙이 표시되고 **접속 주소** 입력란의 자리표시자로도 쓰이며, 직접 입력한 접속 포트가 우선합니다. 공유기 포트 매핑, frp 또는 CDN을 거쳐 접속하면(또는 규칙이 이 호스트의 LAN 주소로 전달하면) 외부 프로토콜이나 포트가 리스너와 다를 수 있으므로 리스너의 **접속 주소**에서 프로토콜과 포트를 직접 지정하세요(예: CDN이 http 8080에서 가져오면 https와 443). 접속 주소는 링크 생성에만 쓰이며 바꿔도 리스너는 재시작하지 않습니다. 저장할 때 도메인은 브라우저가 보내는 형태로 맞춥니다. 소문자로 바꾸고 IPv6는 대괄호를 없애며 국제화 도메인은 punycode로 바꿉니다(`中文.com`은 `xn--fiq228c.com`으로 저장). 포트, 경로, `@`가 들어간 것처럼 절대 일치할 수 없는 값은 거부합니다. Lucky나 nginx에서 가져올 때는 잘못된 도메인만 건너뛰고 알려 줍니다.

사이트에는 「그룹」을 지정할 수 있습니다(최대 64자, 기본 사이트는 그룹에 넣을 수 없음). 목록은 리스너마다 그룹별로 접을 수 있는 영역을 보여 줍니다. 그룹은 처음 나타난 순서대로 배치되고, 그룹이 없는 사이트는 그 뒤에, 기본 사이트는 항상 맨 끝에 옵니다. 각 그룹의 접힘 상태는 브라우저에 저장됩니다. 「정렬 및 일괄」을 누르면 정렬 모드가 되어 사이트를 위아래로 옮기거나 그룹 안에서 끌어 옮기고, 그룹 전체를 옮기고, 리스너 순서도 바꿀 수 있습니다. 순서는 목록 표시에만 쓰이며 도메인 매칭은 사이트 순서와 관계없이 위의 우선순위를 따릅니다. 정렬을 저장할 때도 사이트 목록이 그 자리에서 교체되므로 연결이 끊기지 않습니다. 페이지 상단의 검색 상자로 도메인, 이름, 그룹, 백엔드, 메모로 사이트를 필터링할 수 있으며, 검색하는 동안 접힌 리스너 카드는 자동으로 펼쳐집니다.

정렬 모드에서는 여러 사이트를 선택할 수도 있습니다(그룹 제목의 체크박스로 그룹 전체 선택). 선택한 사이트 중 하나를 끌면 모두 함께 이동하고, 다른 그룹의 사이트나 그룹 제목에 놓으면 그 그룹으로 들어갑니다. 도구 모음에서 선택한 사이트를 지정한 그룹으로 한 번에 옮길 수 있고, 이름을 비우면 그룹에서 뺍니다. 여러 리스너에 걸쳐 선택한 경우 리스너별로 저장됩니다.

그룹 제목에 마우스를 올리고 연필 버튼을 누르면 그룹 이름을 바꿀 수 있습니다. 그룹의 항목도 함께 새 이름으로 바뀌며 위치와 순서는 그대로입니다. 이미 있는 그룹 이름을 고르면 확인 후 두 그룹이 합쳐집니다.

### 사이트 이동 {#move-sites}

사이트는 모든 설정과 함께 다른 리스너로 옮길 수 있습니다.

- 사이트를 편집할 때 "소속 리스너"를 바꾸면 저장 시 변경 사항을 먼저 저장한 뒤 이동합니다. 사이트를 추가할 때는 어느 리스너에 만들지 고를 수 있습니다.
- 정렬 모드에서 사이트를 체크하고(리스너를 넘나들어도 됨) 도구 모음의 "리스너로 이동"을 눌러 대상 리스너와 그룹을 고릅니다(기본값은 각 사이트의 그룹 유지). 사이트는 대상 리스너의 맨 끝 또는 선택한 그룹의 맨 끝에 놓이며, 이미 대상 리스너에 있는 사이트는 그대로입니다.
- 정렬 모드에서 사이트를 다른 리스너의 사이트 위나 아래로 끌어다 놓으면 그 위치에 들어가고 해당 그룹에 속합니다. 그룹 제목에 놓으면 그 그룹의 맨 끝에 들어갑니다. 일반 사이트가 없는 리스너에는 끄는 동안 놓을 영역이 표시됩니다. 놓은 뒤 확인을 거칩니다.

이동은 한 번의 요청으로 처리되며 원본과 대상 리스너가 각각 한 번만 다시 로드되고 사이트 목록이 그 자리에서 교체되므로 다른 사이트의 연결은 끊기지 않습니다. 대상 리스너에 같은 도메인의 사이트가 있으면 이동을 거부하고 어떤 리스너도 바꾸지 않습니다. 기본 사이트는 소속 리스너에 속하므로 옮길 수 없습니다. 사이트 키가 대상 리스너에서 이미 쓰이고 있으면 새 키로 바뀌며, 성능 모니터링 알림 규칙에서 참조하는 사이트도 함께 갱신됩니다. 로그인 세션은 리스너와 사이트별로 분리되어 있어 이동 후 로그인한 방문자는 다시 로그인해야 합니다. 공유 링크의 사용 횟수는 사이트와 함께 옮겨지므로 횟수 제한 링크가 이동으로 다시 쓸 수 있게 되지는 않습니다. 사이트의 통계와 실시간 연결은 새로 시작됩니다. 인증을 켠 사이트를 HTTPS 리스너에서 평문 HTTP 리스너로 옮길 때는 비밀번호와 로그인 쿠키가 암호화되지 않고 전송된다고 경고합니다.

### 일괄 작업

정렬 모드에서 사이트를 선택하면(여러 리스너에 걸쳐도 됨) 도구 모음에서 아래 일괄 작업을 할 수 있습니다. 각 작업은 한 번에 제출됩니다. 모든 사이트가 검증을 통과해야 저장되고, 하나라도 실패하면 아무것도 바꾸지 않고 어느 사이트가 실패했는지 알려 줍니다. 영향을 받는 리스너는 각각 한 번만 다시 불러오며, 사이트 목록을 그 자리에서 교체하므로 연결이 끊기지 않습니다.

- **사용 / 사용 안 함**: 이미 목표 상태인 사이트는 그대로 둡니다.
- **삭제**: 확인 후 선택한 사이트를 삭제합니다. 기본 사이트는 삭제할 수 없습니다.
- **도메인 일괄**:
  - 도메인 추가: 한 줄에 하나씩(쉼표로 구분해도 됨) 입력합니다. 사이트에 이미 있는 도메인은 건너뛰고, 새 도메인은 끝에 추가합니다.
  - 도메인 제거: 전체 도메인으로 일치 여부를 판단합니다. 사이트에 없는 도메인은 무시하며, 사이트의 도메인을 모두 지울 수는 없습니다.
  - 기본 도메인 교체: 도메인의 접미사를 새 접미사로 바꿉니다. 원래 도메인 자체와 그 하위 도메인(`*.원래도메인` 와일드카드 포함)이 모두 바뀌며, 예를 들어 `old.com`을 `new.com`으로 바꾸면 `www.old.com`은 `www.new.com`이 됩니다. 교체 후 중복된 도메인은 합쳐지고, 일치하지 않는 사이트는 그대로입니다.

  새로 추가한 도메인이 같은 리스너의 여러 사이트에 동시에 나타나면 거부됩니다. 같은 리스너 안에서는 첫 번째 사이트만 그 도메인에 매칭되기 때문입니다. 다른 리스너에서는 같은 도메인을 쓸 수 있습니다.
- **옵션 일괄**: 압축, 접근 로그, CORS, 전달 헤더, 거부 시 연결 끊기를 일괄로 켜거나 끄고, WAF를 지정하거나 해제할 수 있습니다. '변경 안 함'을 고른 항목은 각 사이트의 기존 설정을 유지합니다. 인증, 접근 제어, 백엔드 주소처럼 접근에 영향을 주는 설정은 사이트마다 따로 바꿉니다.
- **리스너로 이동**: 체크한 사이트를 다른 리스너로 옮깁니다. [사이트 이동](#move-sites)을 참고하세요.

해당 API는 `POST /api/webservice/sites/batch`이며 요청 본문은 `{"sites": [{"listener": "리스너 key", "site": "사이트 key"}], "action": "...", ...}`입니다. `action`은 `enable`, `disable`, `delete`, `addDomains`, `removeDomains`(`domains`와 함께), `replaceDomain`(`from`, `to`와 함께), `set`(`options`와 함께, 위의 옵션 필드만 허용) 중 하나이며, 실제로 변경한 사이트 수와 변경이 필요 없었던 사이트 수를 반환합니다. 한 번에 최대 500개 사이트, 100개 도메인까지 처리합니다. 리스너 자체도 일반 `PUT /api/webservice/listeners-enable`과 `POST /api/webservice/listeners-delete`를 지원합니다. `action`이 `move`이면 `move`로 대상을 지정합니다(예: `{"listener": "대상 리스너 key"}`). `group`(넣을 그룹, 빈 문자열은 그룹 없음, 생략하면 각 사이트의 그룹 유지) 또는 `before` / `after`(대상 리스너의 사이트 key, 그 앞이나 뒤에 넣고 해당 그룹에 속함)를 더할 수 있습니다. 응답의 `moved`에는 각 사이트의 이동 전후 키가 들어 있습니다.

## 사이트 유형

| 유형 | 설명 |
| --- | --- |
| 리버스 프록시 | 하나 이상의 백엔드로 전달합니다. 백엔드 주소 형식은 `http(s)://호스트:포트`이며 WebSocket을 지원합니다 |
| 리다이렉트 | 전체 URL로 이동합니다. 상태 코드는 301 / 302 / 307 / 308(기본 302)이며 원래 경로와 쿼리 문자열을 유지할 수 있습니다. URL에 `{host}`를 넣으면 방문자가 사용한 도메인으로 바뀝니다. `https://{host}`에 「경로와 매개변수 유지」를 함께 쓰면 모든 HTTP 요청을 같은 도메인의 HTTPS로 보냅니다. `{path}`, `{1}`, `{STUN_규칙이름_PORT}` 등의 변수도 쓸 수 있습니다. [리다이렉트 변수](#redirect-vars) 참고. |
| 정적 파일 | 디렉터리는 절대 경로여야 합니다. 「디렉터리 목록」을 끄면 `index.html`이 있을 때만 디렉터리 요청에 응답합니다. 「확장자 없는 URL」은 파일이 없을 때 `경로.html`과 `경로/index.html`을 시도합니다(VitePress 같은 생성기용이며 nginx의 `try_files $uri $uri.html $uri/index.html`과 같음). 「404 페이지」는 디렉터리 안의 경로(예: `404.html`)이며 상태 코드 404로 반환됩니다 |
| 내비게이션 패널 | [내비게이션 패널](#nav-panel) 라이브러리의 패널 하나를 보여 줍니다. 자주 쓰는 서비스 링크를 그룹별로 한 페이지에 모으며, 내부망 방문자에게는 내부망 주소를 자동으로 씁니다 |
| 고정 텍스트 | 사용자 지정 내용, `Content-Type`(기본 `text/plain; charset=utf-8`), 상태 코드(100-599, 기본 200) |
| 연결 끊기 | 아무것도 보내지 않고 연결을 끊습니다. nginx의 `return 444`와 같습니다. 주로 기본 사이트에 사용해 알 수 없는 도메인을 스캔하는 요청에 응답하지 않으며, 접근 로그에는 444로 기록됩니다. 인증, 접근 제어, WAF, 재작성을 거치지 않으므로 사이트의 다른 설정은 적용되지 않습니다 |

모든 유형의 사이트에 접근 로그, 교차 출처(CORS), 사용자 지정 요청 헤더와 응답 헤더(한 줄에 `Key: Value`, Value를 비우면 해당 헤더 삭제)를 설정할 수 있으며 [WAF 방화벽](/ko/docs/modules/waf) 인스턴스 하나를 참조할 수 있습니다(인스턴스가 없거나 비활성화되어 있으면 통과).요청 헤더, 응답 헤더와 Content-Type 편집 방법은 [요청 헤더와 응답 헤더](#headers)를 참고하세요.

접근 로그에는 클라이언트 IP, 메서드, 도메인과 경로, 상태 코드, 소요 시간, 사이트 이름이 기록되고, 줄 끝에 nginx 형식으로 Referer와 User-Agent(없으면 `-`)가 붙어 같은 공인 IP 뒤의 여러 기기를 User-Agent로 구분할 수 있습니다. 사이트, 상태 코드, 출발지 IP 등으로 로그를 필터링할 수 있습니다. [실행 로그 보기와 필터](/ko/docs/guide/configuration#log-filter)를 확인하세요.

### 리다이렉트 변수 {#redirect-vars}

리다이렉트 사이트의 대상 주소에는 다음 변수를 쓸 수 있습니다:

| 변수 | 의미 |
| --- | --- |
| `{host}` | 방문자가 요청한 도메인(포트 제외). IPv6 주소는 `[2001:db8::1]`처럼 대괄호 포함 |
| `{port}` | 접속한 포트 |
| `{hostAndPort}` | 도메인과 포트, 요청의 Host와 같음 |
| `{path}` / `{PATH}` | 요청 경로, `{PATH}`는 맨 앞의 `/` 제외 |
| `{args}` / `{Args}` | 쿼리 문자열, `{args}`는 맨 앞의 `?` 포함(쿼리가 없으면 빈 값), `{Args}`는 제외 |
| `{domainPartN}` / `{pathPartN}` | 도메인(`.`로 구분) 또는 경로(`/`로 구분)의 N번째 부분, N은 1부터 |
| `{ClientIP}` / `{RemoteIP}` | 클라이언트 IP |
| `{time}` | 현재 시각, 형식 `2006-01-02 15:04:05`. 리디렉션 주소가 올바른 URL 이 되도록 공백은 `%20` 으로 씁니다(`2006-01-02%2015:04:05`) |
| `{1}` | 사이트 도메인 `*.example.com`에서 `*`에 일치한 부분. 정확한 도메인에 일치하면 빈 값, `*`나 기본 사이트에 일치하면 전체 도메인 |
| `{STUN_규칙이름_PORT}` / `{STUN_규칙이름_IP}` / `{STUN_규칙이름_ADDR}` | [STUN 통과](/ko/docs/modules/stun) 규칙의 현재 공인 포트, IP, `IP:포트`. 규칙 이름은 목록에 표시되는 이름이며 밑줄을 포함해도 됩니다 |

- "경로 유지"가 켜져 있을 때 대상에 `{path}`, `{PATH}`, `{pathPartN}`이 있으면 원래 경로를, `{args}`, `{Args}`가 있거나 대상에 자체 쿼리가 있으면 원래 쿼리를 다시 붙이지 않습니다. 나머지 부분은 그대로 붙입니다;
- STUN 포트가 바뀌어도 사이트를 수정할 필요 없이 다음 요청부터 새 포트로 이동합니다. 참조한 규칙이 없거나, 비활성화되었거나, 아직 통과에 성공하지 않았거나, 자동 재시도 중이면 사이트는 503을 반환하고 실행 로그에 이유를 남깁니다;
- 변수를 펼친 대상에 호스트가 없으면(예: 정확한 도메인이 일치해 `{1}`이 비었는데 대상이 `https://{1}`뿐인 경우) 503을 반환합니다. 방문자의 호스트에 `&`, `=`, `/`, `@`처럼 도메인에 쓰이지 않는 문자가 있으면 400을 반환하고 대상에 넣지 않습니다. 대상이 `{host}`, `{hostAndPort}`, `{1}` 또는 `{domainPartN}`을 쓰면 Host 헤더가 없는 요청(HTTP/1.0 프로브 등)도 400을 반환합니다;
- 사이트 도메인은 `*`를 하나만 지원하므로 `{1}`만 있습니다;
- 경로 재작성 규칙의 리다이렉트 대상은 여전히 `{host}`만 지원합니다. 알 수 없는 `{xxx}`는 그대로 남습니다.

예: Cloudflare CDN이 `*.example.com`을 이 기기의 2053 포트로 보내고, 그 리스너에 도메인이 `*.example.com`인 리다이렉트 사이트를 두어 대상을 `https://{1}.v4.example.com:{STUN_web_PORT}{path}{args}`로 지정합니다. `zly.example.com/a?b=1`에 접속하면 `https://zly.v4.example.com:<STUN 포트>/a?b=1`로 이동합니다. STUN 규칙 web은 다른 리스너로 전달하고, 그곳에 `*.v4.example.com` 아래 각 도메인의 리버스 프록시 사이트를 만듭니다.

### 리버스 프록시 옵션 {#proxy-options}

사이트 편집 창 "기본" 탭의 "옵션"입니다. 옆의 물음표 아이콘을 누르면 화면에서 간단한 설명을 보고 이 절로 이동할 수 있습니다.

| 옵션 | 동작 | 켜야 할 때 |
| --- | --- | --- |
| 백엔드 인증서 검증 건너뛰기 | HTTPS 백엔드에 연결할 때 인증서를 검증하지 않습니다 | 백엔드가 자체 서명 또는 만료된 인증서를 쓰는 경우(NAS, 공유기 관리 페이지의 https 포트 등). 백엔드 신원을 확인할 수 없게 되므로 내부망 백엔드에만 사용하세요 |
| Host에 백엔드 주소 사용 | 백엔드로 보내는 Host 헤더를 백엔드 주소로 바꿉니다. 끄면(기본값) 방문자가 요청한 Host를 유지합니다 | 백엔드가 자기 주소만 받아들이는 경우(400 / 403, 잘못된 주소로 이동, Host 불일치 등). 공개 웹사이트나 CDN으로 프록시할 때 대개 필요합니다. 백엔드가 도메인으로 사이트를 구분하거나 접속 도메인으로 링크를 만들어야 하면 끈 상태로 둡니다 |
| 연결 재사용 안 함 | 요청마다 백엔드에 새 연결을 만듭니다(Keep-Alive 끔) | 연결이 가끔 재설정되거나 요청이 멈추는 경우, 또는 지속 연결을 지원하지 않는 백엔드. 지연이 조금 늘어나므로 평소에는 끈 상태로 둡니다 |
| X-Forwarded-* 추가 | `X-Forwarded-For` / `X-Forwarded-Proto` / `X-Forwarded-Host` / `X-Forwarded-Port`와 `X-Real-IP`를 기록해 방문자의 실제 IP, 원래 프로토콜, 도메인, 포트를 백엔드에 알립니다 | 백엔드가 실제 IP를 기록하거나, 외부가 HTTPS임을 알아야 올바른 링크를 만들 수 있는 경우(그렇지 않으면 http로 되돌아가거나 로그인 후 무한 이동). 대부분의 앱에 권장합니다 |
| 백엔드에 PROXY v2 전송 | TCP 연결 앞에 PROXY 프로토콜 v2 헤더를 붙여 실제 클라이언트 IP를 전달합니다. 켜면 요청마다 새 연결을 만들고 백엔드에 HTTP/2를 쓰지 않습니다. 백엔드가 Gately라면 해당 리스너에서 PROXY 프로토콜 수신을 켜고 이 호스트를 신뢰할 PROXY 출처에 추가하세요. | HTTP 헤더는 읽지 않지만 PROXY 프로토콜을 지원하는 백엔드(다른 Gately, haproxy, `proxy_protocol`을 켠 nginx 등). 백엔드에 수신 설정이 없으면 모든 요청이 실패하므로 확실하지 않으면 끄세요 |
| 접속 도메인을 SNI로 사용 | HTTPS 백엔드에만 적용: 핸드셰이크 때 방문자가 쓴 도메인을 보내고 그 도메인으로 인증서를 검증합니다. nginx의 `proxy_ssl_server_name on; proxy_ssl_name $host`와 같습니다 | 같은 포트에서 도메인별로 인증서나 분기를 하는 백엔드(frp `vhost_https`, 여러 HTTPS 사이트를 둔 nginx 등). 백엔드마다 별도 연결 풀을 쓰므로 도메인 간에 연결이 재사용되지 않습니다 |
| Gately 로그인 쿠키 전달 | Gately 자체 로그인 쿠키(싱글 사인온 `gately_sso`, 사이트 세션, 외부 로그인 nonce)를 그대로 백엔드에 넘깁니다. 끄면(기본값) 이 쿠키를 백엔드에 보내지 않아 로그인 자격 증명이 새지 않습니다 | 백엔드가 인증을 담당하는 다른 Gately이고 이 사이트는 인증을 하지 않을 때. 예: 공인 Gately는 WAF와 접근 제어만 하고 내부망 Gately로 프록시하며, 내부망 Gately가 웹 인증과 싱글 사인온을 담당하는 구성. 이 사이트에서 인증을 켠 상태에서는 쓸 수 없으며, 백엔드가 직접 운영하는 Gately일 때만 사용하세요 |

자주 쓰는 조합:

- 내부망 웹 앱(예: `http://192.168.1.10:5000`) 프록시: "X-Forwarded-* 추가"만 켭니다.
- 백엔드가 자체 서명 인증서의 https 주소: "백엔드 인증서 검증 건너뛰기"도 켭니다.
- 공개 웹사이트나 외부 서비스 프록시: "Host에 백엔드 주소 사용"를 켭니다.
- 백엔드 앞에 SNI로 분기하는 서비스가 있음(예: frp `vhost_https`): "접속 도메인을 SNI로 사용"를 켭니다.
- 공인 Gately는 WAF만, 내부망 Gately가 로그인 담당: 공인 사이트는 인증을 끄고 "Gately 로그인 쿠키 전달"을 켭니다. 실제 IP가 필요하면 "백엔드에 PROXY v2 전송"도 켜고, 내부망 Gately에서 PROXY 프로토콜 수신을 켠 뒤 공인 Gately를 신뢰할 수 있는 출처에 추가합니다.

### 요청 헤더와 응답 헤더 {#headers}

사이트 편집 창의 "헤더" 탭에서 설정합니다. 요청 헤더는 백엔드로 보내지며 리버스 프록시 사이트에서만 적용되고, 응답 헤더는 클라이언트에 반환되며 모든 유형의 사이트에 적용됩니다.

- 행별 편집: 이름 칸을 누르면 자주 쓰는 헤더와 용도가 표시되고, 고르면 대표 값이 자동으로 채워지며 값 칸에서 다른 대표 값을 고를 수도 있습니다. 두 칸 모두 직접 입력할 수 있습니다. 값을 비우면 헤더를 삭제하고, 이름 칸에 `Key: Value` 한 줄을 붙여 넣으면 자동으로 나뉩니다.
- "자주 쓰는 보안 헤더 추가"은 `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy: strict-origin-when-cross-origin`을 추가하며 이미 있는 헤더는 중복 추가하지 않습니다.
- "텍스트 모드"에서는 여러 줄의 `Key: Value`를 한 번에 붙여 넣을 수 있고, 행별 편집으로 돌아가도 내용이 유지됩니다.
- "경로별 백엔드"의 경로별 추가 요청 헤더도 같은 방식으로 편집하며, 사이트 요청 헤더 다음에 적용되고 이름이 같으면 경로 설정이 우선합니다.

각 행 아래에 실시간 피드백이 표시됩니다. 빨간색은 저장이 실패하거나 헤더가 적용되지 않음을 뜻합니다(이름 없음, 이름에 공백이나 콜론 같은 잘못된 문자, 텍스트 모드에서 콜론 없음 등). 주황색은 저장은 되지만 기대와 다르게 동작할 수 있음을 뜻합니다:

- 요청 헤더에 설정한 `Host`는 적용되지 않습니다. 바꾸려면 "Host에 백엔드 주소 사용"를 켜세요.
- `X-Forwarded-For`, `X-Real-IP`에 고정 값을 쓰면 실제 클라이언트 IP를 덮어씁니다. 클라이언트 IP를 전달하려면 "X-Forwarded-* 추가"를 켜세요.
- `Content-Length`, `Connection`, `Transfer-Encoding` 등은 연결이 자동으로 관리하므로 직접 설정하면 무시되거나 전송 오류가 납니다.
- 값은 그대로 전송되며 nginx의 `$host` 같은 변수는 지원하지 않습니다. 프리셋 값의 `<token>` 같은 자리 표시자는 바꿔야 합니다.
- 이름이 같은 헤더는 순서대로 적용되며 뒤의 것이 우선합니다.

"고정 텍스트" 사이트의 `Content-Type`은 자주 쓰는 유형에서 고르거나 직접 입력할 수 있습니다. 화면에서 `유형/하위유형; 매개변수=값` 형식을 검사하고, `text/*`에 `charset`이 없으면 한국어 등이 깨질 수 있다고 알려 줍니다. 비워 두면 `text/plain; charset=utf-8`을 사용합니다.

### 내비게이션 패널 {#nav-panel}

왼쪽 메뉴 'Web → 내비게이션 패널'(`#/webpanels`)에서 패널 라이브러리를 관리합니다. 패널은 그룹으로 나눈 링크 묶음입니다. Web 서비스에서 유형이 '내비게이션 패널'인 사이트를 추가하고 패널을 고르면 사이트 도메인의 루트 경로(`/` 또는 `/index.html`)에서 내비게이션 페이지가 열리고, 다른 경로는 404를 반환합니다. 사이트의 인증, IP 접근 제어, 국가 필터, WAF는 그대로 적용됩니다. 내비게이션 페이지는 보통 본인만 쓰므로 웹 인증이나 IP 허용 목록을 켜 두세요. 패널 변경 사항은 저장하는 즉시 반영되며 리스너를 다시 시작할 필요가 없습니다.

- **링크**: 이름, 그룹, 설명, 외부망 주소와 선택 항목인 내부망 주소, 아이콘, 색상을 가지며 현재 탭에서 열거나 페이지에서 숨길 수 있습니다. 그룹은 목록에서 처음 나온 순서로 표시되고, 편집 창에서 그룹 전체를 위아래로 옮길 수 있습니다. 'Web 서비스 사이트에서 추가'는 구체적인 주소를 만들 수 있는 사이트(와일드카드가 아닌 첫 도메인과 리스너의 접속 스킴·포트, 프로토콜 분기나 포트 포워딩으로 들어오는 리스너는 포워딩 입구 포트)를 보여 주고, 선택한 사이트를 링크로 추가하며 사이트 그룹을 링크 그룹으로 씁니다.
- **다른 접속 방식**: 한 서비스에 IPv6 직접 연결, frp, STUN, Cloudflare 터널처럼 여러 입구가 있는 경우가 많습니다. 링크마다 접속 방식을 최대 8개 더 넣을 수 있고(이름 20자 이하, 주소와 변수는 위와 같음), 카드에 작은 링크로 표시되어 새 탭에서 열리며 내부망과 외부망 방문자 모두에게 보입니다. 변수에 아직 값이 없으면 취소선이 그어진 사용 불가 상태로 표시됩니다. 기본 주소를 쓸 수 없어도 다른 접속 방식은 누를 수 있고, 검색도 접속 방식 이름과 일치시킵니다.
- **주소**: `http`, `https`, `ftp`, `ftps`, `sftp`, `ssh`, `smb`, `afp`, `nfs`, `vnc`, `rdp`, `mailto`를 지원하며 비밀번호는 넣을 수 없습니다. 변수 `{host}`, `{port}`, `{hostAndPort}`(방문자가 패널을 연 도메인과 포트), `{1}`, `{domainPartN}`, `{STUN_규칙이름_PORT}`, `{STUN_규칙이름_IP}`, `{STUN_규칙이름_ADDR}`를 [리디렉션 변수](#redirect-vars)와 같은 방식으로 쓸 수 있습니다. 예: `https://{host}:8443`, `http://{STUN_web_ADDR}/`. STUN 규칙에 아직 공인 주소가 없으면 해당 링크는 사용 불가로 표시됩니다. 요청 경로와 쿼리 문자열에서 가져오는 `{path}`, `{args}` 등은 쓸 수 없습니다. 쓸 수 있으면 쿼리 문자열을 붙인 패널 URL만으로 링크 대상을 바꿀 수 있기 때문입니다. `{1}`에 값이 없으면(패널 사이트 도메인이 와일드카드가 아니거나 미리보기 중) 이를 쓰는 링크는 사용 불가로 표시됩니다. IPv6 주소로 패널을 열면 `{host}`는 `[2001:db8::1]`처럼 대괄호를 붙여 펼쳐집니다.
- **내부망과 외부망**: 방문자 주소가 루프백, 사설(10/8, 172.16/12, 192.168/16, fc00::/7), 링크 로컬 주소이거나 패널의 '추가 내부망 주소'(예: Tailscale의 `100.64.0.0/10`)에 있으면 링크는 내부망 주소를 쓰고, 내부망 주소가 없는 링크는 외부망 주소를 그대로 씁니다. CDN이나 리버스 프록시를 거치면 [신뢰할 수 있는 프록시](#real-ip)를 설정하세요. 설정하지 않으면 방문자 주소가 프록시 주소가 됩니다. 내부망 주소가 있는 링크가 있으면 페이지 오른쪽 위에서 내부망과 외부망을 직접 바꿀 수 있고, 선택은 쿠키에 저장되며 '자동 감지'로 되돌립니다.
- **내부망 판정과 노출 범위**: 내부망 여부는 방문자의 직접 접속 주소로 판단합니다. 인터넷 방문자가 이 장치의 frpc, cloudflared, Docker 포트 매핑을 거쳐 들어오면 접속 주소가 이 장치나 컨테이너 네트워크가 되어 내부망 방문자로 처리됩니다. 이런 구성에서는 전달하는 쪽이 PROXY 헤더를 보내게 하고 리스너에서 PROXY 프로토콜을 켜거나, HTTP 프록시를 거치면 [신뢰할 수 있는 프록시](#real-ip)를 설정하세요. 내부망 주소는 패널을 열 수 있는 모든 방문자에게 보이며, 방문자는 `?net=lan`으로 내부망 보기로 바꿀 수도 있습니다. 내부망 주소를 숨기려면 사이트 인증이나 IP 접근 제어를 켜세요.
- **아이콘**: 이모지나 8자 이하 텍스트, `http(s)` 이미지 주소, 업로드한 이미지(PNG, JPEG, GIF, WebP는 128픽셀로 줄여 저장, SVG와 ICO는 그대로 저장, 개당 96 KB, 패널 합계 3 MB 이하)를 쓸 수 있고, 비워 두면 이름의 첫 글자를 표시합니다. 텍스트 아이콘의 배경색은 직접 고를 수 있으며 비워 두면 이름에 따라 정해집니다. '선택'을 눌러 내장 아이콘도 쓸 수 있습니다. Gately 모듈과 frp, Tailscale, NetBird, Cloudflare 같은 관련 도구, Jellyfin, Home Assistant, qBittorrent 같은 앱, OpenWrt, Synology, Proxmox 같은 시스템, 라우터·서버 같은 일반 아이콘이 있으며(브랜드 아이콘은 Simple Icons, 일반 아이콘은 Lucide), `builtin:ID`로 저장됩니다. 내장 아이콘은 아이콘 고유 색상의 타일 위에 그려지고 색상을 바꿀 수 있으며, 밝은 색에서는 도형이 어두운 색으로 바뀝니다.
- **페이지**: 제목(비우면 패널 이름), 부제목, 페이지 아이콘, 테마(시스템 설정·라이트·다크). 페이지에서 검색할 수 있습니다. `/`로 검색창에 이동하고 공백으로 여러 키워드를 나눠 입력하면 이름·설명·주소·그룹으로 찾으며, Enter로 첫 결과를 열고 `Esc`로 지웁니다. 편집 창의 '미리보기'는 외부망 또는 내부망 방문자 기준으로 페이지를 만들고 `{host}`는 관리 화면의 도메인으로 바뀝니다.
- **스킨**: 관리 화면 오른쪽 위 "테마 색상"과 같은 색 구성(Gately 오리지널과 클래식)이며 기본값은 에메랄드입니다. 편집 창에서 패널의 기본 스킨을 고를 수 있습니다. 방문자는 페이지 오른쪽 위 팔레트 버튼으로 테마를 바꿀 수 있습니다: 라이트·다크·시스템 설정, 색 구성 선택(마우스를 올리면 미리 보고, 클릭하면 그 위치에서 새 색이 퍼짐), 강조 색과 모서리 사용자 지정. 휴대폰에서는 아래에서 패널이 열립니다. 선택은 방문자의 브라우저에 저장되고, 선택하기 전에는 패널 설정을 쓰며, 패널과 관리 화면이 같은 도메인에 있으면 선택이 공유됩니다. 편집 창의 미리 보기는 패널 설정으로 표시되고 전환 버튼이 없습니다.
- **보안**: 페이지는 서버에서 만들며 이름과 설명은 모두 이스케이프합니다. 무작위 nonce가 붙은 내장 스타일과 스크립트만 실행되고(`Content-Security-Policy`) 다른 사이트에 삽입될 수 없으며, 아이콘 이미지는 `no-referrer`로 불러옵니다. 방문자 주소에 따라 내용이 달라지므로 응답에 `Cache-Control: no-store`가 붙습니다.

인스턴스 하나에 패널은 최대 50개, 패널마다 링크는 최대 500개입니다. 사이트에서 쓰는 패널은 삭제할 수 없습니다. 읽기 전용 계정과 토큰은 볼 수 있습니다. API는 `GET|POST /api/webservice/panels`, `PUT|DELETE /api/webservice/panels/{key}`, `PUT /api/webservice/panels/{key}/enable`, `POST /api/webservice/panels/preview`입니다.

## 전송 및 프로토콜

- HTTPS: [SSL 인증서](/ko/docs/modules/ssl) 모듈에서 해당 도메인을 포함하는 인증서를 사용합니다.
- 같은 포트의 HTTP: HTTPS를 켠 리스너도 평문 HTTP를 받을 수 있으며, 연결의 첫 바이트로 프로토콜을 구분합니다. "HTTPS로 리디렉션"은 `http://호스트:포트`를 `https://호스트:포트`로 보내며(GET/HEAD는 301, 그 밖의 메서드는 308), 포트를 하나만 쓸 수 있고 스킴을 잘못 입력해도 열리게 하고 싶을 때 유용합니다. "그대로 제공"은 암호화되지 않은 HTTP로 사이트를 응답합니다. ACME HTTP-01 검증 요청은 그대로 응답하며, 이 설정을 바꾸면 리스너가 다시 시작됩니다.
- HTTP 포트: 리스너에 평문 HTTP 포트를 하나 더 지정할 수 있습니다(예: 443 HTTPS 리스너에 80 추가). 메인 포트와 모든 사이트·설정을 공유하므로 같은 사이트를 다시 입력한 HTTP용 리스너를 따로 만들 필요가 없습니다. HTTPS를 켠 경우 "HTTPS로 리디렉션"(기본) 또는 "그대로 제공"을 고릅니다. 리디렉션은 방문자의 도메인·경로·쿼리를 유지하고 포트를 "접속 주소"의 포트(비우면 수신 포트, 443이면 생략)로 바꾸며 GET/HEAD는 301, 그 밖의 메서드는 308을 씁니다. "그대로 제공"은 HTTP로 사이트를 제공하므로 `http://`와 `https://`를 오가며 쓸 때 유용합니다. 대응하는 사이트가 없는 도메인은 리디렉션하지 않습니다. 기본 사이트가 없으면 알 수 없는 도메인으로 404를 반환하고, 기본 사이트가 "연결 끊기"이면 연결을 끊어 HTTPS와 같게 처리합니다(같은 포트 HTTP 리디렉션도 동일). ACME HTTP-01 검증 요청은 그대로 응답하며 PROXY 프로토콜과 방화벽 자동 허용도 이 포트에 적용됩니다. HTTP 포트가 사용 중이면 메인 포트는 계속 동작하고 리스너 상태에 이유가 표시됩니다.
- HTTP/3(QUIC): HTTPS를 켠 리스너에서 활성화하면 같은 포트 번호의 UDP로 HTTP/3도 제공하고 `Alt-Svc` 응답 헤더로 브라우저에 알립니다. 방화벽과 포트 포워딩에서 해당 UDP 포트를 허용해야 합니다.
- WebSocket: 리버스 프록시에서 자동으로 지원합니다.
- PROXY 프로토콜: 리스너가 업스트림(haproxy, frp 등)이 보낸 PROXY 헤더를 받을 수 있으며 「전역 설정 → 신뢰할 PROXY 출처」에 나열된 IP 또는 대역만 신뢰합니다. 비워 두면 어떤 출처도 신뢰하지 않습니다. 리버스 프록시는 백엔드로 PROXY 헤더를 보낼 수 있습니다. 신뢰할 출처에서 들어온 연결의 `X-Forwarded-Proto: https`도 신뢰합니다. 세션 쿠키에 Secure가 붙고, 평문 HTTP를 리디렉션하는 포트에서도 리디렉션하지 않으며, "X-Forwarded-* 추가"를 켜면 백엔드에도 https를 전달합니다.

### 방문자 실제 IP (CDN / WAF 뒤) {#real-ip}

Cloudflare, Alibaba Cloud CDN, Tencent Cloud CDN 같은 HTTP 프록시 뒤에 사이트를 두면 연결은 프록시의 원본 접속 주소에서 들어옵니다. **전역 설정 → 방문자 실제 IP** 에 신뢰 프록시(프록시의 원본 접속 IP 또는 대역, 여러 업체 가능)를 입력하고 실제 IP 헤더를 고르면, Gately 가 요청 헤더에서 방문자 주소를 얻어 접근 로그, IP 허용/차단 목록, 내부망 전용 접근, 국가 필터, 인증 실패 차단, 접근 통계, 경로 탐지, 백엔드로 보내는 `X-Real-IP` / `X-Forwarded-For` 에 사용합니다.

- 원래 상대 주소가 신뢰 프록시일 때만 헤더를 읽습니다. 원래 상대 주소는 PROXY 프로토콜 처리 후의 주소로, 신뢰하는 PROXY 출처에서 온 연결은 PROXY 헤더의 주소, 그 외에는 TCP 상대 주소입니다. 직접 접속한 클라이언트가 보낸 헤더는 항상 무시합니다;
- 헤더는 선택한 순서대로 확인하며 유효한 주소를 주는 첫 헤더를 사용합니다. 선택하지 않으면 `X-Forwarded-For` 입니다. `X-Forwarded-For` 같은 다중 값 헤더는 오른쪽에서 왼쪽으로 신뢰 프록시를 건너뛰고 첫 번째 신뢰하지 않는 주소를 사용하므로, 클라이언트가 왼쪽에 위조한 값은 채택되지 않습니다;
- 프록시가 덮어쓰는 헤더만 선택하세요. 예를 들어 Cloudflare 는 `CF-Connecting-IP` 를 덮어쓰지만 다른 프록시는 클라이언트가 보낸 같은 이름의 헤더를 그대로 전달하는 경우가 많아, 그때는 `X-Forwarded-For` 가 더 안전합니다;
- Cloudflare를 사용할 때는 실제 IP 헤더를 `CF-Connecting-IP` 로 설정하는 것을 권장합니다. Cloudflare가 방문자 주소를 직접 써 넣는 헤더입니다. `X-Forwarded-For` 는 오른쪽에서 왼쪽으로 신뢰 프록시를 건너뛰므로, 신뢰 프록시에 Cloudflare 주소 대역 전체를 넣으면 Cloudflare 자체 출구(예: Workers)를 거쳐 온 요청이 왼쪽에 위조한 주소를 실을 수 있습니다;
- `0.0.0.0/0`, `::/0` 은 저장 시 거부됩니다;
- 프로토콜 라우팅이 루프백으로 웹 서비스에 연결을 넘길 때는 `127.0.0.1` 을 신뢰 프록시에 넣지 말고, 프로토콜 라우팅에서 PROXY 헤더 전송을, 리스너에서 PROXY 프로토콜 수신을 켜세요. 그렇지 않으면 프로토콜 라우팅에 직접 접속한 방문자도 헤더를 위조할 수 있습니다. 프로토콜 라우팅의 패스스루 경로는 계속 순수 TCP 전달이며 이 설정의 영향을 받지 않습니다;
- 신뢰 프록시에서 `X-Forwarded-Proto: https` 를 달고 들어온 요청은 HTTPS 로 처리합니다;
- 신뢰 프록시를 비워 두면 기존 동작 그대로입니다. 연결 수준 차단(침입 방지가 방화벽에 쓰는 규칙)은 TCP 출처를 대상으로 하므로 CDN 뒤의 방문자에게는 효과가 없고, 웹 서비스 자체 차단은 실제 주소 기준으로 동작합니다.

## 인증

사이트 편집 창의 「보안」 탭에서 설정합니다.

- 웹 인증: 브라우저에 로그인 페이지를 표시합니다.
- 기본 인증: HTTP Basic
- 사용자: 한 줄에 `사용자 이름:비밀번호`. 비밀번호에는 bcrypt 해시를 쓸 수 있습니다. 기본 인증을 켜면 사용자가 최소 한 명 필요하고, 웹 인증을 켜면 사용자나 서드파티 로그인 ID가 최소 하나 필요합니다.
- 서드파티 로그인: GitHub, Google, QQ, OIDC를 지원하며 직접 만든 OAuth 앱을 사용합니다. 허용할 ID는 한 줄에 하나씩 `제공자 식별자:계정` 형식으로 쓰며 예를 들어 `github:octocat`, `google:me@gmail.com`처럼 입력합니다. 줄 끝에 `#`을 붙여 메모를 남길 수 있고 `github:*`는 해당 제공자의 모든 계정을 뜻합니다.

서드파티 로그인 제공자는 「전역 설정」에서 구성합니다. 직접 발급한 Client ID / Secret을 입력해 활성화하고, 콜백 주소(Gately의 어떤 리스너가 제공해야 하며 예: `https://auth.example.com`)도 설정합니다. GitHub / Google / QQ에 등록할 콜백 URL은 다음과 같습니다.

```text
https://auth.example.com/__gately_auth/oauth/callback
```

관리 콘솔 자체의 서드파티 로그인은 「설정 → 계정 및 보안」에서 따로 설정합니다.

### 포워드 인증(Authelia 등)

인증을 외부 서비스에 맡깁니다. nginx의 `auth_request`나 Traefik의 `forwardAuth`와 같은 방식입니다. 「보안」 탭에서 「포워드 인증」을 체크합니다. 같은 사이트에서 기본 인증이나 웹 인증과 함께 쓸 수 없습니다.

| 필드 | 설명 |
| --- | --- |
| `url` | 확인용 엔드포인트. 예: Authelia의 `http://127.0.0.1:9091/api/authz/auth-request` |
| `loginUrl` | 엔드포인트가 401을 반환할 때 방문자를 보낼 주소. 예: `https://auth.example.com/?rd={url}&rm={method}`. `{url}`은 원래 주소(URL 인코딩됨), `{method}`는 요청 메서드입니다. 비우면 엔드포인트의 응답을 그대로 반환합니다 |
| `loginFromLocation` | `loginUrl`이 비어 있고 엔드포인트가 http(s) 절대 주소 하나를 `Location`에 담아 401을 반환하면 방문자를 그 주소로 302 리디렉션하고 `Set-Cookie`와 `Cache-Control`도 전달합니다. 401에 동적 로그인 주소를 넣는 서비스(Casdoor 기본 `/api/forward-auth` 등)용입니다. 다른 형태의 `Location`은 따르지 않고 401을 그대로 반환합니다. 기본값은 꺼짐 |
| `copyHeaders` | 엔드포인트 응답에서 백엔드 요청으로 복사할 신원 헤더. 기본값은 `Remote-User`, `Remote-Groups`, `Remote-Email`, `Remote-Name` |

동작 방식은 다음과 같습니다.

- 모든 요청은 먼저 `url`로 본문 없는 GET으로 전송됩니다. 방문자의 헤더(쿠키, `Authorization` 등)에 더해 `X-Original-Method`, `X-Original-URL`, `X-Forwarded-Method`, `X-Forwarded-Proto`, `X-Forwarded-Host`, `X-Forwarded-Uri`, `X-Forwarded-For`, `X-Real-Ip`가 붙습니다. 타임아웃은 10초입니다.
- 2xx 응답이면 요청을 통과시키고 신원 헤더를 추가합니다. 401은 `loginUrl`로 리다이렉트합니다(상태 코드 302). 403이나 리다이렉트 같은 다른 응답은 방문자에게 그대로 반환하며, 서비스에 연결할 수 없으면 502가 됩니다.
- 방문자가 보낸 신원 헤더는 항상 제거되므로 위조할 수 없습니다.
- 경로 규칙과 「인증 범위」를 지원하므로 일부 경로(예: `/admin`)에서만 로그인을 요구할 수 있으며, 임시 공유 링크와도 함께 쓸 수 있습니다.

### 공유 사용자: TOTP와 통합 로그인 {#shared-users}

계정을 한 번 정의해 여러 사이트에서 쓰며, TOTP 2단계 인증을 선택적으로 추가할 수 있습니다. 많은 사람이 Authelia를 쓰는 목적을 이것으로 해결할 수 있습니다.

사이드바의 「Web → 인증 사용자」 페이지에서 다음을 설정합니다(웹 서비스 전역 설정 대화상자에는 요약과 링크만 표시됩니다).

- 사용자를 추가하려면 사용자 이름과 비밀번호를 입력합니다. 비밀번호는 bcrypt 해시로 저장되며 API가 반환하지 않습니다. TOTP를 추가하려면 「TOTP 사용」을 누르고 인증 앱(Google Authenticator, 1Password 등)으로 QR 코드를 스캔한 뒤 저장합니다. 키를 다시 생성하면 이전 키는 무효가 됩니다.
- 이메일, 표시 이름, 그룹을 선택적으로 입력할 수 있습니다. [OIDC 통합 로그인](/ko/docs/modules/oidc)은 이를 `email`, `name`, `groups` 클레임으로 앱에 전달하며, OIDC 클라이언트의 허용 사용자에서 `group:그룹명`으로 그룹 단위 허용이 가능합니다.
- 통합 로그인(SSO) 도메인(예: `example.com`): 이 도메인이나 하위 도메인의 사이트 중 하나에서 로그인하면 그곳의 다른 사이트에서는 다시 로그인할 필요가 없습니다. 상위 도메인 쿠키(`gately_sso`, 유효 기간 7일)를 사용하며 이 쿠키는 백엔드로 전달되지 않습니다. 비우면 사이트마다 따로 로그인합니다.

사이트에서 웹 인증이나 기본 인증 옆의 「공유 사용자 사용」을 체크합니다. 사이트 자체 사용자도 계속 사용할 수 있습니다. 「인증 사용자」 페이지의 사이트 목록에서 리스너별로 보고 필터링해 일괄 체크할 수도 있습니다. 인증이 꺼진 사이트를 체크하면 웹 인증도 켜집니다. 공유 사용자로만 인증하는 사이트의 체크를 해제하면 「저장 후 인증 끔」으로 표시되고, 저장할 때 이런 사이트 목록을 확인합니다. 확인하면 사이트의 인증도 꺼져 로그인 없이 접근할 수 있게 됩니다. 포워드 인증을 쓰는 사이트는 공유 사용자를 쓸 수 없습니다. 페이지의 사용자, OIDC, 사이트 변경은 아래쪽 「저장」을 누르면 함께 적용되고, 하나라도 검증에 실패하면 아무것도 저장되지 않으며, 저장하지 않은 변경이 있을 때 페이지를 떠나면 먼저 확인합니다.

동작은 다음과 같습니다.

- 공유 사용자 중 TOTP를 쓰는 사용자가 있으면 로그인 페이지에 인증 코드 입력란이 표시됩니다. 각 코드는 한 번만 사용할 수 있습니다.
- 사용자의 비밀번호나 TOTP 키를 바꾸면 해당 사용자의 세션이 종료됩니다.
- 기본 인증에서는 TOTP가 없는 공유 사용자만 사용할 수 있습니다. 브라우저의 비밀번호 입력창에는 코드를 입력할 곳이 없기 때문입니다.
- 실패한 시도는 다른 로그인과 같은 속도 제한과 자동 차단에 집계됩니다.

Gitea, OpenList, Grafana 등의 앱이 어떤 사용자가 로그인했는지 알게 하려면 [OIDC 통합 로그인](/ko/docs/modules/oidc)으로 공유 사용자를 앱에 제공하세요.

### 비밀번호 직접 변경 {#self-service-password}

「인증 사용자」 페이지에서 「비밀번호 직접 변경」을 켜면 공유 사용자가 관리자 없이 직접 비밀번호를 바꿀 수 있습니다.

- '공유 사용자 사용'이 켜진 사이트에서 `https://사이트 도메인/__gately_auth/password`에 접속합니다. 로그인 페이지에도 '비밀번호 변경' 링크가 표시됩니다. [OIDC 싱글 사인온](/ko/docs/modules/oidc) 사용자는 발급자 도메인의 `/__gately_oidc/password`를 사용할 수 있습니다.
- 사용자 이름, 현재 비밀번호, 새 비밀번호(8~128자, 현재 비밀번호와 달라야 함)를 두 번 입력합니다. TOTP를 켠 사용자는 인증 코드도 입력합니다.
- 변경 후 해당 사용자의 모든 사이트 세션은 즉시 만료되어 새 비밀번호로 다시 로그인해야 합니다. 발급된 OIDC 갱신 토큰은 무효화되고 이전 Access Token으로도 사용자 정보를 읽을 수 없습니다. 앱이 직접 검증하는 토큰은 만료 전까지 유효하며, 앱 자체의 로그인 세션도 그대로 유지됩니다.
- 같은 계정은 변경에 성공한 뒤 1분 동안 다시 변경할 수 없습니다. 반복 변경으로 FTP, SMB가 계속 다시 로드되어 다른 사람의 연결이 끊기는 것을 막기 위해서입니다. 저장 시 서비스 검사에서 거부된 자세한 이유는 웹 서비스 로그에만 기록되고, 화면에는 관리자에게 문의하라는 안내만 표시됩니다.
- 현재 비밀번호나 코드 오류는 로그인 실패와 같은 속도 제한·자동 차단에 포함되며, 다른 웹사이트에서 대신 제출한 양식은 거부됩니다. 웹 서비스 로그에 변경한 사용자와 출발지 IP가 기록됩니다.
- 같은 페이지에서 [파일 서비스 공유 사용자](/ko/docs/modules/tools#shared-users)의 비밀번호도 바꿀 수 있습니다. 두 종류의 계정은 각각 켜고 끌 수 있으며, 둘 다 켜면 페이지에서 계정 종류를 고릅니다. 이름이 같은 두 종류의 계정은 서로 영향을 주지 않습니다.

## 접근 제어

### IP 허용·차단 목록

사이트 「보안」 탭의 「IP 접근 제어」에서 끄기, 허용 목록, 차단 목록 중에서 선택하며 목록에는 한 줄에 IP 또는 대역(예: `192.168.1.0/24`)을 하나씩 씁니다. 구독 IP 목록도 함께 참조할 수 있습니다.

### 거부 방식

사이트 「보안」 탭의 「거부 방식」은 차단, IP 접근 제어(경로 규칙 포함) 또는 국가 필터로 거부된 요청의 처리 방식을 정합니다. 기본값은 「403 반환」이며, 「연결 끊기」를 선택하면 아무것도 보내지 않고 끊고 접근 로그에는 444로 기록합니다(연결 끊기 사이트와 같음). 허용 목록과 함께 쓰면 "내 IP는 정상 접근, 나머지는 모두 끊기"를 구현할 수 있습니다. 속도 제한(429)과 WAF 차단에는 영향이 없습니다.

기본 사이트도 같은 방식으로 설정할 수 있습니다. 유형을 「리버스 프록시」로 하고 백엔드를 지정한 뒤, IP 접근 제어에서 허용 목록 또는 차단 목록을 선택하고(아래의 구독 IP 목록 사용 가능) 거부 방식을 「연결 끊기」로 설정합니다. 허용 목록에 있거나 차단 목록에 없는 요청은 백엔드로 프록시되고 나머지는 끊깁니다. 구독 목록이 갱신되면 바로 적용됩니다. 「연결 끊기」 사이트 유형에는 백엔드가 없으며 모든 요청을 끊습니다.

연결 끊기(사이트 유형이든 거부 방식이든)는 HTTP 응답을 보내지 않을 뿐이며 서비스가 살아 있다는 사실은 숨길 수 없습니다.

- TCP 핸드셰이크가 이미 끝났으므로 상대는 포트가 열려 있음을 알 수 있습니다.
- HTTP/1.x에서는 연결을 닫지만 HTTP/2·HTTP/3에서는 이 요청만 재설정하고 연결은 유지되어 계속 재사용할 수 있습니다.
- HTTPS에서는 인증서가 없는 도메인이 TLS 핸드셰이크 단계에서 실패하므로, 기본 사이트에 도달한 요청은 이미 인증서와 그 안의 도메인을 받은 상태입니다.

이후 스캐너에게 시간 초과만 보이게 하려면 [침입 방지](/ko/docs/modules/guard)에서 해당 주소를 차단하세요. 방화벽 동기화를 켜면 커널에서 트래픽을 버립니다.

### 구독 IP 목록

「전역 설정 → 구독 IP 목록」에서 목록을 추가합니다. 다운로드 URL과 새로고침 간격(기본 24시간)을 입력합니다. 다운로드 주소(예: GitHub)에 직접 연결할 수 없으면 「다운로드 프록시」에서 전역 업데이트 프록시를 선택하거나 프록시 주소를 입력할 수 있습니다. Gately가 주기적으로 내려받아 설정 디렉터리에 캐시하므로, 재시작한 뒤에도 네트워크 없이 사용할 수 있습니다. 내용은 한 줄에 IP, CIDR 또는 `시작-끝` 범위 하나이며, `#`, `;`, `//` 뒤는 주석입니다. 예를 들어 중국 성·시 IP 대역은 [metowolf/iplist](https://github.com/metowolf/iplist)의 `https://metowolf.github.io/iplist/data/cncity/440000.txt`(광둥성)를 쓸 수 있습니다.

- 사이트와 경로 규칙의 허용 목록, 차단 목록은 여러 목록을 참조할 수 있으며, 직접 입력한 IP 대역과 함께 판단해 하나라도 일치하면 목록에 있는 것으로 봅니다.
- 내려받은 내용을 해석할 수 없으면(예: 오류 페이지가 반환된 경우) 이전 목록을 유지하고 목록에 원인을 표시하며, 1시간 후 다시 시도합니다.
- 목록을 처음 내려받기 전에는 빈 목록으로 처리합니다. 따라서 허용 목록은 접근을 거부하고, 차단 목록은 추가로 차단하는 것이 없습니다.
- 참조 중인 목록을 비활성화하면 이를 참조하는 허용 목록은 모든 출발지를 거부하고, 차단 목록은 어떤 출발지도 차단하지 않습니다.
- 참조 중인 목록은 삭제가 거부됩니다.

### 경로 규칙

「보안」 탭의 「경로 규칙」에서 경로 접두사별로 사이트의 인증과 IP 설정을 덮어씁니다.

| 필드 | 값 |
| --- | --- |
| `prefix` | `/`로 시작하는 경로 접두사. 예: `/admin` |
| `auth` | 사이트 설정 따름(비움), `off`(인증 불필요), `on`(인증 필수) |
| `ipMode` / `ipList` | 사이트 설정 따름(비움), `whitelist`, `blacklist`, 그리고 IP 또는 대역 목록 |

매칭 규칙은 다음과 같습니다.

- 가장 긴 접두사가 우선합니다.
- 경로 세그먼트 경계로 매칭하므로 `/admin`은 `/admin`과 `/admin/x`에 일치하고 `/administrator`에는 일치하지 않습니다.
- 요청 경로를 먼저 정규화(`.`, `..`, 중복 슬래시 제거)한 뒤 매칭하므로 `/public/../admin`은 `/admin`으로 처리됩니다.
- 같은 접두사에는 규칙을 하나만 설정할 수 있습니다.

「인증 범위」 옵션(`authOptional`): 체크하면 인증이 규칙에서 「인증 필수」로 표시된 경로에만 적용되고 나머지 경로는 공개됩니다. 이 옵션을 쓰려면 먼저 기본 인증이나 웹 인증을 켜야 합니다.

「로그인한 사용자 신뢰」 옵션(`trustAuthUsers`): 체크하면 이 사이트의 Gately 인증을 통과한 방문자는 WAF를 거치지 않고, 요청도 침입 방지의 웹 경로 탐색에 집계되지 않습니다. WAF나 404·미끼 경로 규칙이 자기 사용자를 잘못 차단할 때 사용합니다. Gately가 발급한 자격 증명만 해당합니다: 웹 인증과 외부 로그인 세션, 공유 사용자 SSO, 기본 인증(기본 인증 자격 증명은 처음 검증에 성공한 뒤부터 신뢰되며 비밀번호를 바꾸거나 사용자를 삭제하면 즉시 무효가 됩니다). 전달 인증과 공유 링크는 해당하지 않습니다. 차단된 주소, IP·국가 접근 제어, 속도 제한은 그대로 적용되고 로그인 실패도 그대로 집계됩니다. 이 옵션을 쓰려면 먼저 기본 인증이나 웹 인증을 켜야 합니다. 켜면 로그인한 사용자의 요청은 WAF 보호를 받지 않으므로 신뢰할 수 있는 사용자일 때만 켜세요.

### 임시 공유 링크

기본 인증이나 웹 인증을 켜면 사이트에 공유 링크를 만들어 방문자가 계정 없이 접근하게 할 수 있습니다.

| 필드 | 설명 |
| --- | --- |
| 이름 | 메모용 이름. 예: 「홍길동에게」 |
| 만료 시간 | 비우면 만료되지 않습니다 |
| 사용 횟수 `maxUses` | 교환할 수 있는 최대 횟수이며 0은 무제한입니다. 재시작하면 카운트가 초기화됩니다 |
| 경로 제한 `pathPrefix` | 비어 있지 않으면 링크로 해당 접두사 아래 경로만 접근할 수 있으며 `/`로 시작해야 합니다 |

방문자가 `https://도메인/임의경로?_gs=토큰`에 접속하면 세션으로 교환됩니다. 교환에 성공하면 서버가 로그인 불필요 쿠키를 설정하고 `_gs` 매개변수를 제거한 주소로 이동시키며, 세션은 최대 24시간이고 링크의 만료 시간을 넘지 않습니다. 토큰이 유효하지 않으면 일반 접근으로 처리하며 실패 이유를 알려 주지 않습니다. 링크를 삭제하면 이미 발급된 세션도 즉시 무효가 됩니다. 토큰은 저장한 뒤에 생성되며(16자 이상) UI에서 전체 링크를 복사할 수 있습니다.

### 인증 실패 제한과 자동 차단

- 같은 출처 IP가 15분 안에 인증에 10번 실패하면 한동안 더 이상의 시도를 거부합니다.
- 「전역 설정 → 자동 차단 → 인증 실패 차단」에 분 단위 값(0~43200)을 입력하면 10번 실패한 출처 IP를 그 시간 동안 차단합니다. 0이면 차단하지 않고 제한만 합니다.
- 자동 차단이 발동하면 `AuthBanned` 이벤트가 발행되며 [알림 센터](/ko/docs/modules/notify)로 푸시할 수 있습니다.
- IPv6 주소는 /64 대역 단위로 집계하고 차단합니다.

### 차단 목록

「전역 설정」의 차단 목록에는 현재 차단된 IP, 사유(인증 연속 실패 또는 수동 차단), 만료 시간이 표시되며 「해제」를 누를 수 있습니다. 수동으로 차단할 수도 있습니다. IP와 시간(1~720시간, 최대 30일)을 입력하며 API의 기본 기간은 24시간입니다. 루프백 주소와 신뢰할 수 있는 프록시에 속한 주소는 수동으로 차단할 수 없으며, 이유는 아래 「끊고 차단」을 참고하세요. 「영구」를 선택하면 만료 없이 차단합니다(API에서는 seconds가 -1).

차단 목록은 [침입 방지](/ko/docs/modules/guard)와 공유됩니다. 침입 방지 모듈이 켜져 있으면 여기에는 차단 수만 표시되고 침입 방지 페이지에서 관리합니다. 차단은 포트 포워딩, STUN 등에도 적용되며, 방화벽 동기화를 켜면 시스템 방화벽에서 삭제됩니다. "LAN 주소 무시"를 켜면 LAN 주소는 자동으로 차단되지 않습니다.

### GeoIP 국가 필터

사이트 「국가 필터」에는 끄기, 허용만, 거부의 세 가지 모드가 있으며 두 글자 ISO 국가 코드를 쉼표로 구분해 입력합니다(예: `CN, HK, US`). 사용하려면 국가를 하나 이상 입력해야 합니다.

- 필터링은 GeoIP 데이터베이스가 필요하므로 먼저 「전역 설정 → GeoIP 데이터베이스」에서 가져와야 합니다. `.mmdb` 파일을 업로드하거나 다운로드 주소를 입력합니다(「다운로드 프록시」는 기본적으로 전역 업데이트 프록시를 사용하며, 업데이트 프록시가 설정되어 있지 않으면 직접 연결합니다). MaxMind GeoLite2, DB-IP 등의 국가 DB나 도시 DB를 지원하며 업로드 제한은 129 MB입니다.
- 데이터베이스가 로드되지 않았으면 필터가 동작하지 않고(모든 방문자 통과) UI에 안내가 표시됩니다.
- 내부망 주소는 항상 통과합니다.
- 「거부」 모드에서 DB에서 국가를 찾을 수 없는 주소는 통과합니다.

## 경로별 백엔드

리버스 프록시 사이트에서 경로 접두사별로 다른 백엔드로 요청을 보냅니다. nginx의 `location /api/ { proxy_pass ...; }`와 같습니다. 사이트 편집 창 「기본」 탭의 「경로별 백엔드」에서 추가합니다.

| 필드 | 설명 |
| --- | --- |
| `prefix` | `/api/` 같은 경로 접두사. 경로 세그먼트 경계로 매칭하므로 `/api`와 `/api/` 모두 `/api`와 `/api/x`에 일치하고 `/apix`에는 일치하지 않습니다 |
| `targets` | 이 경로의 백엔드이며 사이트의 백엔드와 같은 방식으로 씁니다. 비우면 사이트의 백엔드를 사용하고 아래 헤더만 추가합니다 |
| `requestHeaders` | 이 경로에 추가할 요청 헤더. 한 줄에 `Key: Value` 하나씩. 사이트 헤더 뒤에 적용되며 이름이 같은 헤더는 사이트의 값을 덮어씁니다 |

- 가장 긴 접두사가 우선하며 경로는 그대로 전달됩니다(접두사를 제거하지 않음).
- Host 옵션, 인증서 검증, 전달 헤더, PROXY 프로토콜, 로드 밸런싱 정책, 헬스 체크 등 사이트의 다른 설정은 모든 경로별 백엔드에 적용됩니다.
- 압축, 속도 제한, 캐시, 재작성은 사이트 전체에 적용됩니다.

## 사용자별 분배 {#user-routes}

리버스 프록시 사이트에서 로그인한 사용자마다 요청을 각자의 백엔드로 보냅니다. nginx의 `map $remote_user $backend`와 같습니다. 먼저 사이트에서 기본 인증, 웹 인증 또는 포워드 인증을 켜야 합니다. 그런 다음 사이트 편집 창 「보안」 탭의 「사용자별 분배」에서 규칙을 추가합니다. 각 규칙에는 사용자 목록과 그 사용자들의 백엔드를 입력하며, 백엔드는 사이트의 백엔드와 같은 방식으로 씁니다.

리디렉션, 정적 파일, 내비게이션 패널, 고정 텍스트 사이트에서도 사용자별로 분기할 수 있습니다. 규칙에 일치하는 사용자는 해당 규칙의 백엔드로 리버스 프록시되고, 목록에 없는 사용자와 공개 경로의 로그인하지 않은 방문자는 평소대로 사이트 유형에 따라 처리됩니다. 예를 들어 관리자는 관리 백엔드로 보내고, 다른 로그인 사용자는 안내 페이지로 리디렉션하거나 "접근 권한 없음" 고정 텍스트를 보여 줄 수 있습니다. 이때 「기본」 탭의 백엔드 옵션과 「트래픽」 탭의 부하 분산, 백엔드 시간 초과, 상태 검사는 분기된 백엔드에 적용되며, 응답 캐시는 여전히 리버스 프록시 사이트에서만 사용됩니다. 연결 끊기 사이트는 인증을 거치지 않으므로 사용자별로 분기할 수 없습니다.

사용자는 다음 식별자로 일치시킵니다.

- 사이트 사용자 또는 [공유 사용자](#shared-users)의 사용자 이름
- 서드파티 로그인 ID는 `제공자key:ID` 형식으로 씁니다. 예: `github:octocat`. 해당 ID의 다른 식별자도 함께 일치합니다.
- 포워드 인증은 인증 서비스 응답에서 복사해 온 `Remote-User`

분배 규칙은 다음과 같습니다.

- 목록에 없는 사용자, 그리고 공개 경로(인증이 필요 없는 경로)에서 로그인하지 않은 방문자는 사이트 백엔드를 사용합니다. 공개 경로에서도 웹 인증으로 이미 로그인한 방문자는 신원에 따라 분배되므로 같은 앱의 페이지가 같은 백엔드로 갑니다.
- 자체 백엔드가 있는 경로별 백엔드 규칙(위 절 참고)이 우선합니다. 요청 헤더만 추가하는 경로별 규칙은 해당 사용자의 백엔드를 사용합니다.
- 메모리 응답 캐시를 켜면 캐시 키에 선택된 사용자 경로가 포함되고, [신원 정보 전달](#identity-headers)을 설정하면 백엔드로 보낸 신원 정보도 포함되어 서로 다른 백엔드나 사용자의 응답이 섞이지 않습니다.

저장할 때 사이트에 인증이 켜져 있는지, 각 규칙에 사용자가 한 명 이상 있고 백엔드가 올바른지, 같은 사용자가 두 규칙에 들어 있지 않은지 확인합니다. 사이트 목록에서 사용자별 분배가 설정된 사이트에는 규칙 개수 태그가 표시됩니다.

### 신원 정보 전달 {#identity-headers}

「신원 정보 전달」은 인증된 사용자의 신원 정보를 요청 헤더에 담아 백엔드로 보냅니다. 헤더로 사용자를 식별하는 앱에 맞으며, 예를 들어 Firefly III는 `Remote-Email`로 계정을 식별합니다. 각 줄에서 항목과 헤더 이름을 지정합니다.

| 항목 | 자주 쓰는 헤더 | 출처 |
|---|---|---|
| 사용자 이름 | `Remote-User` | 사이트 사용자나 공유 사용자의 이름. 타사 로그인은 `제공자키:ID`, 전달 인증은 `Remote-User` |
| 이메일 | `Remote-Email` | 공유 사용자의 이메일 또는 전달 인증이 복사해 온 `Remote-Email` |
| 표시 이름 | `Remote-Name` | 공유 사용자의 표시 이름 또는 전달 인증이 복사해 온 `Remote-Name` |
| 그룹 | `Remote-Groups` | 공유 사용자의 그룹(쉼표 구분) 또는 전달 인증이 복사해 온 `Remote-Groups` |

- 「자주 쓰는 Remote-* 헤더 추가」는 현재 인증 방식이 제공하는 항목을 위 표대로 한 번에 추가합니다.
- 이메일·표시 이름·그룹은 [공유 사용자](#shared-users) 또는 전달 인증을 쓰는 사이트에서만 고를 수 있으며, 사이트 사용자와 타사 로그인에는 사용자 이름만 있습니다. 공유 사용자 정보를 수정하면 로그인된 세션에도 곧바로 새 값이 전달됩니다. 공유 사용자와 이름이 같은 사이트 사용자가 사이트 사용자 비밀번호로 로그인하면 사용자 이름만 전달합니다.
- 전달 인증은 복사해 온 헤더만 믿습니다. 복사 목록에 `Remote-Email` 등이 없으면 방문자가 보낸 같은 이름의 헤더를 신원 정보로 쓰지 않습니다. 인증 서비스가 `Remote-User`를 돌려주지 않으면 다른 정보도 전달하지 않습니다.
- 방문자가 보낸 같은 이름의 헤더는 하이픈 대신 밑줄을 쓴 표기(`Remote_Email` 등)까지 항상 삭제되므로 위조할 수 없습니다. 로그인하지 않았거나 공유 링크로 접근한 경우에는 신원 정보를 전혀 전달하지 않고, 값이 비어 있는 항목의 헤더도 보내지 않습니다.
- 저장할 때 헤더 이름이 올바르고 겹치지 않는지(대소문자 구분 없음, `-`와 `_`는 같은 것으로 봄), `Host`, `Cookie`, `Authorization`, `X-Forwarded-For`처럼 전달이나 인증에 영향을 주는 헤더가 아닌지, 사이트나 경로 규칙의 요청 헤더 설정과 이름이 같지 않은지(같으면 인증 결과를 덮어씀) 확인합니다. 최대 16줄입니다.
- 이전 버전의 「사용자 이름 전달」은 사이트를 편집할 때 사용자 이름 줄로 표시되며, 저장하면 이 목록에 합쳐집니다.

## 리버스 프록시 고급 기능

이 옵션들은 사이트 편집 창의 「트래픽」 탭에 있습니다.

### 백엔드, 가중치, 예비

백엔드 목록은 한 줄에 주소 하나이며 주소 뒤에 매개변수를 붙일 수 있습니다.

```text
http://10.0.0.2:8080 weight=3
http://10.0.0.3:8080 backup
```

- `weight=N`: 가중치, 1~100 정수, 기본값 1
- `backup`: 예비 백엔드로, 예비가 아닌 백엔드가 모두 사용 불가일 때만 활성화됩니다. 모든 백엔드가 사용 불가이면 예비가 아닌 백엔드 전체로 되돌아가 계속 시도합니다.
- 백엔드에 연결할 수 없으면(연결 거부, 도달 불가, 연결 시간 초과) 같은 요청을 바로 다음 백엔드로 다시 시도합니다. 다른 주 백엔드를 먼저, 그다음 백업을 시도하며 최대 3개까지 시도합니다. 이 시점에는 요청이 아직 전송되지 않았으므로 POST 같은 요청을 다시 보내도 안전합니다. 연결이 맺어진 뒤의 실패는 다시 시도하지 않으며, 실패한 백엔드는 그대로 수동 검사에 집계됩니다.

### 헬스 체크

액티브 체크 스위치는 기본적으로 꺼져 있습니다. 켰을 때의 필드와 기본값은 다음과 같습니다.

| 필드 | 기본값 | 범위 |
| --- | --- | --- |
| 방식 `mode` | `http` | `http`(체크 경로를 요청하고 상태 코드가 400 미만이면 정상으로 판단) 또는 `tcp`(연결만 테스트) |
| 경로 `path` | `/` | `/`로 시작, http 방식에서만 사용 |
| 간격 `interval` | 10초 | 1~3600 |
| 타임아웃 `timeout` | 3초 | 1~60 |
| 연속 실패 `fails` | 3회 연속이면 사용 불가 | 1~20 |
| 연속 성공 `passes` | 2회 연속이면 복구 | 1~20 |

백엔드로 PROXY 프로토콜을 보내도록 설정하면 HTTP 체크는 자동으로 TCP로 바뀝니다.

패시브 체크는 항상 동작합니다. 백엔드가 여러 개일 때 연속 3번 연결에 실패한 백엔드는 30초간 중단한 뒤 다시 시도합니다(백엔드가 하나뿐이고 액티브 체크도 꺼져 있으면 제외하지 않습니다). 액티브 체크를 켜면 복구는 전적으로 체크 결과에 따라 결정됩니다. 백엔드 상태가 바뀌면 업스트림 사용 불가 / 복구 이벤트가 발행되며 [알림 센터](/ko/docs/modules/notify)로 푸시할 수 있습니다.

### 백엔드 시간 제한 {#backend-timeouts}

리버스 프록시 사이트가 백엔드에 연결할 때의 시간 제한으로, 단위는 초이며 0은 기본값입니다. 경로별 백엔드와 사용자별 백엔드도 같은 설정을 씁니다.

| 항목 | 기본값 | 범위 | 설명 |
| --- | --- | --- | --- |
| 연결 `timeouts.connect` | 10초 | 1~300 | 백엔드와 TCP 연결 수립 |
| TLS 핸드셰이크 `timeouts.tlsHandshake` | 10초 | 1~300 | HTTPS 백엔드와 TLS 핸드셰이크 완료 |
| 응답 헤더 대기 `timeouts.responseHeader` | 무제한 | 1~86400 | 요청(본문 포함)을 다 보낸 뒤 백엔드의 응답 헤더를 기다리는 시간 |

- 응답 헤더 대기는 헤더가 도착하기 전까지만 제한하며, 이후 응답 본문 전송, 파일 다운로드, WebSocket·SSE 같은 장시간 연결에는 영향이 없습니다. 큰 파일을 업로드할 때는 요청 본문을 다 보낸 뒤부터 계산합니다;
- 시간 초과 시 504(Gateway Timeout), 연결 거부 같은 다른 오류는 502를 반환합니다. 시간 초과도 연결 실패처럼 수동 검사에 집계됩니다;
- 늦게 시작하는 백엔드나 느린 회선 뒤의 백엔드는 연결 시간 제한을 늘리고, 멈춘 백엔드를 빨리 오류로 처리하려면 응답 헤더 대기 시간 제한을 설정합니다.

### 방문자 시간 제한 {#client-timeouts}

방문자에 대한 읽기·쓰기 유휴 시간 제한으로, 단위는 초이며 0은 기본값 60초(nginx의 `client_body_timeout`, `send_timeout` 기본값과 같음)입니다. 연결 끊기를 제외한 모든 사이트 유형에서 설정할 수 있습니다.

| 항목 | 기본값 | 범위 | 설명 |
| --- | --- | --- | --- |
| 요청 본문 `clientTimeouts.readIdle` | 60초 | 1~3600 | 요청 본문을 한 번 읽을 때 기다리는 최대 시간 |
| 응답 `clientTimeouts.writeIdle` | 60초 | 1~3600 | 응답을 한 번 쓸 때 기다리는 최대 시간 |

- 한 번의 읽기나 쓰기가 멈췄을 때만 계산하므로 데이터가 계속 오가는 큰 파일 업로드·다운로드, 백엔드 처리 대기 시간, WebSocket 같은 장시간 연결에는 영향이 없습니다;
- 요청 본문을 매우 느리게 보내거나 응답을 매우 느리게 읽는 방문자(slowloris, slow read)를 끊어 연결을 오래 점유하지 못하게 합니다;
- 요청 본문 읽기 시간 초과 시 408을 반환하고 연결을 닫으며 백엔드의 수동 검사에는 집계하지 않습니다. 쓰기 시간 초과 시 연결을 끊습니다;
- HTTP/1, HTTP/2, HTTP/3 모두에 적용됩니다.

### 압축

리버스 프록시, 정적 파일, 고정 텍스트 사이트에서 압축을 켤 수 있습니다(리다이렉트 사이트 제외). `Accept-Encoding`에 따라 `br`을 우선하고 그다음 `gzip`을 선택합니다.

- 텍스트 계열 콘텐츠만 압축합니다: `text/*`, JSON, JavaScript, XML, XHTML, RSS / Atom, WebAssembly, SVG. `text/event-stream`은 제외됩니다.
- 선언된 `Content-Length`가 256바이트 미만인 응답은 그대로 둡니다.
- 이미 `Content-Encoding`이 있는 응답은 그대로 두며 WebSocket 업그레이드 요청은 바로 통과시킵니다.
- 압축 후에는 강한 ETag가 약한 ETag로 바뀝니다.

### IP별 속도 제한

클라이언트 IP별 토큰 버킷 방식의 속도 제한이며 필드는 다음과 같습니다.

| 필드 | 설명 |
| --- | --- |
| `rate` | 초당 허용하는 요청 수 |
| `burst` | 버스트 용량. `rate`를 설정하고 `burst`가 0이면 자동으로 `rate`를 정수로 내린 값에 1을 더한 값을 사용합니다 |
| `maxConns` | IP 하나당 동시 요청 상한이며 0은 무제한입니다 |

속도 제한을 켤 때는 `rate`와 `maxConns` 중 최소 하나를 설정해야 합니다.

### 메모리 응답 캐시

리버스 프록시 사이트에서만 동작하며 캐시는 메모리에 저장되고 LRU 방식으로 제거됩니다.

| 필드 | 기본값 | 범위 |
| --- | --- | --- |
| `ttl` 기본 시간 | 0 | 0~30일(초 단위). 업스트림이 캐시 지시자를 선언하지 않았을 때 200 응답을 이 시간 동안 캐시합니다. 0이면 업스트림이 명시적으로 허용한 응답만 캐시합니다 |
| `maxMb` 캐시 용량 | 64 | 1~4096 MB |

캐시 규칙은 다음과 같습니다.

- GET 요청만 캐시하며 요청에 `Range` 헤더나 `Cache-Control: no-cache`가 없어야 합니다.
- 자격 증명이 있는 요청은 캐시하지 않습니다. 요청 헤더에 `Authorization`, `Proxy-Authorization`, `Cookie`, `X-Api-Key`, `X-Auth-Token`, `X-Access-Token`, `X-CSRF-Token`, `X-Emby-Token`, `X-Emby-Authorization`, `X-MediaBrowser-Token`, `X-Plex-Token`, `X-Jellyfin-Token` 중 하나가 있거나 쿼리 문자열에 `api_key`, `X-Plex-Token`, `token`, `access_token` 매개변수가 있는 경우입니다(매개변수 이름은 대소문자를 구분하지 않음).
- 원래 요청 경로에 `;`, `\`, `%2F`, `%5C`(대소문자 구분 없음)가 있는 요청은 캐시하지 않습니다. 이런 경로는 정규화 후 백엔드가 다르게 해석할 수 있습니다.
- 상태 코드 200 응답만 캐시합니다. 응답에 `Set-Cookie`, `Vary: *`가 있거나 `Cache-Control`이 `no-store` / `private` / `no-cache`이면 건너뜁니다.
- 응답의 `Vary`에는 `Accept-Encoding`만 올 수 있고, 사이트에서 CORS를 켠 경우 `Origin`도 올 수 있습니다. 다른 헤더가 있으면 캐시하지 않습니다. 백엔드가 직접 반환한 `Access-Control-Allow-Origin`이 `*`가 아니어도 캐시하지 않습니다.
- 사이트에서 CORS를 켠 경우 캐시 항목에는 Gately가 방문자 출처에 맞춰 쓴 CORS 헤더를 저장하지 않고, 적중 시 이번 요청의 `Origin`으로 다시 만듭니다.
- `s-maxage`를 따르고 그다음 `max-age`를 따릅니다.
- 항목 하나의 상한은 4 MB이며 전체 용량의 4분의 1을 넘지 않습니다.
- 캐시 적중 시 `X-Cache: HIT`와 `Age` 헤더를 반환하고 미적중이면 `X-Cache: MISS`입니다.
- 캐시 키에는 Host, 전체 요청 URI, `Accept-Encoding`이 포함됩니다. [사용자별 분배](#user-routes)를 설정하면 선택된 사용자 경로도 포함되고, [신원 정보 전달](#identity-headers)을 설정하면 백엔드로 보낸 신원 정보도 포함됩니다.

경로별 캐시(`rules`, 사이트 편집 창 「트래픽」 탭의 「경로별 캐시」, 최대 200개):

| 필드 | 설명 |
| --- | --- |
| `path` | 대조할 경로입니다. `/`로 시작하고 공백, `?`, `#`, `.`·`..` 경로 세그먼트, 연속된 `/`를 포함할 수 없으며 같은 사이트 안에서 중복될 수 없습니다. `%`는 쓸 수 없고(디코딩된 경로를 그대로 입력, 예: `/中文/*`) 대소문자를 구분합니다. `*`가 없으면 경로 세그먼트 단위 접두사로 대조합니다. `/api`는 `/api`와 `/api/x`에 일치하고 `/apix`에는 일치하지 않습니다. `*`가 있으면 경로 전체를 와일드카드로 대조하며 `*`는 `/`를 포함한 임의의 문자에 일치합니다(예: `/api/products/*`, `/static/*.js`) |
| `noCache` | 켜면 「캐시 안 함」: 해당 경로는 캐시를 읽지도 쓰지도 않습니다 |
| `ttl` | 캐시 시간, 0~30일(초 단위). 0이면 사이트 기본 시간을 사용합니다 |
| `override` | 켜면 「강제 캐시」: 백엔드 `Cache-Control`의 `no-store`, `no-cache`, `max-age`를 무시하고 200 응답을 캐시 시간 동안 캐시합니다. 백엔드가 `private`를 선언하면 캐시하지 않습니다. 규칙이나 사이트 중 한쪽의 시간이 0보다 커야 합니다 |

- 화면에서는 세 가지 모드를 고릅니다. 「캐시」는 백엔드의 `Cache-Control`을 따르고 백엔드가 아무것도 선언하지 않으면 캐시 시간 동안 캐시합니다. 「강제 캐시」는 `override`, 「캐시 안 함」은 `noCache`에 해당합니다.
- 더 구체적인 규칙이 우선합니다. `*`를 뺀 문자 수가 많은 규칙부터 대조하고, 같으면 설정 순서를 따릅니다. 어떤 규칙에도 일치하지 않는 경로는 사이트 기본 설정을 사용합니다. 특정 경로만 캐시하려면 `/`를 캐시 안 함으로 설정합니다.
- 규칙은 정규화한 요청 경로로 대조하므로 `//api`, `/x/../api`는 `/api`로 처리됩니다.
- 어떤 모드에서도 위에 나열한 자격 증명이 있는 요청, 경로에 `;` 등이 있는 요청, `Set-Cookie`·`Vary: *`·`Cache-Control: private`가 있는 응답은 캐시하지 않습니다.
- 강제 캐시한 응답은 모든 방문자가 함께 쓰므로 정적 리소스처럼 방문자와 관계없이 같은 내용에만 사용하세요. 백엔드가 출발지 IP로 인증을 생략하는 경우(예: 내부망에서는 로그인 불필요)에는 사용하지 마세요. 내부망 방문자가 본 내용이 캐시에서 외부 방문자에게 전달됩니다.

캐시 확인과 비우기: 저장된 사이트를 편집하면 「트래픽」 탭에 해당 사이트에서 동작 중인 캐시의 항목 수와 사용량(「현재 캐시」)이 표시되고 「새로 고침」, 「모두 비우기」를 할 수 있으며, 규칙마다 그 경로의 캐시만 비울 수도 있습니다. 해당 API는 다음과 같습니다.

- `GET /api/webservice/cache?listener=&site=`: `enabled`, `entries`, `bytes`, `maxBytes`를 반환합니다. `site`는 사이트 식별자이며 기본 사이트는 `default`입니다. 사이트가 없거나 소속 리스너가 실행 중이 아니면 404를 반환합니다.
- `POST /api/webservice/cache/purge`(요청 본문 `{"listener", "site", "path"}`): `path`를 비우면 사이트 캐시 전체를 비우고, 값을 주면 경로가 일치하는 항목만 비웁니다. 작성법과 대조 방식은 규칙의 `path`와 같습니다. 삭제한 개수 `removed`와 비운 뒤의 상태를 반환하며, 사이트에 캐시가 켜져 있지 않으면 400을 반환합니다.

### 경로 재작성과 리다이렉트

규칙은 순서대로 매칭하며 첫 번째로 일치하는 규칙에서 멈춥니다.

| 필드 | 설명 |
| --- | --- |
| `pattern` | 요청 경로와 매칭할 정규식. 예: `^/old/(.*)$` |
| `to` | 치환 결과이며 `$1`로 그룹을 참조할 수 있습니다 |
| `redirect` | 끄면 내부 재작성(재작성된 경로가 백엔드로 전송되며 대상은 `/`로 시작해야 함), 켜면 리다이렉트 |
| `code` | 리다이렉트 상태 코드 301 / 302 / 307 / 308, 기본 302 |

리다이렉트는 원래 쿼리 매개변수를 유지합니다. 리다이렉트 대상에는 방문자가 사용한 도메인을 뜻하는 `{host}`를 넣을 수 있습니다. 리다이렉트 규칙은 인증보다 먼저 실행되므로(nginx의 `location = / { return 302 ...; }`와 같음) `/` 같은 경로는 로그인을 요구하지 않고 방문자를 다른 곳으로 보낼 수 있습니다.

## 오류 페이지 {#error-pages}

사이트 편집 창의 「오류 페이지」 탭에서 방문자에게 보이는 404와 5xx 페이지를 정합니다. 기본적으로 Gately 내장 스타일을 사용하며, 10가지 내장 스타일(미니멀, 터미널, 네온, 별하늘, 신문, 브루탈리스트, 오로라, 픽셀, 청사진, 상태 체인) 중 하나로 바꾸거나 직접 만든 페이지를 사용할 수 있습니다. 모든 스타일이 휴대폰 화면에 맞게 표시되고, 문구는 방문자 브라우저의 언어로 표시됩니다. 카드 오른쪽 아래의 눈 버튼으로 상태 코드별, 데스크톱·휴대폰 크기별 미리보기를 볼 수 있습니다.

- 적용 범위: Gately가 사이트에 대해 생성하는 404와 5xx 페이지입니다. 예를 들어 백엔드에 연결할 수 없을 때의 502, 정적 파일이 없을 때의 404, 리다이렉트 대상을 일시적으로 쓸 수 없을 때의 503, 전달 인증 서비스를 쓸 수 없을 때의 오류가 해당합니다. 정적 사이트에 「404 페이지」가 입력되어 있으면 파일을 찾지 못할 때 여전히 그것이 우선합니다. 접근 제어에 의한 403과 속도 제한에 의한 429는 영향을 받지 않습니다.
- 기본 사이트: 해당 설정은 접속한 도메인과 일치하는 사이트가 없을 때의 404에도 사용되며, 기본 사이트가 꺼져 있어도 동일하게 적용됩니다.
- 브라우저가 아닌 클라이언트(`curl`, API 호출 등)는 이전과 같이 일반 텍스트 오류를 받습니다.

### 백엔드 오류 가로채기 {#intercept-errors}

리버스 프록시 사이트에서 「백엔드 오류 가로채기」를 켜면 백엔드가 반환한 지정 상태 코드를 위에서 선택한 페이지로 바꿉니다. nginx의 `proxy_intercept_errors on`과 `error_page`를 함께 쓰는 것과 같습니다. 상태 코드는 쉼표로 구분하며 범위와 줄임 표기를 지원합니다(예: `404, 500-599`, `5xx`). 400~599만 입력할 수 있습니다.

- 브라우저가 페이지를 여는 요청(`Accept`에 `text/html` 포함)만 바꿉니다. API, 이미지, 스크립트 등의 요청은 백엔드 응답이 그대로 유지되므로, 싱글 페이지 앱의 JSON 404가 웹 페이지로 바뀌는 일은 없습니다.
- 상태 코드와 `Set-Cookie`, `Retry-After` 같은 응답 헤더는 유지되고, 원래 본문을 설명하는 헤더(압축 인코딩, `ETag` 등)는 제거됩니다. `HEAD` 요청에는 응답 헤더만 반환됩니다.
- 「옵션 일괄」로 여러 사이트의 오류 페이지 스타일을 한 번에 바꿀 수 있으며, 각 사이트의 가로채기 설정은 그대로 유지됩니다.

### 사용자 지정 페이지 {#custom-error-pages}

사용자 지정 페이지는 페이지 라이브러리에 저장되며, 「전역 설정 → 사용자 지정 오류 페이지」 또는 사이트의 「오류 페이지」 탭에 있는 「사용자 지정 페이지 관리」에서 관리합니다. 여러 사이트가 같은 페이지를 공유할 수 있습니다. 페이지의 출처는 두 가지입니다.

- 업로드 또는 붙여넣기: `.html` / `.htm` 파일(UTF-8 인코딩, 256 KB 이하)을 선택하거나 코드를 직접 붙여넣습니다. 내용은 설정에 저장되며 이후에도 수정할 수 있습니다.
- 서버 파일: `.html` / `.htm` 파일의 절대 경로를 입력합니다(Docker에서는 컨테이너 내부 경로). 사용할 때마다 파일이 바뀌었는지 확인합니다. 심볼릭 링크가 가리키는 대상도 HTML 파일이어야 하며, 내용이 HTML처럼 보이지 않는 파일은 거부됩니다. 파일이 삭제되었거나 내용이 유효하지 않으면 방문자에게는 기본 스타일이 표시되고, 페이지 라이브러리에는 사용 불가로 표시됩니다.

페이지에서는 자리 표시자를 사용할 수 있으며, 출력할 때 이번 오류의 정보로 바뀌고 HTML 이스케이프가 적용됩니다.

| 자리 표시자 | 내용 |
| --- | --- |
| `{code}` | 상태 코드(예: 502) |
| `{status}` | 영어 상태 문구(예: Bad Gateway) |
| `{title}`, `{detail}` | 오류 제목과 설명(방문자 언어) |
| `{host}`, `{path}` | 접속한 도메인과 경로 |
| `{time}` | 발생 시각(UTC) |

저장하기 전에 보안과 사용 가능 여부를 자동으로 검사하고 미리보기를 표시합니다.

- 오류 페이지는 사이트와 동일 출처입니다. 페이지가 Cookie 탈취나 조작 위조에 악용되지 않도록, 저장할 때 스크립트, `onclick` 같은 이벤트 속성, `javascript:` 링크, 인라인 프레임, 플러그인 개체, 폼, `<base>`, `<meta http-equiv>`(자동 리다이렉트 등), 위험한 스타일 구문을 제거합니다. 검사 결과에 제거된 내용이 나열됩니다.
- 출력할 때 `Content-Security-Policy: sandbox; default-src 'none'; ...`가 추가됩니다. 페이지는 격리된 샌드박스에서 실행되므로 스크립트가 섞여 들어가도 실행되지 않습니다. 인라인 스타일과 `data:`로 내장한 이미지·글꼴 외에는 어떤 리소스도 불러오지 않으므로 방문자의 주소가 제3자에게 유출되지 않습니다. 외부 스타일시트, 이미지, 글꼴, 사이트 내 상대 주소는 불러오지 않으며 검사 시 안내가 표시됩니다. 스타일은 `<style>`에 작성하고 이미지와 글꼴은 `data:`로 내장하세요.
- 내용이 비어 있거나 UTF-8이 아니거나 크기를 초과하거나 HTML이 아니면 저장이 거부됩니다. `viewport`가 없거나, 인코딩 선언이 UTF-8이 아니거나, 자리 표시자를 사용하지 않은 경우에는 안내가 표시됩니다.

## 접속 통계 및 모니터링

### 사이트 통계 {#site-stats}

실행 중인 리스너에서 사이트 행의 「통계」를 누르면 통계 창이 열리며 최근 1시간, 6시간, 24시간 중에서 선택할 수 있습니다.

- 분 단위 접속 통계: 1분에 점 하나, 최근 24시간 보관, 요청 수 곡선과 4xx / 5xx 오류 곡선 포함
- 첫 바이트 지연: 분마다의 P50 / P95 곡선과 선택한 구간의 최고 P95. 요청 도착부터 응답 헤더 전송까지의 시간으로, 응답 본문 전송은 포함하지 않으며 WebSocket 등 프로토콜 업그레이드 요청과 끊긴 요청은 제외됩니다. 백분위는 세분된 구간별 평균 시간으로 추정합니다. 임계값 경보는 [성능 모니터링](/ko/docs/modules/perf) 참고;
- 상태 코드 분포 2xx / 3xx / 4xx / 5xx, 누적 응답 트래픽
- 출처 IP 상위 10개와 국가 상위 10개(국가 통계에는 GeoIP 데이터베이스를 가져와 두어야 함)
- 리버스 프록시 사이트는 백엔드별(경로별 백엔드와 사용자별 분배 백엔드 포함, 경로나 사용자 표시) 상태, 가중치, 예비 여부, 현재 연결 수, 누적 전달 요청 수를 표시
- 차단된 요청이 있으면 원인별 누적 차단 횟수 표시: 차단됨(밴), IP 목록, 국가 필터, 속도 제한, WAF(인증 실패는 집계하지 않음)

통계는 메모리에 저장되며 재시작하거나 리스너 자체의 설정을 바꾸면 다시 집계합니다. 사이트를 수정해도 카운터는 유지됩니다. 순위표는 서로 다른 출처를 최대 5000개까지 집계합니다.

### 실시간 연결 {#connections}

실행 중인 리스너에서는 사이트 행(기본 사이트 포함)의 통계 뒤에 「진행 중 N」이 표시됩니다. 사이트가 지금 처리 중인 요청 수이며 페이지 새로고침에 맞춰 갱신됩니다. 「연결」을 클릭하면 연결 창이 열리고, 2초마다 자동으로 새로고침되며 IP로 검색할 수 있습니다.

- **실시간**: 출발지 주소와 포트, 프로토콜(h1 / h2 / h3, WebSocket은 WS 표시), 요청(메서드, 호스트, 경로, 쿼리 문자열 제외), 시작 시각, 지속 시간, 트래픽(다운로드, 요청 본문이나 WebSocket이 있으면 업로드도). 오래 지속된 순으로 최대 500개를 표시합니다. [신뢰할 수 있는 프록시](#real-ip)를 설정하면 출발지는 실제 방문자 주소이고 경유한 프록시 주소도 함께 표시됩니다.
- **기록**: 최근 종료된 연결의 시작·종료 시각, 지속 시간, 트래픽, 결과(완료 / 끊김). 1초 이상 지속되었거나 수동으로 끊은 연결만 사이트별 최근 200개 보관하며 재시작하면 지워집니다. 짧은 요청은 액세스 로그를 확인하세요.

목록은 진행 중인 요청 단위입니다. HTTP/1.1 keep-alive 연결은 요청 사이에는 어떤 사이트에도 속하지 않고, HTTP/2·HTTP/3 연결 하나는 여러 요청을 동시에 실어 나르므로 요청 단위여야 사이트에 정확히 대응됩니다. 업그레이드된 WebSocket은 연결이 닫힐 때까지 계속 표시됩니다.

각 행의 「끊기」는 확인 즉시 해당 요청을 종료합니다. HTTP/1.x에서는 연결 전체를 닫고, HTTP/2·HTTP/3에서는 이 요청만 재설정하며 같은 연결의 다른 요청은 계속됩니다. 업그레이드된 WebSocket은 백엔드 연결과 함께 닫힙니다. 방문자가 데이터를 읽지 않아 전송이 막힌 경우에도 바로 적용됩니다. 끊은 요청은 액세스 로그에 444로 기록되고(응답을 이미 시작했다면 원래 상태 코드 유지) 백엔드 오류와 경로 탐지에는 집계되지 않습니다. 방문자는 바로 다시 연결할 수 있으므로 막으려면 「끊고 차단」을 사용합니다. 출발지 주소(IPv6는 해당 /64 대역)를 [차단 목록](#차단-목록)에 추가하고 모든 리스너·모든 사이트에서 진행 중인 요청을 끊습니다. 루프백 주소(frp나 PROXY 프로토콜 없는 로컬 포워딩으로 들어온 요청은 모두 이 주소로 표시됨)와 신뢰 프록시에 속한 주소(IPv6는 /64 기준)는 차단할 수 없습니다. 이런 주소를 차단하면 관계없는 방문자가 대량으로 막히기 때문입니다. 차단 없이 끊기만 하는 데에는 제한이 없습니다. 차단 기간은 1~720시간으로 지정하거나 「영구」를 선택합니다.

읽기 전용 계정과 읽기 전용 토큰은 목록을 볼 수 있고, 끊기와 차단에는 쓰기 권한이 필요하며 감사 로그에 기록됩니다.

### 네트워크 토폴로지 {#topology}

사이드 메뉴의 「Web → 토폴로지」는 별도 페이지(`#/webtopology`)이며, Web 서비스 페이지 상단의 「토폴로지」 버튼으로도 열 수 있습니다. 그림은 인터넷 → Gately → 리스너 → 사이트 / 리스너 수준 동작 → 백엔드 / 결과 순으로 펼쳐지고, 2초마다 새로 고치며 페이지가 백그라운드에 있으면 일시 중지합니다. 캔버스 색상은 현재 스킨의 라이트 / 다크 모드를 따릅니다.

- **노드**: 리스너는 주소와 실행 상태를 표시하고 시작에 실패하면 빨간색으로 표시합니다. 사이트는 일치 방식(정확히 일치, 와일드카드, 모든 도메인, 기본 사이트), QPS, 처리 중인 요청 수를 표시합니다. 리버스 프록시 사이트는 경로별 백엔드와 사용자별 분배 백엔드(경로나 사용자 표시)를 포함한 모든 백엔드로 펼쳐지며, 사용할 수 없는 백엔드는 빨간색으로 표시합니다. 리다이렉트, 정적 파일, 고정 텍스트, 연결 끊기 사이트는 각각 결과 노드 하나로 이어집니다. 기본 사이트의 연결 끊기, HTTPS 포트로 들어온 평문 요청의 리다이렉트(301 / 308), 일치하는 사이트가 없고 기본 사이트도 비활성일 때의 404는 의도된 설정이므로 회색으로 표시합니다. 비활성화한 리스너와 사이트도 목록에 나타나며 실행 안 함으로 표시됩니다.
- **링크**: QPS에 따라 굵어지고 트래픽이 있는 링크에는 흐르는 애니메이션이 표시됩니다. 링크가 120개를 넘으면 강조된 경로만 애니메이션되고, 시스템에서 「동작 줄이기」가 켜져 있으면 애니메이션하지 않습니다.
- **강조**: 노드에 포인터를 올리거나 클릭하면 그 노드가 속한 경로 전체(위로는 인터넷, 아래로는 백엔드까지)가 강조되고 링크에 QPS와 트래픽이 표시되며 나머지 노드는 흐려집니다. 빈 곳을 클릭하면 원래대로 돌아갑니다.
- **상세 패널**: 선택한 노드의 QPS(최근 10초 평균), 60초 평균, 다운로드 트래픽, 처리 중인 요청, 누적 요청, 백엔드 오류, 원인별 차단 횟수, 응답 상태 분포, 최근 60초의 초당 요청 수와 트래픽 곡선, 그 노드를 지난 활성 IP를 표시합니다. 각 지표 옆의 ⓘ에서 집계 방식을 설명합니다. 사이트는 패널에서 바로 통계, 연결, 접근 로그, 편집 창을 열 수 있고, 백엔드는 소속 사이트의 접근 로그와 편집 창을, 리스너는 편집 창을 바로 열 수 있습니다.
- **접근 로그 보기**: 사이트 또는 백엔드 노드를 선택하고 「접근 로그」를 누르면 해당 사이트만 담은 접근 로그가 열립니다(사이트 이름이 완전히 일치하는 항목만 포함). 상단에서 이미 특정 IP로 필터링했다면 버튼이 「이 IP의 접근 로그」로 바뀌며 그 주소로도 함께 필터링합니다. 상세 패널의 활성 IP 각 줄 오른쪽에 있는 로그 아이콘은 선택한 사이트에서 그 주소의 접근 로그를 바로 보여 주고, 사이트 계열이 아닌 노드를 선택했다면 모든 사이트에서 그 주소의 접근 로그를 보여 줍니다. 로그 창의 필터 조건은 계속 수정할 수 있으며 사이트 조건은 제거할 수 있는 「사이트: …」 태그로 표시됩니다. 또한 해당 사이트가 속한 리스너의 방문자만 표시하므로 다른 리스너의 같은 이름 사이트(예: IPv4와 IPv6로 나눈, 둘 다 HTTPS라는 이름의 리스너)는 섞이지 않으며, 이 조건은 제거할 수 있는 「리스너: …」 태그로 표시됩니다. 접근 로그를 켠 사이트만 기록이 완전하며, 꺼져 있으면 창 상단에 안내가 표시됩니다. 이름이 없는 사이트는 첫 번째 도메인으로 필터링합니다. Web 서비스 페이지의 각 사이트 행에 있는 「로그」 버튼도 같은 창을 엽니다.
- **활성 IP**: 최근 60초 안에 요청한 방문자 주소와 처리 중인 요청이 있는 주소입니다. 캔버스에는 개수만 표시하고 전체 주소는 상세 패널에 나열합니다. 상단에서 주소를 입력하거나 선택하면(패널의 주소를 클릭해도 됨) 그 주소가 지나간 경로만 개별 백엔드까지 강조하고, 「필터 해제」로 원래대로 돌아갑니다. 사이트, 백엔드, 리스너 수준 동작마다 최근 주소를 최대 1024개 기록하고 API는 한 번에 최대 500개를 반환하므로, 출처가 너무 많으면 패널에 목록이 일부라는 안내가 표시됩니다. [신뢰할 수 있는 프록시](#real-ip)를 설정하면 여기에는 실제 방문자 주소가 표시됩니다.
- **가리기**: 스위치를 켜면 선택한 종류의 주소를 `*`로 표시해 스크린샷을 공유하기 쉽게 합니다. 이 페이지의 표시에만 영향을 주며 검색은 원래 내용으로 일치합니다. 종류는 방문자 IP(활성 IP 목록과 필터. IPv4 마지막 부분, IPv6 뒤 64비트), 백엔드 주소(백엔드와 리디렉션 대상의 IP와 호스트 이름), 리스너 주소(리스너 IP, 리스너 오류 메시지, IP를 도메인으로 쓰는 사이트), 도메인(사이트 도메인과 사이트 이름 속 도메인. `nas.***.com`처럼 첫 레이블과 접미사만 남김)입니다. 기본으로 앞의 세 가지가 선택되며 선택은 기억됩니다.
- **가리기 방식**: 가리기 메뉴 위쪽에서 「별표」 또는 「별칭」을 고릅니다. 별표는 값의 일부만 가리고 네트워크 부분과 앞뒤를 남깁니다. 별칭은 값 전체를 이 페이지에서 일관된 번호로 바꿉니다. 방문자 IP는 `Visitor-01`, 백엔드와 리디렉션 대상의 IP는 `Backend-01`, 수신 주소는 `Listen-01`이 되며, 도메인은 접미사만 남기고 등록 가능한 부분과 호스트 부분을 따로 번호 매깁니다. 예를 들어 `nas.home.example.com`은 `host-01.domain-01.com`이 되고 같은 도메인의 하위 도메인은 `domain` 번호를 공유합니다. 같은 값은 항상 같은 별칭, 다른 값은 다른 별칭을 받으므로 어떤 노드가 같은지 계속 알아볼 수 있습니다. 번호는 나타난 순서대로 붙고 열려 있는 페이지에만 보관되며 새로 고치면 다시 매겨집니다.
- **필터**: 오른쪽 위 「필터」로 일부 리스너만 볼 수 있습니다. 「문제만 보기」는 시작에 실패한 리스너(그 사이트 전체 포함), 활성화되었지만 실행 중이 아닌 사이트, 비정상 백엔드가 있는 사이트를 보여 주며, 비활성화된 리스너와 사이트는 예상된 상태로 봅니다. 「차단 기록 있음」은 이유(차단됨, IP 목록, 국가 필터, 속도 제한, WAF)별로 Gately 시작 이후 그 이유로 요청을 차단한 사이트만 보여 줍니다. 조건은 함께 적용되고 상단 검색과도 조합할 수 있습니다. 문제나 차단으로 필터링하면 리스너 수준 동작과 남은 사이트가 없는 리스너는 숨겨집니다. 필터는 페이지를 열어 둔 동안만 유지됩니다.
- **활성만 보기**: 서비스가 많을 때 오른쪽 위 「활성만 보기」를 누르면 최근 60초 동안 요청이 있었거나, 진행 중인 요청이 있거나, 활성 IP가 지나간 사이트와 리스너 수준 동작만 표시합니다. 프록시 사이트는 활성 백엔드만 남기며(접근 제어로 차단되는 등 백엔드에 요청이 없으면 사이트가 끝 노드로 표시됨), 활동이 없는 리스너는 숨깁니다. 이 모드에서는 리스너 접기와 「N개 더」 묶음이 적용되지 않고, 캔버스가 이 노드들이 모두 보이도록 자동으로 맞춰지며(트리, 세로, 생키는 최소 50%) 서비스 활동이 시작되거나 멈추면 함께 갱신됩니다. 버튼의 숫자는 현재 활성 사이트 수로 필터와 검색을 따르며 꺼져 있을 때도 표시됩니다. 필터, 검색, IP 강조, 모든 레이아웃과 함께 쓸 수 있고 켜짐 상태는 기기별로 기억됩니다. 최근 60초 동안 요청이 전혀 없으면 캔버스에 안내가 나오며 「모두 표시」로 빠져나옵니다.
- **재생**: 오른쪽 위의 **재생**을 누르면 타임라인이 열리고 과거 시점의 토폴로지를 볼 수 있습니다. 기록은 기본적으로 꺼져 있으며, 관리자가 타임라인의 **기록 시작** 또는 **기록 설정**에서 켭니다. 켜면 5초마다 토폴로지 전체(속도, 카운터, 백엔드 상태, 활성 IP)를 한 프레임으로 기록해 압축한 뒤 메모리에만 보관하고, **메모리 한도**(기본 8 MiB, 1–256)를 넘으면 가장 오래된 프레임부터 버립니다. 내용이 같은 연속 프레임(트래픽이 없을 때 등)은 한 번만 저장하므로 트래픽이 적으면 오래, 많으면 짧게 되돌아볼 수 있습니다. 타임라인은 트래픽을 영역 차트로 그리고, 리스너 시작 실패나 백엔드 이상이 있던 구간을 아래쪽에 빨간색으로, 기록이 없는 구간(모듈 비활성, 실행 중인 리스너 없음)을 어두운 색으로 표시합니다. 타임라인을 클릭하거나 드래그해 이동하고, 마우스를 올리면 그 시점의 QPS와 활성 IP 수가 보입니다. 버튼이나 ← →로 한 프레임씩 이동하고 Space로 재생·일시 정지하며, 속도는 1×–60×에서 고르고 **유휴 건너뛰기**를 켜면 재생 중 트래픽과 방문자가 없는 구간을 건너뜁니다. 타임라인 범위는 전체 기록 또는 최근 15분~24시간 중에서 고를 수 있고 기기별로 기억합니다. 재생 중에도 일곱 가지 레이아웃, 필터, 활성만 보기, 마스킹, IP 강조를 그대로 쓸 수 있으며, 상세 패널의 그래프는 선택한 시점 이전 60초(5초마다 한 점)입니다. **연결**은 현재 상태를 보여 주므로 재생 중에는 표시하지 않습니다. **실시간으로**를 누르면 끝납니다. 기록 데이터에는 방문자 IP가 포함되며 Gately를 재시작하거나 기록을 끄면 지워집니다. 한 프레임 기록에 약 0.4ms(사이트 40개, 활성 IP 200개로 측정), 압축 후 약 1–2KB입니다.
- **레이아웃**: 오른쪽 위 레이아웃 메뉴에 일곱 가지가 있으며 선택은 기억됩니다. 전환할 때 페이드되고 캔버스에 다시 맞춥니다. 「트리」는 왼쪽에서 오른쪽으로 다섯 열을 배치해 정보가 가장 자세합니다. 「세로형」은 조직도처럼 위에서 아래로 펼치며 Gately를 중심으로 열리고 좌우로 드래그해 봅니다. 「방사형」은 Gately를 중심으로 리스너, 사이트, 백엔드를 세 겹의 동심원에 두고 이름을 반지름 방향으로 표시합니다. 「생키」는 각 노드를 막대로, 링크를 띠로 그리며 부모 막대를 자식의 QPS 비율로 나눕니다. 막대 높이와 띠 너비는 트래픽에 따라 바뀌고 노드 위치는 그대로입니다. 「선버스트」는 Gately를 중심으로 리스너, 사이트, 백엔드를 세 겹의 고리 구역으로 나타냅니다. 「트리맵」과 「버블」은 Gately, 리스너, 사이트, 백엔드를 중첩된 블록이나 원으로 나타내며 백엔드(또는 결과)마다 면적이 같습니다. 선버스트, 트리맵, 버블은 링크가 없고 색이 진할수록 트래픽이 많아 사이트가 많을 때 전체를 보기 좋습니다. 생키, 선버스트, 트리맵, 버블에는 캔버스의 접기 버튼이 없으니 리스너의 상세 패널에서 접거나 펼칩니다.
- **남는 노드 접기**: 기본적으로 리스너마다 처음 8개 사이트, 사이트마다 처음 6개 백엔드를 표시하고 나머지는 「사이트 / 백엔드 N개 더 보기」 노드로 합쳐 합계 QPS와 처리 중 요청 수를 보여 줍니다. 클릭하면 모두 펼쳐지고, 끝에 추가되는 「접기」 노드로 다시 접습니다. 접힌 노드의 활성 IP는 이 노드에 집계되며 IP 강조도 이 노드에서 멈춥니다. 최근 60초 동안 요청이 있었거나 진행 중인 요청이 있는 사이트와 백엔드는 접히지 않고 상한을 넘어도 원래 순서대로 표시되므로, 묶음 노드에는 유휴 항목만 남고 부제목은 「최근 60초 동안 요청 없음」으로 표시됩니다.
- **이동, 확대/축소, 캔버스 크기**: 캔버스를 드래그해 이동하고 휠로 위아래로 스크롤합니다(가장자리에 닿으면 페이지가 스크롤됨). Ctrl/⌘를 누른 채 스크롤하거나 트랙패드·터치 화면에서 핀치하면 포인터 또는 핀치 중심을 기준으로 15%–250% 범위에서 확대/축소합니다. 오른쪽 아래 버튼으로 확대, 축소, 100%로 되돌리기, 캔버스에 맞추기(전체 보기, 과녁 아이콘)를 할 수 있고, 맨 오른쪽 버튼은 캔버스를 브라우저 창 전체로 넓힙니다. Esc나 같은 버튼으로 돌아옵니다. 캔버스 아래 막대를 드래그하면 높이를 바꿀 수 있고(터치도 가능) 높이는 기기별로 기억됩니다. 막대를 더블클릭하거나 「자동 높이」를 누르면 자동 조절로 돌아갑니다.
- 페이지 상단의 검색 상자는 토폴로지의 사이트를 필터링합니다(이름, 도메인, 그룹, 백엔드 주소). 리스너는 하나씩 접거나 한꺼번에 접을 수 있습니다. 상세 패널의 「편집」과 「리스너 편집」은 Web 서비스 페이지와 같은 편집 창을 이 페이지에서 바로 열며, 저장하면 토폴로지가 즉시 갱신되어 현재 페이지를 벗어나지 않습니다. 통계, 연결, 접근 로그 창도 이 페이지에서 열립니다.

그림의 숫자는 모두 이 인스턴스 메모리의 카운터에서 나옵니다. 재시작하면 0으로 돌아가고, 사이트를 수정해도 카운터는 유지되며, 포트 등 리스너 설정을 바꾸면 해당 리스너는 다시 집계하고, 다른 Gately 인스턴스의 값은 합산하지 않습니다. 토폴로지 보기는 `GET /api/webservice/topology`를 읽으며 읽기 전용 계정과 읽기 전용 토큰도 볼 수 있습니다. 재생은 `GET /api/webservice/topology/replay`(개요와 타임라인)와 `GET /api/webservice/topology/replay/frame`(특정 시점의 스냅숏)을 읽으며 읽기 전용 계정도 볼 수 있습니다. 기록 설정 변경은 `PUT /api/webservice/topology/replay/settings`이며 쓰기 권한이 필요합니다.

### 방문자 감사 {#visitor-audit}

사이드바의 「Web → 방문자 감사」(`#/webvisitors`)는 모든 사이트에 대한 접속을 방문자 주소별로 집계해 누가 언제 어떤 사이트와 경로에 어떤 신원으로 접속했고 몇 번 차단되었는지 보여 줍니다. 기본 사이트와 어떤 사이트에도 일치하지 않는 요청을 포함한 모든 사이트가 대상이며 사이트의 액세스 로그 사용 여부와 무관합니다. [신뢰할 수 있는 프록시](#real-ip)를 설정했다면 방문자의 실제 주소를 기록합니다.

- **집계와 추이**: 페이지 상단에서 범위(오늘, 7일, 30일, 보존 기간 전체)를 고릅니다. 카드에는 방문자 수(신규 포함), 요청 수, 차단 수와 비율, 사이트 인증을 통과한 방문자 수, 현재 차단 중인 방문자 수, 스캐너형 주소 수가 표시되며 카드를 누르면 해당 조건으로 필터링하고 다시 누르면 해제합니다. 일별 막대 그래프는 높이가 요청 수, 빨간 부분이 차단이며, 날짜를 누르거나 마우스를 올리면 그날의 방문자·요청·차단 수를 보여 줍니다.
- **목록**: 방문자마다 국가 코드(GeoIP를 가져온 경우. 사설·로컬 주소는 「LAN」), 범위 내 요청과 차단 수, 많이 방문한 사이트, 신원, 최초·최근 방문, 최근 요청(상태 코드, 메서드, 경로, 도메인, User-Agent)을 표시합니다. 주소, 신원, 사이트, 도메인, 경로, User-Agent로 검색하고 「차단 있음」「인증됨」「관리자」「차단 중」「스캐너형」과 사이트로 필터링하며 최근 방문, 요청 수, 차단 수, 최초 방문 순으로 정렬할 수 있습니다. 두 리스너에 같은 이름의 사이트가 있으면 리스너 이름을 붙여 구분합니다.
- **신원**: 사이트 인증(웹 인증, 기본 인증, 공유 사용자, 외부 로그인, 전달 인증)에 성공하면 사용자 이름을 기록하고, 이 인스턴스의 관리 콘솔 로그인 상태가 있는 요청은 「관리자」로 기록합니다. 비밀번호가 틀린 시도와 차단된 요청은 신원을 기록하지 않습니다.
- **스캐너형**: 차단만 되었거나 일치하지 않는 사이트만 방문했고 한 번도 인증하지 않은 주소입니다.
- **상세**: 행을 누르면 상세가 열립니다. 최초·최근 방문, 전체 요청, 차단 수, 다운로드량, 연결 끊김(444) 횟수, 보존 기간의 일별 그래프, 상태 분포와 차단 사유(차단, IP 목록, 국가 필터, 속도 제한, WAF), 방문한 사이트, 요청이 많은 경로(최대 10개), 신원과 User-Agent를 보여 줍니다. 여기서 차단과 차단 해제(IPv6는 /64 단위), 이 주소의 액세스 로그 보기, 기록 삭제를 할 수 있습니다.

**기록 범위와 저장 위치**: 방문자별 집계 값만 저장하고 개별 요청은 저장하지 않습니다. 경로는 경로 부분만 기록하며 쿼리 문자열, 요청 본문, 쿠키, 자격 증명은 항상 기록에서 제외합니다. 방문자마다 사이트 12개, 경로 10개, 신원 6개, User-Agent 4개까지 보관하고 넘치면 요청이 가장 적은 항목을 교체합니다. 개별 요청은 사이트의 액세스 로그를 켜서 확인합니다. 데이터는 설정 디렉터리의 `visitors/visitors.jsonl.gz`(권한 0600)에 저장되며 변경 후 약 10분마다, 종료 시에는 즉시 기록되고 설정 백업에는 포함되지 않습니다.

**설정**: 페이지 상단의 「설정」에서 기록 중지(기존 데이터 유지), 보존 일수(1~180, 기본 30), 최대 방문자 수(100~100000, 기본 10000)를 설정하고 전체 데이터를 지울 수 있습니다. 최근 방문이 보존 일수보다 오래된 방문자는 자동으로 삭제됩니다. 보존 일수를 줄이면 초과분이 즉시 삭제되므로 저장 전에 확인합니다. 한도를 넘으면 스캐너형 주소를 먼저, 그다음 가장 오래 보이지 않은 주소를 제거합니다. 읽기 전용 계정과 읽기 전용 토큰은 조회할 수 있고 차단, 삭제, 설정 변경에는 쓰기 권한이 필요합니다. API는 `GET /api/webservice/visitors`, `GET /api/webservice/visitors/detail`, `POST /api/webservice/visitors/delete`, `GET|PUT /api/webservice/visitors/settings`입니다.

### Prometheus 메트릭

전역 메트릭 엔드포인트 `GET /api/metrics`는 모든 모듈의 메트릭을 모아 제공합니다. [모니터링 메트릭](/ko/docs/reference/monitoring)을 참고하세요. 아래 모듈 엔드포인트에는 웹 서비스 메트릭만 포함됩니다.

메트릭 엔드포인트는 `GET /api/webservice/metrics`이며 Prometheus 텍스트 형식입니다. 로그인 자격 증명이나 [API 토큰](/en/docs/reference/api-reference)이 필요합니다.

```bash
curl -H "Authorization: Bearer gtl_xxxx" http://localhost:16680/api/webservice/metrics
```

| 메트릭 | 유형 | 설명 |
| --- | --- | --- |
| `gately_site_requests_total` | counter | 사이트 누적 요청 수 |
| `gately_site_errors_total` | counter | 사이트 백엔드 오류 수 |
| `gately_site_active_requests` | gauge | 진행 중인 요청 수 |
| `gately_site_response_bytes_total` | counter | 누적 응답 바이트 수 |
| `gately_site_responses_total` | counter | 상태 클래스(레이블 `class`: `2xx`~`5xx`)별 응답 수 |
| `gately_site_blocked_total` | counter | 원인(레이블 `reason`: `ban` 차단됨(밴), `ip` IP 목록, `country` 국가 필터, `rateLimit` 속도 제한, `waf`)별 차단 횟수 |
| `gately_upstream_up` | gauge | 백엔드 정상 여부, 1은 정상, 0은 사용 불가(레이블 `upstream` 포함) |
| `gately_upstream_requests_total` | counter | 백엔드로 전달한 누적 요청 수(레이블 `upstream` 포함) |
| `gately_upstream_response_bytes_total` | counter | 백엔드가 반환한 응답 본문 누적 바이트 수, WebSocket 업그레이드 이후 데이터 제외(레이블 `upstream` 포함) |
| `gately_listener_requests_total` | counter | 사이트를 거치지 않고 리스너가 직접 처리한 요청, 레이블 `action`은 `https_redirect`(HTTPS 포트로 들어온 평문 요청 리다이렉트) 또는 `not_found`(일치하는 사이트가 없을 때의 404). `listener` 레이블만 붙음 |

`gately_listener_requests_total`을 제외한 메트릭에는 레이블 `listener`(리스너 이름#리스너 key)와 `site`(사이트 이름, 이름이 없으면 첫 번째 도메인)가 붙습니다. 경로별 백엔드와 사용자별 분배 백엔드는 `gately_upstream_*`에 레이블 `route`도 붙으며, 값은 경로 접두사 또는 `@` 뒤에 사용자 목록입니다. `upstream` 레이블은 백엔드 주소이며, 그 안의 사용자 이름, 비밀번호, 쿼리 문자열은 제거됩니다.

## nginx 설정 가져오기 {#import-nginx}

페이지 상단의 「nginx 가져오기」로 기존 nginx 사이트를 Gately의 리스너와 사이트로 변환할 수 있습니다. nginx가 있는 호스트에서 `nginx -T`를 실행하고 전체 출력을 붙여넣는 방식을 권장합니다. 출력에는 include된 모든 파일이 들어 있으며, Gately는 nginx와 같은 방식으로 include를 펼칩니다.

- 먼저 미리 봅니다. 수신 포트별로 묶어 각 사이트의 유형, 백엔드 또는 디렉터리, 원본 파일과 줄 번호, 주의할 점(변수를 쓰는 지시어, 정규식 location, 인증서가 없는 도메인 등)을 보여 주며, 변환할 수 없는 사이트는 그 이유를 알려 줍니다.
- 포트가 같은 사이트는 기존 리스너에 병합하고, 그 밖에는 새 리스너를 만듭니다. 이미 있는 도메인은 건너뛰므로 여러 번 가져와도 됩니다.
- 기본적으로 비활성 상태로 가져오므로 nginx와 병행하면서 하나씩 확인한 뒤 활성화할 수 있습니다. 「가져온 후 바로 활성화」를 체크하면 즉시 적용됩니다(nginx가 같은 포트를 쓰고 있으면 새 리스너는 시작되지 않습니다).
- 변환되는 내용: `proxy_pass`(upstream의 가중치, 예비, 로드 밸런싱 정책 포함), `root` / `alias` 정적 디렉터리(`autoindex`, `try_files $uri.html`, `error_page 404`), `return` 리다이렉트와 고정 내용, 사이트 전체 `rewrite` 리다이렉트, `add_header`, `proxy_set_header`, `gzip`, `allow` / `deny`, location 단위의 경로별 백엔드·접근 제어·리다이렉트, `listen ... proxy_protocol`과 `quic`.
- `proxy_connect_timeout`과 `proxy_read_timeout`은 사이트의 [연결 시간 제한과 응답 헤더 대기 시간 제한](#backend-timeouts)으로 변환됩니다. location /의 값이 server 수준보다 우선하며, 상한을 넘는 값은 상한으로 가져옵니다. 다른 location의 다른 값은 가져오지 않으며 미리보기에서 알려 줍니다;
- `client_body_timeout`과 `send_timeout`은 사이트의 [방문자 시간 제한](#client-timeouts)으로 변환되며 모든 사이트 유형에 적용됩니다;
- `auth_request`는 포워드 인증으로 변환됩니다. 인증 엔드포인트는 인증 하위 요청 location의 `proxy_pass`에서 가져오고(`set` 변수 지원), 로그인 리디렉션은 `error_page 401 =302`에서 가져오므로 Authelia의 일반적인 설정은 그대로 변환됩니다. 일부 location에서만 쓰는 경우에는 「인증 범위」에서 지정한 경로만 인증하도록 변환합니다.
- `auth_basic`은 공유 사용자를 쓰는 기본 인증으로 변환됩니다. nginx의 사용자 파일은 읽지 않으므로 사용자를 추가하기 전에는 아무도 통과할 수 없습니다.
- `stream`의 TCP/UDP 전달은 [포트 포워딩](/ko/docs/modules/portforward)에서 설정하세요. 인증서는 가져오지 않습니다. HTTPS 사이트에 인증서가 없으면 미리 보기에서 nginx가 쓰는 인증서 파일을 보여 주므로 [인증서](/ko/docs/modules/ssl) 페이지에서 파일 경로로 추가할 수 있습니다.

## haproxy와 nginx 대체

프로토콜 라우팅과 웹 서비스를 함께 쓰면 haproxy + nginx 조합을 대체할 수 있습니다. 흔한 구성은 443 포트에 [프로토콜 라우팅](/ko/docs/modules/protoroute) 규칙을 하나 두어 VPN 같은 TLS 서비스는 곧바로 백엔드로, 나머지는 모두 PROXY 프로토콜을 받는 웹 서비스 리스너로 보내는 것입니다. 여기에 80 포트에 리다이렉트 사이트(`https://{host}`)를 둔 웹 서비스 리스너를 추가합니다.

nginx 설정을 옮기는 방법은 다음과 같습니다.

| nginx | Gately |
| --- | --- |
| `server_name`이 있는 `server` | 해당 도메인을 지정한 사이트 |
| `proxy_pass`가 다른 `location` | 경로별 백엔드 |
| `auth_request`(Authelia) | 포워드 인증, 또는 TOTP를 쓰는 공유 사용자 |
| `proxy_ssl_name $host` | 접속 도메인을 SNI로 사용 |
| `return 301 https://$host$request_uri` | `https://{host}`와 「경로와 매개변수 유지」를 지정한 리다이렉트 사이트 |
| `location = /`의 `return 302 /admin` | 「리디렉션」을 켠 재작성, 패턴 `^/$` |
| `try_files $uri $uri.html $uri/index.html`과 `error_page 404` | 확장자 없는 URL과 404 페이지를 설정한 정적 파일 |
| `error_page 502 503 504 /50x.html`과 `proxy_intercept_errors on` | 사이트의 [오류 페이지](#error-pages) 설정과 백엔드 오류 가로채기 |
| `add_header` | 응답 헤더 |
| `return 444` | 연결 끊기 사이트 |
| HTTPS server의 `error_page 497 https://$host:$server_port$request_uri` | 새 리스너의 「같은 포트의 HTTP」를 「HTTPS로 리디렉션」으로 설정합니다. 기존 리스너에 병합할 때는 경고만 표시하고 설정은 바꾸지 않습니다 |

## 방화벽 자동 허용 {#auto-firewall}

OpenWrt 같은 라우터나 방화벽을 켠 Linux 호스트에서 Gately를 실행하면 시스템 방화벽이 외부에서 들어오는 연결을 기본으로 막으므로, 리스너의 포트를 허용해야 접속할 수 있습니다. 리스너에서 「방화벽 자동 허용」을 켜면 Gately가 이 호스트의 방화벽에서 해당 리스너의 포트만 허용합니다.

- 수신에 성공한 포트만 허용합니다. 다른 프로그램이 포트를 쓰고 있어 리스너가 시작되지 못하면 허용하지 않으며, 그 프로그램(라우터 관리 페이지 등)은 외부에 계속 닫혀 있습니다.
- 리스너의 네트워크를 따릅니다. 「IPv6만」은 IPv6, 「IPv4만」은 IPv4, 듀얼 스택은 둘 다 허용합니다. 수신 주소를 지정하면 그 주소로 오는 연결만 허용하고, 127.0.0.1·::1에서만 수신하면 허용할 필요가 없습니다.
- HTTP/3를 켜면 같은 번호의 UDP 포트도 허용합니다.
- 리스너를 끄거나 삭제하거나 시작에 실패하거나 스위치를 끄면 취소되며, Gately가 종료될 때도 제거됩니다.
- nftables(OpenWrt fw4, firewalld 등)는 input 필터 체인 맨 앞에, iptables / ip6tables(OpenWrt fw3, ufw 등)는 INPUT 체인 맨 앞에 규칙을 넣습니다. 규칙에는 `gately-open:` 주석이 붙고, 방화벽을 다시 불러온 뒤 30초 안에 복구됩니다.
- nf_tables가 없는 커널(Synology DSM 등)에서는 iptables(legacy)를 사용합니다. 허용 규칙은 Gately 전용 filter 체인(`GTLY_OPEN_`으로 시작)에 쓰이고, INPUT의 첫 규칙이 이 체인으로 점프합니다. 시스템 방화벽이 자신의 규칙을 앞에 넣으면 30초 안에 점프 규칙을 맨 앞으로 되돌립니다. Docker 이미지에는 iptables(legacy)가 포함되어 있습니다.
- Linux 전용입니다. Docker 배포에는 host 네트워크와 `cap_add: NET_ADMIN`이 필요합니다. 리스너 카드에 결과가 표시되고, 허용에 실패하면 「방화벽」 태그가 주황색으로 바뀝니다.

[포트 포워딩](/ko/docs/modules/portforward#auto-firewall)과 [프로토콜 라우팅](/ko/docs/modules/protoroute#auto-firewall) 규칙에도 같은 스위치가 있고, [STUN](/ko/docs/modules/stun#auto-firewall) 규칙은 채널 포트를 허용합니다.

### 수동으로 허용하기 {#manual-firewall}

수동으로 허용할 때는 외부에 공개할 포트마다 허용 규칙을 추가하고 wan 영역의 수신은 거부로 둡니다. wan 영역 전체의 수신을 허용으로 바꾸면 라우터 관리 페이지(80 / 443), SSH 등도 함께 인터넷에 노출됩니다. OpenWrt에서는 「네트워크 → 방화벽 → 트래픽 규칙」에서 추가하거나 `/etc/config/firewall`에 작성합니다.

```
config rule
	option name 'Allow-Gately-HTTPS'
	option src 'wan'
	option family 'ipv6'
	option proto 'tcp'
	option dest_port '50663'
	option target 'ACCEPT'
```

- Gately를 Docker bridge 네트워크로 실행하면 컨테이너에서는 라우터의 방화벽이 보이지 않으므로, 호스트나 라우터에서 매핑한 포트를 허용해야 합니다.
- Gately를 LAN의 다른 장치(macvlan으로 독립된 IPv6 주소를 받은 컨테이너 등)에서 실행하면 트래픽이 라우터를 거쳐 전달되므로, 라우터에 전달 규칙을 추가합니다. 대상 영역은 lan, 장치 주소와 사용하는 포트를 지정합니다. 통신사가 주는 IPv6 접두사는 바뀌므로 `option dest_ip '::1234/::ffff:ffff:ffff:ffff'`처럼 주소 뒷부분으로 일치시킵니다.

## 배포 팁

웹 서비스는 호스트의 80 / 443 등의 포트를 수신해야 하므로 Docker 배포에서는 `--network host`를 권장합니다.
