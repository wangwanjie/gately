# 웹 서비스

도메인별 리버스 프록시, 리다이렉트, 정적 파일, 고정 텍스트를 제공하는 Gately의 통합 웹 진입점입니다. 메뉴 위치: 사이드바 「웹 → 웹 서비스」.

## 구조: 리스너, 사이트, 기본 사이트

설정은 세 계층입니다.

1. 리스너: 수신 포트 하나. 네트워크(`tcp` 듀얼 스택, `tcp4`, `tcp6`), 수신 주소(비우면 모든 주소), 포트, HTTPS 스위치, 최소 TLS 버전(1.0 / 1.1 / 1.2 / 1.3), PROXY 프로토콜 수신 여부 필드가 있습니다.
2. 사이트: 리스너 아래에서 도메인으로 매칭되는 사이트. 도메인은 정확한 도메인, `*.example.com`(모든 단계의 서브도메인과 일치), `*`(모두 일치)를 지원하며 매칭 우선순위는 정확한 도메인, 와일드카드, `*` 순입니다.
3. 기본 사이트: 일치하는 사이트가 없을 때 사용되며 사용하지 않으면 404를 반환합니다. 기본 사이트를 「연결 끊기」로 설정하면 알 수 없는 도메인 요청에 아무 응답도 하지 않습니다. 기본 사이트를 설정하면 사이트 목록 맨 끝에 표시됩니다. 아직 설정하지 않았다면 리스너 카드의 「기본 사이트 설정」을 클릭해 설정합니다.

사이트나 기본 사이트의 변경을 저장하면 사이트 목록이 그 자리에서 교체됩니다. 리스너는 계속 실행되고, 열려 있는 연결(WebSocket 포함)은 유지되며, 각 사이트의 통계도 그대로 이어집니다. 새 설정이 올바르지 않으면 이전 사이트가 계속 서비스됩니다. 리스너 자체의 설정(네트워크, 주소, 포트, HTTPS, 최소 TLS, HTTP/3, PROXY 프로토콜)을 바꾸면 해당 리스너가 재시작됩니다.

사이트에는 「그룹」을 지정할 수 있습니다(최대 64자, 기본 사이트는 그룹에 넣을 수 없음). 목록은 리스너마다 그룹별로 접을 수 있는 영역을 보여 줍니다. 그룹은 처음 나타난 순서대로 배치되고, 그룹이 없는 사이트는 그 뒤에, 기본 사이트는 항상 맨 끝에 옵니다. 각 그룹의 접힘 상태는 브라우저에 저장됩니다. 「정렬」을 누르면 정렬 모드가 되어 사이트를 위아래로 옮기거나 그룹 안에서 끌어 옮기고, 그룹 전체를 옮기고, 리스너 순서도 바꿀 수 있습니다. 순서는 목록 표시에만 쓰이며 도메인 매칭은 사이트 순서와 관계없이 위의 우선순위를 따릅니다. 정렬을 저장할 때도 사이트 목록이 그 자리에서 교체되므로 연결이 끊기지 않습니다. 페이지 상단의 검색 상자로 도메인, 이름, 그룹, 백엔드, 메모로 사이트를 필터링할 수 있습니다.

정렬 모드에서는 여러 사이트를 선택할 수도 있습니다(그룹 제목의 체크박스로 그룹 전체 선택). 선택한 사이트 중 하나를 끌면 모두 함께 이동하고, 다른 그룹의 사이트나 그룹 제목에 놓으면 그 그룹으로 들어갑니다. 도구 모음에서 선택한 사이트를 지정한 그룹으로 한 번에 옮길 수 있고, 이름을 비우면 그룹에서 뺍니다. 여러 리스너에 걸쳐 선택한 경우 리스너별로 저장됩니다.

그룹 제목에 마우스를 올리고 연필 버튼을 누르면 그룹 이름을 바꿀 수 있습니다. 그룹의 항목도 함께 새 이름으로 바뀌며 위치와 순서는 그대로입니다. 이미 있는 그룹 이름을 고르면 확인 후 두 그룹이 합쳐집니다.

## 사이트 유형

| 유형 | 설명 |
| --- | --- |
| 리버스 프록시 | 하나 이상의 백엔드로 전달합니다. 백엔드 주소 형식은 `http(s)://호스트:포트`이며 WebSocket을 지원합니다 |
| 리다이렉트 | 전체 URL로 이동합니다. 상태 코드는 301 / 302 / 307 / 308(기본 302)이며 원래 경로와 쿼리 문자열을 유지할 수 있습니다. URL에 `{host}`를 넣으면 방문자가 사용한 도메인으로 바뀝니다. `https://{host}`에 「경로와 매개변수 유지」를 함께 쓰면 모든 HTTP 요청을 같은 도메인의 HTTPS로 보냅니다. `{path}`, `{1}`, `{STUN_규칙이름_PORT}` 등의 변수도 쓸 수 있습니다. [리다이렉트 변수](#redirect-vars) 참고. |
| 정적 파일 | 디렉터리는 절대 경로여야 합니다. 「디렉터리 목록」을 끄면 `index.html`이 있을 때만 디렉터리 요청에 응답합니다. 「확장자 없는 URL」은 파일이 없을 때 `경로.html`과 `경로/index.html`을 시도합니다(VitePress 같은 생성기용이며 nginx의 `try_files $uri $uri.html $uri/index.html`과 같음). 「404 페이지」는 디렉터리 안의 경로(예: `404.html`)이며 상태 코드 404로 반환됩니다 |
| 고정 텍스트 | 사용자 지정 내용, `Content-Type`(기본 `text/plain; charset=utf-8`), 상태 코드(100-599, 기본 200) |
| 연결 끊기 | 아무것도 보내지 않고 연결을 끊습니다. nginx의 `return 444`와 같습니다. 주로 기본 사이트에 사용해 알 수 없는 도메인을 스캔하는 요청에 응답하지 않으며, 접근 로그에는 444로 기록됩니다. 인증, 접근 제어, WAF, 재작성을 거치지 않으므로 사이트의 다른 설정은 적용되지 않습니다 |

모든 유형의 사이트에 접근 로그, 교차 출처(CORS), 사용자 지정 요청 헤더와 응답 헤더(한 줄에 `Key: Value`, Value를 비우면 해당 헤더 삭제)를 설정할 수 있으며 [WAF 방화벽](/ko/docs/modules/waf) 인스턴스 하나를 참조할 수 있습니다(인스턴스가 없거나 비활성화되어 있으면 통과).요청 헤더, 응답 헤더와 Content-Type 편집 방법은 [요청 헤더와 응답 헤더](#headers)를 참고하세요.

접근 로그에는 클라이언트 IP, 메서드, 도메인과 경로, 상태 코드, 소요 시간, 사이트 이름이 기록되고, 줄 끝에 nginx 형식으로 Referer와 User-Agent(없으면 `-`)가 붙어 같은 공인 IP 뒤의 여러 기기를 User-Agent로 구분할 수 있습니다. 사이트, 상태 코드, 출발지 IP 등으로 로그를 필터링할 수 있습니다. [실행 로그 보기와 필터](/ko/docs/guide/configuration#log-filter)를 확인하세요.

### 리다이렉트 변수 {#redirect-vars}

리다이렉트 사이트의 대상 주소에는 다음 변수를 쓸 수 있습니다:

| 변수 | 의미 |
| --- | --- |
| `{host}` | 방문자가 요청한 도메인(포트 제외) |
| `{port}` | 접속한 포트 |
| `{hostAndPort}` | 도메인과 포트, 요청의 Host와 같음 |
| `{path}` / `{PATH}` | 요청 경로, `{PATH}`는 맨 앞의 `/` 제외 |
| `{args}` / `{Args}` | 쿼리 문자열, `{args}`는 맨 앞의 `?` 포함(쿼리가 없으면 빈 값), `{Args}`는 제외 |
| `{domainPartN}` / `{pathPartN}` | 도메인(`.`로 구분) 또는 경로(`/`로 구분)의 N번째 부분, N은 1부터 |
| `{ClientIP}` / `{RemoteIP}` | 클라이언트 IP |
| `{time}` | 현재 시각, 형식 `2006-01-02 15:04:05`. 리디렉션 주소가 올바른 URL 이 되도록 공백은 `%20` 으로 씁니다(`2006-01-02%2015:04:05`) |
| `{1}` | 사이트 도메인 `*.example.com`에서 `*`에 일치한 부분. 정확한 도메인에 일치하면 빈 값, `*`나 기본 사이트에 일치하면 전체 도메인 |
| `{STUN_규칙이름_PORT}` / `{STUN_규칙이름_IP}` / `{STUN_규칙이름_ADDR}` | [STUN 통과](/ko/docs/modules/stun) 규칙의 현재 공인 포트, IP, `IP:포트`. 규칙 이름은 목록에 표시되는 이름이며 밑줄을 포함해도 됩니다 |

- "경로 유지"가 켜져 있을 때 대상에 `{path}`, `{PATH}`, `{pathPartN}`이 있으면 원래 경로를, `{args}`, `{Args}`가 있거나 대상에 자체 쿼리가 있으면 원래 쿼리를 다시 붙이지 않습니다. 나머지 부분은 그대로 붙입니다;
- STUN 포트가 바뀌어도 사이트를 수정할 필요 없이 다음 요청부터 새 포트로 이동합니다. 참조한 규칙이 없거나, 비활성화되었거나, 아직 통과에 성공하지 않았거나, 자동 재시도 중이면 사이트는 503을 반환하고 실행 로그에 이유를 남깁니다;
- 변수를 펼친 대상에 호스트가 없으면(예: 정확한 도메인이 일치해 `{1}`이 비었는데 대상이 `https://{1}`뿐인 경우) 503을 반환합니다. 방문자의 호스트에 `&`, `=`, `/`, `@`처럼 도메인에 쓰이지 않는 문자가 있으면 400을 반환하고 대상에 넣지 않습니다;
- 사이트 도메인은 `*`를 하나만 지원하므로 `{1}`만 있습니다;
- 경로 재작성 규칙의 리다이렉트 대상은 여전히 `{host}`만 지원합니다. 알 수 없는 `{xxx}`는 그대로 남습니다.

예: Cloudflare CDN이 `*.example.com`을 이 기기의 2053 포트로 보내고, 그 리스너에 도메인이 `*.example.com`인 리다이렉트 사이트를 두어 대상을 `https://{1}.v4.example.com:{STUN_web_PORT}{path}{args}`로 지정합니다. `zly.example.com/a?b=1`에 접속하면 `https://zly.v4.example.com:<STUN 포트>/a?b=1`로 이동합니다. STUN 규칙 web은 다른 리스너로 전달하고, 그곳에 `*.v4.example.com` 아래 각 도메인의 리버스 프록시 사이트를 만듭니다.

### 리버스 프록시 옵션 {#proxy-options}

사이트 편집 창 "기본" 탭의 "옵션"입니다. 옆의 물음표 아이콘을 누르면 화면에서 간단한 설명을 보고 이 절로 이동할 수 있습니다.

| 옵션 | 동작 | 켜야 할 때 |
| --- | --- | --- |
| 백엔드 인증서 검증 건너뛰기 | HTTPS 백엔드에 연결할 때 인증서를 검증하지 않습니다 | 백엔드가 자체 서명 또는 만료된 인증서를 쓰는 경우(NAS, 공유기 관리 페이지의 https 포트 등). 백엔드 신원을 확인할 수 없게 되므로 내부망 백엔드에만 사용하세요 |
| Host에 백엔드 주소 사용 | 백엔드로 보내는 Host 헤더를 백엔드 주소로 바꿉니다. 끄면(기본값) 방문자가 요청한 Host를 유지합니다 | 백엔드가 자기 주소만 받아들이는 경우(400 / 403, 잘못된 주소로 이동, Host 불일치 등). 공개 웹사이트나 CDN으로 프록시할 때 대개 필요합니다. 백엔드가 도메인으로 사이트를 구분하거나 접속 도메인으로 링크를 만들어야 하면 끈 상태로 둡니다 |
| 연결 재사용 안 함 | 요청마다 백엔드에 새 연결을 만듭니다(Keep-Alive 끔) | 연결이 가끔 재설정되거나 요청이 멈추는 경우, 또는 지속 연결을 지원하지 않는 백엔드. 지연이 조금 늘어나므로 평소에는 끈 상태로 둡니다 |
| X-Forwarded-* 추가 | `X-Forwarded-For` / `X-Forwarded-Proto` / `X-Forwarded-Host` / `X-Forwarded-Port`와 `X-Real-IP`를 기록해 방문자의 실제 IP, 원래 프로토콜, 도메인, 포트를 백엔드에 알립니다 | 백엔드가 실제 IP를 기록하거나, 외부가 HTTPS임을 알아야 올바른 링크를 만들 수 있는 경우(그렇지 않으면 http로 되돌아가거나 로그인 후 무한 이동). 대부분의 앱에 권장합니다 |
| 백엔드에 PROXY v2 전송 | TCP 연결 앞에 PROXY 프로토콜 v2 헤더를 붙여 실제 클라이언트 IP를 전달합니다. 켜면 요청마다 새 연결을 만들고 백엔드에 HTTP/2를 쓰지 않습니다. 백엔드가 Gately라면 해당 리스너에서 PROXY 프로토콜 수신을 켜고 이 호스트를 신뢰할 PROXY 출처에 추가하세요. | HTTP 헤더는 읽지 않지만 PROXY 프로토콜을 지원하는 백엔드(다른 Gately, haproxy, `proxy_protocol`을 켠 nginx 등). 백엔드에 수신 설정이 없으면 모든 요청이 실패하므로 확실하지 않으면 끄세요 |
| 접속 도메인을 SNI로 사용 | HTTPS 백엔드에만 적용: 핸드셰이크 때 방문자가 쓴 도메인을 보내고 그 도메인으로 인증서를 검증합니다. nginx의 `proxy_ssl_server_name on; proxy_ssl_name $host`와 같습니다 | 같은 포트에서 도메인별로 인증서나 분기를 하는 백엔드(frp `vhost_https`, 여러 HTTPS 사이트를 둔 nginx 등). 백엔드마다 별도 연결 풀을 쓰므로 도메인 간에 연결이 재사용되지 않습니다 |
| Gately 로그인 쿠키 전달 | Gately 자체 로그인 쿠키(싱글 사인온 `gately_sso`, 사이트 세션, 외부 로그인 nonce)를 그대로 백엔드에 넘깁니다. 끄면(기본값) 이 쿠키를 백엔드에 보내지 않아 로그인 자격 증명이 새지 않습니다 | 백엔드가 인증을 담당하는 다른 Gately이고 이 사이트는 인증을 하지 않을 때. 예: 공인 Gately는 WAF와 접근 제어만 하고 내부망 Gately로 프록시하며, 내부망 Gately가 웹 인증과 싱글 사인온을 담당하는 구성. 이 사이트에서 인증을 켠 상태에서는 쓸 수 없으며, 백엔드가 직접 운영하는 Gately일 때만 사용하세요 |

자주 쓰는 조합:

- 내부망 웹 앱(예: `http://192.168.1.10:5000`) 프록시: "X-Forwarded-* 추가"만 켭니다.
- 백엔드가 자체 서명 인증서의 https 주소: "백엔드 인증서 검증 건너뛰기"도 켭니다.
- 공개 웹사이트나 외부 서비스 프록시: "Host에 백엔드 주소 사용"를 켭니다.
- 백엔드 앞에 SNI로 분기하는 서비스가 있음(예: frp `vhost_https`): "접속 도메인을 SNI로 사용"를 켭니다.
- 공인 Gately는 WAF만, 내부망 Gately가 로그인 담당: 공인 사이트는 인증을 끄고 "Gately 로그인 쿠키 전달"을 켭니다. 실제 IP가 필요하면 "백엔드에 PROXY v2 전송"도 켜고, 내부망 Gately에서 PROXY 프로토콜 수신을 켠 뒤 공인 Gately를 신뢰할 수 있는 출처에 추가합니다.

### 요청 헤더와 응답 헤더 {#headers}

사이트 편집 창의 "헤더" 탭에서 설정합니다. 요청 헤더는 백엔드로 보내지며 리버스 프록시 사이트에서만 적용되고, 응답 헤더는 클라이언트에 반환되며 모든 유형의 사이트에 적용됩니다.

- 행별 편집: 이름 칸을 누르면 자주 쓰는 헤더와 용도가 표시되고, 고르면 대표 값이 자동으로 채워지며 값 칸에서 다른 대표 값을 고를 수도 있습니다. 두 칸 모두 직접 입력할 수 있습니다. 값을 비우면 헤더를 삭제하고, 이름 칸에 `Key: Value` 한 줄을 붙여 넣으면 자동으로 나뉩니다.
- "자주 쓰는 보안 헤더 추가"은 `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy: strict-origin-when-cross-origin`을 추가하며 이미 있는 헤더는 중복 추가하지 않습니다.
- "텍스트 모드"에서는 여러 줄의 `Key: Value`를 한 번에 붙여 넣을 수 있고, 행별 편집으로 돌아가도 내용이 유지됩니다.
- "경로별 백엔드"의 경로별 추가 요청 헤더도 같은 방식으로 편집하며, 사이트 요청 헤더 다음에 적용되고 이름이 같으면 경로 설정이 우선합니다.

각 행 아래에 실시간 피드백이 표시됩니다. 빨간색은 저장이 실패하거나 헤더가 적용되지 않음을 뜻합니다(이름 없음, 이름에 공백이나 콜론 같은 잘못된 문자, 텍스트 모드에서 콜론 없음 등). 주황색은 저장은 되지만 기대와 다르게 동작할 수 있음을 뜻합니다:

- 요청 헤더에 설정한 `Host`는 적용되지 않습니다. 바꾸려면 "Host에 백엔드 주소 사용"를 켜세요.
- `X-Forwarded-For`, `X-Real-IP`에 고정 값을 쓰면 실제 클라이언트 IP를 덮어씁니다. 클라이언트 IP를 전달하려면 "X-Forwarded-* 추가"를 켜세요.
- `Content-Length`, `Connection`, `Transfer-Encoding` 등은 연결이 자동으로 관리하므로 직접 설정하면 무시되거나 전송 오류가 납니다.
- 값은 그대로 전송되며 nginx의 `$host` 같은 변수는 지원하지 않습니다. 프리셋 값의 `<token>` 같은 자리 표시자는 바꿔야 합니다.
- 이름이 같은 헤더는 순서대로 적용되며 뒤의 것이 우선합니다.

"고정 텍스트" 사이트의 `Content-Type`은 자주 쓰는 유형에서 고르거나 직접 입력할 수 있습니다. 화면에서 `유형/하위유형; 매개변수=값` 형식을 검사하고, `text/*`에 `charset`이 없으면 한국어 등이 깨질 수 있다고 알려 줍니다. 비워 두면 `text/plain; charset=utf-8`을 사용합니다.

## 전송 및 프로토콜

- HTTPS: [SSL 인증서](/ko/docs/modules/ssl) 모듈에서 해당 도메인을 포함하는 인증서를 사용합니다.
- 같은 포트의 HTTP: HTTPS를 켠 리스너도 평문 HTTP를 받을 수 있으며, 연결의 첫 바이트로 프로토콜을 구분합니다. "HTTPS로 리디렉션"은 `http://호스트:포트`를 `https://호스트:포트`로 보내며(GET/HEAD는 301, 그 밖의 메서드는 308), 포트를 하나만 쓸 수 있고 스킴을 잘못 입력해도 열리게 하고 싶을 때 유용합니다. "그대로 제공"은 암호화되지 않은 HTTP로 사이트를 응답합니다. ACME HTTP-01 검증 요청은 그대로 응답하며, 이 설정을 바꾸면 리스너가 다시 시작됩니다.
- HTTP/3(QUIC): HTTPS를 켠 리스너에서 활성화하면 같은 포트 번호의 UDP로 HTTP/3도 제공하고 `Alt-Svc` 응답 헤더로 브라우저에 알립니다. 방화벽과 포트 포워딩에서 해당 UDP 포트를 허용해야 합니다.
- WebSocket: 리버스 프록시에서 자동으로 지원합니다.
- PROXY 프로토콜: 리스너가 업스트림(haproxy, frp 등)이 보낸 PROXY 헤더를 받을 수 있으며 「전역 설정 → 신뢰할 PROXY 출처」에 나열된 IP 또는 대역만 신뢰합니다. 비워 두면 어떤 출처도 신뢰하지 않습니다. 리버스 프록시는 백엔드로 PROXY 헤더를 보낼 수 있습니다. 신뢰할 출처에서 들어온 연결의 `X-Forwarded-Proto: https`도 신뢰합니다. 세션 쿠키에 Secure가 붙고, 평문 HTTP를 리디렉션하는 포트에서도 리디렉션하지 않으며, "X-Forwarded-* 추가"를 켜면 백엔드에도 https를 전달합니다.

## 인증

사이트 편집 창의 「보안」 탭에서 설정합니다.

- 웹 인증: 브라우저에 로그인 페이지를 표시합니다.
- 기본 인증: HTTP Basic
- 사용자: 한 줄에 `사용자 이름:비밀번호`. 비밀번호에는 bcrypt 해시를 쓸 수 있습니다. 기본 인증을 켜면 사용자가 최소 한 명 필요하고, 웹 인증을 켜면 사용자나 서드파티 로그인 ID가 최소 하나 필요합니다.
- 서드파티 로그인: GitHub, Google, QQ, OIDC를 지원하며 직접 만든 OAuth 앱을 사용합니다. 허용할 ID는 한 줄에 하나씩 `제공자 식별자:계정` 형식으로 쓰며 예를 들어 `github:octocat`, `google:me@gmail.com`처럼 입력합니다. 줄 끝에 `#`을 붙여 메모를 남길 수 있고 `github:*`는 해당 제공자의 모든 계정을 뜻합니다.

서드파티 로그인 제공자는 「전역 설정」에서 구성합니다. 직접 발급한 Client ID / Secret을 입력해 활성화하고, 콜백 주소(Gately의 어떤 리스너가 제공해야 하며 예: `https://auth.example.com`)도 설정합니다. GitHub / Google / QQ에 등록할 콜백 URL은 다음과 같습니다.

```text
https://auth.example.com/__gately_auth/oauth/callback
```

관리 콘솔 자체의 서드파티 로그인은 「설정 → 계정 및 보안」에서 따로 설정합니다.

### 포워드 인증(Authelia 등)

인증을 외부 서비스에 맡깁니다. nginx의 `auth_request`나 Traefik의 `forwardAuth`와 같은 방식입니다. 「보안」 탭에서 「포워드 인증」을 체크합니다. 같은 사이트에서 기본 인증이나 웹 인증과 함께 쓸 수 없습니다.

| 필드 | 설명 |
| --- | --- |
| `url` | 확인용 엔드포인트. 예: Authelia의 `http://127.0.0.1:9091/api/authz/auth-request` |
| `loginUrl` | 엔드포인트가 401을 반환할 때 방문자를 보낼 주소. 예: `https://auth.example.com/?rd={url}&rm={method}`. `{url}`은 원래 주소(URL 인코딩됨), `{method}`는 요청 메서드입니다. 비우면 엔드포인트의 응답을 그대로 반환합니다 |
| `copyHeaders` | 엔드포인트 응답에서 백엔드 요청으로 복사할 신원 헤더. 기본값은 `Remote-User`, `Remote-Groups`, `Remote-Email`, `Remote-Name` |

동작 방식은 다음과 같습니다.

- 모든 요청은 먼저 `url`로 본문 없는 GET으로 전송됩니다. 방문자의 헤더(쿠키, `Authorization` 등)에 더해 `X-Original-Method`, `X-Original-URL`, `X-Forwarded-Method`, `X-Forwarded-Proto`, `X-Forwarded-Host`, `X-Forwarded-Uri`, `X-Forwarded-For`, `X-Real-Ip`가 붙습니다. 타임아웃은 10초입니다.
- 2xx 응답이면 요청을 통과시키고 신원 헤더를 추가합니다. 401은 `loginUrl`로 리다이렉트합니다(상태 코드 302). 403이나 리다이렉트 같은 다른 응답은 방문자에게 그대로 반환하며, 서비스에 연결할 수 없으면 502가 됩니다.
- 방문자가 보낸 신원 헤더는 항상 제거되므로 위조할 수 없습니다.
- 경로 규칙과 「인증 범위」를 지원하므로 일부 경로(예: `/admin`)에서만 로그인을 요구할 수 있으며, 임시 공유 링크와도 함께 쓸 수 있습니다.

### 공유 사용자: TOTP와 통합 로그인 {#shared-users}

계정을 한 번 정의해 여러 사이트에서 쓰며, TOTP 2단계 인증을 선택적으로 추가할 수 있습니다. 많은 사람이 Authelia를 쓰는 목적을 이것으로 해결할 수 있습니다.

사이드바의 「Web → 인증 사용자」 페이지에서 다음을 설정합니다(웹 서비스 전역 설정 대화상자에는 요약과 링크만 표시됩니다).

- 사용자를 추가하려면 사용자 이름과 비밀번호를 입력합니다. 비밀번호는 bcrypt 해시로 저장되며 API가 반환하지 않습니다. TOTP를 추가하려면 「TOTP 사용」을 누르고 인증 앱(Google Authenticator, 1Password 등)으로 QR 코드를 스캔한 뒤 저장합니다. 키를 다시 생성하면 이전 키는 무효가 됩니다.
- 이메일, 표시 이름, 그룹을 선택적으로 입력할 수 있습니다. [OIDC 통합 로그인](/ko/docs/modules/oidc)은 이를 `email`, `name`, `groups` 클레임으로 앱에 전달하며, OIDC 클라이언트의 허용 사용자에서 `group:그룹명`으로 그룹 단위 허용이 가능합니다.
- 통합 로그인(SSO) 도메인(예: `example.com`): 이 도메인이나 하위 도메인의 사이트 중 하나에서 로그인하면 그곳의 다른 사이트에서는 다시 로그인할 필요가 없습니다. 상위 도메인 쿠키(`gately_sso`, 유효 기간 7일)를 사용하며 이 쿠키는 백엔드로 전달되지 않습니다. 비우면 사이트마다 따로 로그인합니다.

사이트에서 웹 인증이나 기본 인증 옆의 「공유 사용자 사용」을 체크합니다. 사이트 자체 사용자도 계속 사용할 수 있습니다. 「인증 사용자」 페이지의 사이트 목록에서 리스너별로 보고 필터링해 일괄 체크할 수도 있습니다. 인증이 꺼진 사이트를 체크하면 웹 인증도 켜집니다. 공유 사용자로만 인증하는 사이트는 실수로 로그인 없이 공개되지 않도록 여기서 체크를 해제할 수 없으며, 공개하려면 사이트 설정에서 인증을 끄세요. 포워드 인증을 쓰는 사이트는 공유 사용자를 쓸 수 없습니다. 페이지의 사용자, OIDC, 사이트 변경은 아래쪽 「저장」을 누르면 함께 적용되고, 하나라도 검증에 실패하면 아무것도 저장되지 않으며, 저장하지 않은 변경이 있을 때 페이지를 떠나면 먼저 확인합니다.

동작은 다음과 같습니다.

- 공유 사용자 중 TOTP를 쓰는 사용자가 있으면 로그인 페이지에 인증 코드 입력란이 표시됩니다. 각 코드는 한 번만 사용할 수 있습니다.
- 사용자의 비밀번호나 TOTP 키를 바꾸면 해당 사용자의 세션이 종료됩니다.
- 기본 인증에서는 TOTP가 없는 공유 사용자만 사용할 수 있습니다. 브라우저의 비밀번호 입력창에는 코드를 입력할 곳이 없기 때문입니다.
- 실패한 시도는 다른 로그인과 같은 속도 제한과 자동 차단에 집계됩니다.

Gitea, OpenList, Grafana 등의 앱이 어떤 사용자가 로그인했는지 알게 하려면 [OIDC 통합 로그인](/ko/docs/modules/oidc)으로 공유 사용자를 앱에 제공하세요.

### 비밀번호 직접 변경 {#self-service-password}

「인증 사용자」 페이지에서 「비밀번호 직접 변경」을 켜면 공유 사용자가 관리자 없이 직접 비밀번호를 바꿀 수 있습니다.

- '공유 사용자 사용'이 켜진 사이트에서 `https://사이트 도메인/__gately_auth/password`에 접속합니다. 로그인 페이지에도 '비밀번호 변경' 링크가 표시됩니다. [OIDC 싱글 사인온](/ko/docs/modules/oidc) 사용자는 발급자 도메인의 `/__gately_oidc/password`를 사용할 수 있습니다.
- 사용자 이름, 현재 비밀번호, 새 비밀번호(8~128자, 현재 비밀번호와 달라야 함)를 두 번 입력합니다. TOTP를 켠 사용자는 인증 코드도 입력합니다.
- 변경 후 해당 사용자의 모든 사이트 세션은 즉시 만료되어 새 비밀번호로 다시 로그인해야 합니다. 발급된 OIDC 갱신 토큰은 무효화되고 이전 Access Token으로도 사용자 정보를 읽을 수 없습니다. 앱이 직접 검증하는 토큰은 만료 전까지 유효하며, 앱 자체의 로그인 세션도 그대로 유지됩니다.
- 같은 계정은 변경에 성공한 뒤 1분 동안 다시 변경할 수 없습니다. 반복 변경으로 FTP, SMB가 계속 다시 로드되어 다른 사람의 연결이 끊기는 것을 막기 위해서입니다. 저장 시 서비스 검사에서 거부된 자세한 이유는 웹 서비스 로그에만 기록되고, 화면에는 관리자에게 문의하라는 안내만 표시됩니다.
- 현재 비밀번호나 코드 오류는 로그인 실패와 같은 속도 제한·자동 차단에 포함되며, 다른 웹사이트에서 대신 제출한 양식은 거부됩니다. 웹 서비스 로그에 변경한 사용자와 출발지 IP가 기록됩니다.
- 같은 페이지에서 [파일 서비스 공유 사용자](/ko/docs/modules/tools#shared-users)의 비밀번호도 바꿀 수 있습니다. 두 종류의 계정은 각각 켜고 끌 수 있으며, 둘 다 켜면 페이지에서 계정 종류를 고릅니다. 이름이 같은 두 종류의 계정은 서로 영향을 주지 않습니다.

## 접근 제어

### IP 허용·차단 목록

사이트 「보안」 탭의 「IP 접근 제어」에서 끄기, 허용 목록, 차단 목록 중에서 선택하며 목록에는 한 줄에 IP 또는 대역(예: `192.168.1.0/24`)을 하나씩 씁니다. 구독 IP 목록도 함께 참조할 수 있습니다.

### 거부 방식

사이트 「보안」 탭의 「거부 방식」은 차단, IP 접근 제어(경로 규칙 포함) 또는 국가 필터로 거부된 요청의 처리 방식을 정합니다. 기본값은 「403 반환」이며, 「연결 끊기」를 선택하면 아무것도 보내지 않고 끊고 접근 로그에는 444로 기록합니다(연결 끊기 사이트와 같음). 허용 목록과 함께 쓰면 "내 IP는 정상 접근, 나머지는 모두 끊기"를 구현할 수 있습니다. 속도 제한(429)과 WAF 차단에는 영향이 없습니다.

연결 끊기(사이트 유형이든 거부 방식이든)는 HTTP 응답을 보내지 않을 뿐이며 서비스가 살아 있다는 사실은 숨길 수 없습니다.

- TCP 핸드셰이크가 이미 끝났으므로 상대는 포트가 열려 있음을 알 수 있습니다.
- HTTP/1.x에서는 연결을 닫지만 HTTP/2·HTTP/3에서는 이 요청만 재설정하고 연결은 유지되어 계속 재사용할 수 있습니다.
- HTTPS에서는 인증서가 없는 도메인이 TLS 핸드셰이크 단계에서 실패하므로, 기본 사이트에 도달한 요청은 이미 인증서와 그 안의 도메인을 받은 상태입니다.

이후 스캐너에게 시간 초과만 보이게 하려면 [침입 방지](/ko/docs/modules/guard)에서 해당 주소를 차단하세요. 방화벽 동기화를 켜면 커널에서 트래픽을 버립니다.

### 구독 IP 목록

「전역 설정 → 구독 IP 목록」에서 목록을 추가합니다. 다운로드 URL과 새로고침 간격(기본 24시간)을 입력하면 Gately가 주기적으로 내려받아 설정 디렉터리에 캐시하므로, 재시작한 뒤에도 네트워크 없이 사용할 수 있습니다. 내용은 한 줄에 IP, CIDR 또는 `시작-끝` 범위 하나이며, `#`, `;`, `//` 뒤는 주석입니다. 예를 들어 중국 성·시 IP 대역은 [metowolf/iplist](https://github.com/metowolf/iplist)의 `https://metowolf.github.io/iplist/data/cncity/440000.txt`(광둥성)를 쓸 수 있습니다.

- 사이트와 경로 규칙의 허용 목록, 차단 목록은 여러 목록을 참조할 수 있으며, 직접 입력한 IP 대역과 함께 판단해 하나라도 일치하면 목록에 있는 것으로 봅니다.
- 내려받은 내용을 해석할 수 없으면(예: 오류 페이지가 반환된 경우) 이전 목록을 유지하고 목록에 원인을 표시하며, 1시간 후 다시 시도합니다.
- 목록을 처음 내려받기 전에는 빈 목록으로 처리합니다. 따라서 허용 목록은 접근을 거부하고, 차단 목록은 추가로 차단하는 것이 없습니다.
- 사이트에서 참조 중인 목록은 삭제할 수 없습니다.

### 경로 규칙

「보안」 탭의 「경로 규칙」에서 경로 접두사별로 사이트의 인증과 IP 설정을 덮어씁니다.

| 필드 | 값 |
| --- | --- |
| `prefix` | `/`로 시작하는 경로 접두사. 예: `/admin` |
| `auth` | 사이트 설정 따름(비움), `off`(인증 불필요), `on`(인증 필수) |
| `ipMode` / `ipList` | 사이트 설정 따름(비움), `whitelist`, `blacklist`, 그리고 IP 또는 대역 목록 |

매칭 규칙은 다음과 같습니다.

- 가장 긴 접두사가 우선합니다.
- 경로 세그먼트 경계로 매칭하므로 `/admin`은 `/admin`과 `/admin/x`에 일치하고 `/administrator`에는 일치하지 않습니다.
- 요청 경로를 먼저 정규화(`.`, `..`, 중복 슬래시 제거)한 뒤 매칭하므로 `/public/../admin`은 `/admin`으로 처리됩니다.
- 같은 접두사에는 규칙을 하나만 설정할 수 있습니다.

「인증 범위」 옵션(`authOptional`): 체크하면 인증이 규칙에서 「인증 필수」로 표시된 경로에만 적용되고 나머지 경로는 공개됩니다. 이 옵션을 쓰려면 먼저 기본 인증이나 웹 인증을 켜야 합니다.

### 임시 공유 링크

기본 인증이나 웹 인증을 켜면 사이트에 공유 링크를 만들어 방문자가 계정 없이 접근하게 할 수 있습니다.

| 필드 | 설명 |
| --- | --- |
| 이름 | 메모용 이름. 예: 「홍길동에게」 |
| 만료 시간 | 비우면 만료되지 않습니다 |
| 사용 횟수 `maxUses` | 교환할 수 있는 최대 횟수이며 0은 무제한입니다. 재시작하면 카운트가 초기화됩니다 |
| 경로 제한 `pathPrefix` | 비어 있지 않으면 링크로 해당 접두사 아래 경로만 접근할 수 있으며 `/`로 시작해야 합니다 |

방문자가 `https://도메인/임의경로?_gs=토큰`에 접속하면 세션으로 교환됩니다. 교환에 성공하면 서버가 로그인 불필요 쿠키를 설정하고 `_gs` 매개변수를 제거한 주소로 이동시키며, 세션은 최대 24시간이고 링크의 만료 시간을 넘지 않습니다. 토큰이 유효하지 않으면 일반 접근으로 처리하며 실패 이유를 알려 주지 않습니다. 링크를 삭제하면 이미 발급된 세션도 즉시 무효가 됩니다. 토큰은 저장한 뒤에 생성되며(16자 이상) UI에서 전체 링크를 복사할 수 있습니다.

### 인증 실패 제한과 자동 차단

- 같은 출처 IP가 15분 안에 인증에 10번 실패하면 한동안 더 이상의 시도를 거부합니다.
- 「전역 설정 → 자동 차단 → 인증 실패 차단」에 분 단위 값(0~43200)을 입력하면 10번 실패한 출처 IP를 그 시간 동안 차단합니다. 0이면 차단하지 않고 제한만 합니다.
- 자동 차단이 발동하면 `AuthBanned` 이벤트가 발행되며 [알림 센터](/ko/docs/modules/notify)로 푸시할 수 있습니다.
- IPv6 주소는 /64 대역 단위로 집계하고 차단합니다.

### 차단 목록

「전역 설정」의 차단 목록에는 현재 차단된 IP, 사유(인증 연속 실패 또는 수동 차단), 만료 시간이 표시되며 「해제」를 누를 수 있습니다. 수동으로 차단할 수도 있습니다. IP와 시간(1~720시간, 최대 30일)을 입력하며 API의 기본 기간은 24시간입니다.

차단 목록은 [침입 방지](/ko/docs/modules/guard)와 공유됩니다. 침입 방지 모듈이 켜져 있으면 여기에는 차단 수만 표시되고 침입 방지 페이지에서 관리합니다. 차단은 포트 포워딩, STUN 등에도 적용되며, 방화벽 동기화를 켜면 시스템 방화벽에서 삭제됩니다. "LAN 주소 무시"를 켜면 LAN 주소는 자동으로 차단되지 않습니다.

### GeoIP 국가 필터

사이트 「국가 필터」에는 끄기, 허용만, 거부의 세 가지 모드가 있으며 두 글자 ISO 국가 코드를 쉼표로 구분해 입력합니다(예: `CN, HK, US`). 사용하려면 국가를 하나 이상 입력해야 합니다.

- 필터링은 GeoIP 데이터베이스가 필요하므로 먼저 「전역 설정 → GeoIP 데이터베이스」에서 가져와야 합니다. `.mmdb` 파일을 업로드하거나 다운로드 주소를 입력합니다. MaxMind GeoLite2, DB-IP 등의 국가 DB나 도시 DB를 지원하며 업로드 제한은 129 MB입니다.
- 데이터베이스가 로드되지 않았으면 필터가 동작하지 않고(모든 방문자 통과) UI에 안내가 표시됩니다.
- 내부망 주소는 항상 통과합니다.
- 「거부」 모드에서 DB에서 국가를 찾을 수 없는 주소는 통과합니다.

## 경로별 백엔드

리버스 프록시 사이트에서 경로 접두사별로 다른 백엔드로 요청을 보냅니다. nginx의 `location /api/ { proxy_pass ...; }`와 같습니다. 사이트 편집 창 「기본」 탭의 「경로별 백엔드」에서 추가합니다.

| 필드 | 설명 |
| --- | --- |
| `prefix` | `/api/` 같은 경로 접두사. 경로 세그먼트 경계로 매칭하므로 `/api`와 `/api/` 모두 `/api`와 `/api/x`에 일치하고 `/apix`에는 일치하지 않습니다 |
| `targets` | 이 경로의 백엔드이며 사이트의 백엔드와 같은 방식으로 씁니다. 비우면 사이트의 백엔드를 사용하고 아래 헤더만 추가합니다 |
| `requestHeaders` | 이 경로에 추가할 요청 헤더. 한 줄에 `Key: Value` 하나씩. 사이트 헤더 뒤에 적용되며 이름이 같은 헤더는 사이트의 값을 덮어씁니다 |

- 가장 긴 접두사가 우선하며 경로는 그대로 전달됩니다(접두사를 제거하지 않음).
- Host 옵션, 인증서 검증, 전달 헤더, PROXY 프로토콜, 로드 밸런싱 정책, 헬스 체크 등 사이트의 다른 설정은 모든 경로별 백엔드에 적용됩니다.
- 압축, 속도 제한, 캐시, 재작성은 사이트 전체에 적용됩니다.

## 사용자별 분배 {#user-routes}

리버스 프록시 사이트에서 로그인한 사용자마다 요청을 각자의 백엔드로 보냅니다. nginx의 `map $remote_user $backend`와 같습니다. 먼저 사이트에서 기본 인증, 웹 인증 또는 포워드 인증을 켜야 합니다. 그런 다음 사이트 편집 창 「보안」 탭의 「사용자별 분배」에서 규칙을 추가합니다. 각 규칙에는 사용자 목록과 그 사용자들의 백엔드를 입력하며, 백엔드는 사이트의 백엔드와 같은 방식으로 씁니다.

사용자는 다음 식별자로 일치시킵니다.

- 사이트 사용자 또는 [공유 사용자](#shared-users)의 사용자 이름
- 서드파티 로그인 ID는 `제공자key:ID` 형식으로 씁니다. 예: `github:octocat`. 해당 ID의 다른 식별자도 함께 일치합니다.
- 포워드 인증은 인증 서비스 응답에서 복사해 온 `Remote-User`

분배 규칙은 다음과 같습니다.

- 목록에 없는 사용자, 그리고 공개 경로(인증이 필요 없는 경로)에서 로그인하지 않은 방문자는 사이트 백엔드를 사용합니다. 공개 경로에서도 웹 인증으로 이미 로그인한 방문자는 신원에 따라 분배되므로 같은 앱의 페이지가 같은 백엔드로 갑니다.
- 자체 백엔드가 있는 경로별 백엔드 규칙(위 절 참고)이 우선합니다. 요청 헤더만 추가하는 경로별 규칙은 해당 사용자의 백엔드를 사용합니다.
- 「사용자 이름 전달」에 `X-Remote-User` 같은 요청 헤더 이름을 입력하면 인증된 사용자 이름이 그 헤더에 담겨 백엔드로 전달됩니다. 방문자가 직접 보낸 같은 이름의 헤더는 항상 삭제되므로 위조할 수 없습니다.
- 메모리 응답 캐시를 켜면 캐시 키에 선택된 사용자 경로가 포함되고, 「사용자 이름 전달」을 켰을 때는 사용자 이름도 포함되어 백엔드나 사용자가 다른 응답이 서로 섞이지 않습니다.

저장할 때 사이트에 인증이 켜져 있는지, 각 규칙에 사용자가 한 명 이상 있고 백엔드가 올바른지, 같은 사용자가 두 규칙에 들어 있지 않은지, 헤더 이름이 올바르고 `Host`, `Cookie`, `Authorization`, `X-Forwarded-For`처럼 전달이나 인증에 영향을 주는 헤더가 아닌지 확인합니다. 사이트 목록에서 사용자별 분배가 설정된 사이트에는 규칙 개수 태그가 표시됩니다.

## 리버스 프록시 고급 기능

이 옵션들은 사이트 편집 창의 「트래픽」 탭에 있습니다.

### 백엔드, 가중치, 예비

백엔드 목록은 한 줄에 주소 하나이며 주소 뒤에 매개변수를 붙일 수 있습니다.

```text
http://10.0.0.2:8080 weight=3
http://10.0.0.3:8080 backup
```

- `weight=N`: 가중치, 1~100 정수, 기본값 1
- `backup`: 예비 백엔드로, 예비가 아닌 백엔드가 모두 사용 불가일 때만 활성화됩니다. 모든 백엔드가 사용 불가이면 예비가 아닌 백엔드 전체로 되돌아가 계속 시도합니다.

### 로드 밸런싱 정책

| UI 옵션 | `lbPolicy` | 설명 |
| --- | --- | --- |
| 라운드 로빈 (가중치 적용) | 비움 | 기본값 |
| 랜덤 (가중치 적용) | `random` | |
| IP 해시 (세션 유지) | `ip_hash` | 같은 클라이언트 IP가 같은 백엔드로 갑니다 |
| 최소 연결 | `least_conn` | 「연결 수 / 가중치」가 가장 작은 백엔드를 선택합니다 |

### 헬스 체크

액티브 체크 스위치는 기본적으로 꺼져 있습니다. 켰을 때의 필드와 기본값은 다음과 같습니다.

| 필드 | 기본값 | 범위 |
| --- | --- | --- |
| 방식 `mode` | `http` | `http`(체크 경로를 요청하고 상태 코드가 400 미만이면 정상으로 판단) 또는 `tcp`(연결만 테스트) |
| 경로 `path` | `/` | `/`로 시작, http 방식에서만 사용 |
| 간격 `interval` | 10초 | 1~3600 |
| 타임아웃 `timeout` | 3초 | 1~60 |
| 연속 실패 `fails` | 3회 연속이면 사용 불가 | 1~20 |
| 연속 성공 `passes` | 2회 연속이면 복구 | 1~20 |

백엔드로 PROXY 프로토콜을 보내도록 설정하면 HTTP 체크는 자동으로 TCP로 바뀝니다.

패시브 체크는 항상 동작합니다. 백엔드가 여러 개일 때 연속 3번 연결에 실패한 백엔드는 30초간 중단한 뒤 다시 시도합니다(백엔드가 하나뿐이고 액티브 체크도 꺼져 있으면 제외하지 않습니다). 액티브 체크를 켜면 복구는 전적으로 체크 결과에 따라 결정됩니다. 백엔드 상태가 바뀌면 업스트림 사용 불가 / 복구 이벤트가 발행되며 [알림 센터](/ko/docs/modules/notify)로 푸시할 수 있습니다.

### 압축

리버스 프록시, 정적 파일, 고정 텍스트 사이트에서 압축을 켤 수 있습니다(리다이렉트 사이트 제외). `Accept-Encoding`에 따라 `br`을 우선하고 그다음 `gzip`을 선택합니다.

- 텍스트 계열 콘텐츠만 압축합니다: `text/*`, JSON, JavaScript, XML, XHTML, RSS / Atom, WebAssembly, SVG. `text/event-stream`은 제외됩니다.
- 선언된 `Content-Length`가 256바이트 미만인 응답은 그대로 둡니다.
- 이미 `Content-Encoding`이 있는 응답은 그대로 두며 WebSocket 업그레이드 요청은 바로 통과시킵니다.
- 압축 후에는 강한 ETag가 약한 ETag로 바뀝니다.

### IP별 속도 제한

클라이언트 IP별 토큰 버킷 방식의 속도 제한이며 필드는 다음과 같습니다.

| 필드 | 설명 |
| --- | --- |
| `rate` | 초당 허용하는 요청 수 |
| `burst` | 버스트 용량. `rate`를 설정하고 `burst`가 0이면 자동으로 `rate`를 정수로 내린 값에 1을 더한 값을 사용합니다 |
| `maxConns` | IP 하나당 동시 요청 상한이며 0은 무제한입니다 |

속도 제한을 켤 때는 `rate`와 `maxConns` 중 최소 하나를 설정해야 합니다.

### 메모리 응답 캐시

리버스 프록시 사이트에서만 동작하며 캐시는 메모리에 저장되고 LRU 방식으로 제거됩니다.

| 필드 | 기본값 | 범위 |
| --- | --- | --- |
| `ttl` 기본 시간 | 0 | 0~30일(초 단위). 업스트림이 캐시 지시자를 선언하지 않았을 때 200 응답을 이 시간 동안 캐시합니다. 0이면 업스트림이 명시적으로 허용한 응답만 캐시합니다 |
| `maxMb` 캐시 용량 | 64 | 1~4096 MB |

캐시 규칙은 다음과 같습니다.

- GET 요청만 캐시하며 요청에 `Authorization`, `Cookie`, `Range` 헤더나 `Cache-Control: no-cache`가 없어야 합니다.
- 상태 코드 200 응답만 캐시합니다. 응답에 `Set-Cookie`, `Vary: *`가 있거나 `Cache-Control`이 `no-store` / `private` / `no-cache`이면 건너뜁니다.
- `s-maxage`를 따르고 그다음 `max-age`를 따릅니다.
- 항목 하나의 상한은 4 MB이며 전체 용량의 4분의 1을 넘지 않습니다.
- 캐시 적중 시 `X-Cache: HIT`와 `Age` 헤더를 반환하고 미적중이면 `X-Cache: MISS`입니다.
- 캐시 키에는 Host, 전체 요청 URI, `Accept-Encoding`이 포함됩니다. [사용자별 분배](#user-routes)를 설정하면 선택된 사용자 경로도 포함되고, 「사용자 이름 전달」을 켜면 사용자 이름도 포함됩니다.

### 경로 재작성과 리다이렉트

규칙은 순서대로 매칭하며 첫 번째로 일치하는 규칙에서 멈춥니다.

| 필드 | 설명 |
| --- | --- |
| `pattern` | 요청 경로와 매칭할 정규식. 예: `^/old/(.*)$` |
| `to` | 치환 결과이며 `$1`로 그룹을 참조할 수 있습니다 |
| `redirect` | 끄면 내부 재작성(재작성된 경로가 백엔드로 전송되며 대상은 `/`로 시작해야 함), 켜면 리다이렉트 |
| `code` | 리다이렉트 상태 코드 301 / 302 / 307 / 308, 기본 302 |

리다이렉트는 원래 쿼리 매개변수를 유지합니다. 리다이렉트 대상에는 방문자가 사용한 도메인을 뜻하는 `{host}`를 넣을 수 있습니다. 리다이렉트 규칙은 인증보다 먼저 실행되므로(nginx의 `location = / { return 302 ...; }`와 같음) `/` 같은 경로는 로그인을 요구하지 않고 방문자를 다른 곳으로 보낼 수 있습니다.

## 접속 통계 및 모니터링

### 사이트 통계

실행 중인 리스너에서 사이트 행의 「통계」를 누르면 통계 창이 열리며 최근 1시간, 6시간, 24시간 중에서 선택할 수 있습니다.

- 분 단위 접속 통계: 1분에 점 하나, 최근 24시간 보관, 요청 수 곡선과 4xx / 5xx 오류 곡선 포함
- 상태 코드 분포 2xx / 3xx / 4xx / 5xx, 누적 응답 트래픽
- 출처 IP 상위 10개와 국가 상위 10개(국가 통계에는 GeoIP 데이터베이스를 가져와 두어야 함)
- 리버스 프록시 사이트는 백엔드별 상태, 가중치, 예비 여부, 현재 연결 수를 표시

통계는 메모리에 저장되며 재시작하거나 리스너 자체의 설정을 바꾸면 다시 집계합니다. 사이트를 수정해도 카운터는 유지됩니다. 순위표는 서로 다른 출처를 최대 5000개까지 집계합니다.

### Prometheus 메트릭

전역 메트릭 엔드포인트 `GET /api/metrics`는 모든 모듈의 메트릭을 모아 제공합니다. [모니터링 메트릭](/ko/docs/reference/monitoring)을 참고하세요. 아래 모듈 엔드포인트에는 웹 서비스 메트릭만 포함됩니다.

메트릭 엔드포인트는 `GET /api/webservice/metrics`이며 Prometheus 텍스트 형식입니다. 로그인 자격 증명이나 [API 토큰](/en/docs/reference/api-reference)이 필요합니다.

```bash
curl -H "Authorization: Bearer gtl_xxxx" http://localhost:16680/api/webservice/metrics
```

| 메트릭 | 유형 | 설명 |
| --- | --- | --- |
| `gately_site_requests_total` | counter | 사이트 누적 요청 수 |
| `gately_site_errors_total` | counter | 사이트 백엔드 오류 수 |
| `gately_site_active_requests` | gauge | 진행 중인 요청 수 |
| `gately_site_response_bytes_total` | counter | 누적 응답 바이트 수 |
| `gately_site_responses_total` | counter | 상태 클래스(레이블 `class`: `2xx`~`5xx`)별 응답 수 |
| `gately_upstream_up` | gauge | 백엔드 정상 여부, 1은 정상, 0은 사용 불가(레이블 `upstream` 포함) |

모든 메트릭에는 레이블 `listener`(리스너 이름#리스너 key)와 `site`(사이트 이름, 이름이 없으면 첫 번째 도메인)가 붙습니다.

## nginx 설정 가져오기 {#import-nginx}

페이지 상단의 「nginx 가져오기」로 기존 nginx 사이트를 Gately의 리스너와 사이트로 변환할 수 있습니다. nginx가 있는 호스트에서 `nginx -T`를 실행하고 전체 출력을 붙여넣는 방식을 권장합니다. 출력에는 include된 모든 파일이 들어 있으며, Gately는 nginx와 같은 방식으로 include를 펼칩니다.

- 먼저 미리 봅니다. 수신 포트별로 묶어 각 사이트의 유형, 백엔드 또는 디렉터리, 원본 파일과 줄 번호, 주의할 점(변수를 쓰는 지시어, 정규식 location, 인증서가 없는 도메인 등)을 보여 주며, 변환할 수 없는 사이트는 그 이유를 알려 줍니다.
- 포트가 같은 사이트는 기존 리스너에 병합하고, 그 밖에는 새 리스너를 만듭니다. 이미 있는 도메인은 건너뛰므로 여러 번 가져와도 됩니다.
- 기본적으로 비활성 상태로 가져오므로 nginx와 병행하면서 하나씩 확인한 뒤 활성화할 수 있습니다. 「가져온 후 바로 활성화」를 체크하면 즉시 적용됩니다(nginx가 같은 포트를 쓰고 있으면 새 리스너는 시작되지 않습니다).
- 변환되는 내용: `proxy_pass`(upstream의 가중치, 예비, 로드 밸런싱 정책 포함), `root` / `alias` 정적 디렉터리(`autoindex`, `try_files $uri.html`, `error_page 404`), `return` 리다이렉트와 고정 내용, 사이트 전체 `rewrite` 리다이렉트, `add_header`, `proxy_set_header`, `gzip`, `allow` / `deny`, location 단위의 경로별 백엔드·접근 제어·리다이렉트, `listen ... proxy_protocol`과 `quic`.
- `auth_request`는 포워드 인증으로 변환됩니다. 인증 엔드포인트는 인증 하위 요청 location의 `proxy_pass`에서 가져오고(`set` 변수 지원), 로그인 리디렉션은 `error_page 401 =302`에서 가져오므로 Authelia의 일반적인 설정은 그대로 변환됩니다. 일부 location에서만 쓰는 경우에는 「인증 범위」에서 지정한 경로만 인증하도록 변환합니다.
- `auth_basic`은 공유 사용자를 쓰는 기본 인증으로 변환됩니다. nginx의 사용자 파일은 읽지 않으므로 사용자를 추가하기 전에는 아무도 통과할 수 없습니다.
- `stream`의 TCP/UDP 전달은 [포트 포워딩](/ko/docs/modules/portforward)에서 설정하세요. 인증서는 가져오지 않습니다. HTTPS 사이트에 인증서가 없으면 미리 보기에서 nginx가 쓰는 인증서 파일을 보여 주므로 [인증서](/ko/docs/modules/ssl) 페이지에서 파일 경로로 추가할 수 있습니다.

## haproxy와 nginx 대체

프로토콜 라우팅과 웹 서비스를 함께 쓰면 haproxy + nginx 조합을 대체할 수 있습니다. 흔한 구성은 443 포트에 [프로토콜 라우팅](/ko/docs/modules/protoroute) 규칙을 하나 두어 VPN 같은 TLS 서비스는 곧바로 백엔드로, 나머지는 모두 PROXY 프로토콜을 받는 웹 서비스 리스너로 보내는 것입니다. 여기에 80 포트에 리다이렉트 사이트(`https://{host}`)를 둔 웹 서비스 리스너를 추가합니다.

nginx 설정을 옮기는 방법은 다음과 같습니다.

| nginx | Gately |
| --- | --- |
| `server_name`이 있는 `server` | 해당 도메인을 지정한 사이트 |
| `proxy_pass`가 다른 `location` | 경로별 백엔드 |
| `auth_request`(Authelia) | 포워드 인증, 또는 TOTP를 쓰는 공유 사용자 |
| `proxy_ssl_name $host` | 접속 도메인을 SNI로 사용 |
| `return 301 https://$host$request_uri` | `https://{host}`와 「경로와 매개변수 유지」를 지정한 리다이렉트 사이트 |
| `location = /`의 `return 302 /admin` | 「리디렉션」을 켠 재작성, 패턴 `^/$` |
| `try_files $uri $uri.html $uri/index.html`과 `error_page 404` | 확장자 없는 URL과 404 페이지를 설정한 정적 파일 |
| `add_header` | 응답 헤더 |
| `return 444` | 연결 끊기 사이트 |
| HTTPS server의 `error_page 497 https://$host:$server_port$request_uri` | 새 리스너의 「같은 포트의 HTTP」를 「HTTPS로 리디렉션」으로 설정합니다. 기존 리스너에 병합할 때는 경고만 표시하고 설정은 바꾸지 않습니다 |

## 배포 팁

웹 서비스는 호스트의 80 / 443 등의 포트를 수신해야 하므로 Docker 배포에서는 `--network host`를 권장합니다.
