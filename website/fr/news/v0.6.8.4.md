# Gately v0.6.8.4 disponible

19 novembre 2026

[Télécharger v0.6.8.4](/fr/download) · [GitHub Release](https://github.com/wangwanjie/gately/releases/tag/v0.6.8.4)

## Correctif de sécurité

- **Les clés des canaux de notification pouvaient apparaître dans les erreurs de livraison (faible)** : les jetons de bot Telegram, les clés d'appareil Bark, les SendKey ServerChan et autres secrets figurent dans l'URL de la requête. Quand la connexion échouait, le message d'erreur reprenait l'URL complète et l'écrivait dans le journal du module de notification et dans les entrées « Envois récents », où les comptes en lecture seule et les jetons d'API disposant seulement de la lecture des notifications pouvaient la voir. Les clés de canal sont désormais remplacées par `***` dans les messages d'erreur. Les versions v0.6.8.2 et antérieures sont concernées ; « Envois récents » n'est conservé qu'en mémoire et se vide au redémarrage suivant la mise à jour ; les journaux d'exécution peuvent conserver d'anciennes entrées, il est donc conseillé de changer la clé de tout canal dont l'envoi a déjà échoué (GHSA-p368-wcp9-rv4q).

## Modifier la configuration ne vous enferme plus dehors

- **Confirmation après enregistrement, annulation automatique à l'expiration** : après l'enregistrement de la redirection de ports, du routage par protocole, des services Web ou des paramètres globaux dans l'interface d'administration, la page ouvre une nouvelle connexion pour confirmer que l'interface reste accessible. Si la confirmation est impossible (par exemple, vous avez changé le port d'écoute par lequel passe l'interface d'administration), la configuration d'avant la modification est rétablie au bout de 90 secondes par défaut. En cas d'échec de confirmation, un compte à rebours s'affiche et vous pouvez annuler aussitôt ; si 3 redémarrages passent sans confirmation, l'annulation a aussi lieu. « Paramètres système › Contrôle d'accès » permet de désactiver la fonction ou d'ajuster l'attente (30 à 600 secondes). Une annulation envoie une notification « Modifications de configuration ».
- **Avertissement sur le chemin d'accès avant l'enregistrement** : l'interface retrace les redirections de ports, routages par protocole et sites Web que traverse votre accès actuel. Quand une modification à enregistrer affecte ce chemin (changement de port, désactivation, suppression, passage à une adresse sur laquelle cette machine ne peut pas écouter, etc.), elle en explique d'abord la raison et met en évidence le maillon concerné. « Paramètres système › Contrôle d'accès » affiche le chemin d'accès actuel.
- **Modifications groupées appliquées ensemble** : quand plusieurs éléments doivent changer ensemble pour que cela fonctionne (par exemple le routage par protocole puis l'écouteur Web), choisissez « Mettre en attente, appliquer ensemble ». Une bannière en haut liste les règles et écouteurs en attente ; « Tout appliquer » confirme tout le lot et l'annule entièrement en cas d'échec, « Abandonner » l'abandonne. Avant l'application, les écouteurs qui ne peuvent pas démarrer sont listés.
- **Annulation en ligne de commande** : `gately rollback` liste les modifications en attente de confirmation et les 15 derniers enregistrements de configuration ; vous pouvez en annuler un par son numéro, ou utiliser `-last`, `-pending` ou `-config` avec `-version`. Si Gately tourne, il rétablit et redémarre en 2 secondes ; sinon, il réécrit directement le fichier de configuration.
- Avant la suppression d'un fichier de configuration, une copie est conservée dans l'historique de configuration ; une suppression peut donc aussi être annulée depuis l'historique.

## Notifications : nouvelle tentative et renvoi après échec

- Après un échec d'envoi, une nouvelle tentative a lieu après 10, 30 puis 60 secondes (3 tentatives par défaut, réglable de 0 à 10) ; les messages qui échouent encore entrent dans une file de renvoi et sont envoyés dans l'ordre chronologique au rétablissement du canal, et la file survit aux redémarrages (conservée 24 heures par défaut, réglable de 0 à 168, 0 la désactive ; 100 messages au maximum par canal).
- Lorsqu'un canal a déjà des messages en attente de renvoi, un nouveau message n'est tenté qu'une seule fois et, en cas d'échec, placé derrière l'arriéré au lieu d'attendre les nouvelles tentatives une par une.
- « Envois récents » affiche « En attente de renvoi », « Renvoyée » et le nombre de tentatives ; une bannière au-dessus compte les messages en attente par canal et permet de les vider.

## Certificats : utiliser le certificat système fnOS (#105)

- La source du certificat s'enrichit de « Certificat système fnOS » : choisissez un domaine parmi les certificats déjà gérés par fnOS ; toutes les 30 minutes, Gately lit le dernier certificat pour suivre les renouvellements de fnOS (en utilisant la chaîne complète lorsqu'elle existe) ; après un changement, il le charge et le déploie automatiquement.
- Les certificats se gèrent dans fnOS sous « Paramètres → Sécurité → Certificat ». L'application native fnOS (fpk) peut les lire directement ; en déploiement Docker, montez `/usr/trim/etc/network_cert_all.conf` et `/usr/trim/var/trim_connect/ssls` en lecture seule dans le conteneur, aux mêmes chemins, et exécutez le conteneur en root (valeur par défaut de l'image officielle). Voir [Certificats SSL](/fr/docs/modules/ssl).

## Utilisation du stockage

- « Paramètres système › Réseau et exécution » gagne une carte d'utilisation du stockage : capacité de la partition contenant le répertoire de configuration, taille totale de ce répertoire, ainsi que l'occupation et le chemin de chaque type de données, dont les journaux d'exécution, l'audit des visiteurs, l'historique de configuration, les sauvegardes, les certificats, les programmes gérés, la file de renvoi des notifications et les données File Browser.

## Corrections

- **Prévention d'intrusion** : le port d'administration est enregistré comme port ouvert avant le démarrage des modules ; auparavant, quand la plage des ports pièges contenait le port d'administration, l'écouteur piège de Gately l'occupait en premier, l'écouteur d'administration échouait et Gately quittait à chaque redémarrage. Aucun port piège n'est plus défini pendant le démarrage des modules ; les ports enregistrés par des modules comme frps, EasyTier et les ports passifs FTP ne servent pas de pièges même s'ils n'écoutent pas encore ; les ports pièges sont recalculés quand les ports changent ; l'écouteur HTTP-01 temporaire utilisé lors de la demande de certificat n'est plus bloqué par les ports pièges.
- **Services Web** : quand le backend d'un site est un autre écouteur Web de la même instance (par exemple site en 443 → écouteur 444 de cette machine → interface d'administration), le cookie de connexion de l'interface d'administration est transmis tel quel, et une erreur 401 n'apparaît plus juste après la connexion.

## Remarques de mise à niveau

- Docker : tirez la nouvelle image et recréez le conteneur. OpenWrt : installez le nouveau `.apk` / `.ipk` par-dessus l'ancien. fnOS : installez manuellement le nouveau `.fpk` dans le Centre d'applications. Les autres déploiements peuvent se mettre à jour en ligne dans « Paramètres système ».
- La confirmation après enregistrement est activée par défaut. L'enregistrement de la configuration par script ou avec un jeton d'API n'est pas concerné ; seuls les enregistrements d'une session de l'interface d'administration portant l'en-tête de confirmation doivent être confirmés.
