# 入侵防护

类似 fail2ban 的入侵防护：从日志中识别暴力破解，在没有使用的端口上设诱饵，统计端口扫描，把恶意 IP 加入封禁表，并同步到系统防火墙（nftables / iptables + ipset），在内核层丢弃它的全部流量。

## 能力

- **日志规则**：读取日志文件、systemd 日志、命令输出（如 OpenWrt 的 `logread -f`）或 Docker 容器日志，用正则找出失败记录，同一 IP 在统计窗口内达到次数即封禁；内置 SSH、Dropbear、Nginx、Vaultwarden、Home Assistant、Proxmox VE 等模板，规则编辑时可粘贴日志样例直接测试；
- **Gately 事件**：管理后台登录失败、WAF 拦截、[端口敲门](/docs/modules/knock)被拒绝也可以作为规则来源，无需写正则；
- **Web 路径探测**：直接统计 Web 服务处理的请求，按监听、路径与状态码计数，访问 `/.env`、`/.git` 等诱饵路径或反复扫描未知域名的来源会被封禁，无需读取日志；
- **诱饵端口**：在本机没有使用的端口上设下诱饵（默认 23、135、1433、3389、5900、6379 等），任何来源一连接就封禁；
- **端口扫描检测**：同一来源每分钟连接本机未开放端口的次数超过阈值即封禁；
- **统一封禁表**：手动封禁（支持 CIDR 网段与永久封禁）、Web 服务认证失败的自动封禁都在这里管理；手动封禁不能包含回环地址（经本机转发进来的连接都显示为该地址）；封禁会持久化，重启后恢复；
- **递增封禁**：同一地址 30 天内再次被封禁时时长翻倍，直到上限；
- **白名单**：默认忽略内网、回环、100.64.0.0/10（Tailscale）与本机网卡所在的 IPv6 /64 网段（封禁按 /64 进行，同一局域网的公网 IPv6 设备不会被连带封禁），可追加 IP 或网段；白名单中的单个 IPv6 地址会保护它所在的整个 /64。

## 生效范围

| 环境 | 封禁效果 | 诱饵端口 | 端口扫描检测 |
| --- | --- | --- | --- |
| Linux（root 或 `CAP_NET_ADMIN`，已安装 nftables） | 内核层丢弃全部流量，包括 SSH、其他程序与转发给 Docker 容器、内网设备的流量 | 内核处理，能发现只发 SYN 的扫描 | 可用 |
| Docker（host 网络 + `cap_add: NET_ADMIN`） | 同上，规则写入宿主机 | 同上 | 可用 |
| 飞牛 fnOS 安装包、OpenWrt 22.03 及以上 | 同上（以 root 运行，系统自带 nftables） | 同上 | 可用 |
| 群晖 DSM 等内核未启用 nf_tables 的 Linux（Docker host 网络 + `NET_ADMIN`；直接安装需要 ipset 与 iptables legacy） | 同上，改用 iptables 的 mangle 表与 ipset | 同上 | 可用（阈值最高按 255 次/分钟处理） |
| 其他情况（Windows、macOS、FreeBSD、既没有 nftables、也没有 iptables（legacy）与 ipset，或没有权限的 Linux） | 只对 Gately 自身的服务生效：端口转发、Web 服务、STUN、WebDAV、FTP、SMB、frps 登录、管理后台 | 由 Gately 监听，只能发现完成握手的连接 | 不可用 |

页面顶部会显示防火墙同步状态，不可用时给出原因与处理办法。

## 防火墙规则

开启「同步到系统防火墙」后，Gately 在 nftables 中创建独立的 `inet gately` 表，不改动系统已有的规则（fw4、Docker、ufw 等）：

- `prerouting` 链（优先级 -190，在连接跟踪之后、目的地址转换之前）丢弃被封禁地址发来的数据包，发往本机、转发给容器或内网设备的流量都会被丢弃；本机主动发起的连接（例如访问 DNS、软件源）的回包照常放行，即使对方地址被封禁也不受影响；IPv6 按 /64 网段封禁；
- `input` 链只统计发往本机的新连接，用于诱饵端口与扫描检测，白名单地址不参与；
- 关闭同步或停止 Gately 时整张表被删除；表被其他程序清除后 10 秒内自动重写。

内核没有 nf_tables（如群晖 DSM）时改用 iptables（legacy）与 ipset，同样不改动系统已有的规则：mangle 表 `PREROUTING`、`INPUT` 的第一条规则分别跳到 Gately 自己的 `GATELY_PRE`、`GATELY_IN` 链，作用与上面两条链相同；被封禁的单个地址放在 ipset 集合 `gately_ban4` / `gately_ban6`（IPv6 按 /64），网段与永久封禁写成 `GATELY_DENY` 链中的规则。群晖防火墙等程序把自己的规则插到前面时，10 秒内把跳转挪回第一位；链被清除后自动重写。扫描检测用 recent 模块计数，阈值最高按每分钟 255 次处理。

页面上的「查看规则」可以看到当前写入的完整规则。

::: tip Docker 部署
需要 `network_mode: host` 并授予 `NET_ADMIN`，规则才会写入宿主机：

```yaml
    network_mode: host
    cap_add:
      - NET_ADMIN
```

不授予时封禁仍对 Gately 自身的服务生效。读取宿主机日志需要把日志目录挂载进容器，例如 `- /var/log:/var/log/host:ro`，规则中填写 `/var/log/host/auth.log`；systemd 日志来源在容器中不可用。
:::

## 日志规则

| 来源 | 填写 | 说明 |
| --- | --- | --- |
| 日志文件 | 文件路径，每行一个 | 从文件末尾开始读取新增内容，轮转（改名或截断）后自动切换 |
| systemd 日志 | 服务单元，如 `ssh.service` | 通过 `journalctl -f` 读取 |
| 命令输出 | 一条命令，如 `logread -f` | 命令退出后自动重启 |
| Docker 容器 | 容器名 | 通过 Docker 管理模块连接的 Docker 读取 |
| Gately 事件 | 管理后台登录失败 / WAF 拦截 / 端口敲门被拒绝 | 事件自带来源 IP，无需过滤规则 |
| Web 路径探测 | 监听（可留空）与路径规则 | 统计 Web 服务的请求，见下文 |

过滤规则是 Go 正则表达式（RE2 语法），每行一条，用 `<HOST>` 表示来源地址，例如：

```
Failed password for (?:invalid user )?\S* ?from <HOST>
```

「排除规则」中匹配的行不计数。统计窗口、失败次数与封禁时长可按规则设置，封禁时长可选默认、自定义或永久。

## Web 路径探测

来源选「Web 路径探测」时，规则直接统计 Web 服务处理的请求，不读取日志：

- **监听**：可选一个或多个，留空表示全部监听；
- **路径规则**：每行一条，留空表示全部路径。`*` 匹配任意字符（含 `/`），整条路径匹配，不区分大小写，例如 `*/.env` 匹配 `/.env` 与 `/api/.env`；以 `~` 开头为 Go 正则。`//.env`、`/a/../.env` 这类写法按规范化后的路径同样命中；
- **排除路径**：写法同上，命中的请求不计数；
- **统计口径**：默认只统计 404 与 444（访问了不存在的内容，或被「断开连接」站点直接断开），访问正常页面的请求不计数；开启「任意状态码」后所有响应都计数，适合诱饵路径，因为单页应用对任意路径都返回 200。任意状态码需搭配路径规则或「只统计未知域名」，否则保存时会被拒绝；
- **访问控制拒绝**：站点的拒绝方式为「断开连接」时，被封禁、IP 访问控制或国家过滤拒绝的请求在普通站点上按 403 统计，避免名单外的正常访客被误封；在默认站点上按 444 统计，与「断开连接」类型的默认站点一致，默认站点改用反向代理加白名单放行自家 IP 后，未知域名扫描仍会被统计；
- **只统计未知域名**：只统计域名没有匹配任何站点的请求，即由默认站点处理、或没有默认站点时由监听直接返回 404 的请求。

内置三个模板：

| 模板 | 条件 | 说明 |
| --- | --- | --- |
| Web 诱饵路径 | `/.env`、`/.git`、`wp-login.php`、`phpinfo.php`、`phpmyadmin` 等，任意状态码 1 次 | 封禁 1 天。站点本身是 WordPress、phpMyAdmin 等程序时先删掉对应的行 |
| 未知域名扫描 | 只统计未知域名，1 分钟 5 次 | 封禁 1 天。与默认站点的「断开连接」搭配：扫描器几次 444 后被封禁，开启防火墙同步后之后的连接直接被丢弃 |
| Web 404 探测 | 全部路径，1 分钟 10 次 | 已排除 favicon、robots.txt、`.map` 等浏览器常请求的路径。反代后端返回的 404 同样计数，图库缩略图缺失、应用轮询不存在的接口等情况可能触发，启用前先看访问日志，必要时调高次数或补充排除路径 |

在 Web 服务的监听卡片上点「路径探测封禁」会跳到这里，预选该监听并套用诱饵路径模板；规则的存储与执行都在入侵防护。编辑规则时可以粘贴请求路径测试路径规则。

站点开启「信任已登录用户」（见 [Web 服务](./web)）后，已通过该站点 Gately 认证的访客的请求不计入路径探测。默认站点处理的未知域名请求、未登录访客照常计数，端口扫描、诱饵端口与登录失败等其他规则不受影响。

双层 Gately 的外层站点开启「信任后端认证标记」后，内层确认的已登录用户的请求在外层同样不计入路径探测。

::: warning 封禁范围
无论哪个监听触发，封禁都写入同一张封禁表，对全部监听、站点与 Gately 的其他服务生效；开启防火墙同步后，还会在系统防火墙层丢弃该地址的全部流量。
:::

来源地址与访问日志一致，只经 PROXY 协议还原。站点经 CDN 回源、由请求头传递真实 IP 时，封禁的会是 CDN 节点，这类监听不要启用路径探测；Gately 位于本机其他反向代理之后时，来源是回环地址，开启「忽略内网地址」后不会被封禁，但规则也不起作用。

## 端口扫描检测的取舍

扫描检测统计的是连接**本机未在监听的端口**的新连接：正在监听的 TCP 端口每 10 秒自动刷新，视为开放；由其他防火墙规则转发出去的端口不经过 `input` 链，不会被统计。阈值默认每分钟 12 次，正常客户端重试一个关闭的端口每分钟约 5 次，不建议设得低于 10。

诱饵端口中正在被监听的端口会被自动排除，避免误封正常访问者。

## IPv6 严格模式

IPv6 没有 NAT，每个设备都有公网地址，地址一旦出现在 DNS 或证书透明日志里就会被扫描器直连。端口扫描检测里的「IPv6 严格模式」把检测改成白名单方式：IPv6 来源只能连接开放端口（正在监听的端口加「额外开放端口」），第一次连接其他端口即被封禁，不再按阈值计数；IPv4 仍按阈值检测。

- 封禁按 /64 网段生效，同一网段的其他设备一并被封；白名单地址与「忽略内网地址」覆盖的地址不受影响；
- 新开始监听的端口最长约 10 秒后才被视为开放，开启严格模式或重启后约 15 秒才生效，这段时间内仍按阈值检测；读不到监听端口时同样按阈值检测；
- 端口停止监听后 30 秒内仍视为开放，frps 重连、程序或监听重启期间重试连接的访客不会被封；FTP 服务设置了被动端口范围时，整个范围自动计入开放端口；被动端口由系统随机分配时无法事先列出，IPv6 访客的数据连接会被当成扫描封禁，运行日志会给出提示，需要在 FTP 服务中设置被动端口范围；
- 由其他程序通过防火墙规则使用的端口必须先加入「额外开放端口」，否则访问它们的来源会被封禁；
- 只统计 TCP 的新连接，需要防火墙同步生效，并且要先启用端口扫描检测。

## 与 Web 服务的关系

Web 服务「认证失败封禁」产生的封禁写入同一张封禁表，因此开启防火墙同步后会对整台主机生效，不再只限于 Web 站点。开启「忽略内网地址」时，内网地址不会被自动封禁。

Web 服务与 WAF 只通过 PROXY 协议识别真实客户端地址。站点经 CDN 回源、由请求头传递真实 IP 时，认证失败封禁与「WAF 拦截」规则封禁的会是 CDN 节点，这类站点不要启用它们。

## 通知

封禁产生 `入侵防护：IP 已被封禁` 事件，可在[通知中心](/docs/modules/notify)订阅；诱饵端口与扫描检测在同一轮检查中封禁的多个地址合并为一条通知。

## 验证

在飞牛 fnOS（Debian 12，nftables 1.0.6）与 iStoreOS 24.10（nftables 1.1.1）的独立网络命名空间中验证：诱饵端口与扫描检测（IPv4 与 IPv6）在内核层封禁并导入封禁表，日志文件（含轮转）、systemd 日志、Docker 容器日志与管理后台登录失败均能触发封禁；手动网段与永久封禁、解封、递增时长、重启后恢复、规则被外部删除后重写、停止时清理规则均符合预期；Docker 容器在没有 `NET_ADMIN` 时识别为权限不足并退回用户态诱饵端口。
