# Веб-службы

Обратный прокси, редиректы, статические файлы и фиксированный текст по доменам — единая веб-точка входа Gately. Расположение в меню: боковая панель «Веб → Веб-службы».

## Структура: слушатель, сайт и сайт по умолчанию

Конфигурация состоит из трёх уровней:

1. Слушатель: один прослушиваемый порт. Поля: сеть (`tcp` — двойной стек, `tcp4`, `tcp6`), адрес прослушивания (пусто — все адреса), порт, переключатель HTTPS, минимальная версия TLS (1.0 / 1.1 / 1.2 / 1.3), приём протокола PROXY.
2. Сайт: сайт внутри слушателя, выбираемый по домену. Домен может быть точным, `*.example.com` (любой уровень поддоменов), `api-*.example.com` (один `*` в первой метке совпадает с нулём или более символов этой метки и остаётся в её пределах) или `*` (все); приоритет сопоставления: точный домен, wildcard, `*`. Если совпадают несколько wildcard, побеждает более длинное правило; при равной длине побеждает сайт, стоящий в списке раньше. Wildcard в первой метке работает и при импорте, пакетном редактировании и в переменной перенаправления `{1}`. Сайтам с HTTPS нужен сертификат, покрывающий реальные имена, например `*.example.com`; центры сертификации выпускают wildcard-сертификаты только вида `*.example.com`.
3. Сайт по умолчанию: используется, если ни один сайт не подошёл; если не включён, возвращает 404. Сайту по умолчанию можно задать тип «Закрыть соединение», чтобы запросы к неизвестным доменам не получали никакого ответа. Настроенный сайт по умолчанию отображается последним в списке сайтов; если он ещё не настроен, нажмите «Настроить сайт по умолчанию» на карточке прослушивателя.

При сохранении изменений сайта или сайта по умолчанию список сайтов заменяется на месте: слушатель продолжает работать, открытые соединения (включая WebSocket) не разрываются, а статистика каждого сайта сохраняется. Если новая конфигурация недопустима, продолжают работать прежние сайты. Изменение собственных настроек слушателя (сеть, адрес, порт, HTTPS, минимальная версия TLS, HTTP/3, протокол PROXY) перезапускает этот слушатель.

Каждый конкретный домен в списке сайтов — полная ссылка, которая открывается в новой вкладке; кнопка рядом копирует ссылку. Домены с подстановкой (`*.example.com`, `*`) по-прежнему показываются текстом. Адрес строится по слушателю: `https` при включённом HTTPS, иначе `http`, порт — порт слушателя, стандартные порты 443 и 80 опускаются, например `https://example.com:8443`. Если в слушателе не указан порт доступа, а включённое правило маршрутизации по протоколу или проброса портов передаёт трафик на этот слушатель, ссылки сайтов автоматически используют входной (прослушиваемый) порт правила, например 443 для слушателя на 8443, куда маршрутизация по протоколу передаёт трафик с 443. Целевой адрес правила должен вести на слушатель: loopback или неуказанный адрес для слушателя на всех адресах, тот же адрес для слушателя на конкретном адресе. Маршрутизация по протоколу сопоставляется по каждому домену в том же порядке, что и при маршрутизации (точный домен, затем самая конкретная подстановка, затем `*`, затем цель по умолчанию); отключённые маршруты и маршруты, принимающие только небраузерные ALPN вроде `acme-tls/1`, пропускаются. Правила проброса портов, передающие только UDP, не учитываются; диапазоны портов сопоставляются один к одному; выигрывает первое подходящее включённое правило. В заголовке слушателя показываются найденный порт и правило, из которого он взят, а поле **Адрес доступа** использует его как подсказку; порт доступа, указанный вручную, по-прежнему имеет приоритет. Если посетители приходят через проброс порта на роутере, frp или CDN (или правило передаёт трафик на LAN-адрес этого хоста), внешние схема и порт могут отличаться от слушателя; укажите их в поле **Адрес доступа** слушателя (например, https и 443, когда CDN забирает данные по http с порта 8080). Адрес доступа влияет только на ссылки, его изменение не перезапускает слушатель. При сохранении домены приводятся к виду, в котором их отправляют браузеры: нижний регистр, IPv6 без квадратных скобок, интернационализированные домены в punycode (`中文.com` сохраняется как `xn--fiq228c.com`); значения, которые никогда не совпадут, например с портом, путём или `@`, отклоняются. При импорте из Lucky или nginx пропускаются только неверные домены, о чём выводится предупреждение.

Сайту можно задать «Группу» (до 64 символов; сайт по умолчанию в группу не входит). В каждом слушателе список показывает группы как сворачиваемые разделы: группы идут в порядке первого появления, сайты без группы — после них, а сайт по умолчанию всегда последний. Свёрнутое состояние каждой группы хранится в браузере. Нажмите «Сортировка и пакет», чтобы перейти в режим сортировки: в нём сайты можно перемещать вверх и вниз, перетаскивать внутри группы, перемещать группы целиком и менять порядок слушателей. Порядок влияет только на список: домены сопоставляются по приоритету, описанному выше, независимо от порядка сайтов, а сохранение нового порядка заменяет список сайтов на месте, без разрыва соединений. Поле поиска вверху страницы фильтрует сайты по домену, имени, группе, бэкенду или примечанию; на время поиска свёрнутые карточки слушателей автоматически раскрываются.

В режиме сортировки можно также отметить несколько сайтов (флажок в заголовке группы выбирает всю группу). Перетаскивание любого отмеченного сайта перемещает их все, а если отпустить их на сайте или заголовке другой группы, они перейдут в эту группу. Панель инструментов сразу переносит отмеченные сайты в указанную группу, а при пустом имени убирает их из группы; отмеченные сайты разных слушателей сохраняются по каждому слушателю.

Наведите указатель на заголовок группы и нажмите карандаш, чтобы переименовать её: все элементы получают новое имя и сохраняют место и порядок. Если выбрать имя существующей группы, после подтверждения группы объединятся.

### Перенос сайтов {#move-sites}

Сайт можно перенести в другой слушатель вместе со всеми настройками:

- При редактировании сайта измените поле **Слушатель**; при сохранении сначала сохраняются изменения, затем сайт переносится. При добавлении сайта это поле определяет, в каком слушателе он будет создан.
- В режиме сортировки отметьте сайты (в том числе из разных слушателей), нажмите **Перенести в слушатель** на панели инструментов и выберите целевой слушатель и группу (по умолчанию каждый сайт сохраняет свою группу). Сайты ставятся в конец целевого слушателя или в конец выбранной группы; сайты, уже находящиеся в целевом слушателе, не меняются.
- В режиме сортировки перетащите сайты выше или ниже сайта другого слушателя, чтобы вставить их в это место и в его группу, или на заголовок группы, чтобы поставить их в конец этой группы. Во время перетаскивания у слушателей без обычных сайтов появляется область для сброса. После сброса запрашивается подтверждение.

Каждый перенос выполняется одним запросом: исходный и целевой слушатели перезагружаются по одному разу, их списки сайтов заменяются на месте, поэтому соединения с другими сайтами не разрываются. Если в целевом слушателе уже есть сайт с тем же доменом, перенос отклоняется и ни один слушатель не меняется; сайт по умолчанию принадлежит своему слушателю и не переносится. Если ключ сайта в целевом слушателе уже занят, сайт получает новый ключ, а правила оповещений мониторинга производительности, ссылающиеся на сайт, обновляются. Сессии входа разделены по слушателям и сайтам, поэтому после переноса вошедшим посетителям придётся войти снова; счётчики использования ссылок общего доступа переносятся вместе с сайтом, так что ограниченная ссылка не станет снова действительной; статистика и активные соединения сайта начинаются заново. При переносе сайта со входом из HTTPS-слушателя в слушатель с открытым HTTP выводится предупреждение о том, что пароли и cookie входа будут передаваться без шифрования.

### Пакетные операции

Отметьте сайты в режиме сортировки (можно в разных слушателях), и панель инструментов предложит пакетные операции, описанные ниже. Каждая операция отправляется за один раз: изменения сохраняются, только если все сайты прошли проверку; если хотя бы один не прошёл, ничего не меняется, и указывается, какой сайт вызвал ошибку. Каждый затронутый слушатель перезагружается один раз и заменяет список сайтов на месте, без разрыва соединений.

- **Включить / Отключить**: сайты, уже находящиеся в нужном состоянии, остаются как есть.
- **Удалить**: удаляет отмеченные сайты после подтверждения; сайт по умолчанию удалить нельзя.
- **Домены пакетно**:
  - Добавить домены: по одному в строке (можно и через запятую); домены, которые у сайта уже есть, пропускаются, новые добавляются в конец;
  - Убрать домены: сопоставление по полному домену; домены, которых у сайта нет, игнорируются, и у сайта нельзя убрать все домены;
  - Заменить основной домен: меняет суффикс домена на новый. Заменяются сам исходный домен и его поддомены (включая шаблон `*.исходный-домен`); например, при замене `old.com` на `new.com` домен `www.old.com` становится `www.new.com`. Дубликаты после замены объединяются, сайты без совпадений не меняются.

  Новый домен отклоняется, если он окажется у нескольких сайтов одного слушателя, так как внутри слушателя с ним сможет совпасть только первый из этих сайтов; разные слушатели могут использовать один и тот же домен.
- **Опции пакетно**: пакетно включает или выключает Сжатие, Журнал доступа, CORS, Пересылаемые заголовки и Разрывать соединение при отказе, а также задаёт или снимает WAF. Пункты со значением «Не менять» сохраняют собственную настройку каждого сайта. Настройки, влияющие на доступ, например аутентификация, контроль доступа и адреса бэкендов, меняются для каждого сайта отдельно.
- **Перенести в слушатель**: переносит отмеченные сайты в другой слушатель, см. [Перенос сайтов](#move-sites).

Соответствующий эндпоинт — `POST /api/webservice/sites/batch` с телом `{"sites": [{"listener": "ключ слушателя", "site": "ключ сайта"}], "action": "...", ...}`. `action` принимает значения `enable`, `disable`, `delete`, `addDomains`, `removeDomains` (вместе с `domains`), `replaceDomain` (вместе с `from` и `to`) или `set` (вместе с `options`, где допускаются только перечисленные выше поля опций). В ответе указано число изменённых сайтов и число сайтов, которым изменения не понадобились. Один запрос обрабатывает до 500 сайтов и 100 доменов. Сами слушатели также поддерживают общие `PUT /api/webservice/listeners-enable` и `POST /api/webservice/listeners-delete`. Для `move` цель задаётся в `move`, например `{"listener": "ключ целевого слушателя"}`, при необходимости с `group` (группа для сайтов; пустая строка — без группы, без поля каждый сайт сохраняет свою группу) или `before` / `after` (ключ сайта в целевом слушателе, перед или после которого вставить, с переходом в его группу). Поле `moved` в ответе перечисляет ключи каждого сайта до и после переноса.

## Типы сайтов

| Тип | Описание |
| --- | --- |
| Обратный прокси | Пересылает запросы на один или несколько бэкендов; адрес бэкенда имеет вид `http(s)://хост:порт`, поддерживается WebSocket |
| Редирект | Перенаправление на полный URL с кодом 301 / 302 / 307 / 308 (по умолчанию 302), можно сохранять исходный путь и строку запроса. В URL можно использовать `{host}`, который заменяется доменом, использованным посетителем: `https://{host}` вместе с «Сохранять путь» направляет все HTTP-запросы на HTTPS того же домена. Также доступны переменные `{path}`, `{1}`, `{STUN_ИмяПравила_PORT}` и другие; см. [Переменные редиректа](#redirect-vars). |
| Статические файлы | Каталог должен быть абсолютным путём; при выключенном «списке каталогов» запрос каталога возвращает ответ только если в нём есть `index.html`. «URL без расширения» пробует `путь.html` и `путь/index.html`, если файл не найден (для VitePress и подобных генераторов, аналог `try_files $uri $uri.html $uri/index.html` в nginx). «Страница 404» — путь внутри каталога, например `404.html`, возвращается с кодом 404 |
| Панель навигации | Показывает панель из библиотеки [панелей навигации](#nav-panel): ссылки на ваши сервисы по группам на одной странице; посетителям из локальной сети автоматически даются локальные адреса |
| Фиксированный текст | Произвольное содержимое, `Content-Type` (по умолчанию `text/plain; charset=utf-8`) и код состояния (100-599, по умолчанию 200) |
| Закрыть соединение | Ничего не отправляет и закрывает соединение, как `return 444` в nginx. Обычно используется как сайт по умолчанию, чтобы запросы, перебирающие неизвестные домены, не получали ответа; в журнале доступа они записываются с кодом 444; аутентификация, контроль доступа, WAF и перезапись не применяются, остальные настройки сайта не действуют |

Для сайтов любого типа можно настроить журнал доступа, CORS, собственные заголовки запроса и ответа (по одному `Key: Value` в строке; пустой Value удаляет заголовок), а также подключить экземпляр [брандмауэра WAF](/ru/docs/modules/waf) (если экземпляр не существует или отключён, запросы пропускаются). Как редактировать заголовки запроса, заголовки ответа и Content-Type, см. в разделе [Заголовки запроса и ответа](#headers).

Записи журнала доступа содержат IP клиента, метод, домен и путь, код состояния, время обработки и имя сайта, а в конце строки — Referer и User-Agent в формате nginx (`-`, если их нет), поэтому разные устройства за одним внешним IP можно различить по User-Agent. Журнал можно фильтровать по сайту, коду состояния, IP источника и другим условиям; см. [просмотр и фильтрация журналов работы](/ru/docs/guide/configuration#log-filter).

### Переменные редиректа {#redirect-vars}

В адресе назначения сайта-редиректа можно использовать следующие переменные:

| Переменная | Значение |
| --- | --- |
| `{host}` | Домен, запрошенный посетителем, без порта; IPv6-адрес — в квадратных скобках, например `[2001:db8::1]` |
| `{port}` | Порт, на который пришёл запрос |
| `{hostAndPort}` | Домен и порт, как в Host запроса |
| `{path}` / `{PATH}` | Путь запроса; `{PATH}` без начального `/` |
| `{args}` / `{Args}` | Строка запроса; `{args}` с начальным `?` (пусто, если строки запроса нет), `{Args}` без него |
| `{domainPartN}` / `{pathPartN}` | N-я часть домена (разделитель `.`) или пути (разделитель `/`), считая с 1 |
| `{ClientIP}` / `{RemoteIP}` | IP клиента |
| `{time}` | Текущее время в формате `2006-01-02 15:04:05`; пробел записывается как `%20` (`2006-01-02%2015:04:05`), чтобы адрес перенаправления оставался корректным URL |
| `{1}` | Часть, совпавшая с `*` в домене сайта вида `*.example.com`; пусто при точном совпадении домена, весь домен при совпадении с `*` или сайтом по умолчанию |
| `{STUN_ИмяПравила_PORT}` / `{STUN_ИмяПравила_IP}` / `{STUN_ИмяПравила_ADDR}` | Текущие публичные порт, IP и `IP:порт` правила [STUN-обхода](/ru/docs/modules/stun); имя — то, что показано в списке, может содержать подчёркивания |

- При включённом «Сохранять путь» исходный путь не добавляется, если в адресе есть `{path}`, `{PATH}` или `{pathPartN}`, а исходная строка запроса — если есть `{args}`, `{Args}` или своя строка запроса; другая часть по-прежнему добавляется;
- При смене порта STUN сайт редактировать не нужно: следующий запрос уйдёт на новый порт. Если указанное правило не существует, отключено, ещё не прошло обход или выполняет автоматический повтор, сайт возвращает 503, а причина записывается в журнал работы;
- Если после подстановки переменных в адресе нет хоста (например, `{1}` пуст из-за точного совпадения домена, а адрес — просто `https://{1}`), сайт возвращает 503; если хост посетителя содержит символы, которых не бывает в доменах, например `&`, `=`, `/` или `@`, сайт возвращает 400 и не подставляет его в адрес; если адрес использует `{host}`, `{hostAndPort}`, `{1}` или `{domainPartN}`, запросы без заголовка Host (например, проверки по HTTP/1.0) тоже получают 400;
- Домены сайта поддерживают только одну `*`, поэтому есть только `{1}`;
- Цели редиректа в правилах перезаписи пути по-прежнему поддерживают только `{host}`; неизвестные `{xxx}` остаются как есть.

Пример: CDN Cloudflare отправляет `*.example.com` на порт 2053 этой машины, а на этом слушателе есть сайт-редирект для `*.example.com` с адресом `https://{1}.v4.example.com:{STUN_web_PORT}{path}{args}`. Запрос `zly.example.com/a?b=1` перенаправляется на `https://zly.v4.example.com:<порт STUN>/a?b=1`; правило STUN web пересылает трафик на другой слушатель, где для доменов под `*.v4.example.com` созданы сайты обратного прокси.

### Параметры обратного прокси {#proxy-options}

Это «Параметры» на вкладке «Основное» редактора сайта. Значок вопроса рядом показывает краткое описание в интерфейсе и ведёт в этот раздел.

| Параметр | Что делает | Когда включать |
| --- | --- | --- |
| Не проверять сертификат бэкенда | Не проверяет сертификат при подключении к HTTPS-бэкенду | Бэкенд использует самоподписанный или просроченный сертификат, например https-порт NAS или панели роутера. Подлинность бэкенда подтвердить уже нельзя, поэтому используйте только для бэкендов в локальной сети |
| Использовать адрес бэкенда как Host | Заменяет заголовок Host, отправляемый бэкенду, на адрес бэкенда; если выключено (по умолчанию), сохраняется Host из запроса посетителя | Бэкенд принимает только свой адрес: например, отвечает 400 / 403, перенаправляет не туда или сообщает о несовпадении Host; обычно нужно при проксировании на публичные сайты и CDN. Не включайте, если бэкенд различает сайты по домену или строит ссылки с посещаемым доменом |
| Отключить повторное использование соединений | Открывает новое соединение с бэкендом для каждого запроса (Keep-Alive выключен) | Бэкенд иногда сбрасывает соединения, запросы зависают или он не поддерживает постоянные соединения. Немного увеличивает задержку, поэтому обычно не включайте |
| Добавлять X-Forwarded-* | Записывает `X-Forwarded-For` / `X-Forwarded-Proto` / `X-Forwarded-Host` / `X-Forwarded-Port` и `X-Real-IP`, сообщая бэкенду реальный IP, исходный протокол, домен и порт посетителя | Бэкенд записывает реальные IP или должен знать, что снаружи HTTPS, чтобы строить правильные ссылки (иначе может возвращать на http или зацикливаться после входа). Рекомендуется для большинства приложений |
| Отправлять бэкенду PROXY v2 | Добавляет в начало TCP-соединения заголовок протокола PROXY v2 с реальным IP клиента. При включении каждый запрос открывает новое соединение, а HTTP/2 к бэкенду не используется. Если бэкенд — Gately, включите на его слушателе приём протокола PROXY и добавьте этот хост в доверенные источники PROXY. | Бэкенд не читает HTTP-заголовки, но поддерживает протокол PROXY: другой Gately, haproxy или nginx с `proxy_protocol`. Если бэкенд не настроен на его приём, все запросы завершатся ошибкой; если не уверены, не включайте |
| Использовать посещаемый домен как SNI | Только для HTTPS-бэкендов: при рукопожатии отправляет домен посетителя и проверяет сертификат по нему, как nginx `proxy_ssl_server_name on; proxy_ssl_name $host` | Бэкенд на одном порту выбирает сертификат или маршрут по домену, например frp `vhost_https` или nginx с несколькими HTTPS-сайтами. У каждого бэкенда свой пул соединений, между доменами они не переиспользуются |
| Пересылать cookie входа Gately | Передаёт бэкенду без изменений собственные cookie входа Gately (единый вход `gately_sso`, сеанс сайта, nonce входа через стороннего провайдера); в выключенном состоянии (по умолчанию) они не отправляются бэкенду, чтобы не раскрывать учётные данные | Бэкенд — другой Gately, отвечающий за аутентификацию, а на этом сайте её нет. Например, публичный Gately только с WAF и контролем доступа проксирует на Gately в локальной сети, который выполняет веб-аутентификацию и единый вход. Недоступно, пока на сайте включена аутентификация; используйте, только если бэкенд — ваш собственный Gately |

Типичные сочетания:

- Проксирование веб-приложения в локальной сети (например, `http://192.168.1.10:5000`): включите только «Добавлять X-Forwarded-*»;
- Бэкенд — https-адрес с самоподписанным сертификатом: дополнительно включите «Не проверять сертификат бэкенда»;
- Проксирование публичного сайта или стороннего сервиса: включите «Использовать адрес бэкенда как Host»;
- Перед бэкендом стоит сервис, распределяющий по SNI (например, frp `vhost_https`): включите «Использовать посещаемый домен как SNI».
- Публичный Gately только для WAF, вход выполняет Gately в локальной сети: на публичном сайте аутентификация выключена, включите «Пересылать cookie входа Gately», а для реальных IP ещё и «Отправлять бэкенду PROXY v2»; Gately в локальной сети принимает протокол PROXY и доверяет публичному Gately.

### Заголовки запроса и ответа {#headers}

Настраиваются на вкладке «Заголовки» редактора сайта. Заголовки запроса отправляются бэкенду и действуют только для сайтов с обратным прокси; заголовки ответа возвращаются клиенту и действуют для сайтов любого типа.

- Построчное редактирование: щелчок по полю имени показывает типовые заголовки и их назначение; при выборе подставляется типовое значение, а поле значения предлагает другие типовые значения. Оба поля допускают и ручной ввод. Пустое значение удаляет заголовок, а вставленная в поле имени строка `Key: Value` автоматически разделяется;
- «Добавить типовые заголовки безопасности» добавляет `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN` и `Referrer-Policy: strict-origin-when-cross-origin`, не дублируя уже имеющиеся;
- В режиме «Текстовый режим» можно вставить сразу несколько строк `Key: Value`; при возврате к построчному редактированию содержимое сохраняется;
- Дополнительные заголовки запроса для каждого пути в «Бэкенды по путям» редактируются так же и применяются после заголовков сайта; при совпадении имени действует заголовок пути.

Под каждой строкой сразу появляется подсказка. Красный цвет означает, что сохранение не удастся или заголовок не подействует: нет имени, в имени пробелы, двоеточия или другие недопустимые символы, в текстовом режиме нет двоеточия. Оранжевый означает, что сохранить можно, но результат может отличаться от ожидаемого:

- `Host` в заголовках запроса не действует; чтобы его переписать, включите «Использовать адрес бэкенда как Host»;
- Фиксированное значение `X-Forwarded-For` или `X-Real-IP` подменяет реальный IP клиента; чтобы передать его, включите «Добавлять X-Forwarded-*»;
- `Content-Length`, `Connection`, `Transfer-Encoding` и подобными заголовками управляет соединение; ручное значение игнорируется или ломает передачу;
- Значения отправляются как есть, переменные nginx вроде `$host` не поддерживаются; заполнители вроде `<token>` в предложенных значениях нужно заменить;
- Одноимённые заголовки применяются по порядку, действует последний.

Для сайтов типа «Фиксированный текст» `Content-Type` можно выбрать из типовых вариантов или ввести вручную. Интерфейс проверяет формат `тип/подтип; параметр=значение`, предупреждает, что для `text/*` без `charset` неанглийский текст может отображаться неверно, и при пустом поле использует `text/plain; charset=utf-8`.

### Панели навигации {#nav-panel}

Пункт меню «Web → Панели навигации» (`#/webpanels`) управляет библиотекой панелей. Панель — это набор ссылок, разбитых на группы. Добавьте в веб-сервисе сайт типа «Панель навигации» и выберите панель — по корневому пути сайта (`/` или `/index.html`) откроется страница, остальные пути возвращают 404. Аутентификация, контроль доступа по IP, фильтр по странам и WAF сайта действуют как обычно. Стартовая страница обычно нужна только вам, поэтому включите веб-аутентификацию или белый список IP. Изменения панели применяются сразу после сохранения, без перезапуска слушателя.

- **Ссылки**: у ссылки есть название, группа, описание, адрес в интернете и необязательный адрес в локальной сети, значок и цвет; её можно открывать в той же вкладке или скрыть. Группы идут в порядке первого появления в списке; в редакторе группу можно целиком сдвинуть вверх или вниз. «Добавить из сайтов веб-сервиса» показывает сайты с конкретным адресом (первый домен без шаблона, со схемой и портом доступа слушателя; для слушателей за маршрутизацией по протоколу или пробросом портов — входной порт проброса) и добавляет отмеченные как ссылки, сохраняя группу сайта.
- **Другие способы доступа**: у сервиса часто несколько входов — прямой IPv6, frp, STUN, туннель Cloudflare. К каждой ссылке можно добавить до 8 способов доступа (название до 20 символов; адреса и переменные как выше). Они показываются маленькими ссылками на карточке, открываются в новой вкладке и видны посетителям и из локальной сети, и из интернета; если у переменной ещё нет значения, способ показывается зачёркнутым как недоступный. Даже когда основной адрес недоступен, другие способы доступа остаются кликабельными, а поиск учитывает их названия.
- **Адреса**: поддерживаются `http`, `https`, `ftp`, `ftps`, `sftp`, `ssh`, `smb`, `afp`, `nfs`, `vnc`, `rdp` и `mailto`; пароли запрещены. В адресах можно использовать `{host}`, `{port}`, `{hostAndPort}` (домен и порт, по которым посетитель открыл панель), `{1}`, `{domainPartN}` и `{STUN_правило_PORT}`, `{STUN_правило_IP}`, `{STUN_правило_ADDR}` в том же виде, что и [переменные перенаправления](#redirect-vars), например `https://{host}:8443` или `http://{STUN_web_ADDR}/`. Пока у правила STUN нет публичного адреса, ссылка показывается как недоступная. Переменные из пути и строки запроса, такие как `{path}` и `{args}`, использовать нельзя: иначе любой мог бы составить адрес панели со строкой запроса, меняющей цель ссылки. Пока у `{1}` нет значения (домен сайта панели не wildcard или в предпросмотре), ссылки с этой переменной показываются как недоступные. Если панель открыта по IPv6-адресу, `{host}` подставляется в квадратных скобках, например `[2001:db8::1]`.
- **Локальная сеть и интернет**: если адрес посетителя — loopback, частный (10/8, 172.16/12, 192.168/16, fc00::/7) или link-local либо входит в «Дополнительные локальные адреса» панели (например, `100.64.0.0/10` для Tailscale), ссылки используют локальный адрес; ссылки без него остаются с адресом в интернете. За CDN или обратным прокси настройте [доверенные прокси](#real-ip), иначе адресом посетителя будет адрес прокси. Если у какой-либо ссылки есть локальный адрес, посетитель может переключить локальную сеть и интернет в правом верхнем углу; выбор хранится в cookie, «Автоопределение» возвращает автоматический режим.
- **Определение локальной сети и видимость**: локальная сеть или интернет определяется по прямому адресу посетителя. Если посетители из интернета приходят через frpc, cloudflared или проброс портов Docker на этой машине, прямым адресом будет эта машина или сеть контейнеров, и они считаются посетителями из локальной сети. В таких схемах пусть пересылающая сторона отправляет заголовок PROXY, а на слушателе включён протокол PROXY; при HTTP-прокси настройте [доверенные прокси](#real-ip). Локальные адреса видны всем, кто может открыть панель, и любой посетитель может переключиться на локальный вид через `?net=lan`; чтобы скрыть локальные адреса, включите для сайта аутентификацию или контроль доступа по IP.
- **Значки**: эмодзи или текст до 8 символов, адрес изображения `http(s)` или загруженное изображение (PNG, JPEG, GIF и WebP уменьшаются до 128 пикселей, SVG и ICO сохраняются как есть; до 96 КБ каждое и до 3 МБ на панель). Если пусто, показывается первая буква названия. У текстового значка можно выбрать цвет фона; если пусто, он выбирается по названию. Кнопка «Выбрать» открывает встроенные значки: модули Gately и связанные инструменты (frp, Tailscale, NetBird, Cloudflare), приложения (Jellyfin, Home Assistant, qBittorrent), системы (OpenWrt, Synology, Proxmox) и общие значки вроде маршрутизатора и сервера (значки брендов — из Simple Icons, общие — из Lucide); сохраняются как `builtin:id`. Встроенный значок рисуется на плитке его собственного цвета; цвет можно изменить, на светлом фоне рисунок становится тёмным.
- **Страница**: заголовок (если пуст — название панели), подзаголовок, значок страницы и тема (как в системе, светлая, тёмная). На странице есть поиск: `/` переводит фокус в поле, ключевые слова разделяются пробелами и ищутся в названиях, описаниях, адресах и группах; Enter открывает первый результат, `Esc` очищает. Предпросмотр в редакторе строит страницу для посетителя из интернета или локальной сети, `{host}` заменяется доменом панели управления.
- **Безопасность**: страница формируется на сервере, названия и описания экранируются. Выполняются только встроенные стили и скрипт со случайным nonce (`Content-Security-Policy`), другие сайты не могут встроить страницу, изображения значков загружаются с `no-referrer`. Страница зависит от адреса посетителя, поэтому ответы содержат `Cache-Control: no-store`.

В одном экземпляре может быть до 50 панелей, по 500 ссылок в каждой; панель, которую использует сайт, удалить нельзя. Учётные записи и токены только для чтения могут просматривать панели. API: `GET|POST /api/webservice/panels`, `PUT|DELETE /api/webservice/panels/{key}`, `PUT /api/webservice/panels/{key}/enable` и `POST /api/webservice/panels/preview`.

## Транспорт и протоколы

- HTTPS: используется сертификат из модуля [SSL-сертификатов](/ru/docs/modules/ssl), покрывающий домен;
- HTTP на том же порту: прослушивание с HTTPS может принимать и незашифрованный HTTP, протокол определяется по первому байту соединения. «Перенаправлять на HTTPS» отправляет `http://хост:порт` на `https://хост:порт` (301 для GET/HEAD, 308 для остальных методов) — удобно, когда доступен только один порт, а посетители могут ошибиться схемой; «Обслуживать» отвечает по незашифрованному HTTP. Проверки ACME HTTP-01 обрабатываются как обычно, изменение параметра перезапускает прослушивание;
- HTTP-порт: к слушателю можно добавить открытый HTTP-порт (например, 80 рядом с HTTPS-слушателем на 443), который использует все сайты и настройки основного порта, — отдельный слушатель для HTTP с теми же сайтами не нужен. При включённом HTTPS выберите «Перенаправлять на HTTPS» (по умолчанию) или «Обслуживать»: перенаправление сохраняет домен, путь и строку запроса посетителя и подставляет порт из «Адреса доступа» (если пусто — порт прослушивания, 443 опускается), с кодом 301 для GET/HEAD и 308 для остальных методов; «Обслуживать» отвечает по HTTP, это удобно при переключении между `http://` и `https://`. Проверки ACME HTTP-01 по-прежнему обрабатываются, PROXY-протокол и автоматическое открытие брандмауэра действуют и на этот порт. Если HTTP-порт занят, основной порт продолжает работать, а в состоянии слушателя показана причина;
- HTTP/3 (QUIC): включается в прослушивании с HTTPS; на том же номере порта по UDP дополнительно обслуживается HTTP/3, а браузерам он объявляется заголовком ответа `Alt-Svc`; разрешите этот UDP-порт в брандмауэре и пробросе портов;
- WebSocket: обратный прокси поддерживает его автоматически;
- Протокол PROXY: слушатель может принимать заголовки PROXY от вышестоящих компонентов (haproxy, frp и т. п.) и доверяет только IP или подсетям из списка «Глобальные настройки → Доверенные источники PROXY»; пустой список означает, что источникам не доверяют. Обратный прокси может отправлять заголовок PROXY бэкенду. `X-Forwarded-Proto: https` в соединениях от доверенного источника тоже учитывается: cookie сеанса получают Secure, порты с перенаправлением открытого HTTP больше не перенаправляют, а при включённом «Добавлять X-Forwarded-*» бэкенду передаётся https.

### Реальный IP посетителя (за CDN / WAF) {#real-ip}

Когда сайт находится за HTTP-прокси, например Cloudflare, Alibaba Cloud CDN или Tencent Cloud CDN, соединения приходят с адресов прокси, обращающихся к источнику. Укажите доверенные прокси (IP или диапазоны прокси, можно нескольких поставщиков) в **Глобальные настройки → Реальный IP посетителя** и выберите заголовки реального IP. Тогда Gately берёт адрес посетителя из заголовков запроса и использует его в журналах доступа, списках разрешённых/запрещённых IP, доступе только из LAN, фильтре по странам, блокировках за ошибки аутентификации, статистике, обнаружении сканирования путей и в передаваемых бэкендам `X-Real-IP` / `X-Forwarded-For`.

- Заголовки читаются, только если исходный узел — доверенный прокси. Исходный узел — адрес после обработки протокола PROXY: для соединений от доверенного источника PROXY это адрес из заголовка PROXY, иначе TCP-узел. Заголовки клиентов, подключившихся напрямую, всегда игнорируются;
- Заголовки проверяются в выбранном порядке, используется первый с корректным адресом; если ничего не выбрано — `X-Forwarded-For`. Многозначные заголовки, такие как `X-Forwarded-For`, читаются справа налево с пропуском доверенных прокси, берётся первый недоверенный адрес, поэтому подделанные клиентом значения слева не используются;
- Выбирайте только заголовки, которые ваш прокси перезаписывает. Например, Cloudflare перезаписывает `CF-Connecting-IP`, а другие прокси часто пропускают одноимённый заголовок клиента без изменений; там надёжнее `X-Forwarded-For`;
- При работе через Cloudflare рекомендуется выбрать заголовок реального IP `CF-Connecting-IP`: Cloudflare записывает в него адрес посетителя напрямую. `X-Forwarded-For` читается справа налево с пропуском доверенных прокси, поэтому если в доверенные прокси внесены целые диапазоны Cloudflare, запрос, отправленный через собственный выход Cloudflare (например, Workers), может нести слева подделанный адрес;
- `0.0.0.0/0` и `::/0` отклоняются при сохранении;
- Если маршрутизация по протоколу передаёт соединения веб-сервисам через loopback, включите в ней отправку заголовка PROXY, а на слушателе — его приём, вместо добавления `127.0.0.1` в доверенные прокси; иначе посетители, подключающиеся напрямую к маршрутизации по протоколу, смогут подделать заголовки. Сквозные маршруты маршрутизации по протоколу остаются чистой TCP-пересылкой и не затрагиваются;
- Запросы от доверенного прокси с `X-Forwarded-Proto: https` считаются HTTPS;
- Без доверенных прокси поведение не меняется. Блокировки на уровне соединений (правила брандмауэра от защиты от вторжений) действуют на TCP-источник и не влияют на посетителей за CDN; собственные блокировки веб-сервисов применяются к реальному адресу.

## Аутентификация

Настраивается на вкладке «Безопасность» в окне редактирования сайта:

- Веб-аутентификация: браузер показывает страницу входа;
- Базовая аутентификация: HTTP Basic;
- Пользователи: по одному `имя_пользователя:пароль` в строке, пароль может быть bcrypt-хешем. Для базовой аутентификации нужен хотя бы один пользователь; для веб-аутентификации нужен хотя бы один пользователь или сторонняя учётная запись;
- Вход через сторонние сервисы: поддерживаются GitHub, Google, QQ, OIDC с вашими собственными OAuth-приложениями. Разрешённые учётные записи указываются по одной в строке в формате `идентификатор_провайдера:аккаунт`, например `github:octocat`, `google:me@gmail.com`; в конце строки можно добавить примечание после `#`, а `github:*` разрешает любой аккаунт этого провайдера.

Провайдеры входа через сторонние сервисы настраиваются в «Глобальных настройках»: укажите собственные Client ID / Secret и включите провайдера, а также задайте адрес обратного вызова (он должен обслуживаться одним из слушателей Gately, например `https://auth.example.com`). URL обратного вызова, который нужно зарегистрировать в GitHub / Google / QQ:

```text
https://auth.example.com/__gately_auth/oauth/callback
```

Вход через сторонние сервисы для самой панели управления настраивается отдельно в разделе «Настройки → Аккаунт и безопасность».

### Внешняя аутентификация (Authelia и подобные)

Передаёт аутентификацию внешнему сервису, как `auth_request` в nginx или `forwardAuth` в Traefik. Отметьте «Внешняя аутентификация» на вкладке «Безопасность». Её нельзя сочетать с базовой или веб-аутентификацией на одном сайте.

| Поле | Описание |
| --- | --- |
| `url` | Адрес проверки, например `http://127.0.0.1:9091/api/authz/auth-request` для Authelia |
| `loginUrl` | Куда отправить посетителя, когда сервис отвечает 401, например `https://auth.example.com/?rd={url}&rm={method}`. `{url}` — исходный адрес (с URL-кодированием), `{method}` — метод запроса. Если пусто, ответ сервиса возвращается как есть |
| `loginFromLocation` | Если `loginUrl` пуст, а сервис отвечает 401 с единственным абсолютным http(s)-адресом в `Location`, посетитель перенаправляется туда с кодом 302, `Set-Cookie` и `Cache-Control` передаются вместе с ним. Для сервисов, которые отдают в 401 динамический адрес входа, например родной `/api/forward-auth` в Casdoor; `Location` другого вида игнорируется, и 401 возвращается как есть. По умолчанию выключено |
| `copyHeaders` | Заголовки личности, которые копируются из ответа сервиса в запрос к бэкенду; по умолчанию `Remote-User`, `Remote-Groups`, `Remote-Email` и `Remote-Name` |

Как это работает:

- каждый запрос сначала отправляется на `url` как GET без тела, с заголовками посетителя (cookie, `Authorization` и т. д.) плюс `X-Original-Method`, `X-Original-URL`, `X-Forwarded-Method`, `X-Forwarded-Proto`, `X-Forwarded-Host`, `X-Forwarded-Uri`, `X-Forwarded-For` и `X-Real-Ip`. Таймаут — 10 секунд;
- ответ 2xx пропускает запрос, добавляя заголовки личности; ответ 401 перенаправляет на `loginUrl` (код 302); другие ответы, например 403 или редирект, возвращаются посетителю; если сервис недоступен, возвращается 502;
- заголовки личности, присланные посетителями, всегда удаляются, поэтому их нельзя подделать;
- работает с правилами путей и «Областью аутентификации», так что вход требуется только для части путей (например, `/admin`), а также с временными ссылками для доступа.

### Общие пользователи: TOTP и единый вход {#shared-users}

Определите учётные записи один раз и используйте их на нескольких сайтах, при желании с двухэтапной проверкой TOTP. Это покрывает то, ради чего многие запускают Authelia.

На странице «Веб → Пользователи входа» в боковой панели (в диалоге глобальных настроек веб-сервиса показываются только сводка и ссылка):

- добавляйте пользователей с именем и паролем. Пароли хранятся в виде хешей bcrypt и никогда не возвращаются через API. Чтобы добавить TOTP, нажмите «Включить TOTP», отсканируйте QR-код приложением-аутентификатором (Google Authenticator, 1Password и т. д.) и сохраните. Повторное создание ключа делает прежний недействительным;
- При желании укажите e-mail, отображаемое имя и группы; [единый вход OIDC](/ru/docs/modules/oidc) передаёт их приложениям как утверждения `email`, `name` и `groups`, а в разрешённых пользователях клиента OIDC можно разрешать доступ группе через `group:имя`;
- домен единого входа, например `example.com`: после входа на любом сайте этого домена или его поддоменов остальным сайтам повторный вход не нужен. Используется cookie родительского домена (`gately_sso`, действует 7 дней), которая никогда не передаётся бэкендам. Оставьте поле пустым, чтобы входить на каждом сайте отдельно.

На сайте отметьте «Использовать общих пользователей» рядом с веб- или базовой аутентификацией. Собственные пользователи сайта продолжают работать. Сайты можно отметить и массово в списке сайтов на странице «Пользователи входа», сгруппированном по слушателям и с фильтром: при выборе сайта без аутентификации также включается веб-аутентификация; если снять отметку с сайта, который проверяет только общих пользователей, он помечается «Аутентификация отключится», а при сохранении такие сайты показываются для подтверждения; после подтверждения их аутентификация отключается и они становятся доступны без входа; сайты с внешней аутентификацией не могут использовать общих пользователей. Изменения пользователей, OIDC и сайтов на странице применяются вместе по кнопке «Сохранить» внизу; если хоть одно не проходит проверку, ничего не сохраняется, а при уходе со страницы с несохранёнными изменениями сначала запрашивается подтверждение.

Поведение:

- страница входа показывает поле кода подтверждения, если TOTP включён хотя бы у одного общего пользователя. Каждый код действует один раз;
- смена пароля или ключа TOTP пользователя завершает его сессии;
- базовая аутентификация принимает только общих пользователей без TOTP, потому что в окне запроса пароля браузера негде ввести код;
- неудачные попытки учитываются в том же ограничении частоты и автоблокировке, что и другие входы.

Чтобы Gitea, OpenList, Grafana и другие приложения знали, какой пользователь вошёл, предоставьте им общих пользователей через [единый вход OIDC](/ru/docs/modules/oidc).

### Самостоятельная смена пароля {#self-service-password}

Включите «Самостоятельная смена пароля» на странице «Пользователи входа», и общие пользователи смогут менять пароль сами, без администратора:

- Откройте `https://домен-сайта/__gately_auth/password` на сайте с включённым «Использовать общих пользователей»; на странице входа также появится ссылка «Сменить пароль». Пользователи [единого входа OIDC](/ru/docs/modules/oidc) могут открыть `/__gately_oidc/password` на домене издателя;
- Введите имя пользователя, текущий пароль и дважды новый (от 8 до 128 символов, отличный от текущего); пользователи с TOTP также вводят код подтверждения;
- После смены все сеансы пользователя на сайтах сразу завершаются, и он входит заново с новым паролем; выданные токены обновления OIDC отзываются, а старые Access Token больше не позволяют читать данные пользователя; токены, которые приложения проверяют сами, действуют до истечения срока, а собственные сеансы входа приложений сохраняются;
- После успешной смены та же учётная запись не может снова сменить пароль в течение 1 минуты, чтобы повторные смены не заставляли FTP и SMB постоянно перезагружаться и обрывать чужие подключения; если проверка службы отклоняет сохранение, подробная причина записывается только в журнал веб-сервиса, а страница лишь предлагает обратиться к администратору;
- Неверный текущий пароль или код учитываются в том же ограничении попыток и автоматической блокировке, что и неудачные входы, а формы, отправленные с других сайтов, отклоняются; журнал веб-сервиса фиксирует пользователя и IP-адрес источника;
- На той же странице можно сменить пароль [общих пользователей файловых служб](/ru/docs/modules/tools#shared-users). У каждого типа учётных записей свой переключатель; если включены оба, на странице выбирается тип учётной записи. Одноимённые учётные записи разных типов не влияют друг на друга.

## Контроль доступа

### Белые и чёрные списки IP

В блоке «Контроль доступа по IP» на вкладке «Безопасность» сайта можно выбрать: выключено, белый список или чёрный список; в списке по одному IP или подсети в строке (например, `192.168.1.0/24`); дополнительно можно ссылаться на подписные списки IP.

### При отказе

Параметр **При отказе** на вкладке «Безопасность» сайта определяет, что делать с запросами, отклонёнными блокировкой, контролем доступа по IP (включая правила путей) или фильтром стран: по умолчанию **Вернуть 403**; **Закрыть соединение** ничего не отправляет и обрывает запрос, в журнале доступа — 444, как у сайта «Закрыть соединение». Вместе с белым списком это пропускает ваши IP и обрывает всех остальных. Ограничение частоты (429) и блокировки WAF не меняются.

Сайт по умолчанию настраивается так же: тип **Обратный прокси** с бэкендом, белый или чёрный список в «Контроль доступа по IP» (можно использовать подписные списки IP, описанные ниже) и **При отказе** — **Закрыть соединение**. Запросы из белого списка или вне чёрного списка проксируются на бэкенд, остальные обрываются; обновлённый подписной список действует сразу. У типа сайта «Закрыть соединение» нет бэкенда, он обрывает все запросы.

Закрытие соединения — и как тип сайта, и как действие при отказе — лишь не отдаёт HTTP-ответ и не скрывает, что сервис работает:

- рукопожатие TCP уже завершено, клиент знает, что порт слушает;
- в HTTP/1.x соединение закрывается, а в HTTP/2 и HTTP/3 сбрасывается только запрос, соединение остаётся открытым и может использоваться повторно;
- в HTTPS домены без сертификата отсекаются ещё на рукопожатии TLS, поэтому запросы, дошедшие до сайта по умолчанию, уже получили сертификат и указанные в нём домены.

Чтобы сканеры дальше видели только тайм-ауты, заблокируйте их адреса в [защите от вторжений](/ru/docs/modules/guard); при синхронизации с брандмауэром их трафик отбрасывается в ядре.

### Подписные списки IP

Списки добавляются в «Глобальные настройки → Подписные списки IP»: укажите URL и интервал обновления (по умолчанию 24 часа). Если адрес загрузки (например, GitHub) напрямую недоступен, в поле «Прокси для загрузки» выберите глобальный прокси обновлений или укажите адрес прокси. Gately периодически скачивает список и кеширует его в каталоге конфигурации, поэтому после перезапуска он доступен без сети. Содержимое — по одному IP, CIDR или диапазону `начало-конец` в строке; всё после `#`, `;` или `//` считается комментарием. Например, для диапазонов IP провинций и городов Китая подходит [metowolf/iplist](https://github.com/metowolf/iplist): `https://metowolf.github.io/iplist/data/cncity/440000.txt` (провинция Гуандун).

- Белые и чёрные списки сайтов и правил путей могут ссылаться на несколько подписных списков; они проверяются вместе с введёнными вручную диапазонами, и совпадение с любым означает попадание в список;
- если скачанное содержимое не распознано (например, вместо списка пришла страница ошибки), сохраняется прежний список, причина показывается у списка, а повторная попытка выполняется через час;
- пока список не загружен, он считается пустым: белый список запрещает доступ, а чёрный ничего дополнительно не блокирует;
- если отключить список, на который есть ссылки, ссылающиеся на него белые списки запрещают все источники, а чёрные перестают что-либо блокировать;
- удаление списка, на который есть ссылки, отклоняется.

### Правила путей

В блоке «Правила путей» на вкладке «Безопасность» настройки аутентификации и IP сайта можно переопределять по префиксу пути:

| Поле | Значения |
| --- | --- |
| `prefix` | Префикс пути, начинающийся с `/`, например `/admin` |
| `auth` | Как у сайта (пусто), `off` (аутентификация не нужна), `on` (аутентификация обязательна) |
| `ipMode` / `ipList` | Как у сайта (пусто), `whitelist`, `blacklist`, плюс список IP или подсетей |

Правила сопоставления:

- приоритет у самого длинного префикса;
- сопоставление идёт по границам сегментов пути: `/admin` совпадает с `/admin` и `/admin/x`, но не с `/administrator`;
- путь запроса сначала нормализуется (убираются `.`, `..` и повторяющиеся слэши), поэтому `/public/../admin` обрабатывается как `/admin`;
- для одного префикса можно задать только одно правило.

Параметр «Область аутентификации» (`authOptional`): если он включён, аутентификация действует только для путей, помеченных в правилах как «аутентификация обязательна», а остальные пути открыты. Для этого параметра сначала нужно включить базовую или веб-аутентификацию.

### Временные ссылки для доступа

После включения базовой или веб-аутентификации для сайта можно создавать ссылки для доступа, чтобы гости заходили без учётной записи:

| Поле | Описание |
| --- | --- |
| Название | Примечание, например «Для Ивана» |
| Срок действия | Пусто — бессрочно |
| Число использований `maxUses` | Сколько раз ссылку можно активировать, 0 — без ограничений; счётчик сбрасывается при перезапуске |
| Ограничение пути `pathPrefix` | Если задано, ссылка даёт доступ только к путям с этим префиксом; должен начинаться с `/` |

Гость открывает `https://домен/любой/путь?_gs=токен` и получает сессию. После успешной активации сервер выставляет cookie для входа без пароля и перенаправляет на адрес без параметра `_gs`; сессия действует не более 24 часов и не дольше срока действия ссылки. Недействительный токен обрабатывается как обычный запрос, причина отказа не раскрывается. После удаления ссылки уже выданные сессии сразу становятся недействительными. Токен генерируется после сохранения (не короче 16 символов), полную ссылку можно скопировать в интерфейсе.

### Ограничение попыток аутентификации и автоматическая блокировка

- Если с одного IP-адреса за 15 минут накапливается 10 неудачных попыток аутентификации, дальнейшие попытки временно отклоняются;
- в «Глобальные настройки → Автоблокировка → Блокировка при ошибках аутентификации» укажите число минут (от 0 до 43200): при 10 неудачных попытках IP-адрес источника блокируется; 0 означает отсутствие блокировки, только ограничение частоты;
- при срабатывании автоблокировки публикуется событие `AuthBanned`, которое можно отправить через [центр уведомлений](/ru/docs/modules/notify);
- IPv6-адреса учитываются и блокируются по подсетям /64.

### Список блокировок

Список блокировок в «Глобальных настройках» показывает заблокированные IP, причину (повторные ошибки аутентификации или ручная блокировка) и время окончания; запись можно снять кнопкой «Разблокировать». Блокировку можно задать и вручную: укажите IP и число часов (от 1 до 720, то есть не более 30 дней); в API по умолчанию действует 24 часа. Адреса loopback и адреса доверенных прокси нельзя заблокировать вручную — причина описана ниже в разделе **Разорвать и заблокировать**. Отметьте **Навсегда**, чтобы заблокировать без срока (в API seconds равно -1).

Список блокировок общий с [защитой от вторжений](/ru/docs/modules/guard): когда этот модуль включён, здесь показывается только число блокировок и ссылка на его страницу для управления. Блокировки действуют и на переадресацию портов, STUN и другие службы, а при включённой синхронизации отбрасываются системным брандмауэром; при включённом «Игнорировать адреса локальной сети» такие адреса не блокируются автоматически.

### Фильтрация по странам (GeoIP)

В блоке «Фильтр по странам» сайта есть три режима: выключено, только разрешённые, запрещённые; укажите двухбуквенные коды стран ISO через запятую, например `CN, HK, US`. При включении нужно указать хотя бы одну страну.

- Фильтрация использует базу GeoIP, которую сначала нужно импортировать в «Глобальные настройки → База GeoIP»: загрузите файл `.mmdb` или укажите адрес для скачивания («Прокси для загрузки» по умолчанию использует глобальный прокси обновлений, а пока он не задан, соединение идёт напрямую). Поддерживаются базы стран и городов MaxMind GeoLite2, DB-IP и другие; лимит загрузки — 129 МБ;
- пока база не загружена, фильтр не действует (пропускаются все посетители), в интерфейсе отображается предупреждение;
- адреса внутренней сети пропускаются всегда;
- в режиме «запрещённые» адреса, страну которых не удалось определить по базе, пропускаются.

## Бэкенды по путям

Для сайта с обратным прокси направляет запросы с определённым префиксом пути на другие бэкенды, как `location /api/ { proxy_pass ...; }` в nginx. Добавьте их в «Бэкенды по путям» на вкладке «Основное» окна редактирования сайта.

| Поле | Описание |
| --- | --- |
| `prefix` | Префикс пути, например `/api/`. Сопоставление идёт по границам сегментов пути: `/api` и `/api/` оба совпадают с `/api` и `/api/x`, но не с `/apix` |
| `targets` | Бэкенды для этого пути, записываются так же, как бэкенды сайта. Если пусто, используются бэкенды сайта, и добавляются только заголовки ниже |
| `requestHeaders` | Заголовки запроса, добавляемые для этого пути, по одному `Key: Value` в строке. Применяются после заголовков сайта, и заголовок с тем же именем переопределяет заголовок сайта |

- приоритет у самого длинного префикса, путь передаётся без изменений (префикс не удаляется);
- остальные настройки сайта, такие как параметр Host, проверка сертификатов, заголовки forwarded, протокол PROXY, политика балансировки нагрузки и проверки работоспособности, действуют для каждого бэкенда по пути;
- сжатие, ограничение частоты, кеш и переписывание действуют на весь сайт.

## Распределение по пользователям {#user-routes}

Для сайта с обратным прокси направляет запросы каждого вошедшего пользователя на его собственные бэкенды, как `map $remote_user $backend` в nginx. Сначала на сайте нужно включить базовую, веб- или внешнюю аутентификацию. Затем добавьте правила в «Распределение по пользователям» на вкладке «Безопасность» окна редактирования сайта: в каждом правиле указывается набор пользователей и бэкенды для них, записанные так же, как бэкенды сайта.

Пользователи сопоставляются по следующим идентификаторам:

- имя пользователя сайта или [общего пользователя](#shared-users);
- для входа через сторонние сервисы — `идентификатор_провайдера:id`, например `github:octocat`; другие идентификаторы той же учётной записи тоже совпадают;
- для внешней аутентификации — `Remote-User`, скопированный из ответа сервиса аутентификации.

Маршрутизация:

- пользователи, не указанные в правилах, и не вошедшие посетители на открытых путях (путях без аутентификации) используют бэкенды сайта. Посетитель, уже вошедший через веб-аутентификацию, и на открытых путях распределяется по своей учётной записи, чтобы страницы одного приложения попадали на один бэкенд;
- приоритет у бэкендов по путям с собственными бэкендами (см. предыдущий раздел); бэкенды по путям, которые только добавляют заголовки, используют бэкенды пользователя;
- при включённом кешировании ответов в памяти ключ кеша включает выбранное правило пользователя, а если настроена [передача данных пользователя](#identity-headers), — и переданные бэкенду данные пользователя, поэтому ответы разных бэкендов и пользователей не смешиваются.

При сохранении проверяется, что на сайте включена аутентификация, в каждом правиле есть хотя бы один пользователь и допустимые бэкенды и ни один пользователь не входит в два правила. В списке сайтов у сайта с правилами по пользователям отображается метка с числом правил.

### Передача данных пользователя {#identity-headers}

«Передавать данные пользователя» передаёт бэкенду данные вошедшего пользователя в заголовках запроса — это нужно приложениям, которые узнают пользователя по заголовку; например, Firefly III определяет учётную запись по `Remote-Email`. В каждой строке выбирается поле и имя заголовка:

| Поле | Обычный заголовок | Источник |
|---|---|---|
| Имя пользователя | `Remote-User` | Имя пользователя сайта или общего пользователя; `ключ-провайдера:ID` при входе через сторонние сервисы; `Remote-User` при внешней аутентификации |
| E-mail | `Remote-Email` | E-mail общего пользователя или `Remote-Email`, скопированный внешней аутентификацией |
| Отображаемое имя | `Remote-Name` | Отображаемое имя общего пользователя или `Remote-Name`, скопированный внешней аутентификацией |
| Группы | `Remote-Groups` | Группы общего пользователя (через запятую) или `Remote-Groups`, скопированный внешней аутентификацией |

- «Добавить стандартные заголовки Remote-*» сразу добавляет строки из таблицы для полей, которые даёт текущий способ входа;
- e-mail, отображаемое имя и группы можно выбрать только на сайтах с [общими пользователями](#shared-users) или внешней аутентификацией; у пользователей сайта и при входе через сторонние сервисы есть только имя пользователя. После изменения данных общего пользователя открытые сеансы сразу передают новые значения; пользователь сайта с тем же именем, что у общего пользователя, при входе с паролем пользователя сайта передаёт только имя пользователя;
- внешняя аутентификация доверяет только скопированным заголовкам: если `Remote-Email` и подобных нет в списке копирования, такие же заголовки от посетителя никогда не считаются данными пользователя; если сервис аутентификации не вернул `Remote-User`, остальное тоже не передаётся;
- такие же заголовки от посетителя всегда удаляются, в том числе записанные с подчёркиванием вместо дефиса (например, `Remote_Email`), поэтому их нельзя подделать; посетителям без входа и пришедшим по ссылке общего доступа данные пользователя не передаются совсем, а заголовок с пустым значением не отправляется;
- при сохранении проверяется, что имена заголовков допустимы и не повторяются (без учёта регистра, `-` и `_` считаются одинаковыми), не относятся к заголовкам, влияющим на пересылку и аутентификацию (например, `Host`, `Cookie`, `Authorization`, `X-Forwarded-For`), и не совпадают с заголовками запроса сайта или правила пути, которые перезаписали бы результат аутентификации; не более 16 строк;
- «Передавать имя пользователя» из прежних версий при редактировании сайта отображается строкой с именем пользователя и после сохранения переходит в этот список.

## Расширенные возможности обратного прокси

Эти параметры находятся на вкладке «Трафик» в окне редактирования сайта.

### Бэкенды, веса и резервные серверы

В списке бэкендов один адрес в строке, после адреса можно указать параметры:

```text
http://10.0.0.2:8080 weight=3
http://10.0.0.3:8080 backup
```

- `weight=N`: вес, целое число от 1 до 100, по умолчанию 1;
- `backup`: резервный бэкенд, включается только когда недоступны все нерезервные; если недоступны вообще все, запросы снова направляются на нерезервные бэкенды.
- Если к бэкенду не удаётся подключиться (отказ в подключении, недоступность или тайм-аут подключения), тот же запрос сразу повторяется на следующем бэкенде: сначала на других основных, затем на резервных, не более чем на 3 бэкендах. В этот момент запрос ещё не отправлен, поэтому повторная отправка POST и подобных запросов безопасна. Ошибки после установления соединения не повторяются, а сбойный бэкенд по-прежнему учитывается пассивной проверкой.

### Политика балансировки нагрузки

| Пункт интерфейса | `lbPolicy` | Описание |
| --- | --- | --- |
| Round-robin (с учётом весов) | пусто | По умолчанию |
| Случайный (с учётом весов) | `random` | |
| Хеш по IP (привязка сессии) | `ip_hash` | Один и тот же IP клиента попадает на один бэкенд |
| Наименьшее число соединений | `least_conn` | Выбирается минимум «число соединений / вес» |

### Проверки работоспособности

Активная проверка по умолчанию выключена. Поля после включения и их значения по умолчанию:

| Поле | По умолчанию | Диапазон |
| --- | --- | --- |
| Метод `mode` | `http` | `http` (запрос по пути проверки, код ниже 400 считается здоровым) или `tcp` (только проверка соединения) |
| Путь `path` | `/` | Начинается с `/`, только для метода http |
| Интервал `interval` | 10 секунд | от 1 до 3600 |
| Таймаут `timeout` | 3 секунды | от 1 до 60 |
| Подряд неудач `fails` | 3 — признаётся недоступным | от 1 до 20 |
| Подряд успехов `passes` | 2 — восстанавливается | от 1 до 20 |

Если включена отправка протокола PROXY бэкенду, HTTP-проверка автоматически заменяется на TCP.

Пассивная проверка действует всегда: из нескольких бэкендов тот, на котором 3 раза подряд не удалось установить соединение, приостанавливается на 30 секунд, после чего его пробуют снова (единственный бэкенд без активной проверки из ротации не исключается). Если включена активная проверка, восстановление определяется только её результатами. При изменении состояния бэкенда публикуются события «upstream недоступен» / «восстановлен», которые можно отправить через [центр уведомлений](/ru/docs/modules/notify).

### Тайм-ауты бэкенда {#backend-timeouts}

Тайм-ауты подключений сайта обратного прокси к его бэкендам, в секундах; 0 — значение по умолчанию. Бэкенды по путям и по пользователям используют те же настройки.

| Поле | По умолчанию | Диапазон | Назначение |
| --- | --- | --- | --- |
| Подключение `timeouts.connect` | 10 с | 1–300 | Установка TCP-соединения с бэкендом |
| TLS-рукопожатие `timeouts.tlsHandshake` | 10 с | 1–300 | Завершение TLS-рукопожатия с HTTPS-бэкендом |
| Заголовки ответа `timeouts.responseHeader` | Без ограничения | 1–86400 | Ожидание заголовков ответа бэкенда после отправки запроса вместе с телом |

- Тайм-аут заголовков ограничивает только ожидание до их прихода; тело ответа, загрузка файлов и долгие соединения вроде WebSocket и SSE после этого не затрагиваются. При загрузке больших файлов отсчёт начинается после полной отправки тела запроса;
- При превышении возвращается 504 (Gateway Timeout), другие ошибки, например отказ в подключении, — 502. Тайм-ауты учитываются пассивной проверкой так же, как ошибки подключения;
- Увеличьте тайм-аут подключения для бэкендов, которые медленно стартуют или находятся за медленными каналами; задайте тайм-аут заголовков, если зависший бэкенд должен быстро возвращать ошибку.

### Тайм-ауты посетителя {#client-timeouts}

Тайм-ауты простоя при обмене с посетителями, в секундах; 0 — значение по умолчанию 60 секунд (как у `client_body_timeout` и `send_timeout` в nginx по умолчанию). Их можно задать для всех типов сайтов, кроме «Разорвать соединение».

| Поле | По умолчанию | Диапазон | Назначение |
| --- | --- | --- | --- |
| Тело запроса `clientTimeouts.readIdle` | 60 с | 1–3600 | Наибольшее ожидание одного чтения тела запроса |
| Ответ `clientTimeouts.writeIdle` | 60 с | 1–3600 | Наибольшее ожидание одной записи ответа |

- Учитывается только зависшее отдельное чтение или запись, поэтому идущие большие загрузки и скачивания, ожидание бэкенда и долгие соединения вроде WebSocket не затрагиваются;
- Отключает посетителей, которые крайне медленно отправляют тело запроса или читают ответ (slowloris, slow read), чтобы они не занимали соединения надолго;
- Превышение при чтении тела запроса возвращает 408 и закрывает соединение, не учитываясь пассивной проверкой бэкенда; превышение при записи разрывает соединение;
- Действует для HTTP/1, HTTP/2 и HTTP/3.

### Сжатие

Сжатие можно включить для сайтов с обратным прокси, статическими файлами и фиксированным текстом (кроме редиректов). По `Accept-Encoding` предпочтение отдаётся `br`, затем `gzip`.

- Сжимается только текстовое содержимое: `text/*`, JSON, JavaScript, XML, XHTML, RSS / Atom, WebAssembly, SVG; `text/event-stream` исключён;
- ответы с объявленным `Content-Length` меньше 256 байт остаются без изменений;
- ответы, у которых уже есть `Content-Encoding`, остаются без изменений; запросы на обновление до WebSocket пропускаются напрямую;
- сильный ETag после сжатия заменяется слабым.

### Ограничение частоты по IP

Ограничение по алгоритму token bucket для IP клиента; поля:

| Поле | Описание |
| --- | --- |
| `rate` | Число разрешённых запросов в секунду |
| `burst` | Ёмкость всплеска; если задан `rate`, а `burst` равен 0, берётся целая часть `rate` плюс 1 |
| `maxConns` | Максимум одновременных запросов с одного IP, 0 — без ограничений |

При включённом ограничении нужно задать хотя бы одно из полей `rate` и `maxConns`.

### Кеш ответов в памяти

Работает только для сайтов с обратным прокси; кеш хранится в памяти, вытеснение по LRU.

| Поле | По умолчанию | Диапазон |
| --- | --- | --- |
| `ttl` — срок по умолчанию | 0 | от 0 до 30 дней (в секундах). Если вышестоящий сервер не указал директив кеширования, ответ 200 кешируется на это время; 0 — кешируются только ответы, явно разрешённые вышестоящим сервером |
| `maxMb` — размер кеша | 64 | от 1 до 4096 МБ |

Правила кеширования:

- кешируются только запросы GET, в которых нет заголовка `Range` и нет `Cache-Control: no-cache`;
- запросы с учётными данными не кешируются: заголовок из списка `Authorization`, `Proxy-Authorization`, `Cookie`, `X-Api-Key`, `X-Auth-Token`, `X-Access-Token`, `X-CSRF-Token`, `X-Emby-Token`, `X-Emby-Authorization`, `X-MediaBrowser-Token`, `X-Plex-Token`, `X-Jellyfin-Token` или параметр запроса `api_key`, `X-Plex-Token`, `token`, `access_token` (имена параметров без учёта регистра);
- запросы, исходный путь которых содержит `;`, `\`, `%2F`, `%5C` (без учёта регистра), не кешируются: после нормализации бэкенд может понимать такие пути иначе;
- кешируются только ответы с кодом 200; ответы с `Set-Cookie`, `Vary: *` или `Cache-Control` со значением `no-store` / `private` / `no-cache` пропускаются;
- `Vary` ответа может содержать только `Accept-Encoding`, а при включённом CORS сайта ещё и `Origin`; любой другой заголовок в `Vary` исключает ответ из кеша, как и `Access-Control-Allow-Origin` от бэкенда со значением, отличным от `*`;
- при включённом CORS сайта записи кеша не хранят CORS-заголовки, которые Gately записал для источника посетителя; при попадании они заново формируются по `Origin` текущего запроса;
- учитывается `s-maxage`, затем `max-age`;
- размер одной записи не больше 4 МБ и не больше четверти общего объёма;
- при попадании в кеш возвращаются заголовки `X-Cache: HIT` и `Age`, при промахе — `X-Cache: MISS`;
- ключ кеша включает Host, полный URI запроса и `Accept-Encoding`; при [распределении по пользователям](#user-routes) — также выбранное правило пользователя, а если настроена [передача данных пользователя](#identity-headers), — и переданные бэкенду данные пользователя.

Кеширование по путям (`rules`, «Кэш по путям» на вкладке «Трафик» редактора сайта, до 200 правил):

| Поле | Описание |
| --- | --- |
| `path` | Путь для сопоставления. Начинается с `/`, без пробелов, `?` и `#`, без сегментов `.` и `..` и без нескольких `/` подряд, уникален в пределах сайта. Не может содержать `%` (укажите декодированный путь, например `/中文/*`), регистр учитывается. Без `*` сопоставляется как префикс по границам сегментов: `/api` совпадает с `/api` и `/api/x`, а `/apix` не затрагивает; с `*` весь путь сопоставляется по шаблону, `*` соответствует любым символам, включая `/`, например `/api/products/*` или `/static/*.js` |
| `noCache` | Включено — «Не кэшировать»: путь не читает и не пишет кеш |
| `ttl` | Срок кеширования, от 0 до 30 дней (в секундах); 0 — срок сайта по умолчанию |
| `override` | Включено — «Принудительно»: `no-store`, `no-cache` и `max-age` в `Cache-Control` бэкенда игнорируются, ответы 200 кешируются на заданный срок; если бэкенд указал `private`, ответ не кешируется; у правила или у сайта срок должен быть больше 0 |

- В интерфейсе три режима: «Кэшировать» следует `Cache-Control` бэкенда и использует срок, если бэкенд ничего не указал; «Принудительно» соответствует `override`; «Не кэшировать» — `noCache`;
- приоритет у более конкретного правила: сначала проверяются правила, в которых больше символов без учёта `*`, при равенстве — по порядку в настройках; пути без подходящего правила используют настройки сайта по умолчанию. Чтобы кешировать только отдельные пути, задайте для `/` режим «Не кэшировать»;
- правила сопоставляются с нормализованным путём запроса, поэтому `//api` и `/x/../api` обрабатываются как `/api`;
- в любом режиме перечисленные выше запросы с учётными данными, запросы с `;` и подобными символами в пути, а также ответы с `Set-Cookie`, `Vary: *` или `Cache-Control: private` не кешируются;
- принудительно закешированные ответы общие для всех посетителей, поэтому используйте режим только для содержимого, одинакового для всех, например статических файлов. Не используйте его, если бэкенд пропускает аутентификацию по IP источника (например, без входа из локальной сети): иначе содержимое, которое видят посетители из локальной сети, будет отдаваться из кеша посетителям из интернета.

Просмотр и очистка кеша: при редактировании сохранённого сайта вкладка «Трафик» показывает число записей и объём работающего кеша сайта («Текущий кэш»), есть кнопки «Обновить» и «Очистить всё», а у каждого правила — очистка кеша его пути. Соответствующий API:

- `GET /api/webservice/cache?listener=&site=` возвращает `enabled`, `entries`, `bytes` и `maxBytes`; `site` — ключ сайта, для сайта по умолчанию `default`; если сайта нет или его слушатель не запущен, возвращается 404;
- `POST /api/webservice/cache/purge` с телом `{"listener", "site", "path"}`: пустой `path` очищает весь кеш сайта, иначе удаляются только записи с подходящим путём, синтаксис и сопоставление те же, что у `path` правила; в ответе число удалённых записей `removed` и состояние кеша после очистки; если кеш для сайта не включён, возвращается 400.

### Переписывание путей и редиректы

Правила проверяются по порядку, срабатывает первое совпавшее.

| Поле | Описание |
| --- | --- |
| `pattern` | Регулярное выражение для пути запроса, например `^/old/(.*)$` |
| `to` | Результат подстановки, группы доступны как `$1` |
| `redirect` | Выключено — внутреннее переписывание (переписанный путь отправляется бэкенду, цель должна начинаться с `/`); включено — редирект |
| `code` | Код редиректа 301 / 302 / 307 / 308, по умолчанию 302 |

Редирект сохраняет исходные параметры запроса. Цель редиректа может содержать `{host}` — домен, использованный посетителем. Правила редиректа выполняются до аутентификации, как `location = / { return 302 ...; }` в nginx, поэтому по пути вроде `/` посетителей можно перенаправлять, не требуя входа.

## Страницы ошибок {#error-pages}

Вкладка «Страницы ошибок» в редакторе сайта определяет, какие страницы 404 и 5xx видят посетители. По умолчанию используется встроенный стиль Gately; его можно заменить одним из 10 встроенных стилей (Минимализм, Терминал, Неон, Звёздное небо, Газета, Брутализм, Аврора, Пиксели, Чертёж, Цепочка статуса) или собственной страницей. Все стили адаптированы под экраны телефонов, текст показывается на языке браузера посетителя, а кнопка с глазом в правом нижнем углу карточки позволяет просматривать разные коды состояния в размерах для компьютера и телефона.

- Область действия: страницы 404 и 5xx, которые Gately формирует для сайта, например 502, когда бэкенд недоступен, 404, когда статического файла нет, 503, когда цель редиректа временно недоступна, и ошибка, когда недоступен сервис аутентификации для пересылки. Если у статического сайта задана «Страница 404», для ненайденных файлов по-прежнему используется она. Ответ 403 от контроля доступа и 429 от ограничения частоты не затрагиваются.
- Сайт по умолчанию: его настройка также применяется к ответу 404, когда ни один сайт не соответствует запрошенному домену, в том числе при выключенном сайте по умолчанию.
- Клиенты, отличные от браузеров (`curl`, вызовы API и т. п.), по-прежнему получают ошибку в виде простого текста.

### Перехват ошибок бэкенда {#intercept-errors}

Сайт с обратным прокси может включить «Перехватывать ошибки бэкенда», чтобы заменять указанные коды состояния, возвращаемые бэкендом, выбранной выше страницей; это аналог `proxy_intercept_errors on` вместе с `error_page` в nginx. Коды разделяются запятыми; поддерживаются диапазоны и сокращённая запись, например `404, 500-599` или `5xx`, допустимы только значения от 400 до 599.

- Заменяются только запросы, которыми браузер открывает страницу (`Accept` содержит `text/html`). Запросы API, изображений, скриптов и т. п. сохраняют ответ бэкенда, поэтому JSON-ответ 404 одностраничного приложения никогда не подменяется веб-страницей.
- Код состояния и заголовки вроде `Set-Cookie` и `Retry-After` сохраняются; заголовки, описывающие исходное тело (кодировка содержимого, `ETag` и т. п.), удаляются. На запросы `HEAD` возвращаются только заголовки.
- Через «Опции пакетно» можно сразу изменить стиль страницы ошибки у нескольких сайтов; настройка перехвата каждого сайта остаётся прежней.

### Пользовательские страницы {#custom-error-pages}

Пользовательские страницы хранятся в библиотеке страниц, которая ведётся в разделе «Глобальные настройки → Пользовательские страницы ошибок» или через «Управление пользовательскими страницами» на вкладке «Страницы ошибок» сайта; одну страницу могут использовать несколько сайтов. Страница берётся из одного из двух источников:

- Загрузка или вставка: выберите файл `.html` / `.htm` (UTF-8, до 256 КБ) или вставьте код напрямую. Содержимое сохраняется в конфигурации и остаётся доступным для редактирования.
- Файл на сервере: укажите абсолютный путь к файлу `.html` / `.htm` (в Docker путь внутри контейнера). При каждом использовании проверяется, не изменился ли файл. Символьная ссылка тоже должна вести на HTML-файл, а файлы, содержимое которых не похоже на HTML, отклоняются. Если файл удалён или его содержимое стало недействительным, посетители видят стиль по умолчанию, а в библиотеке страница помечается как недоступная.

В странице можно использовать плейсхолдеры: при выводе они заменяются сведениями о текущей ошибке и экранируются как HTML:

| Плейсхолдер | Содержимое |
| --- | --- |
| `{code}` | Код состояния, например 502 |
| `{status}` | Английская формулировка состояния, например Bad Gateway |
| `{title}`, `{detail}` | Заголовок и описание ошибки на языке посетителя |
| `{host}`, `{path}` | Запрошенные домен и путь |
| `{time}` | Время возникновения ошибки (UTC) |

Перед сохранением безопасность и пригодность проверяются автоматически, и показывается предпросмотр:

- Страница ошибки имеет тот же origin, что и сайт. Чтобы её нельзя было использовать для кражи cookie или подделки действий, при сохранении удаляются скрипты, атрибуты событий вроде `onclick`, ссылки `javascript:`, встроенные фреймы, объекты плагинов, формы, `<base>`, `<meta http-equiv>` (автоматические редиректы и т. п.) и опасные конструкции стилей; в результате проверки перечислено, что было удалено.
- В ответ добавляется `Content-Security-Policy: sandbox; default-src 'none'; ...`: страница выполняется в изолированной песочнице, поэтому внедрённые скрипты не запустятся, а загружаются только встроенные стили и изображения или шрифты, встроенные как `data:`, так что адрес посетителя не утекает третьим лицам. Внешние таблицы стилей, изображения, шрифты и относительные адреса внутри сайта не загружаются, и проверка выводит предупреждение; пишите стили в `<style>`, а изображения и шрифты встраивайте как `data:`.
- Сохранение отклоняется, если содержимое пустое, не в UTF-8, превышает допустимый размер или не является HTML. Отсутствие `viewport`, объявление кодировки не UTF-8 или отсутствие плейсхолдеров сопровождаются подсказкой.

## Статистика доступа и мониторинг

### Статистика сайта {#site-stats}

Для работающего слушателя нажмите «Статистика» в строке сайта, чтобы открыть окно статистики; доступны периоды: последний 1 час, 6 часов, 24 часа:

- поминутная статистика доступа: одна точка в минуту, хранятся последние 24 часа, включает график числа запросов и график ошибок 4xx / 5xx;
- время до первого байта: P50 / P95 по минутам и максимальный P95 за выбранный период. Задержка считается от прихода запроса до отправки заголовков ответа, без передачи тела; WebSocket и другие запросы со сменой протокола, а также оборванные запросы не учитываются, процентили оцениваются по среднему времени в узких интервалах. Оповещения по порогам — в разделе [Производительность](/ru/docs/modules/perf);
- распределение кодов состояния 2xx / 3xx / 4xx / 5xx и суммарный объём трафика ответов;
- топ-10 IP-источников и топ-10 стран (для статистики по странам нужна импортированная база GeoIP);
- для сайтов с обратным прокси показываются состояние здоровья каждого бэкенда, вес, признак резервного, текущее число соединений и число переданных запросов, включая бэкенды по путям и бэкенды распределения по пользователям (с указанием пути или пользователей);
- если запросы блокировались, показывается их число по причинам: бан, список IP, фильтр стран, ограничение частоты и WAF (неудачные входы не учитываются).

Статистика хранится в памяти; при перезапуске или изменении собственных настроек слушателя подсчёт начинается заново. Изменение сайта сохраняет его счётчики. В рейтингах учитывается не более 5000 различных источников.

### Текущие подключения {#connections}

У работающего слушателя в строке каждого сайта (включая сайт по умолчанию) после статистики показано «Активных: N» — сколько запросов сайт обрабатывает прямо сейчас; значение обновляется вместе со страницей. Кнопка **Подключения** открывает окно подключений, оно обновляется каждые 2 секунды и поддерживает поиск по IP:

- **Текущие**: адрес и порт источника, протокол (h1 / h2 / h3, WebSocket помечен WS), запрос (метод, хост и путь без строки запроса), время начала, длительность и трафик (к посетителю; от посетителя — если есть тело запроса или WebSocket). Сортировка от самых долгих, не более 500 строк. Если настроены [доверенные прокси](#real-ip), источником будет реальный адрес посетителя с указанием прокси, через который он пришёл.
- **История**: недавно завершённые подключения со временем начала и окончания, длительностью, трафиком и итогом (завершено / разорвано). Сохраняются только подключения длительностью от 1 секунды или разорванные вручную, последние 200 на сайт; после перезапуска история очищается. Короткие запросы смотрите в журнале доступа.

Список ведётся по выполняющимся запросам: соединение HTTP/1.1 keep-alive между запросами не относится ни к одному сайту, а одно соединение HTTP/2 или HTTP/3 может одновременно нести несколько запросов, поэтому именно запрос точно соотносится с сайтом. Переключённый WebSocket остаётся в списке, пока соединение не закроется.

**Разорвать** в строке сразу после подтверждения завершает этот запрос: в HTTP/1.x закрывается всё соединение; в HTTP/2 и HTTP/3 сбрасывается только этот запрос, остальные запросы того же соединения продолжаются; переключённый WebSocket закрывается вместе с соединением к бэкенду. Это срабатывает сразу и тогда, когда посетитель перестал читать и отправка заблокирована. Разорванный запрос записывается в журнал доступа с кодом 444 (или сохраняет свой код, если ответ уже начался), не считается ошибкой бэкенда и не учитывается при обнаружении сканирования путей. Посетитель может сразу переподключиться; чтобы не пустить его, используйте **Разорвать и заблокировать**: адрес источника (для IPv6 — его диапазон /64) добавляется в [список блокировок](#список-блокировок), а его выполняющиеся запросы на всех слушателях и сайтах разрываются. Нельзя заблокировать loopback-адрес (с ним показываются все запросы, пришедшие через frp или локальную переадресацию без протокола PROXY) и адреса из доверенных прокси (для IPv6 проверяется /64): их блокировка отрезала бы множество посторонних посетителей; на разрыв без блокировки это ограничение не распространяется. Блокировка длится от 1 до 720 часов, либо отметьте **Навсегда**.

Учётные записи и токены только для чтения могут просматривать список; разрыв и блокировка требуют права записи и фиксируются в журнале аудита.

### Сетевая топология {#topology}

Пункт **Web → Топология** в боковом меню — отдельная страница (`#/webtopology`); её также открывает кнопка **Топология** в заголовке страницы веб-сервисов. Схема разворачивается как Интернет → Gately → слушатели → сайты / действия слушателя → бэкенды / исходы, обновляется каждые 2 секунды, приостанавливается, пока страница в фоне, а холст следует светлому или тёмному режиму текущей темы:

- **Узлы**: слушатели показывают адрес и состояние работы, не запустившиеся выделены красным; сайты показывают способ сопоставления (точное, шаблон, любой домен, сайт по умолчанию), QPS и число запросов в процессе; сайты с обратным прокси раскрываются во все свои бэкенды, включая бэкенды по путям и бэкенды распределения по пользователям (с указанием пути или пользователей), недоступные бэкенды выделены красным; сайты типов «Редирект», «Статические файлы», «Фиксированный текст» и «Закрыть соединение» ведут каждый к одному узлу исхода. Закрытие соединения сайтом по умолчанию, перенаправление открытых HTTP-запросов на HTTPS-порту (301 / 308) и ответ 404, когда ни один сайт не совпал и сайт по умолчанию не включён, являются ожидаемым поведением и показаны серым. Отключённые слушатели и сайты тоже отображаются, с пометкой «Не запущен».
- **Связи**: толщина растёт с QPS, связи с трафиком показывают анимацию потока. Если связей больше 120, анимируется только подсвеченный путь; при включённом в системе уменьшении движения анимации нет.
- **Подсветка**: при наведении на узел или щелчке по нему подсвечивается весь его путь, вверх до Интернета и вниз до бэкендов, на связях этого пути подписываются QPS и трафик, остальное затемняется; щелчок по пустому месту сбрасывает подсветку.
- **Панель сведений**: для выбранного узла показываются QPS (среднее за последние 10 секунд), среднее за 60 секунд, исходящий трафик, запросы в процессе, всего запросов, ошибки бэкенда, заблокированные запросы по причинам, распределение кодов состояния, графики запросов и трафика в секунду за последние 60 секунд и активные IP, прошедшие через узел. Значок ⓘ рядом с каждым показателем объясняет, как он считается. Для сайта панель также открывает окна статистики, подключений, журнала доступа и редактирования; для бэкенда — журнал доступа и редактор его сайта, а слушатель можно изменить прямо отсюда.
- **Просмотр журнала доступа**: выберите узел сайта или бэкенда и нажмите «Журнал доступа», чтобы открыть журнал доступа только этого сайта (имя сайта сравнивается целиком, сайты со схожими именами не попадают в выборку). Если вверху уже выбран фильтр по IP, кнопка называется «Журнал доступа этого IP» и дополнительно фильтрует по этому адресу. Значок журнала справа от каждого активного IP в панели сведений открывает журнал доступа этого адреса для выбранного сайта; если выбран не узел сайта, то по всем сайтам. Условия фильтра в окне журнала можно менять дальше, условие по сайту отображается как удаляемая метка «Сайт: …». Кроме того, окно показывает только посетителей слушателя этого сайта, поэтому одноимённый сайт на другом слушателе (например, при раздельных слушателях IPv4 и IPv6, оба с именем HTTPS) не попадает в выборку; это условие отображается как удаляемая метка «Слушатель: …». Полные записи есть только у сайтов с включённым журналом доступа, иначе вверху окна показывается подсказка; сайты без имени фильтруются по первому домену. Кнопка «Журнал» в строке каждого сайта на странице веб-сервисов открывает то же окно.
- **Активные IP**: адреса посетителей с запросами за последние 60 секунд и адреса, у которых ещё есть запросы в процессе. На схеме показывается только их число, полный список адресов есть в панели сведений. Введите или выберите адрес вверху (или щёлкните адрес в панели), чтобы подсветить только пройденный им путь вплоть до конкретного бэкенда; **Сбросить фильтр** отменяет выбор. Каждый сайт, бэкенд и действие слушателя хранит до 1024 недавних адресов, а API возвращает не более 500, поэтому при большом числе источников панель сообщает, что список неполный. Если настроены [доверенные прокси](#real-ip), здесь показываются реальные адреса посетителей.
- **Скрытие**: при включённом переключателе выбранные категории показываются со `*`, чтобы делиться снимками экрана; это влияет только на эту страницу, поиск по-прежнему идёт по полному тексту. Категории: IP посетителей (список активных IP и фильтр; последняя часть IPv4, последние 64 бита IPv6), адреса бэкендов (IP и имена хостов бэкендов и целей перенаправления), адреса слушателей (IP слушателей, сообщения об ошибках слушателя и сайты с IP вместо домена) и домены (домены сайтов и домены в названиях сайтов; остаются первая метка и суффикс, например `nas.***.com`). По умолчанию отмечены первые три, выбор запоминается.
- **Способ скрытия**: вверху меню «Скрытие» выбираются **Звёздочки** или **Псевдонимы**. Звёздочки скрывают часть значения, оставляя сеть и края; псевдонимы заменяют значение целиком номером, постоянным на этой странице: IP посетителей становятся `Visitor-01`, IP в бэкендах и целях перенаправления — `Backend-01`, адреса прослушивания — `Listen-01`, а у доменов остаётся только суффикс, регистрируемая часть и часть хоста нумеруются отдельно: `nas.home.example.com` становится `host-01.domain-01.com`, поддомены одного домена делят его номер `domain`. Одинаковые значения всегда получают один псевдоним, разные — разные, поэтому по-прежнему видно, какие узлы совпадают. Номера выдаются в порядке появления, хранятся только в открытой странице и перевыдаются после перезагрузки.
- **Фильтр**: кнопка **Фильтр** справа вверху ограничивает вид отдельными слушателями; **Только проблемы** показывает не запустившиеся слушатели (со всеми их сайтами), включённые, но не работающие сайты и сайты с неисправным бэкендом, а отключённые слушатели и сайты считаются ожидаемым состоянием; **Были блокировки** показывает по каждой причине (бан, список IP, фильтр стран, ограничение частоты, WAF) только сайты, блокировавшие запросы по этой причине с момента запуска Gately. Условия действуют вместе и сочетаются с поиском в заголовке; при фильтре по проблемам или блокировкам скрываются действия уровня слушателя и слушатели без оставшихся сайтов. Фильтры действуют, пока страница открыта.
- **Только активные**: когда сервисов много, нажмите **Только активные** справа вверху, чтобы видеть только сайты и действия слушателей, у которых были запросы за последние 60 секунд, есть выполняющиеся запросы или через которые прошли активные IP; у прокси-сайтов остаются только активные бэкенды (сайт, бэкенды которого не получали запросов, например из-за блокировки контролем доступа, показывается конечным узлом), а слушатели без активности скрываются. В этом режиме свёртывание слушателей и сводные узлы «ещё N» не действуют, а холст сам подстраивается, чтобы эти узлы были видны целиком (для дерева, вертикальной и санкей-раскладки не меньше 50%), и обновляется, когда сервисы становятся активными или затихают. Число на кнопке — сколько сайтов активно сейчас; оно учитывает фильтр и поиск и показывается, даже когда режим выключен. Режим сочетается с фильтром, поиском, подсветкой по IP и всеми раскладками и запоминается для каждого устройства; если за последние 60 секунд запросов не было, холст сообщает об этом, а **Показать все** выключает режим.
- **Повтор**: кнопка **Повтор** в правом верхнем углу открывает шкалу времени, по которой можно посмотреть топологию в прошлом. Запись по умолчанию выключена; администратор включает её кнопкой **Начать запись** на шкале или в **Настройках записи**. После включения каждые 5 секунд вся топология (скорости, счётчики, состояние бэкендов, активные IP) записывается кадром, сжимается и хранится только в памяти в пределах **Лимита памяти** (по умолчанию 8 МиБ, от 1 до 256), сверх которого старые кадры удаляются; одинаковые подряд кадры (например, без трафика) хранятся один раз, поэтому при малом трафике можно заглянуть далеко назад, а при большом — ближе. Шкала рисует трафик диаграммой с областями, красным внизу отмечает периоды, когда слушатель не запустился или бэкенд был неисправен, и затемняет периоды без записи (модуль выключен или нет работающих слушателей). Щелчок или перетаскивание по шкале переходит к моменту, при наведении видны QPS и число активных IP; кнопками или ← → можно идти по кадрам, Пробел запускает или ставит на паузу, скорость от 1× до 60×, а **Пропускать простой** при воспроизведении пропускает периоды без трафика и посетителей; шкала показывает всю запись или последние от 15 минут до 24 часов, выбор запоминается на устройстве. Во время повтора работают все семь раскладок, фильтр, «Только активные», маскирование и подсветка по IP, а график в панели подробностей охватывает 60 секунд до выбранного момента (точка каждые 5 секунд); **Соединения** показывают текущее состояние, поэтому в повторе скрыты. **К живому виду** завершает повтор. Записанные данные содержат IP посетителей и очищаются при перезапуске Gately или выключении записи; запись кадра занимает около 0,4 мс (замер на 40 сайтах и 200 активных IP), после сжатия кадр весит около 1–2 КБ.
- **Раскладка**: меню раскладки в правом верхнем углу предлагает семь вариантов; выбор запоминается, при переключении — плавный переход и подгонка холста. **Дерево** — пять столбцов слева направо, больше всего подробностей; **Вертикально** — разворачивается сверху вниз, как оргсхема, открывается с Gately в центре и просматривается перетаскиванием в стороны; **Радиально** — Gately в центре, слушатели, сайты и бэкенды на трёх концентрических кольцах, имена идут вдоль радиуса; **Санки** — каждый узел это полоса, каждая связь — лента, полоса родителя делится по доле QPS детей, высота полос и ширина лент меняются вместе с трафиком, а узлы остаются на месте; **Солнечные лучи** — Gately в центре, слушатели, сайты и бэкенды образуют три кольца сегментов; **Карта дерева** и **Пузыри** вкладывают Gately, слушатели, сайты и бэкенды друг в друга блоками или кругами, у каждого бэкенда (или исхода) одинаковая площадь. В раскладках «Солнечные лучи», «Карта дерева» и «Пузыри» нет связей, чем темнее, тем больше трафика; удобно для обзора множества сайтов. В раскладках «Санки», «Солнечные лучи», «Карта дерева» и «Пузыри» на холсте нет кнопок свёртывания — сворачивайте и разворачивайте слушатель в его панели сведений.
- **Свёртывание лишних узлов**: по умолчанию у каждого слушателя показаны первые 8 сайтов, у каждого сайта — первые 6 бэкендов; остальные объединены в узел «Ещё сайтов / бэкендов: N» с их суммарным QPS и числом запросов в процессе. Нажатие разворачивает все, узел **Свернуть** в конце сворачивает обратно. Активные IP свёрнутых узлов засчитываются этому узлу, и подсветка по IP останавливается на нём. Сайты и бэкенды с запросами за последние 60 секунд или с выполняющимися запросами никогда не сворачиваются: они остаются видны в исходном порядке даже сверх лимита, поэтому в сводном узле остаются только простаивающие, а его подзаголовок — «Нет запросов за последние 60 секунд».
- **Перемещение, масштаб и размер холста**: перетаскивайте холст для перемещения, колесом прокручивайте вверх и вниз (у края прокручивается страница); прокрутка с Ctrl/⌘ или сведение пальцев на трекпаде или экране меняет масштаб от 15% до 250% относительно указателя или центра жеста. Кнопки в правом нижнем углу увеличивают, уменьшают, сбрасывают до 100% и вписывают в холст (показать всё, значок мишени); крайняя правая кнопка разворачивает холст на всё окно браузера, Esc или та же кнопка возвращают обратно. Перетащите полосу под холстом, чтобы изменить его высоту (работает и на сенсорных экранах); высота запоминается для устройства, двойной щелчок по полосе или **Автовысота** возвращают автоматический размер.
- Поле поиска в заголовке страницы фильтрует сайты в топологии (имя, домен, группа, адрес бэкенда); слушатели можно сворачивать по одному или все сразу. **Изменить** и «Изменить прослушивание» в панели сведений открывают на этой странице тот же редактор, что и на странице веб-сервисов; после сохранения топология сразу обновляется, страницу покидать не нужно. Окна статистики, соединений и журнала доступа также открываются на этой странице.

Все числа берутся из счётчиков в памяти этого экземпляра: они обнуляются при перезапуске, изменение сайта сохраняет его счётчики, изменение настроек слушателя, например порта, запускает подсчёт этого слушателя заново, а данные других экземпляров Gately не суммируются. Вид топологии читает `GET /api/webservice/topology`, доступный учётным записям и токенам только для чтения. Повтор читает `GET /api/webservice/topology/replay` (обзор и шкала) и `GET /api/webservice/topology/replay/frame` (снимок на момент), доступные и учётным записям только для чтения; настройки записи меняются через `PUT /api/webservice/topology/replay/settings`, для этого нужны права на запись.

### Аудит посетителей {#visitor-audit}

Пункт меню «Web → Аудит посетителей» (`#/webvisitors`) сводит обращения ко всем сайтам по адресу посетителя: кто, когда, к каким сайтам и путям обращался, под какой учётной записью и сколько раз был заблокирован. Учитываются все сайты, включая сайт по умолчанию и запросы без подходящего сайта, независимо от того, включён ли у сайта журнал доступа; при настроенных [доверенных прокси](#real-ip) записывается реальный адрес посетителя.

- **Сводка и динамика**: период выбирается в заголовке страницы (сегодня, 7 дней, 30 дней, весь срок хранения). Карточки показывают число посетителей (в том числе новых), запросов, блокировок и их долю, посетителей, прошедших аутентификацию сайта, заблокированных сейчас и похожих на сканеры; щелчок по карточке включает фильтр, повторный — снимает. На дневной диаграмме высота столбца — число запросов, красная часть — блокировки; щелчок или наведение на день показывает его посетителей, запросы и блокировки.
- **Список**: для каждого посетителя показаны код страны (если импортирована база GeoIP; частные и локальные адреса — «LAN»), запросы и блокировки за период, самые посещаемые сайты, учётные записи, первое и последнее посещение и последний запрос (статус, метод, путь, домен и User-Agent). Поиск по адресу, учётной записи, сайту, домену, пути или User-Agent; фильтры «С блокировками», «С аутентификацией», «Администраторы», «Заблокированы», «Похожие на сканеры» и по сайту; сортировка по последнему посещению, числу запросов, числу блокировок или первому посещению. Одноимённые сайты на двух прослушивателях помечаются именем прослушивателя.
- **Учётная запись**: после успешной аутентификации сайта (веб-вход, базовая аутентификация, общие пользователи, сторонний вход, проксируемая аутентификация) записывается имя пользователя; запросы с сеансом панели управления этого экземпляра записываются как «admin». Попытки с неверным паролем и заблокированные запросы учётную запись не записывают.
- **Похожие на сканеры**: адреса, которые только блокировались или обращались только к несопоставленным сайтам и ни разу не прошли аутентификацию.
- **Подробности**: щелчок по строке открывает посетителя: первое и последнее посещение, всего запросов, блокировок, отдано байт, разорванных соединений (444), дневная диаграмма за срок хранения, распределение статусов и причины блокировок (блокировка, список IP, фильтр по стране, ограничение частоты, WAF), посещённые сайты, самые запрашиваемые пути (до 10), учётные записи и User-Agent. Отсюда можно заблокировать или разблокировать адрес (IPv6 — по /64), открыть журнал доступа этого адреса или удалить запись.

**Что хранится и где**: хранятся только агрегированные счётчики по посетителю, без отдельных запросов; записывается только путь, а строки запроса, тела запросов, cookie и учётные данные всегда исключаются. Для каждого посетителя хранится до 12 сайтов, 10 путей, 6 учётных записей и 4 User-Agent; сверх этого заменяется запись с наименьшим числом запросов. Для отдельных запросов включите журнал доступа сайта. Данные лежат в `visitors/visitors.jsonl.gz` в каталоге конфигурации (права 0600), записываются примерно через 10 минут после изменений и сразу при выходе и не входят в резервные копии конфигурации.

**Настройки**: «Настройки» в заголовке отключают запись (существующие данные сохраняются), задают срок хранения в днях (1–180, по умолчанию 30) и максимум посетителей (100–100000, по умолчанию 10000) и позволяют очистить все данные. Посетители, последнее посещение которых старше срока хранения, удаляются автоматически; при сокращении срока лишние данные удаляются сразу, после подтверждения. При превышении лимита сначала удаляются адреса, похожие на сканеры, затем дольше всего не появлявшиеся. Учётные записи и токены только для чтения могут просматривать; блокировка, удаление и изменение настроек требуют прав записи. API: `GET /api/webservice/visitors`, `GET /api/webservice/visitors/detail`, `POST /api/webservice/visitors/delete` и `GET|PUT /api/webservice/visitors/settings`.

### Метрики Prometheus

Глобальный эндпоинт метрик `GET /api/metrics` объединяет метрики всех модулей, см. [Мониторинг](/ru/docs/reference/monitoring). Эндпоинт модуля ниже содержит только метрики веб-служб.

Эндпоинт метрик — `GET /api/webservice/metrics`, формат текста Prometheus; нужны учётные данные для входа или [API-токен](/en/docs/reference/api-reference).

```bash
curl -H "Authorization: Bearer gtl_xxxx" http://localhost:16680/api/webservice/metrics
```

| Метрика | Тип | Описание |
| --- | --- | --- |
| `gately_site_requests_total` | counter | Суммарное число запросов к сайту |
| `gately_site_errors_total` | counter | Число ошибок бэкенда сайта |
| `gately_site_active_requests` | gauge | Число запросов в обработке |
| `gately_site_response_bytes_total` | counter | Суммарное число байт ответов |
| `gately_site_responses_total` | counter | Число ответов по классам состояния (метка `class`: от `2xx` до `5xx`) |
| `gately_site_blocked_total` | counter | Число заблокированных запросов по причинам (метка `reason`: `ban` бан, `ip` список IP, `country` фильтр стран, `rateLimit` ограничение частоты, `waf`) |
| `gately_upstream_up` | gauge | Здоров ли бэкенд: 1 — здоров, 0 — недоступен (с меткой `upstream`) |
| `gately_upstream_requests_total` | counter | Суммарное число запросов, переданных бэкенду (с меткой `upstream`) |
| `gately_upstream_response_bytes_total` | counter | Суммарное число байт тела ответов бэкенда без данных после перехода на WebSocket (с меткой `upstream`) |
| `gately_listener_requests_total` | counter | Запросы, которые слушатель обрабатывает сам без сайта; метка `action`: `https_redirect` (перенаправление открытого HTTP на HTTPS-порту) или `not_found` (404, когда ни один сайт не совпал); имеет только метку `listener` |

Все метрики, кроме `gately_listener_requests_total`, имеют метки `listener` (имя слушателя#key слушателя) и `site` (название сайта, а если оно не задано — первый домен). Бэкенды по путям и бэкенды распределения по пользователям дополнительно имеют в `gately_upstream_*` метку `route`: префикс пути или `@` со списком пользователей. Метка `upstream` — адрес бэкенда, из которого удалены имя пользователя, пароль и строка запроса.

## Импорт конфигурации nginx {#import-nginx}

Кнопка «Импорт nginx» вверху страницы преобразует существующие сайты nginx в слушатели и сайты Gately. Рекомендуется выполнить `nginx -T` на хосте nginx и вставить весь вывод: он содержит все файлы из include, и Gately раскрывает include так же, как nginx.

- Сначала предпросмотр: сайты сгруппированы по порту прослушивания, для каждого показаны тип, бэкенд или каталог, исходный файл и номер строки, а также то, на что стоит обратить внимание (директивы с переменными, regex-location, домены без сертификата и т. п.); для сайтов, которые нельзя преобразовать, указывается причина;
- сайты на том же порту добавляются к существующему слушателю, иначе создаётся новый; уже существующие домены пропускаются, поэтому импорт можно повторять;
- по умолчанию импортированное остаётся выключенным, чтобы проверить сайты по одному параллельно с nginx и затем включить; при отмеченном «Включить сразу после импорта» всё начинает работать сразу (если nginx ещё занимает тот же порт, новый слушатель не запустится);
- что преобразуется: `proxy_pass` (включая веса, резервные серверы и стратегию балансировки из upstream), статические каталоги `root` / `alias` (`autoindex`, `try_files $uri.html`, `error_page 404`), редиректы и фиксированное содержимое через `return`, редиректы всего сайта через `rewrite`, `add_header`, `proxy_set_header`, `gzip`, `allow` / `deny`, бэкенды по путям, контроль доступа и редиректы на уровне location, `listen ... proxy_protocol` и `quic`;
- `proxy_connect_timeout` и `proxy_read_timeout` становятся [тайм-аутами подключения и ожидания заголовков ответа](#backend-timeouts) сайта; значение в location / имеет приоритет над уровнем server, значения выше предела импортируются с пределом. Отличающиеся значения в других location не импортируются, предпросмотр сообщает об этом;
- `client_body_timeout` и `send_timeout` становятся [тайм-аутами посетителя](#client-timeouts) сайта, для всех типов сайтов;
- `auth_request` преобразуется во внешнюю аутентификацию: адрес проверки берётся из `proxy_pass` location подзапроса аутентификации (поддерживаются переменные из `set`), переход ко входу — из `error_page 401 =302`; типичные конфигурации Authelia преобразуются напрямую. Если аутентификация включена только в части location, «Область аутентификации» ограничивается отмеченными путями;
- `auth_basic` преобразуется в базовую аутентификацию с общими пользователями; файл пользователей nginx не читается, поэтому, пока пользователи не добавлены, пройти аутентификацию не сможет никто;
- TCP/UDP-переадресацию из `stream` настройте в [пробросе портов](/ru/docs/modules/portforward); сертификаты не импортируются: если у HTTPS-сайта нет сертификата, предпросмотр показывает файлы сертификатов, которые использует nginx, и их можно добавить на странице [сертификатов](/ru/docs/modules/ssl) по пути к файлу.

## Замена haproxy и nginx

Маршрутизация по протоколу и веб-службы вместе могут заменить пару haproxy + nginx. Типичная схема: одно правило [маршрутизации по протоколу](/ru/docs/modules/protoroute) на порту 443, которое отправляет VPN и другие TLS-службы прямо на их бэкенды, а всё остальное — на слушатель веб-служб, принимающий протокол PROXY, плюс слушатель веб-служб на порту 80 с сайтом-редиректом (`https://{host}`).

Перенос настроек nginx:

| nginx | Gately |
| --- | --- |
| `server` с `server_name` | сайт с этими доменами |
| `location` с другим `proxy_pass` | бэкенды по путям |
| `auth_request` (Authelia) | внешняя аутентификация или общие пользователи с TOTP |
| `proxy_ssl_name $host` | использование посещаемого домена как SNI |
| `return 301 https://$host$request_uri` | сайт-редирект с `https://{host}` и «Сохранять путь» |
| `return 302 /admin` в `location = /` | правило переписывания с включённым «Редирект», pattern `^/$` |
| `try_files $uri $uri.html $uri/index.html` и `error_page 404` | статические файлы с «URL без расширения» и страницей 404 |
| `error_page 502 503 504 /50x.html` и `proxy_intercept_errors on` | настройка [страниц ошибок](#error-pages) сайта и перехват ошибок бэкенда |
| `add_header` | заголовки ответа |
| `return 444` | сайт «Закрыть соединение» |
| `error_page 497 https://$host:$server_port$request_uri` в HTTPS server | у нового слушателя «HTTP на том же порту» = «Перенаправлять на HTTPS»; при объединении с существующим слушателем выводится только предупреждение, его настройки не меняются |

## Открыть порт в брандмауэре {#auto-firewall}

Когда Gately работает на роутере вроде OpenWrt или на Linux-хосте с включённым брандмауэром, системный брандмауэр по умолчанию блокирует входящие соединения извне, и порт слушателя нужно разрешить, чтобы до него можно было достучаться. Если у слушателя включено «Открыть порт в брандмауэре», Gately разрешает в брандмауэре этого хоста только порт этого слушателя:

- Разрешаются только порты, которые действительно слушаются. Если порт занят другой программой и слушатель не запустился, ничего не разрешается, и эта программа (например, страница администрирования роутера) остаётся закрытой снаружи.
- Семейство адресов задаёт сеть слушателя: «Только IPv6» разрешает IPv6, «Только IPv4» — IPv4, двойной стек — оба. Если указан адрес прослушивания, разрешаются только соединения к этому адресу. Слушателям на 127.0.0.1 или ::1 разрешение не нужно.
- При включённом HTTP/3 разрешается и UDP-порт с тем же номером.
- Правило снимается, когда слушатель отключён, удалён, не запустился или переключатель выключен, а также при завершении Gately.
- nftables (OpenWrt fw4, firewalld и другие): правило вставляется в начало цепочек фильтрации input. iptables / ip6tables (OpenWrt fw3, ufw и другие): в начало цепочки INPUT. У правил есть комментарий `gately-open:`, после перезагрузки брандмауэра они восстанавливаются в течение 30 секунд.
- На ядрах без nf_tables (например, Synology DSM) используется iptables (legacy): правила записываются в собственную цепочку filter Gately (начинается с `GTLY_OPEN_`), на которую переходит первое правило INPUT; если системный брандмауэр ставит свои правила впереди, переход возвращается на первое место в течение 30 секунд. Docker-образ включает iptables (legacy).
- Только Linux. В Docker нужны сеть host и `cap_add: NET_ADMIN`. Карточка слушателя показывает результат; при ошибке метка «Брандмауэр» становится оранжевой.

У правил [проброса портов](/ru/docs/modules/portforward#auto-firewall) и [маршрутизации по протоколу](/ru/docs/modules/protoroute#auto-firewall) есть такой же переключатель, а правила [STUN](/ru/docs/modules/stun#auto-firewall) разрешают свой порт канала.

### Разрешение портов вручную {#manual-firewall}

Вручную добавляйте правило для каждого порта, который должен быть доступен, а входящий трафик зоны wan оставьте отклонённым. Если разрешить весь входящий трафик зоны wan, в интернет попадут и страница администрирования роутера (80 / 443), SSH и другие службы. В OpenWrt правило добавляется в «Сеть → Межсетевой экран → Правила для трафика» или в `/etc/config/firewall`:

```
config rule
	option name 'Allow-Gately-HTTPS'
	option src 'wan'
	option family 'ipv6'
	option proto 'tcp'
	option dest_port '50663'
	option target 'ACCEPT'
```

- Если Gately работает в сети Docker bridge, контейнер не видит брандмауэр роутера; разрешите проброшенный порт на хосте или роутере.
- Если Gately работает на другом устройстве в LAN (например, в контейнере с собственным IPv6-адресом через macvlan), трафик пересылает роутер: добавьте на роутере правило перенаправления с зоной назначения lan, адресом устройства и используемыми портами. IPv6-префикс от провайдера меняется, поэтому сопоставляйте адрес по суффиксу, например `option dest_ip '::1234/::ffff:ffff:ffff:ffff'`.

## Рекомендации по развёртыванию

Веб-службам нужно слушать порты хоста, такие как 80 / 443, поэтому при развёртывании в Docker рекомендуется `--network host`.
