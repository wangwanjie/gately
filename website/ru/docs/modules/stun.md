# STUN-обход NAT

Если оператор не выдаёт постоянный публичный порт, STUN-обход получает публичный адрес и порт через NAT hole punching, и внутренние сервисы становятся доступны снаружи.

## Возможности

- TCP / UDP-обход и keep-alive;
- автоматическое создание проброса портов на роутере через UPnP / NAT-PMP;
- встроенная переадресация: пробитый публичный порт напрямую направляется на внутреннюю цель;
- при смене публичного адреса или порта запускаются Webhook и скрипты, которые можно использовать для обновления DNS, уведомления клиентов и т. п.; Webhook можно отправлять через прокси (глобальный прокси обновлений или свой прокси).
- Контроль доступа по IP источника (белый / чёрный список) для встроенной переадресации.

## Совместное использование

Публичный порт, полученный через STUN, обычно меняется, поэтому рекомендуется сочетать его с:

- [Динамическим DNS](/ru/docs/modules/ddns) или Webhook / скриптами, чтобы синхронизировать новый адрес с DNS; в значениях записей динамического DNS можно сразу писать `{STUN_имя правила_PORT}` и похожие переменные — записи обновляются, как только адрес правила меняется, см. [Переменные в значении записи](/ru/docs/modules/ddns#record-vars);
- [Веб-службами](/ru/docs/modules/web) для HTTPS-входа.
- Сайты-редиректы веб-служб могут ссылаться на текущий публичный адрес правила через переменные вроде `{STUN_ИмяПравила_PORT}` и автоматически переходить на новый порт при его смене; см. [Переменные редиректа](/ru/docs/modules/web#redirect-vars).

## Ограничения и многоуровневый NAT

- **NAT оператора (CGNAT)**: если WAN роутера получает внутренний адрес вроде `100.64.0.0/10`, пробиться удастся только при подходящем типе NAT у оператора. С полным конусом (любой внешний адрес достигает сопоставленного порта) всё работает; с NAT с ограничением по порту или симметричным — нет, тогда используйте [Tailscale, frp или Cloudflare Tunnel](/ru/docs/modules/tunnels).
- **UPnP за несколькими уровнями NAT**: при включённых UPnP / NAT-PMP Gately пробрасывает на роутере порт туннеля на этот хост. Если внешний адрес роутера отличается от публичного адреса, полученного через STUN, снаружи есть ещё один NAT и публичный порт принадлежит ему, поэтому Gately оставляет только проброс порта туннеля и больше не добавляет проброс публичного порта.
- **Фиксированный локальный порт и разрешение в брандмауэре**: пустой локальный порт выбирается случайно при каждом запуске. Если на хосте работает брандмауэр (например, системный брандмауэр fnOS), задайте правилу фиксированный локальный порт и разрешите его в брандмауэре (можно выделить под правила STUN диапазон портов); иначе брандмауэр отбрасывает входящие соединения и адрес недоступен.
- **TCP и конусный NAT роутера**: на некоторых роутерах «NAT1 / полный конус» действует только для UDP, а у TCP исходящий порт переписывается. Для правил TCP нужен UPnP или проброс порта туннеля на этот хост на роутере.

## Открыть порт в брандмауэре {#auto-firewall}

Если в правиле включено «Открыть порт в брандмауэре», Gately разрешает порт канала в брандмауэре этого хоста (и внутренний порт UPnP / NAT-PMP, если он задан) и убирает разрешение, когда правило останавливается или удаляется. Подходит, когда Gately работает на роутере, например OpenWrt, или на Linux-хосте с включённым брандмауэром. Только Linux.

- nftables: разрешающее правило вставляется в начало каждой цепочки фильтрации на хуке input (например, OpenWrt fw4 и firewalld);
- iptables: разрешающее правило вставляется в начало цепочки INPUT таблицы filter (например, OpenWrt fw3 и ufw);
- правила помечены комментарием `gately-open:`; перезагрузка брандмауэра их удаляет, Gately проверяет каждые 30 секунд и добавляет их снова;
- на ядрах без nf_tables (например, Synology DSM) используется iptables (legacy): правила записываются в собственную цепочку filter Gately (начинается с `GTLY_OPEN_`), на которую переходит первое правило INPUT; если системный брандмауэр ставит свои правила впереди, переход возвращается на первое место в течение 30 секунд. Docker-образ включает iptables (legacy);
- в Docker нужны сеть host и `cap_add: NET_ADMIN`; карточка правила показывает результат или причину ошибки;
- брандмауэры, которые работают не через nftables / iptables, например системный брандмауэр fnOS, по-прежнему требуют открыть порт вручную в их настройках.

## Контроль доступа по IP источника

При встроенной переадресации для каждого правила можно задать белый или чёрный список, который по IP источника решает, пересылать ли трафик к цели. Списки и подписанные списки IP работают так же, как в [пробросе портов](/ru/docs/modules/portforward#контроль-доступа-по-ip-источника), блокировки защиты от вторжений и здесь имеют приоритет. Список действует только на переадресацию; STUN-запросы и проверка канала не затрагиваются. Правка списка не запускает проброс заново, публичный порт сохраняется. UDP проверяется для каждого пакета. Без встроенной переадресации внешние соединения не проходят через Gately, и список не действует. Можно также выбрать «Требовать стук»: переадресуются только источники, успешно «постучавшие» через fwknop, подробнее в [Port Knocking](/ru/docs/modules/knock#gately-entries).

## Рекомендации по развёртыванию

STUN должен напрямую слушать порты хоста, поэтому для Docker рекомендуется `--network host`.
