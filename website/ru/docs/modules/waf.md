# Брандмауэр WAF

Файрвол веб-приложений на основе [Coraza](https://coraza.io/) и OWASP CRS v4, который можно подключать к сайтам [веб-служб](/ru/docs/modules/web).

## Возможности

- Встроенный набор правил OWASP CRS v4, включаемый по файлам правил;
- собственные правила SecLang;
- Порядок групп правил можно менять; журналы срабатываний содержат IP клиента, домен, путь и ID правила, их можно фильтровать по домену, IP или ключевым словам;
- режим блокировки и режим только обнаружения;
- настраиваемый лимит проверки тела запроса: при превышении запрос отклоняется или проверяется только его начало; проверку тела можно отключить для отдельных путей;
- режим совместимости с WebDAV: пропускает методы, заголовки и любые типы содержимого загрузок, которые используют облачные диски и WebDAV;
- Может использовать собственный движок обнаружения SafeLine, отдельно или вместе с группами правил;
- несколько экземпляров, на которые сайты ссылаются по необходимости.

## Рекомендации по использованию

1. Для нового сайта сначала включите режим «только обнаружение» и понаблюдайте за журналом, чтобы убедиться в отсутствии ложных срабатываний;
2. Для ложных срабатываний настройте файлы правил или добавьте собственные исключения;
3. Затем переключитесь в режим блокировки.

## Порядок групп правил

Группы правил экземпляра загружаются сверху вниз; кнопки «вверх» и «вниз» меняют порядок. В пределах одной фазы раньше выполняются правила, стоящие выше:

- Блокирующие правила (deny и т. п.) работают в любой позиции;
- Разрешающие или исключающие правила времени выполнения (`allow`, `ctl:ruleRemoveById`, `ctl:ruleRemoveTargetById` и т. п.) должны стоять выше группы OWASP CRS, иначе CRS может заблокировать запрос раньше;
- Директивы конфигурации вроде `SecRuleRemoveById` и `SecRuleUpdateTargetById` действуют только на уже загруженные правила, поэтому их ставят ниже группы CRS; выше они не действуют.

## Сайты с загрузкой больших файлов

По умолчанию WAF проверяет тело запроса размером не более 12,5 МБ, а более крупные запросы отклоняет (413), поэтому на облачных дисках, WebDAV и файловых менеджерах большие файлы не загружаются. Это настраивается в блоке «Проверка тела запроса» экземпляра:

- **Лимит проверки**: 0 — значение по умолчанию 12,5 МБ, максимум 1024 МБ;
- **При превышении**: «Отклонить запрос» работает как раньше; «Проверять только начало» проверяет только часть в пределах лимита, а остальное передаёт бэкенду без изменений — подходит для сайтов с загрузкой больших файлов;
- **Совместимость с WebDAV и загрузками**: по умолчанию OWASP CRS разрешает только GET, HEAD, POST и OPTIONS и блокирует заголовки `Lock-Token`, `If`, `Content-Range` и типы содержимого вне белого списка, поэтому WebDAV-клиенты не могут просматривать каталоги, загружать файлы и ставить блокировки. После включения пропускаются методы PUT, DELETE, PROPFIND, PROPPATCH, MKCOL, COPY, MOVE, LOCK, UNLOCK и другие, а также эти заголовки, а тип содержимого загрузок больше не ограничивается; тело запросов PUT и `application/octet-stream` считается содержимым файла и больше не проверяется как параметры формы. Проверки на внедрение, path traversal и другие атаки продолжают работать;
- **Пути без проверки тела**: по одному префиксу пути на строку (например, `/api/upload`, `/remote.php/dav/`); для подходящих запросов тело не проверяется, а заголовки, URL и параметры проверяются как обычно.

Для облачных дисков, WebDAV и подобных сайтов рекомендуется создать отдельный экземпляр: включить «Совместимость с WebDAV и загрузками» и выбрать «Проверять только начало», а при необходимости добавить адреса загрузки в пути без проверки тела; остальные сайты продолжают использовать настройки по умолчанию.

curl, rclone и другие клиенты при загрузке крупного содержимого отправляют заголовок `Expect: 100-continue`, который CRS 4 по умолчанию блокирует. Все экземпляры Gately пропускают этот заголовок (100-continue Gately обрабатывает сам), дополнительная настройка не нужна.

## Подключение SafeLine

[SafeLine](https://waf.chaitin.com/) — межсетевой экран веб-приложений от Chaitin Tech, который распознаёт атаки семантическим анализатором и даёт мало ложных срабатываний. Gately может отправлять запросы в ваш собственный движок обнаружения SafeLine (safeline-detector) и пропускать или блокировать их по результату; точки входа, сертификаты, аутентификация и блокировки остаются в Gately, поэтому SafeLine больше не нужен как дополнительный слой обратного прокси.

1. Установите SafeLine Community Edition по официальной документации; каталог установки по умолчанию — `/data/safeline`.
2. Выберите способ подключения к движку обнаружения:
   - **Unix-сокет** (Gately и SafeLine на одной машине): по умолчанию движок слушает `/data/safeline/resources/detector/snserver.sock`, поэтому укажите адрес `unix:/data/safeline/resources/detector/snserver.sock`. Если Gately работает в Docker, смонтируйте каталог `/data/safeline/resources/detector` в контейнер Gately и укажите путь внутри контейнера.
   - **TCP**: добавьте две строки ниже в `/data/safeline/resources/detector/detector.yml` и выполните `docker restart safeline-detector`. После перехода на TCP движок перестаёт слушать Unix-сокет.

     ```yaml
     bind_addr: 0.0.0.0
     listen_port: 8000
     ```

     В качестве адреса укажите IP и порт контейнера safeline-detector, например `172.22.222.5:8000`; IP контейнера показывает `docker inspect safeline-detector | grep IPAddress`. Если Gately работает в bridge-сети Docker, подключите его к сети SafeLine командой `docker network connect safeline-ce <имя контейнера Gately>`. У движка обнаружения нет аутентификации, поэтому не открывайте порт 8000 в интернет.
3. В экземпляре WAF включите «Использовать SafeLine», введите адрес и нажмите «Проверить подключение». Gately отправляет heartbeat, а затем пример запроса с SQL-инъекцией на проверку; сообщение «пример атаки обнаружен» означает, что движок работает. Этот пример атаки появится в журнале атак консоли SafeLine с источником 127.0.0.1 и доменом gately-test.invalid.
4. Укажите экземпляр в сайте веб-сервиса.

Примечания:

- При подключённом SafeLine группы правил можно оставить пустыми; если их оставить, запросы сначала проверяет SafeLine, затем группы правил. В режиме «Только обнаружение» атаки, найденные SafeLine, только записываются в журнал, а запрос проходит дальше.
- Заблокированные запросы: браузеры видят страницу блокировки с ID события, остальные клиенты получают тот же JSON, что и официальные плагины SafeLine (с `event_id`). Код ответа берётся из рекомендации движка, обычно 403. Блокировки учитываются в журналах доступа (`deny=waf`), статистике сайта и событиях блокировки WAF, а шаблон «Блокировки WAF» защиты от вторжений тоже срабатывает.
- Атаки также записываются в консоль SafeLine, их можно найти по ID события; эти записи не относятся ни к одному сайту SafeLine.
- По умолчанию на проверку отправляется до 1024 КБ тела запроса; остаток не проверяется и передаётся бэкенду без изменений. «Пути без проверки тела» и «Совместимость с WebDAV и загрузками» действуют и для SafeLine; тела gRPC неизвестной длины по HTTP/2 не проверяются.
- Тайм-аут проверки по умолчанию — 1 секунда. Если движок недоступен (ошибка подключения или тайм-аут), запросы по умолчанию пропускаются, экземпляр показывает «SafeLine недоступен» и в журнал пишется ошибка; при выборе «Отклонять запросы» такие запросы получают 503. Сразу после запуска движок несколько секунд может возвращать нераспознанные результаты, они обрабатываются так же.
- Проверяются только запросы; ответы в SafeLine не отправляются.

## Проверка

WAF тестируется на реальных атакующих payload и блокирует такие атаки, как path traversal.
