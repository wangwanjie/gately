# 性能比較

このページでは、Gately と、それが置き換えられる一般的なツールを、同じマシン・同じ CPU 制限の下で比較します。対象はリバースプロキシ、Web 認証、WAF、侵入防御、ポートノッキング、ダイナミック DNS、そして OpenWrt ソフトルーター上での動作です。数値はすべて 2026 年 11 月の実測値で、テストスクリプト、設定、生の結果はリポジトリの [tools/benchmark](https://github.com/wangwanjie/gately/tree/main/tools/benchmark) ディレクトリにあり、そのまま再現できます。

## 結果の要点

- **リバースプロキシ**：C 言語で書かれた nginx と HAProxy のスループットが最も高く、HTTP は Gately の約 3.5 倍、HTTPS は約 2.6 倍です。Go 実装のゲートウェイの中で Gately は上位グループに入ります。HTTPS スループットは Caddy より 43% 高く、Lucky の 2.3 倍で、Traefik との差は 9% です。TLS の新規接続レートは 7 つのプログラムの中で最高です。
- **サイトが増えても速度が落ちない**：1000 サイトでの Gately のスループット低下は 6% にとどまり、HAProxy、Traefik、Caddy を上回り、nginx に次ぎます。
- **Web 認証**：ログイン済みユーザーのリクエストでは、Gately は nginx + Authelia の 1.9 倍、Caddy + Authelia の 3.7 倍で、メモリは両者の 3 分の 1 です。
- **WAF**：同じ OWASP CRS 4.25 で、Gately は通常のリクエストを nginx + ModSecurity より約 70% 速く処理し、ブロック結果は完全に一致しました。POST ボディの検査では ModSecurity のほうが速く、メモリもはるかに少なくなります。
- **侵入防御**：攻撃元 IP 1 万件のブロックに Gately は 12 秒、fail2ban は 51 秒かかります。同じログ量での CPU 使用率は fail2ban の半分以下です。ログファイルを読み取る方式では、1 回のブロック遅延が fail2ban より約 0.2 秒長くなります。
- **ポートノッキング**：Gately と fwknop のノック遅延はどちらも 10 ms 以内で、開放後のトラフィックはノックプログラムを経由しません。fnOS 標準のノッキングは通常の Linux ではゲートウェイ経由で転送され、短い接続のスループットは直接接続の 3% です。
- **リソース使用量**：単一の機能だけを比べると、Gately のメモリは fail2ban、fwknop、ddns-go などの小さなツールより大きくなります。リバースプロキシ、WAF、認証、DDNS、侵入防御、ポートノッキングを 1 つの Gately で同時に担当すると約 91 MiB で、個別のツールに置き換えた場合の合計は約 204 MiB です。詳しくは[オールインワン](#オールインワン)を参照してください。

テスト対象のバージョン：Gately v0.6.8.1、nginx 1.29.8、HAProxy 3.2.26、Caddy 2.11.9、Traefik 3.7.19、Lucky 3.8.1、Nginx Proxy Manager 2.17.0（OpenResty 1.31.8）、Authelia 4.39.28、ModSecurity 3.0.16（OWASP CRS 4.25.0）、fail2ban 1.1.0、fwknop 2.6.11、fnOS ノッキング fn-knock 2.5.11、ddns-go 6.17.9。fail2ban と fwknop は Debian パッケージを使い、それ以外はすべて公式 Docker イメージを host ネットワークモードで使用しています。

**測定方法**

- スループット：各項目 20 秒、3 ラウンドの中央値を採用します。HTTP と HTTPS は wrk で 128 本の持続接続、TLS 新規接続は oha で同時 64、リクエストごとに接続を張り直し、HTTP/2 は h2load で 64 接続、接続あたり 10 ストリームの同時実行です。
- メモリ：テスト対象コンテナ内の全プロセスの PSS の合計です（複数プロセスで共有されるメモリは按分され、二重に数えません）。「アイドル」は起動と設定の完了から 10 秒後の値、「ピーク」は負荷テスト中の最大値です。
- CPU：テスト対象コンテナの cgroup の CPU 時間で、100% が 1 vCPU に相当します。
- 起動：設定が整った後にプログラムを再起動し、最初のリクエストが正しく返るまでを計時して、3 回の中央値を採用します。
- すべてのプログラムでアクセスログを無効にしています。nginx はオリジンへの持続接続プールを有効にし、接続あたりのリクエスト数の上限を緩めています（一般的なチューニング）。それ以外のプログラムは既定の設定です。

## Web 認証

サイトにログインを必須とし、ログイン済みユーザーのリクエストとログイン自体をテストします。Gately はサイト組み込みの Web 認証と基本認証を使います。比較対象は、nginx または Caddy の前段に Authelia を置いた構成（`auth_request` / `forward_auth`）と、nginx 標準の `auth_basic` です。すべて HTTPS で行います。

- nginx の `auth_basic` はリクエストのたびに bcrypt を再計算するため、40 リクエスト/秒にとどまります。Gately と Caddy は検証結果をキャッシュします。apr1（MD5）に替えると nginx は 13,082 リクエスト/秒です。

## 侵入防御

シナリオ：Web サービスがスキャンされ、60 秒以内に 404 が 5 回あった IP をブロックします（nftables）。fail2ban は pyinotify で nginx のアクセスログを読み、Gately は同等のログファイルルールで同じログを読みます。さらに、Gately の Web サービスに組み込まれたパス探測も別のグループとして測ります。

- Gately はログファイルを毎秒 1 回読み取るため、1 回のブロック遅延は 0〜1 秒の間になり、平均では fail2ban の inotify より約 0.2 秒遅くなります。Web サービス組み込みの探測はリクエスト処理時に直接カウントするため、この遅延がありません。

## ポートノッキング

3 つの方式を比較します。Gately のポートノッキング（fwknop 互換の SPA 単一パケット認可、nftables でブロック）、fwknop 2.6.11（同じく SPA、iptables でブロック）、そして fnOS のノッキング fn-knock 2.5.11（Web でログインした後に接続元 IP を許可し、そのゲートウェイがトラフィックを転送）です。Gately には Web ログイン後に許可する入口もあり、別のグループとして扱います。保護対象は TCP ポート上の nginx サービスで、クライアントはインターネット側のテスト用アドレスを使うため、「内部ネットワークからはノック不要」の影響を受けません。

- Gately と fwknop は開放後にファイアウォールが直接通過させ、トラフィックはノックプログラムを経由しないため、スループットは直接接続と同じです。fn-knock は通常の Linux ではゲートウェイ経由で転送し、新しい接続ごとにコントロールプレーンへ認可を問い合わせるため、短い接続のスループットは直接接続の 3% です。fn-knock には fnOS の fpk 版にファイアウォール直結モードもありますが、ここでは Docker 版を測っています。
- fn-knock のログインでは、先に ALTCHA のプルーフ・オブ・ワークを解く必要があります（このテストでの解答時間は p50 で 28 ms）。解答を除いた値は 50 ms です。
- fwknopd は 1 スレッドでパケットを 1 つずつ処理し、単一の接続元から 5 万パケット/秒が来ると 1 コアを使い切り、正規のノックが失敗し始めます。Gately は接続元ごとにレート制限をかけるため、単一の接続元からのフラッドでも CPU はほとんど使いません。
- 既知の問題：攻撃者が多数の異なる接続元アドレスを偽装すると、Gately の接続元ごとのレート制限テーブルが埋まり、新しい接続元が共有するオーバーフロー枠がフラッドで使い果たされて、正規のノックの大半が失敗します（このときの Gately の CPU は約 19% です）。fwknop はレート制限をしないため、CPU が飽和するまで影響を受けません。

## ダイナミック DNS

各プログラムに DDNS タスクを 20 個、チェック間隔 30 秒で設定します。グローバル IP はローカルのオリジンから取得し、更新は「カスタムコールバック」でローカルのオリジンへ送るため、実際の DNS プロバイダーには触れません。起動して最初の同期が済んだ後、5 分間サンプリングします。

<BenchBars title="DDNS タスク 20 個時の平均メモリ" unit="MiB" better="lower" :digits="1" :better-label="L" :items="[['ddns-go',16.9],['Gately',51.6],['Lucky',131.3]]" />

| プログラム | 平均メモリ | ピークメモリ | 平均 CPU | イメージ |
| --- | --- | --- | --- | --- |
| ddns-go 6.17.9 | **16.9 MiB** | **18.2 MiB** | **0.04%** | 43 MB |
| Gately | 51.6 MiB | 55.4 MiB | 0.16% | 229 MB |
| Lucky 3.8.1 | 131.3 MiB | 134.9 MiB | 0.48% | 58 MB |

- 3 つとも、IP が変わったときか強制同期の周期が来たときだけプロバイダーにリクエストするため、常駐時の負荷はいずれも小さくなります。DDNS だけが必要なら ddns-go が最もメモリを節約できます。Gately の数値は全モジュール分を含み、同じプロセスで証明書、リバースプロキシ、その他の機能も同時に動かせます。

## OpenWrt ソフトルーター

ImmortalWrt 25.12.1 のソフトルーター VM（2 vCPU、メモリ 1 GB）で各プログラムを動かします。負荷マシンは LAN ブリッジ経由でルーターにアクセスし、ルーターは負荷マシン上のオリジンへリバースプロキシします。nginx 1.26.3 と HAProxy 3.2.21 は ImmortalWrt のパッケージリポジトリのもの、Gately は公式の OpenWrt apk パッケージ、Lucky は公式の Linux バイナリを使います。

<BenchBars title="ソフトルーター上の HTTPS リクエスト/秒（持続接続）" unit="QPS" :better-label="H" :items="[['nginx',40665],['HAProxy',36266],['Gately',15669],['Lucky',8113]]" />

| プログラム | HTTP | HTTPS | TLS 新規/秒 | 2000 QPS 時の CPU | アイドル時メモリ | 負荷時ピーク | プログラムサイズ |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **Gately** | 16,439 | 15,669 | 2,665 | 27% | 43 MiB | 65 MiB | 40.5 MB |
| nginx | **49,566** | **40,665** | **3,111** | **12%** | **15 MiB** | **22 MiB** | **0.8 MB** |
| HAProxy | 43,046 | 36,266 | 2,337 | 12% | 24 MiB | 29 MiB | 3.7 MB |
| Lucky | 8,642 | 8,113 | 2,021 | 44% | 64 MiB | 81 MiB | 17.9 MB |

- ルーターのボトルネックは主にカーネルのネットワーク送受信（ソフト割り込み）で、どのプログラムも 2 コアを使い切っていないため、負荷マシンでの差より小さくなります。Gately のスループットは Lucky の約 2 倍で、メモリは 3 分の 1 少なくなります。
- OpenWrt のカーネルには smaps がないため、ここでのメモリは `/proc/<pid>/statm` から推定しています（各プロセスのプライベート常駐メモリの合計に共有部分 1 つ分を加えたもの）。テスト中はファイアウォール既定の SYN フラッド保護（毎秒約 25 個の新規接続）を一時的に無効にしました。有効のままだと TLS 新規接続のテストがそこで頭打ちになるためです。
- リバースプロキシだけなら、パッケージリポジトリの nginx がサイズもメモリも最小です。Gately の 40 MB は全モジュールを含み、[build.gately.cn](https://build.gately.cn) で必要なモジュールだけを選べば、より小さなインストールパッケージを生成できます。フラッシュ容量の小さいルーターでは、先に空き容量を確認してください。

## オールインワン

1 つの Gately で次をすべて同時に有効にします。リバースプロキシサイト 2 つ（HTTP と HTTPS、いずれも WAF 有効）、Web 認証サイト 1 つ、DDNS タスク 20 個、侵入防御のログルール 1 つ、ポートノッキングのルール 1 つです。比較対象は、同じ機能を個別のツールで実現した組み合わせで、前述の各実測アイドル時メモリを足し合わせています。

- Gately のオールインワンインスタンスは、WAF を通る HTTPS トラフィック 1000 リクエスト/秒のとき、メモリピーク 114 MiB、CPU 71% で、20 個の DDNS タスクはすべて同期に成功しました。
- 証明書の取得（certbot、acme.sh）は更新時だけ実行されるため、常駐メモリには含めていません。

## 再現手順

```bash
git clone https://github.com/wangwanjie/gately && cd gately/tools/benchmark
# Debian 13 の VM で root として実行。Docker と wrk、oha、h2load が必要
bash provision-debian.sh
python3 lib/run.py gately 3     # リバースプロキシ。nginx、haproxy、caddy、traefik、lucky、npm に置き換え可能
bash auth/run.sh                # Web 認証
bash waf/run.sh                 # WAF
bash guard/run.sh               # 侵入防御
bash knock/run.sh               # ポートノッキング
bash scale/run.sh 1000          # 1000 サイト
bash ddns/run.sh 20             # ダイナミック DNS
bash bundle/run.sh              # オールインワン
bash router/run.sh              # ソフトルーター（別途 OpenWrt マシンが必要）
```

各ディレクトリの README に、設定、測定方法、既知の制限が書かれています。結果はハードウェア、仮想化、設定によって変わるため、自分の業務負荷で再テストすることをお勧めします。
