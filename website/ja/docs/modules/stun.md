# STUN 穿孔

回線事業者から固定の公開ポートが提供されない場合、STUN 穿孔は NAT ホールパンチングで公開側のマッピングアドレスとポートを取得し、外部から LAN 内のサービスへアクセスできるようにします。

## 機能

- TCP / UDP の穿孔とキープアライブ
- UPnP / NAT-PMP によるルーターへのポートマッピングの自動作成
- 内蔵フォワーディング。穿孔で得た公開ポートを LAN 内のターゲットへ直接転送
- 公開アドレスやポートが変化したときに Webhook とスクリプトを実行。DNS の更新やクライアントへの通知に利用できます
- 内蔵転送の送信元 IP アクセス制御（許可リスト / ブラックリスト）。

## 組み合わせ

STUN で得られる公開ポートは通常変化するため、次のものとの併用をおすすめします。

- [ダイナミック DNS](/ja/docs/modules/ddns)、または Webhook / スクリプトで、新しいアドレスを DNS に同期する（ダイナミック DNS のレコード値には `{STUN_ルール名_PORT}` などの変数も書け、ルールのアドレスが変わるとすぐ同期します。[レコード値の変数](/ja/docs/modules/ddns#record-vars) を参照）
- [Web サービス](/ja/docs/modules/web) で HTTPS の入口を提供する
- Web サービスのリダイレクトサイトでは `{STUN_ルール名_PORT}` などの変数でルールの現在のパブリックアドレスを参照でき、ポートが変わると自動で新しいポートへ転送します。[リダイレクト変数](/ja/docs/modules/web#redirect-vars)を参照。

## 制限と多段 NAT

- **キャリアグレード NAT（CGNAT）**：ルーターの WAN が `100.64.0.0/10` などの内部アドレスを取得している場合、貫通できるかはキャリア側 NAT の種類で決まります。フルコーン（外部の任意のアドレスからマッピングされたポートに届く）なら貫通できますが、ポート制限型や対称型ではできません。その場合は [Tailscale・frp・Cloudflare トンネル](/ja/docs/modules/tunnels) を使ってください。
- **多段 NAT での UPnP**：UPnP / NAT-PMP を有効にすると、Gately はルーター上でトンネルポートをこのホストにマッピングします。ルーターの外部アドレスが STUN で得たパブリックアドレスと異なる場合は外側にもう 1 段 NAT があり、パブリックポートはその外側のものなので、Gately はトンネルポートのマッピングだけを残し、パブリックポートの追加マッピングは行いません。
- **ローカルポートを固定してファイアウォールで許可する**：ローカルポートを空にすると起動のたびにランダムに選ばれます。ホストでファイアウォール（例：fnOS のシステムファイアウォール）を使っている場合は、ルールのローカルポートを固定し、そのポートをファイアウォールで許可してください（STUN ルール用にポート範囲を確保しておくこともできます）。許可しないと受信接続がファイアウォールで破棄され、貫通アドレスにアクセスできません。
- **TCP とルーターのコーン型 NAT**：一部のルーターでは「NAT1 / フルコーン」が UDP にしか効かず、TCP は送信時に送信元ポートが書き換えられます。TCP ルールでは UPnP を有効にするか、ルーターでトンネルポートをこのホストにマッピングしてください。

## 送信元 IP アクセス制御

内蔵転送を使う場合、各ルールに許可リストまたはブラックリストを設定し、送信元 IP で転送先への転送可否を決められます。リストと購読 IP リストの使い方は[ポート転送](/ja/docs/modules/portforward#送信元-ip-アクセス制御)と同じで、侵入防御のブロックが優先される点も同じです。リストは転送にのみ適用され、STUN 問い合わせとチャネル検査には影響しません。リストを編集しても再トラバーサルは行わず、公開ポートは変わりません。UDP はパケットごとに判定します。内蔵転送を使わない場合、外部からの接続は Gately を経由しないためリストは効きません。

## デプロイのヒント

STUN はホストのポートを直接待ち受ける必要があるため、Docker でデプロイする場合は `--network host` を推奨します。
