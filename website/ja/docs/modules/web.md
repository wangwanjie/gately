# Web サービス

ドメインごとにリバースプロキシ、リダイレクト、静的ファイル、固定テキストを提供する、Gately 共通の Web 入口です。メニューの場所：サイドバーの「Web → Web サービス」。

## 構成：リスナー、サイト、デフォルトサイト

設定は 3 層で構成されます。

1. リスナー：待ち受けポート 1 つ。フィールドは、ネットワーク（`tcp` デュアルスタック、`tcp4`、`tcp6`）、待ち受けアドレス（空欄ですべてのアドレス）、ポート、HTTPS スイッチ、最低 TLS バージョン（1.0 / 1.1 / 1.2 / 1.3）、PROXY プロトコルを受信するかどうかです。
2. サイト：リスナーの配下で、ドメインに一致する 1 つのサイト。ドメインには、完全一致のドメイン、`*.example.com`（任意の階層のサブドメインに一致）、`*`（すべてに一致）を指定できます。一致の優先順位は、完全一致、ワイルドカード、`*` の順です。
3. デフォルトサイト：一致するサイトがないときに使われます。無効の場合は 404 を返します。デフォルトサイトを「接続を切断」にすると、未知のドメインへのリクエストに一切応答しません。設定済みのデフォルトサイトはサイト一覧の最後に表示されます。まだ設定していない場合は、リスナーカードの「デフォルトサイトを設定」をクリックして設定します。

サイトまたはデフォルトサイトの変更を保存すると、サイトの一覧がその場で入れ替わります。リスナーは動き続け、開いている接続（WebSocket を含む）は維持され、各サイトの統計も引き継がれます。新しい設定が無効な場合は、以前のサイトが引き続き配信されます。リスナー自体の設定（ネットワーク、アドレス、ポート、HTTPS、最低 TLS バージョン、HTTP/3、PROXY プロトコル）を変更すると、そのリスナーが再起動します。

サイトには「グループ」を設定できます（最大 64 文字。デフォルトサイトはグループに入れられません）。一覧では、リスナーごとにグループが折りたたみ可能なセクションとして表示されます。グループは最初に現れた順に並び、グループなしのサイトはその後ろ、デフォルトサイトは常に最後です。各グループの折りたたみ状態はブラウザーに保存されます。「並べ替え」をクリックすると並べ替えモードになり、サイトの上下移動、グループ内でのドラッグ、グループ単位の移動、リスナーの並べ替えができます。順序が影響するのは一覧の表示だけで、ドメインの照合はサイトの順序に関係なく上記の優先順位に従います。並べ替えを保存したときもサイトの一覧がその場で入れ替わるため、接続は切断されません。ページ上部の検索ボックスでは、ドメイン、名前、グループ、バックエンド、メモでサイトを絞り込めます。

並べ替えモードでは複数のサイトにチェックを入れることもできます（グループ見出しのチェックボックスでグループ全体を選択）。チェックしたサイトのどれかをドラッグするとまとめて移動し、別グループのサイトや見出しにドロップするとそのグループに入ります。ツールバーではチェックしたサイトを指定グループへ一括で移動でき、名前を空欄にするとグループから外します。複数のリスナーにまたがって選択した場合はリスナーごとに保存されます。

グループ見出しにマウスを合わせて鉛筆ボタンを押すと、グループ名を変更できます。グループ内の項目もまとめて新しい名前になり、位置と順序は変わりません。既存のグループと同じ名前にすると、確認のうえ 2 つのグループが統合されます。

## サイトの種類

| 種類 | 説明 |
| --- | --- |
| リバースプロキシ | 1 つ以上のバックエンドに転送します。バックエンドのアドレス形式は `http(s)://ホスト:ポート` で、WebSocket に対応しています |
| リダイレクト | 完全な URL へ転送します。ステータスコードは 301 / 302 / 307 / 308（デフォルトは 302）で、元のパスとクエリ文字列を保持することもできます。URL には `{host}` を含められ、訪問者が使ったドメインに置き換えられます。`https://{host}` に「パスとパラメーターを保持」を組み合わせると、すべての HTTP リクエストを同じドメインの HTTPS に転送できます。`{path}`、`{1}`、`{STUN_ルール名_PORT}` などの変数も使えます。[リダイレクト変数](#redirect-vars)を参照 |
| 静的ファイル | ディレクトリは絶対パスで指定します。「ディレクトリ一覧」を無効にすると、ディレクトリへのリクエストは `index.html` がある場合にのみ返されます。「拡張子なし URL」は、ファイルが見つからないときに `パス.html` と `パス/index.html` を試します（VitePress などの生成ツール向けで、nginx の `try_files $uri $uri.html $uri/index.html` に相当）。「404 ページ」はディレクトリ内のパス（例：`404.html`）で、ステータス 404 で返されます |
| 固定テキスト | 任意の内容、`Content-Type`（デフォルトは `text/plain; charset=utf-8`）、ステータスコード（100-599、デフォルトは 200）を指定します |
| 接続を切断 | 何も返さずに接続を切断します。nginx の `return 444` に相当します。主にデフォルトサイトに使い、未知のドメインをスキャンするリクエストに応答しないようにします。アクセスログには 444 として記録されます。認証、アクセス制御、WAF、リライトを通らないため、サイトのその他の設定は効きません |

どの種類のサイトでも、アクセスログ、クロスオリジン（CORS）、カスタムのリクエストヘッダーとレスポンスヘッダー（1 行に `Key: Value`。Value を空にするとそのヘッダーを削除）を設定でき、[WAF ファイアウォール](/ja/docs/modules/waf) のインスタンスを 1 つ参照することもできます（インスタンスが存在しない、または無効の場合はそのまま通します）。リクエストヘッダー、レスポンスヘッダー、Content-Type の編集方法は [リクエストヘッダーとレスポンスヘッダー](#headers) を参照してください。

アクセスログにはクライアント IP、メソッド、ドメインとパス、ステータスコード、処理時間、サイト名が記録され、行末に nginx 形式で Referer と User-Agent（ない場合は `-`）が付きます。同じグローバル IP の背後にある別々の端末を User-Agent で見分けられます。サイト、ステータスコード、接続元 IP などでログを絞り込めます。[実行ログの表示と絞り込み](/ja/docs/guide/configuration#log-filter)を参照してください。

### リダイレクト変数 {#redirect-vars}

リダイレクトサイトの転送先には次の変数を使えます：

| 変数 | 意味 |
| --- | --- |
| `{host}` | 訪問者がリクエストしたドメイン（ポートなし） |
| `{port}` | アクセスしたポート |
| `{hostAndPort}` | ドメインとポート。リクエストの Host と同じ |
| `{path}` / `{PATH}` | リクエストパス。`{PATH}` は先頭の `/` なし |
| `{args}` / `{Args}` | クエリ文字列。`{args}` は先頭の `?` 付き（クエリがなければ空）、`{Args}` は `?` なし |
| `{domainPartN}` / `{pathPartN}` | ドメイン（`.` 区切り）またはパス（`/` 区切り）の N 番目の部分。N は 1 から |
| `{ClientIP}` / `{RemoteIP}` | クライアント IP |
| `{time}` | 現在時刻。形式は `2006-01-02 15:04:05` で、リダイレクト先が正しい URL になるよう空白は `%20` と書きます（`2006-01-02%2015:04:05`） |
| `{1}` | サイトドメイン `*.example.com` の `*` に一致した部分。完全一致のドメインでは空、`*` やデフォルトサイトではドメイン全体 |
| `{STUN_ルール名_PORT}` / `{STUN_ルール名_IP}` / `{STUN_ルール名_ADDR}` | [STUN トラバーサル](/ja/docs/modules/stun) ルールの現在のパブリックポート、IP、`IP:ポート`。ルール名は一覧に表示される名前で、アンダースコアを含めても構いません |

- 「パスとパラメーターを保持」がオンのとき、転送先に `{path}`、`{PATH}`、`{pathPartN}` を書くと元のパスを、`{args}`、`{Args}` を書くか転送先に独自のクエリがあると元のクエリを追加しません。もう一方はこれまでどおり追加します；
- STUN のポートが変わってもサイトを編集する必要はなく、次のリクエストから新しいポートへ転送します。参照したルールが存在しない、無効、まだトラバーサルに成功していない、または自動再試行中の場合、サイトは 503 を返し、実行ログに理由を記録します；
- 変数を展開した転送先にホストがない場合（完全一致のドメインで `{1}` が空なのに転送先が `https://{1}` だけ、など）は 503 を返します。訪問者のホストに `&`、`=`、`/`、`@` などドメインに現れない文字が含まれる場合は 400 を返し、転送先には代入しません；
- サイトドメインの `*` は 1 つだけなので、使えるのは `{1}` のみです；
- パス書き換えルールのリダイレクト先は引き続き `{host}` のみ対応です。未知の `{xxx}` はそのまま残ります。

例：Cloudflare CDN が `*.example.com` を本機の 2053 ポートへ転送し、そのリスナーにドメイン `*.example.com` のリダイレクトサイトを置き、転送先を `https://{1}.v4.example.com:{STUN_web_PORT}{path}{args}` にします。`zly.example.com/a?b=1` へのアクセスは `https://zly.v4.example.com:<STUN ポート>/a?b=1` に転送されます。STUN ルール web は別のリスナーへ転送し、そこで `*.v4.example.com` 配下の各ドメインのリバースプロキシサイトを作成します。

### リバースプロキシのオプション {#proxy-options}

サイト編集画面の「基本」タブにある「オプション」です。横の疑問符アイコンから、画面上で簡単な説明を確認でき、この節へ移動できます。

| オプション | 動作 | オンにする場面 |
| --- | --- | --- |
| バックエンドの証明書検証をスキップ | HTTPS バックエンドへの接続時に証明書を検証しません | バックエンドが自己署名や期限切れの証明書を使っている場合（NAS やルーター管理画面の https ポートなど）。バックエンドの身元を確認できなくなるため、LAN 内のバックエンドにのみ使ってください |
| Host にバックエンドのアドレスを使用 | バックエンドへ送る Host ヘッダーをバックエンドのアドレスにします。オフ（既定）では訪問者がリクエストした Host を保持します | バックエンドが自身のアドレスしか受け付けない場合（400 / 403 になる、誤ったアドレスへ転送される、Host 不一致と表示されるなど）。公開サイトや CDN へのプロキシでは通常必要です。バックエンドがドメインでサイトを分けている、またはアクセス先ドメインでリンクを生成する場合はオフのままにします |
| 接続の再利用を無効化 | リクエストごとにバックエンドへの接続を新しく張ります（Keep-Alive 無効） | 接続のリセットやリクエストの停止が時々起きる、または持続的接続に対応していないバックエンド。遅延が少し増えるため、通常はオフのままにします |
| X-Forwarded-* を付与 | `X-Forwarded-For` / `X-Forwarded-Proto` / `X-Forwarded-Host` / `X-Forwarded-Port` と `X-Real-IP` を書き込み、訪問者の実 IP、元のプロトコル、ドメイン、ポートをバックエンドに伝えます | バックエンドで実 IP を記録したい、または外部が HTTPS であることを知らないと正しいリンクを生成できない場合（http に戻される、ログイン後にループするなど）。多くのアプリで推奨です |
| バックエンドへ PROXY v2 を送信 | TCP 接続の先頭に PROXY プロトコル v2 ヘッダーを付け、実際のクライアント IP を渡します。オンにするとリクエストごとに新しい接続を張り、バックエンドへの HTTP/2 も使いません。バックエンドが Gately の場合は、そのリスナーで PROXY プロトコルの受信を有効にし、このホストを信頼する PROXY 送信元に追加します。 | HTTP ヘッダーを読まないが PROXY プロトコルに対応するバックエンド（別の Gately、haproxy、`proxy_protocol` を有効にした nginx など）。受け入れ設定がないとすべてのリクエストが失敗するため、不明ならオフのままにします |
| アクセス先ドメインを SNI に使う | HTTPS バックエンドのみ：ハンドシェイクで訪問者が使ったドメインを送り、それに対して証明書を検証します。nginx の `proxy_ssl_server_name on; proxy_ssl_name $host` に相当します | 同じポートでドメインごとに証明書や振り分けを行うバックエンド（frp の `vhost_https`、複数の HTTPS サイトを持つ nginx など）。バックエンドごとに独自の接続プールを持つため、ドメイン間で接続が再利用されることはありません |
| Gately のログイン Cookie を転送 | Gately 自身のログイン Cookie（シングルサインオンの `gately_sso`、サイトのセッション、外部ログインのノンス）をそのままバックエンドに渡します。オフ（既定）ではこれらの Cookie をバックエンドに送らず、ログイン資格情報の漏えいを防ぎます | バックエンドが認証を担当する別の Gately で、このサイトでは認証を行わない場合。例：公開側の Gately は WAF とアクセス制御だけを行って LAN 側の Gately にプロキシし、LAN 側の Gately が Web 認証とシングルサインオンを担当する構成。このサイトで認証を有効にしている間は使えません。バックエンドが自分の Gately の場合のみ使用してください |

よくある組み合わせ：

- LAN 内の Web アプリ（例：`http://192.168.1.10:5000`）をプロキシする：「X-Forwarded-* を付与」だけをオン
- バックエンドが自己署名証明書の https アドレス：さらに「バックエンドの証明書検証をスキップ」をオン
- 公開サイトや外部サービスをプロキシする：「Host にバックエンドのアドレスを使用」をオン
- バックエンドの前に SNI で振り分けるサービスがある（例：frp `vhost_https`）：「アクセス先ドメインを SNI に使う」をオン
- 公開側 Gately は WAF のみ、LAN 側 Gately がログインを担当：公開側のサイトでは認証を行わず「Gately のログイン Cookie を転送」をオンにし、実際の IP が必要なら「バックエンドへ PROXY v2 を送信」もオンにして、LAN 側 Gately で PROXY プロトコルを受け付け、公開側 Gately を信頼済みの送信元に追加します。

### リクエストヘッダーとレスポンスヘッダー {#headers}

サイト編集画面の「ヘッダー」タブで設定します。リクエストヘッダーはバックエンドへ送られ、リバースプロキシサイトでのみ有効です。レスポンスヘッダーはクライアントへ返され、すべての種類のサイトで有効です。

- 行ごとの編集：名前欄をクリックするとよく使うヘッダーと用途が一覧表示され、選ぶと代表的な値が自動入力されます。値欄でも他の代表的な値を選べます。どちらも直接入力できます。値を空にするとヘッダーを削除し、名前欄に `Key: Value` の行を貼り付けると自動で分割されます。
- 「よく使うセキュリティヘッダーを追加」は `X-Content-Type-Options: nosniff`、`X-Frame-Options: SAMEORIGIN`、`Referrer-Policy: strict-origin-when-cross-origin` を追加します。既存のヘッダーは重複して追加しません。
- 「テキストモード」では複数行の `Key: Value` をまとめて貼り付けられ、行ごとの編集に戻しても内容は保持されます。
- 「パス別バックエンド」の各パスの追加リクエストヘッダーも同じ方法で編集でき、サイトのリクエストヘッダーの後に適用されます。同名の場合はパスの設定が優先されます。

各行の下にリアルタイムでフィードバックが表示されます。赤は保存に失敗するかヘッダーが効かないことを示します（名前がない、名前に空白やコロンなどの不正な文字がある、テキストモードでコロンがないなど）。オレンジは保存できるものの、期待どおりにならない可能性があることを示します：

- リクエストヘッダーで設定した `Host` は反映されません。書き換えるには「Host にバックエンドのアドレスを使用」をオンにします。
- `X-Forwarded-For`、`X-Real-IP` に固定値を書くと実際のクライアント IP を上書きします。クライアント IP を渡すには「X-Forwarded-* を付与」をオンにします。
- `Content-Length`、`Connection`、`Transfer-Encoding` などは接続が自動管理するため、手動設定は無視されるか転送異常の原因になります。
- 値はそのまま送信され、nginx の `$host` などの変数には対応していません。プリセット値の `<token>` などのプレースホルダーは置き換えが必要です。
- 同名のヘッダーは順に設定され、後のものが優先されます。

「固定テキスト」サイトの `Content-Type` はよく使う種類から選ぶか直接入力できます。画面では `タイプ/サブタイプ; パラメーター=値` の形式を確認し、`text/*` で `charset` が未指定のときは日本語などが文字化けする可能性を知らせます。空欄の場合は `text/plain; charset=utf-8` を使います。

## トランスポートとプロトコル

- HTTPS：[SSL 証明書](/ja/docs/modules/ssl) モジュールで、そのドメインをカバーする証明書が使われます。
- 同一ポートの HTTP：HTTPS を有効にしたリスナーは平文 HTTP も受け付けられ、接続の最初の 1 バイトでプロトコルを判別します。「HTTPS へリダイレクト」は `http://ホスト:ポート` を `https://ホスト:ポート` へ転送し（GET/HEAD は 301、その他のメソッドは 308）、ポートが 1 つしか使えずスキームの打ち間違いにも対応したい場合に便利です。「そのまま提供」は暗号化なしの HTTP でサイトを返します。ACME HTTP-01 の検証リクエストには通常どおり応答し、この設定を変えるとリスナーが再起動します。
- HTTP/3（QUIC）：HTTPS を有効にしたリスナーでオンにすると、同じポート番号の UDP でも HTTP/3 を提供し、`Alt-Svc` レスポンスヘッダーでブラウザに通知します。ファイアウォールとポートマッピングでその UDP ポートを許可する必要があります。
- WebSocket：リバースプロキシで自動的に対応します。
- PROXY プロトコル：リスナーは上流（haproxy、frp など）から送られる PROXY ヘッダーを受信できます。信頼するのは「全体設定 → 信頼する PROXY 送信元」に挙げた IP またはセグメントだけで、空欄の場合はどの送信元も信頼しません。リバースプロキシはバックエンドへ PROXY ヘッダーを送信することもできます。信頼する送信元から入った接続の `X-Forwarded-Proto: https` も採用されます：セッション Cookie に Secure が付き、平文 HTTP をリダイレクトするポートでもリダイレクトせず、「X-Forwarded-* を付与」がオンならバックエンドにも https を渡します。

## 認証

サイト編集ダイアログの「セキュリティ」タブで設定します。

- Web 認証：ブラウザにログインページを表示します。
- Basic 認証：HTTP Basic。
- ユーザー：1 行に `ユーザー名:パスワード`。パスワードには bcrypt ハッシュも指定できます。Basic 認証を有効にするには少なくとも 1 人のユーザーが必要で、Web 認証を有効にするには少なくとも 1 人のユーザーまたは外部ログインの ID が必要です。
- 外部ログイン：GitHub、Google、QQ、OIDC に対応し、自分の OAuth アプリを使います。許可する ID は 1 行に 1 件、形式は `プロバイダー識別子:アカウント` で、たとえば `github:octocat`、`google:me@gmail.com` のように書き、行末に `#` に続けてメモを付けられます。`github:*` はそのプロバイダーの任意のアカウントを表します。

外部ログインのプロバイダーは「全体設定」で設定します。自分の Client ID / Secret を入力して有効にし、同時にコールバックアドレスを設定してください（Gately のいずれかのリスナーで提供される必要があります。例：`https://auth.example.com`）。GitHub / Google / QQ に登録するコールバック URL は次のとおりです。

```text
https://auth.example.com/__gately_auth/oauth/callback
```

管理画面自体の外部ログインは、「設定 → アカウントとセキュリティ」で別途設定します。

### フォワード認証（Authelia など）

認証を外部サービスに任せます。nginx の `auth_request` や Traefik の `forwardAuth` と同じ仕組みです。「セキュリティ」タブで「フォワード認証」にチェックを入れます。同じサイトで Basic 認証や Web 認証と併用することはできません。

| フィールド | 説明 |
| --- | --- |
| `url` | チェック用のエンドポイント。Authelia の `http://127.0.0.1:9091/api/authz/auth-request` など |
| `loginUrl` | エンドポイントが 401 を返したときに訪問者を送る先。例：`https://auth.example.com/?rd={url}&rm={method}`。`{url}` は元のアドレス（URL エンコード済み）、`{method}` はリクエストメソッドです。空の場合は、エンドポイントの応答をそのまま返します |
| `copyHeaders` | エンドポイントの応答からバックエンドへのリクエストにコピーする ID ヘッダー。デフォルトは `Remote-User`、`Remote-Groups`、`Remote-Email`、`Remote-Name` |

仕組み：

- すべてのリクエストは、まず `url` に本文なしの GET として送られます。訪問者のヘッダー（Cookie、`Authorization` など）に加えて、`X-Original-Method`、`X-Original-URL`、`X-Forwarded-Method`、`X-Forwarded-Proto`、`X-Forwarded-Host`、`X-Forwarded-Uri`、`X-Forwarded-For`、`X-Real-Ip` が付きます。タイムアウトは 10 秒です。
- 2xx の応答ならリクエストを通し、ID ヘッダーを付与します。401 は `loginUrl` へリダイレクトします（ステータス 302）。403 やリダイレクトなどそれ以外の応答は訪問者にそのまま返し、サービスに到達できない場合は 502 になります。
- 訪問者が送った ID ヘッダーは常に削除されるため、偽装できません。
- パスルールと「認証の対象範囲」に対応しているため、一部のパス（例：`/admin`）だけログインを必須にできます。一時共有リンクとも併用できます。

### 共有ユーザー：TOTP とシングルサインオン {#shared-users}

アカウントを一度定義すれば複数のサイトで使え、TOTP による 2 段階認証も任意で追加できます。多くの人が Authelia を使う目的をカバーします。

サイドバーの「Web → 認証ユーザー」ページで次を設定します（Web サービスの全体設定ダイアログには概要とリンクだけが表示されます）。

- ユーザーを追加するには、ユーザー名とパスワードを入力します。パスワードは bcrypt ハッシュで保存され、API から返されることはありません。TOTP を追加するには、「TOTP を有効化」を押し、認証アプリ（Google Authenticator、1Password など）で QR コードを読み取って保存します。キーを再生成すると、古いキーは無効になります。
- メールアドレス、表示名、グループは任意で入力できます。[OIDC シングルサインオン](/ja/docs/modules/oidc) はこれらを `email`、`name`、`groups` クレームとしてアプリに渡し、OIDC クライアントの許可ユーザーでは `group:グループ名` でグループ単位に許可できます。
- SSO ドメイン（例：`example.com`）：そのドメインまたはサブドメインのいずれかのサイトでログインすると、そこにある他のサイトでは再ログインが不要になります。親ドメインの Cookie（`gately_sso`、有効期間 7 日）を使い、この Cookie はバックエンドには転送されません。空にすると、サイトごとに個別にログインします。

サイトでは、Web 認証または Basic 認証の横にある「共有ユーザーを使う」にチェックを入れます。サイト独自のユーザーも引き続き使えます。「認証ユーザー」ページのサイト一覧では、リスナーごとに表示・絞り込みしてまとめてチェックすることもできます。認証が無効のサイトをチェックすると Web 認証も有効になります。共有ユーザーだけで認証しているサイトは、誤ってログインなしで公開されないよう、ここではチェックを外せません（公開する場合はサイト設定で認証を無効にしてください）。フォワード認証を使うサイトでは共有ユーザーを使えません。ページ上のユーザー、OIDC、サイトの変更は下部の「保存」でまとめて反映され、どれか一つでも検証に失敗すると何も保存されません。未保存の変更があるままページを離れようとすると確認が表示されます。

動作：

- 共有ユーザーのいずれかが TOTP を使っている場合、ログインページに認証コードの入力欄が表示されます。各コードは 1 回だけ使えます。
- ユーザーのパスワードまたは TOTP キーを変更すると、そのユーザーのセッションは終了します。
- Basic 認証で使えるのは、TOTP のない共有ユーザーだけです。ブラウザのパスワード入力画面にはコードを入力する場所がないためです。
- 失敗した試行は、他のログインと同じレート制限と自動ブロックの対象になります。

Gitea、OpenList、Grafana などのアプリにログインしたユーザーを識別させたい場合は、[OIDC シングルサインオン](/ja/docs/modules/oidc) で共有ユーザーをアプリに提供できます。

### パスワードのセルフ変更 {#self-service-password}

「認証ユーザー」ページで「パスワードのセルフ変更」をオンにすると、共有ユーザーは管理者に頼まずに自分でパスワードを変更できます。

- 「共有ユーザーを使用」が有効なサイトで `https://サイトのドメイン/__gately_auth/password` を開きます。ログインページにも「パスワードを変更」リンクが表示されます。[OIDC シングルサインオン](/ja/docs/modules/oidc)の利用者は発行者ドメインの `/__gately_oidc/password` を使えます。
- ユーザー名、現在のパスワード、新しいパスワード（8〜128 文字で現在のものと異なること）を 2 回入力します。TOTP を有効にしたユーザーはワンタイムコードも入力します。
- 変更後、そのユーザーの各サイトのセッションはすぐに無効になり、新しいパスワードで再ログインします。発行済みの OIDC リフレッシュトークンは失効し、古い Access Token でもユーザー情報を読み取れなくなります。アプリが自分で検証するトークンは有効期限まで有効で、アプリ自身のログインセッションもそのまま残ります。
- 同じアカウントは変更に成功してから 1 分間は再度変更できません。繰り返しの変更で FTP や SMB が再読み込みを繰り返し、他の人の接続が切れるのを防ぐためです。保存時にサービスのチェックで拒否された詳しい理由は Web サービスのログにだけ記録され、画面には管理者への連絡を促すメッセージだけが表示されます。
- 現在のパスワードやコードの誤りはログイン失敗と同じレート制限・自動ブロックの対象で、他のサイトから送信されたフォームは拒否されます。Web サービスのログに変更したユーザーと送信元 IP が記録されます。
- 同じページで[ファイルサービス共有ユーザー](/ja/docs/modules/tools#shared-users)のパスワードも変更できます。2 種類のアカウントは個別にオン・オフでき、両方オンのときはページでアカウントの種類を切り替えます。同名の 2 種類のアカウントは互いに影響しません。

## アクセス制御

### IP のブラックリスト・ホワイトリスト

サイトの「セキュリティ」タブにある「IP アクセス制御」では、オフ、許可リスト、拒否リストを選べます。リストは 1 行に 1 つの IP またはセグメント（例：`192.168.1.0/24`）を書きます。購読 IP リストもあわせて参照できます。

### 拒否時の動作

サイトの「セキュリティ」タブの「拒否時の動作」で、ブロック、IP アクセス制御（パスルールを含む）、国フィルターで拒否されたリクエストの扱いを決めます。既定は「403 を返す」です。「接続を切断」を選ぶと何も返さずに切断し、アクセスログには 444 として記録されます（「接続を切断」サイトと同じ）。ホワイトリストと組み合わせると「自分の IP は通常どおりアクセス、それ以外はすべて切断」にできます。レート制限（429）と WAF のブロックには影響しません。

接続の切断（サイトの種類でも拒否時の動作でも）は HTTP の応答を返さないだけで、サービスが動いていることは隠せません。

- TCP ハンドシェイクは完了しているため、相手はポートが待ち受けていることを確認できます。
- HTTP/1.x では接続を閉じますが、HTTP/2・HTTP/3 ではこのリクエストだけをリセットし、接続は維持されるため再利用できます。
- HTTPS では、証明書のないドメインは TLS ハンドシェイクの段階で失敗します。デフォルトサイトに届くリクエストは証明書を受け取っており、証明書内のドメインは既に知られています。

以後スキャナーにタイムアウトだけを見せるには、[侵入防御](/ja/docs/modules/guard)でそのアドレスをブロックしてください。ファイアウォール同期を有効にすると、カーネルでトラフィックを破棄します。

### 購読 IP リスト

「全体設定 → 購読 IP リスト」でリストを追加します。ダウンロード URL と更新間隔（既定は 24 時間）を入力すると、Gately が定期的にダウンロードして設定ディレクトリにキャッシュするため、再起動後もネットワークに接続せずに使えます。内容は 1 行に 1 つの IP、CIDR、または `開始-終了` の範囲で、`#`、`;`、`//` 以降はコメントです。たとえば中国の省・市の IP 範囲には [metowolf/iplist](https://github.com/metowolf/iplist) の `https://metowolf.github.io/iplist/data/cncity/440000.txt`（広東省）が使えます。

- サイトとパスルールの許可リスト・拒否リストは複数のリストを参照でき、手入力した IP 範囲と合わせて判定し、いずれかに一致すればリスト内とみなします。
- ダウンロードした内容を解析できない場合（エラーページが返された場合など）は前回のリストを保持し、リストに理由を表示して 1 時間後に再試行します。
- ダウンロードが成功するまでは空のリストとして扱います。そのため許可リストではアクセスが拒否され、拒否リストでは追加のブロックは行われません。
- サイトから参照されているリストは削除できません。

### パスルール

「セキュリティ」タブの「パスルール」では、パスの接頭辞ごとにサイトの認証と IP の設定を上書きできます。

| フィールド | 値 |
| --- | --- |
| `prefix` | `/` で始まるパスの接頭辞。例：`/admin` |
| `auth` | サイトの設定を引き継ぐ（空）、`off`（認証不要）、`on`（認証必須） |
| `ipMode` / `ipList` | サイトの設定を引き継ぐ（空）、`whitelist`、`blacklist`。あわせて IP またはセグメントのリストを指定 |

一致のルール：

- 最も長い接頭辞が優先されます。
- パスセグメントの境界で照合されます。`/admin` は `/admin` と `/admin/x` に一致し、`/administrator` には一致しません。
- リクエストパスは先に正規化（`.`、`..`、重複したスラッシュを除去）してから照合され、`/public/../admin` は `/admin` として扱われます。
- 同じ接頭辞には 1 つのルールしか設定できません。

「認証範囲」オプション（`authOptional`）：チェックを入れると、認証は「認証必須」とされたルールのパスにのみ適用され、それ以外のパスは公開されます。このオプションを使うには、先に Basic 認証または Web 認証を有効にする必要があります。

### 一時共有リンク

Basic 認証または Web 認証を有効にすると、サイトに共有リンクを作成して、アカウントのないゲストにアクセスさせることができます。

| フィールド | 説明 |
| --- | --- |
| 名前 | メモ用の名前。例：「張さん用」 |
| 有効期限 | 空欄で無期限 |
| 利用回数 `maxUses` | 引き換えられる最大回数。0 で無制限。再起動するとカウントはリセットされます |
| パス制限 `pathPrefix` | 空でない場合、リンクはこの接頭辞配下のパスにしかアクセスできません。`/` で始める必要があります |

ゲストが `https://ドメイン/任意のパス?_gs=トークン` にアクセスすると、セッションに引き換えられます。引き換えに成功すると、サーバーはログイン不要の Cookie を設定し、`_gs` パラメーターを除いたアドレスへリダイレクトします。セッションは最長 24 時間で、リンクの有効期限を超えることはありません。トークンが無効な場合は通常のアクセスとして扱われ、失敗の理由は明かされません。リンクを削除すると、発行済みのセッションは直ちに無効になります。トークンは保存後に生成され（16 文字以上）、画面から完全なリンクをコピーできます。

### 認証失敗のレート制限と自動ブロック

- 同じ送信元 IP が 15 分間に 10 回認証に失敗すると、しばらく試行が拒否されます。
- 「全体設定 → 自動ブロック → 認証失敗によるブロック」に分数（0 〜 43200）を入力すると、10 回失敗した時点で送信元 IP をブロックします。0 の場合はブロックせず、レート制限のみです。
- 自動ブロックが発動すると `AuthBanned` イベントが発行され、[通知センター](/ja/docs/modules/notify) から通知できます。
- IPv6 アドレスは /64 セグメント単位で集計・ブロックされます。

### ブロックリスト

「全体設定」のブロックリストには、現在ブロックされている IP、理由（認証の連続失敗または手動ブロック）、期限が表示され、「解除」を押せます。手動でブロックすることもでき、IP と時間数（1 〜 720、最長 30 日）を入力します。API のデフォルトは 24 時間です。

ブロック一覧は[侵入防御](/ja/docs/modules/guard)と共通です。侵入防御モジュールが有効な場合、ここにはブロック件数だけが表示され、侵入防御のページで管理します。ブロックはポート転送や STUN などにも適用され、ファイアウォール同期がオンならシステムファイアウォールで破棄されます。「LAN アドレスを無視」がオンなら LAN のアドレスは自動でブロックされません。

### GeoIP による国フィルター

サイトの「国フィルター」には、オフ、許可のみ、拒否の 3 つのモードがあり、2 文字の ISO 国コードをカンマ区切りで入力します（例：`CN, HK, US`）。有効にするには少なくとも 1 か国を入力します。

- フィルターは GeoIP データベースに依存するため、先に「全体設定 → GeoIP データベース」でインポートします。`.mmdb` ファイルをアップロードするか、ダウンロード URL を入力してください。MaxMind GeoLite2、DB-IP などの国データベースまたは都市データベースに対応しており、アップロードの上限は 129 MB です。
- データベースが読み込まれていない場合、フィルターは機能せず（すべての訪問者を通します）、画面に通知が表示されます。
- LAN 内のアドレスは常に通します。
- 「拒否」モードでは、データベースで国が引けないアドレスは通します。

## パス別バックエンド

リバースプロキシサイトで、パスの接頭辞ごとに別のバックエンドへリクエストを振り分けます。nginx の `location /api/ { proxy_pass ...; }` に相当します。サイト編集ダイアログの「基本」タブにある「パス別バックエンド」で追加します。

| フィールド | 説明 |
| --- | --- |
| `prefix` | `/api/` のようなパスの接頭辞。パスセグメントの境界で照合され、`/api` と `/api/` はどちらも `/api` と `/api/x` に一致し、`/apix` には一致しません |
| `targets` | このパスのバックエンド。サイトのバックエンドと同じ書き方です。空の場合はサイトのバックエンドを使い、下のヘッダーだけを追加します |
| `requestHeaders` | このパスで追加するリクエストヘッダー。1 行に `Key: Value`。サイトのヘッダーの後に適用され、同名のヘッダーはサイトの設定を上書きします |

- 最も長い接頭辞が優先され、パスはそのまま転送されます（接頭辞は取り除かれません）。
- Host オプション、証明書の検証、転送ヘッダー、PROXY プロトコル、負荷分散ポリシー、ヘルスチェックなど、サイトのその他の設定はすべてのパス別バックエンドに適用されます。
- 圧縮、レート制限、キャッシュ、書き換えはサイト全体に適用されます。

## ユーザー別振り分け {#user-routes}

リバースプロキシサイトで、ログインしたユーザーごとにリクエストをそれぞれのバックエンドへ送ります。nginx の `map $remote_user $backend` に相当します。サイトで Basic 認証、Web 認証、フォワード認証のいずれかを先に有効にし、サイト編集ダイアログの「セキュリティ」タブにある「ユーザー別振り分け」でルールを追加します。各ルールにはユーザーの集合と、それらのユーザー用のバックエンドを指定します。バックエンドの書き方はサイトのバックエンドと同じです。

ユーザーは次の識別子で照合されます。

- サイトユーザーまたは[共有ユーザー](#shared-users)のユーザー名。
- 外部ログインの ID は `プロバイダーkey:ID` の形式で書きます（例：`github:octocat`）。その ID の他の識別子でも一致します。
- フォワード認証では、認証サービスのレスポンスからコピーされた `Remote-User`。

振り分けのルール：

- 一覧にないユーザーと、公開パス（認証不要のパス）でログインしていない訪問者は、サイトのバックエンドを使います。Web 認証ですでにログインしている訪問者は、公開パスでも ID に基づいて振り分けられるため、同じアプリのページは同じバックエンドに届きます。
- 独自のバックエンドを持つパス別バックエンドのルール（前節を参照）が優先されます。リクエストヘッダーを追加するだけのルールは、そのユーザーのバックエンドを使います。
- 「ユーザー名を渡す」に `X-Remote-User` のようなヘッダー名を指定すると、認証済みのユーザー名をそのリクエストヘッダーに入れてバックエンドに渡します。訪問者が送った同名のヘッダーは常に削除されるため、偽装できません。
- メモリ上のレスポンスキャッシュを有効にしている場合、キャッシュキーには選ばれたユーザールートが含まれ、「ユーザー名を渡す」がオンのときはユーザー名も含まれます。そのため、バックエンドやユーザーごとのレスポンスは別々にキャッシュされます。

保存時には、サイトで認証が有効になっていること、各ルールに 1 人以上のユーザーと有効なバックエンドがあること、同じユーザーが 2 つのルールに含まれていないこと、ヘッダー名が正しく、`Host`、`Cookie`、`Authorization`、`X-Forwarded-For` など転送や認証に影響するヘッダーでないことを確認します。サイト一覧では、ユーザールートを設定したサイトにルール数のタグが表示されます。

## リバースプロキシの拡張機能

以下のオプションは、サイト編集ダイアログの「トラフィック」タブにあります。

### バックエンド、重み、バックアップ

バックエンドのリストは 1 行に 1 アドレスで、アドレスの後ろにパラメーターを付けられます。

```text
http://10.0.0.2:8080 weight=3
http://10.0.0.3:8080 backup
```

- `weight=N`：重み。1 〜 100 の整数で、デフォルトは 1 です。
- `backup`：バックアップのバックエンド。バックアップ以外のバックエンドがすべて利用できないときにのみ使われます。すべてのバックエンドが利用できない場合は、バックアップ以外のすべてのバックエンドに戻って試行を続けます。

### ロードバランシングポリシー

| 画面のオプション | `lbPolicy` | 説明 |
| --- | --- | --- |
| ラウンドロビン（重み付き） | 空 | デフォルト |
| ランダム（重み付き） | `random` | |
| IP ハッシュ（セッション維持） | `ip_hash` | 同じクライアント IP は同じバックエンドに振り分けられます |
| 最小接続数 | `least_conn` | 「接続数 / 重み」が最小のものを選びます |

### ヘルスチェック

アクティブチェックのスイッチはデフォルトでオフです。有効にしたときのフィールドとデフォルト値：

| フィールド | デフォルト値 | 範囲 |
| --- | --- | --- |
| 方式 `mode` | `http` | `http`（チェックパスにリクエストし、ステータスコードが 400 未満なら正常とみなす）または `tcp`（接続のみテスト） |
| パス `path` | `/` | `/` で始まる。http 方式のみ |
| 間隔 `interval` | 10 秒 | 1 〜 3600 |
| タイムアウト `timeout` | 3 秒 | 1 〜 60 |
| 連続失敗 `fails` | 3 回で利用不可と判定 | 1 〜 20 |
| 連続成功 `passes` | 2 回で復帰 | 1 〜 20 |

バックエンドへの PROXY プロトコル送信を有効にしている場合、HTTP チェックは自動的に TCP に切り替わります。

パッシブチェックは常に有効です。複数のバックエンドのうち、接続に 3 回連続で失敗したものは 30 秒間停止してから再度試されます（バックエンドが 1 つだけでアクティブチェックを有効にしていない場合は切り離しません）。アクティブチェックを有効にすると、復帰はチェック結果のみで決まります。バックエンドの状態が変化すると、上流の利用不可 / 復帰イベントが発行され、[通知センター](/ja/docs/modules/notify) から通知できます。

### 圧縮

リバースプロキシ、静的ファイル、固定テキストのサイトで圧縮を有効にできます（リダイレクトサイトを除く）。`Accept-Encoding` に応じて `br` を優先し、次に `gzip` を選びます。

- 圧縮の対象はテキスト系のコンテンツのみです：`text/*`、JSON、JavaScript、XML、XHTML、RSS / Atom、WebAssembly、SVG。`text/event-stream` は除外されます。
- 宣言された `Content-Length` が 256 バイト未満のレスポンスは、そのまま返します。
- すでに `Content-Encoding` があるレスポンスは、そのまま返します。WebSocket のアップグレードリクエストはそのまま通します。
- 圧縮後は、強い ETag が弱い ETag に変更されます。

### IP 単位のレート制限

クライアント IP ごとのトークンバケット方式のレート制限です。フィールド：

| フィールド | 説明 |
| --- | --- |
| `rate` | 1 秒あたりに許可するリクエスト数 |
| `burst` | バースト容量。`rate` を設定して `burst` が 0 の場合は、`rate` を整数に丸めて 1 を足した値が自動で使われます |
| `maxConns` | 1 つの IP の同時リクエスト数の上限。0 で無制限 |

レート制限を有効にする場合、`rate` と `maxConns` の少なくとも一方を設定する必要があります。

### メモリ上のレスポンスキャッシュ

リバースプロキシサイトにのみ適用されます。キャッシュはメモリ上に置かれ、LRU で追い出されます。

| フィールド | デフォルト値 | 範囲 |
| --- | --- | --- |
| `ttl` デフォルトの保持時間 | 0 | 0 〜 30 日（秒単位）。上流がキャッシュ指示を宣言していない場合に、200 レスポンスをこの時間だけキャッシュします。0 は、上流が明示的に許可したレスポンスのみキャッシュすることを意味します |
| `maxMb` キャッシュ容量 | 64 | 1 〜 4096 MB |

キャッシュのルール：

- GET リクエストのみキャッシュされ、リクエストに `Authorization`、`Cookie`、`Range` ヘッダーや `Cache-Control: no-cache` が含まれていないことが条件です。
- ステータスコード 200 のレスポンスのみキャッシュされます。レスポンスに `Set-Cookie` や `Vary: *` が含まれる場合、または `Cache-Control` が `no-store` / `private` / `no-cache` の場合は対象外です。
- `s-maxage` に従い、次に `max-age` に従います。
- 1 エントリーの上限は 4 MB で、かつ総容量の 4 分の 1 を超えません。
- ヒット時は `X-Cache: HIT` と `Age` ヘッダーを返し、ミス時は `X-Cache: MISS` になります。
- キャッシュキーには Host、完全なリクエスト URI、`Accept-Encoding` が含まれます。[ユーザー別振り分け](#user-routes)を設定している場合は選ばれたユーザールートも含まれ、「ユーザー名を渡す」がオンのときはユーザー名も含まれます。

### パスの書き換えとリダイレクト

ルールは順に照合され、最初に一致したものでそれ以降は停止します。

| フィールド | 説明 |
| --- | --- |
| `pattern` | リクエストパスに一致する正規表現。例：`^/old/(.*)$` |
| `to` | 置換結果。`$1` でグループを参照できます |
| `redirect` | オフは内部書き換え（書き換え後のパスがバックエンドに送られ、宛先は `/` で始める必要があります）、オンはリダイレクト |
| `code` | リダイレクトのステータスコード 301 / 302 / 307 / 308。デフォルトは 302 |

リダイレクトでは元のクエリパラメーターが保持されます。リダイレクト先には、訪問者が使ったドメインを表す `{host}` を含められます。リダイレクトのルールは認証より前に実行されます（nginx の `location = / { return 302 ...; }` と同様）。そのため `/` のようなパスでは、ログインを求めずに訪問者を別の場所へ送れます。

## アクセス統計とモニタリング

### サイト統計

稼働中のリスナーでは、サイトの行の「統計」を押すと統計ウィンドウが開き、直近 1 時間、6 時間、24 時間を選べます。

- 分単位のアクセス統計：1 分ごとに 1 点で、直近 24 時間分を保持し、リクエスト数のグラフと 4xx / 5xx エラーのグラフを含みます。
- ステータスコードの分布（2xx / 3xx / 4xx / 5xx）と、累計のレスポンストラフィック。
- 送信元 IP のトップ 10 と国別のトップ 10（国別の統計には GeoIP データベースのインポートが必要です）。
- リバースプロキシサイトでは、各バックエンドのヘルス状態、重み、バックアップかどうか、現在の接続数を表示します。

統計はメモリ上に保持され、再起動またはリスナー自体の設定を変更した後に再集計されます。サイトを編集してもカウンターは維持されます。ランキングは最大 5000 件の異なる送信元まで集計します。

### Prometheus メトリクス

グローバルなメトリクスのエンドポイント `GET /api/metrics` はすべてのモジュールのメトリクスを集約しています。[監視メトリクス](/ja/docs/reference/monitoring) を参照してください。以下のモジュール用エンドポイントには Web サービスのメトリクスのみが含まれます。

メトリクスのエンドポイントは `GET /api/webservice/metrics` で、Prometheus のテキスト形式です。ログイン認証情報または [API トークン](/en/docs/reference/api-reference) が必要です。

```bash
curl -H "Authorization: Bearer gtl_xxxx" http://localhost:16680/api/webservice/metrics
```

| メトリクス | 種類 | 説明 |
| --- | --- | --- |
| `gately_site_requests_total` | counter | サイトの累計リクエスト数 |
| `gately_site_errors_total` | counter | サイトのバックエンドエラー数 |
| `gately_site_active_requests` | gauge | 処理中のリクエスト数 |
| `gately_site_response_bytes_total` | counter | 累計レスポンスバイト数 |
| `gately_site_responses_total` | counter | ステータスのクラス（ラベル `class`：`2xx` 〜 `5xx`）別のレスポンス数 |
| `gately_upstream_up` | gauge | バックエンドが正常か。1 が正常、0 が利用不可（ラベル `upstream` 付き） |

すべてのメトリクスにはラベル `listener`（リスナー名#リスナーの key）と `site`（サイト名。名前がない場合は最初のドメイン）が付きます。

## nginx 設定のインポート {#import-nginx}

ページ上部の「nginx をインポート」で、既存の nginx サイトを Gately のリスナーとサイトに変換できます。nginx のホストで `nginx -T` を実行し、その出力全体を貼り付けることをおすすめします。出力には include されたすべてのファイルが含まれ、Gately は nginx と同じように include を展開します。

- まずプレビュー：待ち受けポートごとにグループ化して、各サイトの種類、バックエンドまたはディレクトリ、元のファイルと行番号、注意が必要な点（変数を使ったディレクティブ、正規表現の location、証明書のないドメインなど）を一覧表示します。変換できないサイトにはその理由が表示されます。
- 同じポートのサイトは既存のリスナーに追加し、それ以外は新しいリスナーを作成します。既存のドメインはスキップされるため、繰り返しインポートできます。
- 既定では無効の状態でインポートされるため、nginx と並行して 1 つずつ確認してから有効にできます。「インポート後すぐに有効化」にチェックを入れるとすぐに有効になります（nginx が同じポートを使用中の場合、新しいリスナーは起動に失敗します）。
- 変換できる内容：`proxy_pass`（upstream の重み、バックアップ、ロードバランシングポリシーを含む）、`root` / `alias` の静的ディレクトリ（`autoindex`、`try_files $uri.html`、`error_page 404`）、`return` によるリダイレクトと固定内容、サイト全体の `rewrite` リダイレクト、`add_header`、`proxy_set_header`、`gzip`、`allow` / `deny`、location 単位のパス別バックエンド・アクセス制御・リダイレクト、`listen ... proxy_protocol` と `quic`。
- `auth_request` はフォワード認証に変換されます。認証 URL は認証サブリクエストの location の `proxy_pass`（`set` 変数に対応）から、ログインのリダイレクト先は `error_page 401 =302` から取得するため、Authelia のよくある書き方はそのまま変換できます。一部の location でのみ有効な場合は「認証必須」にしたパスのみ認証する設定に変換されます。
- `auth_basic` は共有ユーザーを使う Basic 認証に変換されます。nginx のユーザーファイルは読み込まれないため、ユーザーを追加するまでは誰も認証を通過できません。
- `stream` 内の TCP/UDP 転送は [ポート転送](/ja/docs/modules/portforward) で設定してください。証明書はインポートされません。HTTPS サイトに証明書がない場合、プレビューには nginx が使っている証明書ファイルが表示されるので、[SSL 証明書](/ja/docs/modules/ssl) ページでファイルパスから追加できます。

## haproxy と nginx の置き換え

ポート転送と Web サービスを組み合わせると、haproxy + nginx の構成を置き換えられます。よくある構成は、443 番ポートに [プロトコル振り分け](/ja/docs/modules/protoroute) のルールを 1 つ置き、VPN などの TLS サービスは直接バックエンドへ、それ以外はすべて PROXY プロトコルを受信する Web サービスのリスナーへ送るものです。これに加えて、80 番ポートにリダイレクトサイト（`https://{host}`）を持つ Web サービスのリスナーを置きます。

nginx の設定の置き換え方：

| nginx | Gately |
| --- | --- |
| `server_name` を持つ `server` | そのドメインを指定したサイト |
| `proxy_pass` が異なる `location` | パス別バックエンド |
| `auth_request`（Authelia） | フォワード認証、または TOTP 付きの共有ユーザー |
| `proxy_ssl_name $host` | アクセス先ドメインを SNI に使う |
| `return 301 https://$host$request_uri` | `https://{host}` と「パスとパラメーターを保持」を指定したリダイレクトサイト |
| `location = /` の `return 302 /admin` | 「リダイレクト」をオンにした書き換え、パターン `^/$` |
| `try_files $uri $uri.html $uri/index.html` と `error_page 404` | 拡張子なし URL と 404 ページを設定した静的ファイル |
| `add_header` | レスポンスヘッダー |
| `return 444` | 「接続を切断」サイト |
| HTTPS の server 内の `error_page 497 https://$host:$server_port$request_uri` | 新規リスナーの「同一ポートの HTTP」を「HTTPS へリダイレクト」に設定。既存リスナーに統合する場合は警告のみで、その設定は変更しません |

## デプロイのヒント

Web サービスはホストの 80 / 443 などのポートを待ち受ける必要があるため、Docker でデプロイする場合は `--network host` を推奨します。
