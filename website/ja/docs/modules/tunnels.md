# Tailscale / NetBird / frp / cloudflared

4 つのモジュールは、公式プログラムをプロセス管理方式で統合しています。自動再起動、ログの画面への集約、設定は画面上で完結します。Gately 本体にはこれらのプログラムを内蔵していません。ページからオンラインでインストール、更新、ロールバックできます。

## オンラインでのインストール・更新・ロールバック {#install}

frp、Cloudflare トンネル、Tailscale、NetBird、[File Browser](/ja/docs/modules/tools#filebrowser) の各ページ下部に「オンラインインストール」カードがあります。

- **ダウンロードしてインストール / 最新版に更新**：上流から最新の安定版をダウンロードし、上流が記録した SHA-256 で検証し、このマシンで実行できることを確認してから設定ディレクトリの `bin/` にインストールします。完了後、そのプログラムを使うプロセスを自動で再起動します。すでに最新版の場合は再ダウンロードしません
- **更新を確認**：上流の最新正式版を照会するだけでダウンロードはしません。新しいバージョンがあるとカードのタイトル横に「新しいバージョン」と表示されます。[自動更新チェック](/ja/docs/guide/install#update-check)が有効な場合、Gately はインストール済みのプログラムを 12 時間ごとにチェックし、新しいバージョンがあれば `program.update` を通知します；
- **バージョンを指定してインストール**：バージョン番号を入力します（例：frp は `v0.65.0`、cloudflared は `2025.8.0`、Tailscale は `1.90.2`）。ダウングレードにも使えます
- **ダウンロードプロキシ**：プログラムごとに設定でき、http、https、socks5 に対応し、インストール開始時に保存されます。空欄の場合は「設定」の更新プロキシを使います
- **旧バージョンとロールバック**：更新やロールバックで置き換えられたバージョンは `bin/.versions/` に最大 3 個保存されます。新バージョンに問題があれば一覧で「ロールバック」を押すと切り戻せます。現在のバージョンも同様に保持されるため、後から再び切り替えられます
- **アンインストール**：`bin/` にインストールしたプログラムと旧バージョンをすべて削除します。モジュール設定は保持されます。その後、そのプログラムを使うプロセスは再起動し、`PATH` に同名のプログラムがあればそれを使い、なければ実行できません

| プログラム | 取得元 | インストールされるファイル |
| --- | --- | --- |
| frp | GitHub fatedier/frp | `frpc`、`frps` |
| cloudflared | GitHub cloudflare/cloudflared | `cloudflared` |
| Tailscale | pkgs.tailscale.com の静的パッケージ（Linux のみ） | `tailscale`、`tailscaled` |
| NetBird | GitHub netbirdio/netbird（Linux、macOS、Windows） | `netbird` |
| FileBrowser Quantum | GitHub gtsteffaniak/filebrowser | `filebrowser` |

macOS と Windows にはそのまま実行できる Tailscale のパッケージがないため、公式インストーラーを使い、設定でパスを入力してください。現在のプラットフォームが対象外の場合はカードに表示されます。

## デフォルト設定に戻す {#reset}

ページヘッダーの「デフォルト設定に戻す」はアンインストールとは別の操作です。モジュールのプロセスをすべて停止し、設定（プログラムのパスとダウンロードプロキシを含む）をデフォルト値に戻し、Gately が生成したファイルを削除します。インストール済みのプログラムは残ります。

| モジュール | 消去される内容 |
| --- | --- |
| frp | すべての frpc / frps インスタンス、プロキシ、プログラム設定と、`frp/` に生成された設定ファイル |
| Cloudflare トンネル | すべてのトンネルとプログラム設定 |
| Tailscale | すべてのインスタンスとプログラム設定、デフォルトの状態ディレクトリ内のログイン状態。デフォルトの状態ディレクトリを使う Gately 管理の tailscaled が実行中の場合は先にログアウトします。カスタムの状態ディレクトリとシステム既存の tailscaled はそのまま残ります |
| NetBird | すべてのインスタンスとプログラム設定、既定の状態ディレクトリ内のログイン状態と鍵。既定の状態ディレクトリを使う管理対象デーモンが実行中の場合は先にログアウトし、このマシンはネットワークから削除されます。カスタムの状態ディレクトリとシステム既存の NetBird サービスはそのままです |
| File Browser | すべてのインスタンスとプログラム設定、各インスタンスのユーザー、共有リンク、キャッシュ。共有ディレクトリ内のファイルはそのまま残ります |

以前の設定は [設定履歴](/ja/docs/guide/audit) に保存されるため、誤って操作しても復元できます。完全に削除するには、先にプログラムをアンインストールしてから、デフォルト設定に戻します。API は `DELETE /api/{module}/install`（アンインストール）と `POST /api/{module}/reset`（デフォルト設定に戻す）です。

## プログラムの配置

実行ファイルは次の順序で探されます。

1. モジュール設定に入力したパス
2. 設定ディレクトリ配下の `bin/` サブディレクトリ（オンラインインストールの配置先）
3. `PATH`

パスを入力している場合、オンラインでインストールしたバージョンは使われず、カードにその旨が表示されます。バイナリを自分で設定ディレクトリに置くこともできます（Docker でデプロイする場合の例：`./gately-data/bin/frpc`）。Tailscale には `tailscale` と `tailscaled` の両方が必要です。システム既存の tailscaled を使う場合は、インストールする `tailscale` コマンドをデーモンと同じバージョンにそろえるのが望ましいです。

トークンとキーはパーミッション 0600 で保存されます。cloudflared のトークンは環境変数で渡されるため、プロセス一覧には現れません。

## Tailscale

複数のインスタンスに対応しています。各インスタンスは独立した tailscaled（状態ディレクトリ、制御ソケット、WireGuard ポート、プロセスが別々）を実行するため、1 台のマシンを別々の tailnet に参加させられます。たとえばカーネル TUN のインスタンスでリモートの Headscale に、ユーザースペースのインスタンスでローカルの Headscale に接続できます。

- 新しいインスタンスの状態ディレクトリは、既定で設定ディレクトリ下の `tailscale/<インスタンス key>` です。既存の状態ディレクトリ（以前の tailscale コンテナがマウントしていたディレクトリなど）を指定すると、ノード ID をそのまま使え、再登録は不要です
- 同時に有効にできるカーネルモード（管理対象でユーザースペースネットワークがオフ）のインスタンスは 1 つまでです。tailscaled のルーティングテーブルとファイアウォールマークは固定のため、カーネルインスタンスが 2 つあると互いに上書きします。制御ソケット、状態ディレクトリ、固定の WireGuard ポートも 2 つのインスタンスで共有できず、保存時や有効化時に競合が表示されます
- インスタンスの編集や有効化・無効化では、そのインスタンスの tailscaled だけを再起動します。ログのソースにはインスタンス名が付きます（例：`tailscaled:home`）
- 0.6.4 以前からアップグレードすると、従来の単一設定は `tailscale` という名前のインスタンスに自動で移行され、状態ディレクトリ、制御ソケット、起動パラメーターは変わりません
- プログラムのパス（tailscaled、tailscale）とオンラインインストールはすべてのインスタンスで共通です

各インスタンスでできること：

- `tailscaled` を管理する（ユーザースペースネットワーク、コンテナ向き）か、システムに既にあるデーモンに接続します
- 認証キーまたはログインリンク。Headscale にも対応
- サブネットルーターとエグジットノード
- ノード一覧と SOCKS5 プロキシ。このプロキシには認証がないため、待ち受けアドレスがこのマシン以外からも届く場合（`0.0.0.0` や LAN の IP など）は画面に警告が表示されます。`127.0.0.1` のみで待ち受けることをおすすめします
- WireGuard の UDP ポートを固定でき、ファイアウォールで直接接続を許可しやすくなります
- tailscaled の追加パラメーターと環境変数。ホストの iptables が nf_tables バックエンドの場合は、環境変数に `TS_DEBUG_FIREWALL_MODE=nftables` を追加すると、サブネット転送が有効になります

## NetBird

複数のインスタンスに対応しています。各インスタンスは独立した NetBird デーモン（状態ディレクトリ、制御アドレス、WireGuard ポート、プロセスがそれぞれ別）を実行するため、1 台のマシンを別々の NetBird ネットワークに参加させられます。たとえばカーネルモードのインスタンスで NetBird クラウドに、ユーザースペースのインスタンスで自前の管理サーバーに接続できます。

- 新しいインスタンスの状態ディレクトリは既定で設定ディレクトリ内の `netbird/<インスタンス key>`、制御アドレスは状態ディレクトリ内の `netbird.sock` です。既存の状態ディレクトリ（以前の NetBird コンテナがマウントしていた `/var/lib/netbird` など）を指定すると、再登録せずに元のピア ID を使えます；
- 同時に有効にできるカーネルモード（管理対象でユーザースペースネットワークなし）のインスタンスは 1 つまでです。NetBird のカーネルモードは固定のルーティングテーブル、ファイアウォールマーク、nftables テーブルを使い、既定のインターフェース名も常に `wt0` のため、2 つのカーネルインスタンスは互いに上書きします。状態ディレクトリと制御アドレスは 2 つのインスタンスで共有できません。管理対象インスタンスの WireGuard ポートは重複できません（0 は既定の 51820 とみなし、ポートが使用中だと NetBird は黙ってランダムなポートに切り替えます）。管理対象のユーザースペースインスタンスの SOCKS5 アドレスも重複できません（空欄は `127.0.0.1:1080` とみなします）。保存、有効化、一括有効化、複製のときに競合を通知し、手動編集で競合が生じた設定では後ろにある競合インスタンスを起動せず理由を表示します；
- インスタンスを編集・有効化・無効化すると、そのインスタンスのデーモンだけが再起動し、ログのソースにはインスタンス名が付きます（`daemon:home`、`netbird:home` など）。ログインリンク、デバイスコード、ピア一覧、ログアウトもインスタンスごとに表示されます；
- 既定の状態ディレクトリを使う管理対象インスタンスを削除すると、先にログアウトしてからそのディレクトリを削除します。カスタムの状態ディレクトリと移行した旧ディレクトリは、新しいインスタンスで再利用できるよう残します；
- 0.6.4 以前からアップグレードすると、従来の単一設定は `netbird` という名前のインスタンスに移行され、状態ディレクトリ（設定ディレクトリ内の `netbird`）、制御アドレス、起動引数、環境変数は変わりません；
- プログラムのパスとオンラインインストールはすべてのインスタンスで共用します。

各インスタンスでは次のことができます：

- NetBird クラウドまたは自前の管理サーバー（URL を入力）のネットワークに参加します。
- セットアップキーまたはログインリンクで認証します。Linux のログインリンクはデバイスコードログインで、どのデバイスでも開けます。macOS と Windows では通常 Gately を動かしているマシンのブラウザでしかログインを完了できないため、リモート管理ではセットアップキーを使ってください。リンクは期限切れになると自動で更新されます。
- `netbird` デーモンの管理（ユーザースペースネットワーク、コンテナ対応）、またはシステムにインストール済みの NetBird サービスへの接続。
- ユーザースペースネットワークでは、他のピアからこのマシンのサービスへのアクセスを既定で許可します（127.0.0.1 のみで待ち受けるサービスも含み、管理サーバーのアクセスポリシーは引き続き適用されます）。ローカルのプログラムは SOCKS5 プロキシ（既定 `127.0.0.1:1080`）経由でネットワーク内のデバイスにアクセスします。
- SOCKS5 プロキシには認証がなく、待ち受けアドレスがこのマシン以外からも届く場合は画面に警告が表示されます。0.75 より前の NetBird はユーザースペースネットワークで設定したアドレスを無視し、常に `0.0.0.0` で認証なしの SOCKS5 プロキシを提供するため、他のデバイスがそれを経由してネットワークにアクセスできます。Gately がデーモンを管理していてこうしたバージョンを検出すると、ログに警告を出します。0.75 以降にアップグレードしてください。
- ネットワークルート、出口ノード、アクセスポリシーは NetBird の管理画面で設定します。Gately ではルートの受け入れ、ルーティングピアになるか、DNS の受け入れ、受信の拒否を選べます。
- 直接接続かリレーか、遅延、ネットワークルートを表示するピア一覧。
- WireGuard ポートの固定、デーモンの追加引数と環境変数（NetBird ドキュメントにある `NB_` で始まる詳細オプション）。
- ユーザースペースネットワークをオフにするとカーネルの WireGuard を使います。root と TUN デバイスが必要で、`wt0` インターフェースを作成して独自のファイアウォールルールを追加します（OpenWrt の fw4 でも `wt0` の受信を許可します）。他のピアからアクセスさせるローカルサービスは、全アドレスか NetBird のアドレスで待ち受ける必要があります。
- `netbird` プログラムは約 41 MB、実行時のメモリは約 60 MB で、オンラインインストールは `bin/.versions/` に最大 3 つの旧バージョンを残します。フラッシュ容量の小さいルーターでは空き容量に注意し、インストールカードで旧バージョンを削除するか、プログラムを外部ストレージに置いて設定でパスを入力してください。
- デフォルト設定に戻す操作と `POST /api/netbird/instances/{key}/logout` は、管理サーバーからこのマシンの登録を解除し、ネットワークから削除します。再参加には再認証が必要です。

## frp

- **frpc クライアント**：frpc インスタンスを複数追加でき、各インスタンスは 1 台の frps に接続して個別に動作し、個別に有効化・停止・再起動できます。プロキシはいずれかのインスタンスに属し、tcp / udp / http / https / stcp / xtcp に対応します。プロキシを変更すると所属するインスタンスだけが再起動します
- **プロキシのアクセスアドレス**：frpc は frps の HTTP / HTTPS ポートとサブドメインのルートドメインを知らないため、frpc インスタンスの「アクセスアドレス」に入力します（このマシンに frps インスタンスがあればワンクリックで入力でき、frps の前にリバースプロキシや CDN があれば訪問者が実際に使うプロトコルとポートを入力）。入力すると http / https プロキシのドメイン（サブドメインから組み立てた完全なドメインを含む）をクリックで開け、完全な URL をコピーできます。未入力ならこれまでどおりテキストです。アクセスアドレスはリンクの作成にだけ使い、変更しても frpc は再起動しません。カスタムドメインは Web サービスと同じく小文字と punycode にそろえて保存し、ポートやパスを含む書き方は拒否します。サブドメインは frps の要件どおり `nas` のような 1 階層の名前だけです。
- **frps サーバー**：異なるポートで frps インスタンスを複数追加でき、それぞれにポートのホワイトリスト、サブドメイン、ダッシュボードがあります
- **旧バージョンからのアップグレード**：0.5.9 以前の単一の frpc / frps 設定は、`frpc` / `frps` という名前のインスタンスに自動で移行されます。既存のプロキシはその frpc インスタンスに属し、プログラムのパスはページ下部の「プログラム」カードに移ります
- **frps の待ち受けアドレス**：「待ち受けアドレス」は frpc 接続ポートの待ち受け先、「プロキシ待ち受けアドレス」は HTTP / HTTPS ポートと tcp / udp プロキシのリモートポートの待ち受け先で、空欄ならすべてのアドレスで待ち受けます。frps を Gately などのリバースプロキシの背後に置く場合は、待ち受けアドレスを `127.0.0.1` にし、Web サービスでサイトを `127.0.0.1:<バインドポート>` にリバースプロキシして、frpc の転送プロトコルを websocket または wss にしてそのサイトへ接続します。プロキシ待ち受けアドレスは空欄のままにすれば、tcp プロキシのリモートポートは従来どおり外部から使えます。frps 設定のインポート時、元の設定に `proxyBindAddr` がなければ frps と同じく `bindAddr` を引き継ぎます。
- **frps の送信元 IP アクセス制御**：frps インスタンスごとに許可リストまたは拒否リストを設定し、送信元 IP によって frpc のログイン（バインドポートへの接続）を許可するかを決められます。リストは手入力の IP / ネットワークセグメントと Web サービスの購読 IP リストを合わせたもので、いずれかに一致すればリスト内とみなします。購読リストは Web サービスモジュールが定期的にダウンロードし、更新されると frps を再起動せずに即時反映されます。初回ダウンロードまでは空として扱います。判定は frps がトークンを検証する前に行います。Gately はループバックアドレスにチェック用エンドポイントを開き、生成する frps 設定の末尾に `[[httpPlugins]]`（`ops = ["Login"]`）を書き込むため、対象は frpc のログインだけで、tcp / udp プロキシのリモートポートと HTTP / HTTPS ポートはこれまでどおり公開されます。侵入防御のブロックはリストより優先され、ブロックされたアドレスは許可リストのセグメント内でもログインできません。アクセス制御を設定していないインスタンスもブロックリストに従い、ファイアウォール同期の有無は関係ありません。拒否された frpc には `gately: client address ... is not in the allowlist` のようなエラーが返り、インスタンスカードには Gately 起動以降の拒否回数が表示されます。リストは frpc のログイン時に確認し、frpc が frps のバインドポートへ接続する部分に効きます。リストを厳しくしたりアドレスがブロックされたりしても、ログイン済みの frpc は接続を保ち、次回のログイン時に拒否されます。すぐに反映するにはその frps インスタンスを再起動してください。stcp / xtcp の visitor 接続はログインの確認を通らないため、制限するには[侵入防御](/ja/docs/modules/guard)のファイアウォール同期を併用します。frps をリバースプロキシの背後に置く場合（待ち受けアドレス `127.0.0.1`）、frps から見える送信元はプロキシのアドレスになるため、IP アクセス制御は Web サービスのサイト側で行ってください。プロトコル振り分けやポート転送の背後に置く場合は frps から見える送信元がローカルアドレスになり、リストで訪問者を判別できないため、振り分けや転送のルールで送信元 IP アクセス制御を設定してください。
- **既存設定のインポート**：ページ上部の「設定をインポート」は、旧バージョンの `frpc.ini` / `frps.ini`（`[common]` セクションを含む）と frp 0.52+ の `toml` に対応しており、ファイルの選択または内容の貼り付けができ、既存のインスタンスか新規インスタンスかを選んでインポートします。まず解析結果と無視されたフィールドをプレビューしてから、インポートを確定します。既存の frpc インスタンスへのインポートでは、追記（同名のプロキシは変更されません）またはそのインスタンスのすべてのプロキシの置き換えを選べます。既存のインスタンスでは有効状態がそのまま保たれ、新規インスタンスは無効の状態で作成されます。API の `POST /api/frp/import` からも呼び出せます。Lucky から移行すると、Lucky の各 frpc / frps インスタンスがそれぞれ Gately のインスタンスとしてインポートされます。

- 公開アドレスの表示

### ルート {#cloudflared-ingress}

トークン方式のトンネルの公開ホスト名とオリジンサービス（ルート）は Cloudflare 上に保存され、実行中の cloudflared が自動で取得します。トンネル設定で任意の **API トークン** を入力すると、カードの「ルート」から直接編集できます。

- トークンには「Cloudflare Tunnel：編集」権限が必要です。DNS レコードを自動作成するには対象ゾーンの「DNS：編集」権限も必要です。アカウントとトンネル ID はトンネルトークンから読み取ります。
- 各ルールはホスト名、任意のパス正規表現、サービス（`http://localhost:8080`、`ssh://localhost:22`、`http_status:404` など）で構成され、上から順に照合して最初に一致したルールで転送します。「オリジン証明書を検証しない」とオリジンへの Host ヘッダーを設定でき、その他のオリジン設定はそのまま保持されます。どのルールにも一致しない場合はキャッチオールのサービスを使い、既定は `http_status:404` です。
- 保存するとすぐに反映され、トンネルの再起動は不要です。その間に Cloudflare ダッシュボードなどでルートが変更されていた場合は、上書きを防ぐため保存時にその旨を表示し、「再読み込み」を示します。HTTP 系のサービスにはパスを付けられず、末尾の単独の `/`（`http://nas:5000/` など）は保存時に自動で取り除きます。残すと cloudflared が設定全体を拒否します。
- トンネルがローカルの設定ファイルで管理されている場合（リモートのルートが反映されない旨が画面に表示されます）、保存前にもう一度確認します。リモート設定を書き込むとトンネルはリモート管理に切り替わり、ローカル設定ファイルのルートは反映されなくなります。
- 「DNS を同期」をオンにすると、各ホスト名に `<トンネルID>.cfargotunnel.com` を指すプロキシ有効の CNAME レコードを作成します。既に別のレコードがあるホスト名や、トンネルを指していてもプロキシが無効の CNAME（この場合トラフィックはトンネルに入りません）があるホスト名はそのまま残し、結果に表示します。ドメインはトンネルが属するアカウント内だけで検索します。ルールを削除しても DNS レコードは残るので、必要に応じて Cloudflare で削除してください。
