# WAF ファイアウォール

[Coraza](https://coraza.io/) と OWASP CRS v4 をベースにした Web アプリケーションファイアウォールで、[Web サービス](/ja/docs/modules/web) のサイトに適用できます。

## 機能

- OWASP CRS v4 ルールセットを内蔵し、ルールファイル単位で有効化できます
- カスタム SecLang ルールに対応
- ルールグループの順序を変更できます。検知ログにはクライアント IP、ドメイン、パス、ルール ID が記録され、ログ画面でドメイン、IP、キーワードで絞り込めます
- ブロックモードと検出のみのモード
- リクエストボディの検査上限を調整でき、上限を超えた場合はリクエストを拒否するか先頭部分のみを検査します。パスごとにボディ検査を省くこともできます
- WebDAV 互換モード：クラウドドライブや WebDAV で使うメソッド、リクエストヘッダー、任意のアップロード用コンテンツタイプを許可します
- 自前で構築した SafeLine（雷池）検知エンジンに接続でき、ルールグループと併用できます
- 複数のインスタンスを作成し、サイトから必要に応じて参照できます

## 利用のヒント

1. 新しいサイトではまず「検出のみ」にして、しばらくログを観察し、誤検知がないことを確認します。
2. 誤検知があれば、ルールファイルを調整するか、カスタムの除外ルールを追加します。
3. そのうえで「ブロック」に切り替えます。

## 管理画面からのリクエスト

WAF を設定したサイト経由で管理画面をリバースプロキシしている場合、このインスタンスの有効な管理者セッションを持つリクエストは WAF（SafeLine を含む）を通りません。設定を保存するリクエストボディにはファイルパス（nginx インポートが書き込んだ備考など）、HTML（カスタムエラーページ）、スクリプト（証明書のデプロイ）などが含まれることが多く、CRS のパストラバーサル、XSS、コマンドインジェクションのルールに 403 で誤検知されるためです。セッションはサーバーが署名しており、管理者ロールのみが対象です。読み取り専用アカウント、訪問者、他インスタンスの管理画面からのリクエストは通常どおり検査されます。

## ログイン済みユーザー

サイトで「ログイン済みユーザーを信頼」を有効にすると（[Web サービス](./web)を参照）、そのサイトの Gately 認証を通過した訪問者（Web 認証、許可リストに個別に列挙された外部ログインの ID、共有ユーザーのシングルサインオン、検証済みの Basic 認証）は WAF を通りません。ログインしていない訪問者、ログインページ自体へのリクエスト、`github:*` のようなワイルドカードで許可された外部ログインの ID、転送認証と共有リンクは引き続き検査されます。

## ルールグループの順序

インスタンスのルールグループは上から順に読み込まれ、上へ・下へボタンで並べ替えられます。同じフェーズでは先にあるルールから実行されます。

- ブロックルール（deny など）はどこに置いても有効です。
- 実行時の許可・除外ルール（`allow`、`ctl:ruleRemoveById`、`ctl:ruleRemoveTargetById` など）は OWASP CRS グループより上に置きます。下に置くと先に CRS にブロックされることがあります。
- `SecRuleRemoveById`、`SecRuleUpdateTargetById` などの設定時ディレクティブは読み込み済みのルールにだけ作用するため、CRS グループより下に置きます。上に置いても効果はありません。

## 大きなファイルをアップロードするサイト

WAF は既定で 12.5 MB までのリクエストボディしか検査せず、それより大きなリクエストは拒否されます（413）。そのため、クラウドドライブ、WebDAV、ファイルマネージャーなどのサイトでは大きなファイルをアップロードできません。インスタンスの「リクエストボディの検査」で次の項目を調整できます。

- **検査上限**：0 は既定の 12.5 MB、最大 1024 MB です
- **上限を超えた場合**：「リクエストを拒否」はこれまでと同じ動作です。「先頭部分のみ検査」は上限までの部分だけを検査し、残りはそのままバックエンドへ転送するため、大きなファイルをアップロードするサイトに向いています
- **WebDAV・アップロード互換**：OWASP CRS は既定で GET、HEAD、POST、OPTIONS のみを許可し、`Lock-Token`、`If`、`Content-Range` リクエストヘッダーと許可リスト外のコンテンツタイプをブロックするため、WebDAV クライアントはディレクトリの一覧表示、アップロード、ロックができません。有効にすると PUT、DELETE、PROPFIND、PROPPATCH、MKCOL、COPY、MOVE、LOCK、UNLOCK などのメソッドとこれらのヘッダーを許可し、アップロードのコンテンツタイプも制限しなくなります。PUT と `application/octet-stream` のリクエストボディはファイルの中身として扱い、フォームパラメーターとしての検査は行いません。インジェクションやパストラバーサルなどの攻撃の検査は引き続き有効です
- **ボディ検査を省くパス**：1 行に 1 つのパスのプレフィックス（例：`/api/upload`、`/remote.php/dav/`）。一致したリクエストはボディを検査しませんが、ヘッダー、URL、パラメーターは通常どおり検査します

クラウドドライブや WebDAV のサイトには専用のインスタンスを作成し、「WebDAV・アップロード互換」を有効にして「先頭部分のみ検査」を選び、必要に応じてアップロード用のエンドポイントを省くパスに追加することをおすすめします。他のサイトは既定の設定のまま使えます。

curl や rclone などのクライアントは大きな内容をアップロードするときに `Expect: 100-continue` リクエストヘッダーを付けますが、CRS 4 は既定でこれをブロックします。Gately はすべてのインスタンスでこのヘッダーを許可している（100-continue は Gately 自身が処理します）ため、追加の設定は不要です。

## SafeLine（雷池）との連携

[SafeLine](https://waf.chaitin.com/) は Chaitin Tech の Web アプリケーションファイアウォールで、意味解析エンジンで攻撃を見分けるため誤検知が少ないのが特徴です。Gately はリクエストを自前で構築した SafeLine 検知エンジン（safeline-detector）に送り、結果に応じて通過またはブロックします。入口、証明書、認証、ブロックリストは引き続き Gately が担当するため、SafeLine をリバースプロキシとしてもう一段挟む必要はありません。

1. SafeLine の公式ドキュメントに従ってコミュニティ版をインストールします。既定のインストール先は `/data/safeline` です。
2. 検知エンジンへの接続方法を選びます。
   - **Unix ソケット**（Gately と SafeLine が同じマシン上にある場合）：検知エンジンは既定で `/data/safeline/resources/detector/snserver.sock` を待ち受けるので、アドレスに `unix:/data/safeline/resources/detector/snserver.sock` を指定します。Gately を Docker で動かしている場合は、`/data/safeline/resources/detector` ディレクトリを Gately のコンテナにマウントし、コンテナ内のパスを指定します。
   - **TCP**：`/data/safeline/resources/detector/detector.yml` に次の 2 行を書き、`docker restart safeline-detector` を実行します。TCP に切り替えると検知エンジンは Unix ソケットを待ち受けなくなります。

     ```yaml
     bind_addr: 0.0.0.0
     listen_port: 8000
     ```

     アドレスには safeline-detector コンテナの IP とポート（例: `172.22.222.5:8000`）を指定します。コンテナの IP は `docker inspect safeline-detector | grep IPAddress` で確認できます。Gately が Docker の bridge ネットワークで動いている場合は、`docker network connect safeline-ce <Gately のコンテナ名>` で SafeLine のネットワークに参加させます。検知エンジンには認証がないため、8000 番ポートをインターネットに公開しないでください。
3. WAF インスタンスで「SafeLine を使う」をオンにし、アドレスを入力して「接続テスト」をクリックします。Gately はハートビートを送った後、サンプルの SQL インジェクションリクエストを検査に送ります。「サンプル攻撃が検知されました」と表示されれば検知エンジンは正常です。このサンプル攻撃は送信元 127.0.0.1、ドメイン gately-test.invalid として SafeLine コンソールの攻撃記録に表示されます。
4. Web サービスのサイトからこのインスタンスを参照します。

補足：

- SafeLine 接続時はルールグループを空にできます。ルールグループも残す場合、リクエストはまず SafeLine で検知され、その後ルールグループで検査されます。「検出のみ」モードでは、SafeLine が検知した攻撃はログに記録するだけで、リクエストはそのまま通ります。
- ブロックされたリクエスト：ブラウザにはイベント ID 付きのブロックページが表示され、その他のクライアントには SafeLine 公式プラグインと同じ JSON（`event_id` を含む）が返ります。ステータスコードは検知エンジンが示した値で、通常は 403 です。ブロックはアクセスログ（`deny=waf`）、サイト統計、WAF ブロックイベントに反映され、侵入防御の「WAF ブロック」プリセットも機能します。
- 攻撃記録は SafeLine コンソールにも書き込まれ、イベント ID で検索できます。これらの記録は SafeLine のどのサイトにも属しません。
- 検査に送るリクエストボディは既定で最大 1024 KB で、超えた部分は検査せず、そのままバックエンドへ転送します。「ボディ検査を省くパス」と「WebDAV・アップロード互換」は SafeLine にも適用されます。HTTP/2 で送られる長さ不明の gRPC リクエストボディは検査に送りません。
- 検知タイムアウトは既定で 1 秒です。検知エンジンを利用できない（接続失敗、タイムアウト）ときは既定でリクエストを通し、インスタンスに「SafeLine 停止」と表示してエラーログを記録します。「リクエストを拒否」を選ぶと、こうしたリクエストには 503 を返します。検知エンジンの起動直後の数秒間は認識できない結果を返すことがあり、これも利用不可として扱います。
- 検査するのはリクエストのみで、レスポンスは送りません。
