# Gately v0.6.8.4 リリース

2026年11月19日

[v0.6.8.4 をダウンロード](/ja/download) · [GitHub Release](https://github.com/wangwanjie/gately/releases/tag/v0.6.8.4)

## セキュリティ修正

- **通知チャネルのキーが配信エラーに表示されることがありました（低）**：Telegram Bot Token、Bark のデバイスキー、ServerChan の SendKey などはリクエスト URL に含まれます。接続に失敗すると、エラーメッセージに URL 全体が含まれて通知モジュールのログと「最近の配信」の記録に書き込まれ、読み取り専用アカウントや通知の読み取り権限だけを持つ API トークンからも見える状態でした。エラーメッセージ内のチャネルキーは `***` に置き換わります。v0.6.8.2 以前が影響を受けます。「最近の配信」はメモリ上にのみ保存され、アップグレード後の再起動で消えます。実行ログには古い記録が残っている場合があるため、過去に送信が失敗したチャネルはキーの変更を推奨します（GHSA-p368-wcp9-rv4q）。

## 設定変更で自分を締め出さない

- **保存後の確認、タイムアウトで自動ロールバック**：管理画面でポート転送・プロトコル振り分け・Web サービス・全体設定を保存すると、ページが新しい接続で管理画面にまだアクセスできることを確認します。確認できない場合（たとえば管理画面が経由するリッスンポートを誤って変更したときなど）、既定で 90 秒後に変更前の設定へ自動的に戻ります。確認に失敗するとカウントダウンが表示され、すぐにロールバックもできます。確認できないまま 3 回再起動した場合もロールバックされます。「システム設定 › アクセス制御」でこの機能をオフにしたり、待ち時間（30～600 秒）を調整したりできます。ロールバックすると「設定変更」通知が送られます。
- **保存前にアクセス経路を警告**：管理画面は、現在のアクセスがどのポート転送・プロトコル振り分け・Web サイトを経由しているかをたどります。保存する変更がこの経路に影響する場合（ポート変更、無効化、削除、このマシンでリッスンできないアドレスへの変更など）、先に理由を説明し、影響を受けるホップを強調表示します。「システム設定 › アクセス制御」で現在のアクセス経路を確認できます。
- **一括変更をまとめて反映**：複数の箇所を同時に変更しないと通らない場合（たとえば先にプロトコル振り分けを、次に Web のリスナーを変更する場合）は、「保留して後でまとめて反映」を選べます。上部のバナーに保留中のルールとリスナーが並び、「すべて反映」でバッチ全体を確認し、失敗すれば全体をロールバックします。「変更を破棄」で破棄することもできます。反映の前に、起動できないリスナーを先に一覧表示します。
- **コマンドラインでのロールバック**：`gately rollback` は確認待ちの変更と直近 15 回の設定保存を一覧表示し、番号を指定して取り消せます。`-last`、`-pending`、`-config` を `-version` と組み合わせて使うこともできます。Gately が動作中なら 2 秒以内に復元して再起動し、停止中なら設定ファイルを直接書き換えます。
- 設定ファイルを削除する前に設定履歴へコピーを保存するため、削除も設定履歴から取り消せます。

## 通知：失敗時の再試行と再送

- 送信に失敗すると 10 秒、30 秒、60 秒後に再試行します（既定 3 回、0～10 で設定可能）。それでも失敗したメッセージは再送キューに入り、チャネル復旧後に時系列順で送られ、再起動後も続きます（既定で 24 時間保持、0～168 で設定可能、0 でオフ。チャネルごとに最大 100 件）。
- チャネルに再送待ちのメッセージがすでにある間は、新しいメッセージは 1 回だけ試行し、失敗したら滞留分の後ろに並べます。1 件ずつ再試行を待つことはありません。
- 「最近の配信」には「再送待ち」「再送済み」と試行回数が表示されます。上部のバナーにはチャネルごとの再送待ち件数が表示され、クリアもできます。

## 証明書：fnOS システム証明書を使う（#105）

- 証明書の取得元に「fnOS システム証明書」を追加しました。fnOS がすでに管理している証明書からドメインを選ぶと、Gately は 30 分ごとに最新の証明書を読み取って fnOS の更新に追従します（完全なチェーンがあればそれを使用）。変更があれば自動で読み込み、デプロイします。
- 証明書は fnOS の「設定 → セキュリティ → 証明書」で管理します。fnOS ネイティブアプリ（fpk）は直接読み取れます。Docker 構成では、`/usr/trim/etc/network_cert_all.conf` と `/usr/trim/var/trim_connect/ssls` を同じパスのままコンテナーに読み取り専用でマウントし、コンテナーを root で実行する必要があります（公式イメージの既定）。詳しくは [SSL 証明書](/ja/docs/modules/ssl) を参照してください。

## ストレージ使用量

- 「システム設定 › ネットワークと実行」にストレージ使用量カードを追加しました。設定ディレクトリがあるパーティションの容量、設定ディレクトリ全体のサイズ、そして実行ログ、訪問者監査、設定履歴、バックアップ、証明書、管理プログラム、通知の再送キュー、File Browser データなど用途別の使用量とパスを表示します。

## 修正

- **侵入防御**：管理ポートはモジュール起動前に開放ポートとして登録されます。以前は、おとりポートの範囲に管理ポートが含まれていると、Gately 自身のおとりリスナーが先にそのポートを占有し、管理画面のリッスンに失敗して再起動のたびに終了していました。モジュールの起動中はおとりポートを設定しません。frps、EasyTier、FTP パッシブポートなどのモジュールが登録したポートは、まだリッスンしていなくてもおとりに使いません。おとりポートはポートの変更に合わせて再計算されます。証明書の申請時に使う一時的な HTTP-01 リスナーは、おとりポートに妨げられなくなりました。
- **Web サービス**：サイトのバックエンドが同じインスタンスの別の Web リスナーである場合（たとえば 443 のサイト → このマシンの 444 リスナー → 管理画面）、管理画面のログイン Cookie がそのまま転送され、ログイン直後に 401 になることがなくなりました。

## アップグレードの注意

- Docker は新しいイメージを取得してコンテナーを再作成します。OpenWrt は新しい `.apk` / `.ipk` を上書きインストールします。fnOS はアプリセンターで新しい `.fpk` を手動でインストールします。その他の環境は「システム設定」でオンラインアップグレードできます。
- 保存後の確認は既定で有効です。スクリプトや API トークンによる設定の保存は影響を受けません。確認が必要なのは、確認用のリクエストヘッダーを付けた管理画面セッションからの保存だけです。
