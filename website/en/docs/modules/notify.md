# Notification Center

The Notification Center subscribes to Gately's internal event bus and, according to your rules, pushes events such as DDNS changes, certificate expiry, WAF blocks and process failures to Webhook, Telegram, Bark, ntfy, Gotify, Pushover, Discord, Slack, ServerChan, PushPlus, WeCom, DingTalk, Feishu and email. The management UI is under the sidebar "System" group → "Notifications".

## How it works

1. Each module publishes events to the in-process event bus when its state changes. Publishing never blocks business logic.
2. When the Notification Center receives an event, it checks the rules one by one: the rule is enabled, the event level is not lower than the rule's minimum level, and the event type matches the rule's event list.
3. After a matching rule passes silence deduplication, the message is delivered to the enabled channels selected by the rule. If one event matches several rules, each channel is sent to only once.
4. The result of each delivery (success, or the reason for failure) is written to "Recent deliveries", which keeps the latest 200 entries in memory. Failures are also written to the module log.

A single delivery times out after 45 seconds.

## Notification language

Notification content and logs use the server language from "System settings". When the server language is "Follow system", Gately uses the language set by the environment variable `GATELY_LANG`, then `LANG`. Services on Docker, fnOS and OpenWrt usually set neither variable; in that case the language follows the interface language the administrator used at the most recent login or top-bar language switch, and English is used when neither exists. Logins by read-only accounts do not change this language. The "Source" of a notification is translated when it is a name generated by the program (such as "Admin console"); task names and other names entered by users are kept as is.

## Server name {#server-name}

Every notification carries the name of the server that sent it: the title looks like `[Gately · fnOS-B760] Certificate expiring soon` and the body contains a "Server: fnOS-B760" line, so notifications from several servers delivered to the same mailbox or chat are easy to tell apart. Set the name under **Server name** in the page header's **Notification settings**; when it is empty the machine's hostname is used (the host's hostname when Docker uses host networking), and the title stays `[Gately]` if no hostname is available. The name is at most 64 characters and cannot contain control characters such as line breaks.

## Channels

Click "Add channel", choose a type and fill in the fields. Every channel has a name (required), a remark and an enable switch. Secret fields are not shown again after saving; leaving them empty when editing keeps the original value.

| Type | Required fields | Optional fields |
| --- | --- | --- |
| Webhook | Request URL | Request method (default GET; GET, POST, PUT or PATCH), headers (one `Key: Value` per line), body, success-match content, timeout (seconds, default 20), skip certificate verification |
| Telegram | Bot Token, Chat ID | API URL (leave empty to use `https://api.telegram.org`) |
| Bark | Device Key | Server URL (leave empty to use `https://api.day.app`) |
| WeCom | Bot URL | None |
| DingTalk | Bot URL | Signing secret (fill in when the bot has "signature" enabled) |
| Feishu | Bot URL | Signing secret (fill in when the bot has "signature verification" enabled) |
| Email | Server, recipients, and at least one of sender or username | Encryption, port, username, password |
| ntfy | Topic | Server URL (leave empty to use `https://ntfy.sh`), access token |
| Gotify | Server URL, application token | None |
| Pushover | Application token, user key | None |
| Discord | Webhook URL | None |
| Slack | Webhook URL | None |
| ServerChan | SendKey | None |
| PushPlus | Token | None |

URL fields need a full address starting with `http://` or `https://`.

### Webhook template variables

The following variables can be used in the request URL and body, written as the variable name wrapped in curly braces (the `#` prefix form is also accepted):

| Variable | Content |
| --- | --- |
| `title` | Title, in the form `[Gately · server name] Event title` |
| `server` | Server name, see [Server name](#server-name) |
| `message` | Detailed description of the event |
| `text` | Full body, including description, source, level and time |
| `type` | Event type, such as `ddns.changed` |
| `source` | Event source |
| `level` | Level: `info`, `warn` or `error` |
| `time` | Time in RFC 3339 format |

Extra fields carried by an event (such as `ip` and `container`) can also be used as variables. If a name collides with the table above, the table above takes precedence. Variable values in the URL are URL-escaped.

### Email

| Encryption | Value | Default port |
| --- | --- | --- |
| STARTTLS | `starttls` | 587 |
| SSL/TLS | `tls` | 465 |
| None | `none` | 25 |

A port of 0 uses the default port for the chosen encryption. You can enter several recipients separated by commas. Emails are sent as UTF-8 plain text. PLAIN authentication is used when the server supports AUTH and a username is set; when the sender is empty, the username is used.

### Signatures and response codes

- DingTalk: once a signing secret is set, requests automatically carry `timestamp` and `sign`.
- Feishu: once a signing secret is set, the request body automatically carries `timestamp` and `sign`.
- WeCom, DingTalk, Feishu and Bark check the business return code in the response. An HTTP 200 with a business failure is also recorded as a failed delivery.

### Proxy {#proxy}

When the notification service cannot be reached directly and only works through a proxy (for example Telegram, Discord or Slack), notifications can go through a proxy:

- **Global proxy**: under "Notification settings" in the page header, set the default proxy for all channels: "No proxy", "Use the global update proxy" (reuses the proxy used for update checks in [System settings](/en/docs/guide/configuration); changes take effect immediately, and an empty update proxy behaves like no proxy) or "Custom proxy".
- **Channel proxy**: the "Proxy" field in each channel's editor defaults to "Follow notification settings". You can also pick "Direct (no proxy)", "Use the global update proxy" or a custom proxy for that channel, which overrides the global setting. Self-hosted ntfy, Gotify and similar services on the LAN can be set to direct.
- Proxy addresses support `http://`, `https://`, `socks5://` and `socks5h://`, and may include a username and password, such as `http://user:pass@127.0.0.1:7890`; channel cards hide the password when they show the proxy.
- With "No proxy", HTTP channels follow environment variables such as `HTTPS_PROXY` and `NO_PROXY`, and email connects directly, as before; "Direct" does not read the environment variables either.
- Email supports proxies as well: through an `http(s)://` proxy it opens a tunnel to the mail server port with the CONNECT method (the proxy must allow connections to that port, which common proxies such as Clash do by default), and through a `socks5://` proxy the proxy resolves the server domain name. STARTTLS / SSL and authentication then happen inside the tunnel, so the proxy cannot see the mail content.
- When the connection through the proxy fails, delivery records and test messages show "Connection through proxy … failed", with the proxy password replaced by `xxxxx`.

## Rules

Click "Add rule":

| Field | Description |
| --- | --- |
| Name | Required |
| Events | At least one. Pick specific event types, `*` for all events, or enter a wildcard such as `ddns.*`. Wildcards use Go `path.Match` syntax |
| Minimum level | `info`, `warn` or `error`; empty means info. Events below this level are not pushed |
| Channels | At least one |
| Silence (seconds) | Within one rule, events of the same type from the same source are pushed only once in this period, and repeats are dropped. 0 disables deduplication |
| Enabled | Switch |

::: tip
WAF blocks and upstream state changes can happen frequently. For rules covering them, set a silence time of 300 seconds or more.
:::

## Rule templates

When creating a rule, click a template to prefill the events, level and silence time, then pick channels and save:

| Template | Events |
| --- | --- |
| Critical failures | DDNS update failed, certificate renewal failed, upstream down, child process exited abnormally, backup failed, container exited |
| Certificate expiry | Certificate expiring soon, renewal failed (24-hour silence) |
| Address changes | DDNS record updated, STUN address changed |
| Service health | Upstream down and recovered, container exited, child process exited |
| Security & sign-ins | Login failures, IP bans, successful logins, sign-ins from new addresses, access to sensitive content |
| Performance alerts | Performance alert firing and recovery (no silence) |
| Configuration changes | Every configuration change made in the management UI |
| Updates | Gately security updates and new versions, new versions of managed programs and container images (no silence) |

## Event types

| Event type | Name | Level | Trigger |
| --- | --- | --- | --- |
| `ddns.changed` | Dynamic DNS: record updated | Info | A DDNS task updated its record successfully |
| `ddns.failed` | Dynamic DNS: update failed | Error | A DDNS task failed to update |
| `stun.changed` | STUN: traversal address changed | Info | The traversal address of a STUN rule changed |
| `ssl.expiring` | Certificate: expiring soon | Warning | Less than 7 days of validity left; each certificate is reminded at most once every 24 hours |
| `ssl.renew_failed` | Certificate: renewal failed | Error | Certificate issuance or renewal failed |
| `ssl.deploy_failed` | Certificate: deployment failed | Error | Deploying a certificate to one of its targets (directory, SSH or local command) failed; Gately retries later |
| `waf.blocked` | WAF: request blocked | Warning | The WAF blocked a request, with the fields `ip`, `host` and `path` |
| `upstream.down` | Reverse proxy: upstream down | Error | A backend of a Web service was judged unavailable |
| `upstream.up` | Reverse proxy: upstream recovered | Info | An unavailable backend recovered |
| `docker.exited` | Docker: container exited | Warning or Error | A container exited with a non-zero exit code (warning), or was killed for running out of memory (error) |
| `process.exited` | Child process exited abnormally | Error | A child process managed by Gately exited abnormally and will be restarted automatically; the source is that process's log name |
| `backup.done` | Backup: completed | Info | A scheduled or manual backup succeeded for all destinations; see [Configuration Backup](/en/docs/modules/backup) |
| `backup.failed` | Backup: failed | Error | Backup packaging failed, or writing to any destination failed |
| `auth.failed` | Authentication: repeated failures | Warning | A management UI login failed, with the `ip` field |
| `auth.banned` | Authentication: IP banned | Warning | Repeated Web service authentication failures triggered an automatic ban |
| `guard.banned` | Intrusion prevention: IP banned | Warning | A log rule, trap port or port-scan detection banned an IP address or network, with the `ip` and `reason` fields (and `count` when several addresses were banned together) |
| `knock.opened` | Port knocking: knock succeeded | Info | A knock passed authentication and the source address was let through, with the fields `ip`, `rule` and `ports`; see [Port Knocking](/en/docs/modules/knock) |
| `knock.failed` | Port knocking: knock rejected | Warning | A knock was refused: a UDP knock packet passed HMAC authentication but was refused by the rule (replay, expired timestamp, port not allowed, wrong user, etc.), or a knock packet submitted over a Protocol Routing TCP connection failed authentication or checks. Carries the fields `ip`, `reason` and `via` (`udp` or `tcp`); recorded at most once every 5 seconds per source, and intrusion prevention can count it towards a ban. UDP source addresses can be forged, so UDP packets that fail HMAC authentication are only counted and publish no event |
| `login.success` | Management UI: login succeeded | Info | A management UI login succeeded, with the `ip` and `user` fields |
| `login.newip` | Management UI: login from a new address | Warning | A management UI login succeeded from a source address that has never logged in successfully before, with the `ip` and `user` fields. Password, Passkey, third-party and fnOS unified gateway logins are all checked; the first login only builds the baseline and sends no notification; IPv6 addresses are merged per /64; at most 200 sources are recorded, and the one not seen for the longest time is evicted when the limit is exceeded |
| `audit.change` | Management UI: configuration changed | Info | Any change made in the management UI, with the `actor`, `ip`, `method` and `path` fields; see [Audit Log & Config History](/en/docs/guide/audit) |
| `audit.access` | Management UI: sensitive content accessed | Warning | Downloading a backup, diagnostics bundle or certificate private key, opening a terminal, and similar; same fields as above |
| `perf.alert` | Performance: alert firing | Warning or Error | A performance alert rule's condition has held for its duration; the level comes from the rule, with the `rule`, `metric`, `target`, `value` and `condition` fields; see [Performance](/en/docs/modules/perf) |
| `perf.recovered` | Performance: alert recovered | Info | The condition of a firing performance alert has cleared; same fields as above |
| `system.update` | Gately: new version available | Info | An automatic or manual update check found a new version; fields `current`, `latest`, `url`; each version is notified once, see [Automatic update checks](/en/docs/guide/install#update-check) |
| `system.security` | Gately: security update | Error | The current version is affected by a published security advisory, or a newer version contains security fixes; fields `current`, `latest`, `url`, `advisories`, `securityReleases`; notified again when a new security issue appears |
| `program.update` | Managed programs: new version available | Info | The automatic check found a new version of the installed frp, cloudflared, Tailscale, NetBird or File Browser; the source is the program name; fields `program`, `current`, `latest` |
| `docker.update` | Docker: newer image available | Info | The scheduled Docker check found newer container images; one notice per check, each new image notified once; field `count` |
| `notify.test` | Test notification | Info | Produced by the channel's "Test" button; it does not take part in rule matching |

## Sending a test

The "Test" button on a channel card sends a message titled "Test notification" directly to that channel. It bypasses rules and works even if the channel is not enabled. On success, "Test notification sent" is shown; on failure, the specific error is shown. Test results also appear in "Recent deliveries", with "Test" in the rule column.

The matching API is `POST /api/notify/channels/{key}/test`, which can be called with the `notify:write` scope of an [API token](/en/docs/reference/api).
