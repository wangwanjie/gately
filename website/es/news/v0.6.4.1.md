# Gately v0.6.4.1 publicado

4 de noviembre de 2026

[Descargar v0.6.4.1](/es/download) · [GitHub Release](https://github.com/wangwanjie/gately/releases/tag/v0.6.4.1)

## Varias instancias de Tailscale

- Cada instancia ejecuta su propio tailscaled con su propio directorio de estado, socket de control y puerto WireGuard, así que un equipo puede unirse a varios tailnets a la vez; por ejemplo, una instancia en modo kernel para un Headscale remoto y otra en espacio de usuario para uno local.
- Se puede reutilizar un directorio de estado existente para conservar la identidad y la dirección del nodo; la antigua configuración de instancia única pasa a ser una instancia llamada `tailscale` al actualizar, con la misma línea de comandos.
- Solo puede haber una instancia en modo kernel habilitada a la vez (tailscaled usa una tabla de rutas y una marca de cortafuegos fijas); los conflictos de directorio de estado, socket y puerto se informan al guardar o habilitar. Editar una instancia solo reinicia esa instancia.
- Cambio de API: `/api/tailscale/secrets`, `/restart` y `/logout` pasan a `/api/tailscale/instances/{key}/…` por instancia, y `PUT /api/tailscale/settings` solo guarda las rutas del programa; los scripts que usen los endpoints antiguos deben actualizarse.

## Varias instancias de NetBird

- El mismo enfoque que Tailscale: demonios, directorios de estado, direcciones de control y puertos WireGuard separados; la configuración antigua migra a una instancia llamada `netbird`.
- Las comprobaciones de conflictos también cubren los puertos WireGuard (0 equivale al predeterminado 51820) y la dirección SOCKS5 de las instancias en espacio de usuario (vacía equivale a `127.0.0.1:1080`).
- Si un servicio NetBird instalado aparte se ejecuta en modo kernel (existe una interfaz `wt` o el socket del sistema informa de una interfaz kernel conectada), una instancia en modo kernel no se ejecuta junto a él y muestra el motivo.
- Cambio de API: las instancias están en `/api/netbird/instances`, con estado, reinicio, cierre de sesión y clave de configuración por instancia.

Consulte [Túneles y redes](/es/docs/modules/tunnels).

## Las notificaciones incluyen el nombre del servidor

El título pasa a ser `[Gately · nombre del servidor] Título del evento` y el cuerpo añade una línea Servidor, así que las notificaciones de varios servidores enviadas al mismo buzón o grupo se distinguen fácilmente. El nombre se define en la configuración de notificaciones; si está vacío se usa el nombre de host, y las plantillas de Webhook pueden usar la variable `{server}`. Consulte [Notificaciones](/es/docs/modules/notify#server-name).

## Otras mejoras y correcciones

- Las rutas del enrutamiento por protocolo pueden desactivarse temporalmente: se conservan los ajustes, las conexiones pasan a rutas más amplias o al destino predeterminado y el cambio no interrumpe otras conexiones.
- Corrección de DNSPod: dnsapi.cn empezó a rechazar los User-Agent que contienen `DDNS Client`, lo que hacía fallar toda sincronización de registros DNSPod y la validación DNS-01 de certificados.
- ipw.cn ya no resuelve: las consultas de IP pública predeterminadas empiezan ahora por `ipv4.ddnspod.com` e `ipv6.ddnspod.com`, y las direcciones de ipw.cn guardadas se sustituyen al arrancar.
- Con la página de copias de seguridad abierta ya no se registra cada pocos segundos una entrada de auditoría de acceso sensible con su notificación; solo se registra la descarga de un archivo de copia.
- Las cuentas de solo lectura ya no ven el botón para renombrar grupos.
